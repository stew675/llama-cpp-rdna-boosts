# The MoE weighted reduction, exact: no fma contraction, and the reduction fold ahead of the MUL-only fold

**r324, block 10, contributor PR #335 (briansp2020).**  Measured 2026-11-19 on `gfx1201` (R9700, 1 GPU unless
stated), ROCm 10.1.0 (`/opt/rocm-10.1.0-gfx120X`), r323 build `bdd7fc6ee` as the "before" arm.

## What it is

The expert weighted reduction has two implementations of one arithmetic and a precedence rule between them.

| path | code | where it runs |
|---|---|---|
| standalone kernels | `moe_weighted_reduction_f32_vec4` / `_f32` (`moe-weighted-reduction.cu`) | the prefill/verify band, and every shape the fold declines |
| the fold | `mul_mat_vec_q_moe`'s `fusion.red_dst` (`mmvq-moe.cu`) | 1-token decode: the down `MUL_MAT_ID` and the reduction are ONE launch |

Both accumulated `sum + (x * scale) * w` and HIP clang **contracts** that into `v_fmac_f32`; no unfused graph
does, so both differed from the graph's `MUL` / `VIEW` / `ADD` chain at rounding level.  Separately,
`ggml_cuda_moe_down_fold_try_fuse` folded the weighted `MUL` into the down through `x_scale`, which
**disqualifies** the larger fold `ggml_cuda_mwr_fold_mark` had already armed for the same `MUL_MAT_ID` — so the
reduction fell back to a second launch per MoE layer.

r324: both accumulations run under `#pragma clang fp contract(off)` behind **one** knob (`GGML_CUDA_MWR_EXACT`),
and the MUL-only fold stands aside for an armed node (`GGML_CUDA_MWR_FOLD_FIRST`).

## Why the pragma is the only mechanism that works

`__fmul_rn` / `__fadd_rn` (the submitter's first attempt) lower to plain ops and still get contracted.  Verified
on this toolchain with `clang++ --offload-arch=gfx1201 --cuda-device-only -O3 -S`:

```
k_default (plain expression)        v_fmac_f32_e32 v1, v2, v3       <- contracted
k_off     (#pragma fp contract off) v_mul_f32_e32 / v_add_f32_e32   <- exact
```

The pragma is only legal at file scope or **at the start of a compound statement**, which is why both sites
open a block for it, and it survives `__forceinline__` template instantiation (checked in the emitted ISA), so
0002's `mwr_acc<exact>` helper works.  It needs HIP clang's default `-ffp-contract=fast-honor-pragmas`; under
plain `fast` (clang-CUDA) or nvcc both variants compile to the contracted one, i.e. **no non-AMD backend changes
behaviour**, which is also why `GGML_CUDA_MWR_FOLD_FIRST` defaults off outside `GGML_USE_HIP`.

## The census: the precedence really flips

`GGML_CUDA_MWR_DEBUG=1`, `-lv 4`, one graph capture, Qwen3.6-35B-A3B UD-Q4_K_M, 1 GPU:

| arm | armed | `MWR FOLD` (fold served) | `MWR FOLD ASIDE` | `MWR FOLD DECLINE` |
|---|---|---|---|---|
| default (`FOLD_FIRST` on) | 163 | **163** | 163 | 0 |
| `GGML_CUDA_MWR_FOLD_FIRST=0` | 163 | **0** | 0 | 0 |

So on the shipped precedence every armed site is served by the fold and every one of them has the MUL-only fold
step back; the old precedence serves none.  On Qwen3-Coder-30B-A3B at `-ub 1` (a different shape, counted per
reduction node rather than per capture) the same flip is 238 of 238 sites.

There is no `MWR FUSED` line in either arm: the standalone kernel does not launch on these shapes — the ADDs the
MUL fold left behind are taken by the ADD-MUL fold, which is why the win is a *launch and an arithmetic* change
rather than the counter-intuitive "one more kernel".

## Purity: the default is now the unfused chain

KLD against the fully unfused graph (`GGML_CUDA_DISABLE_MOE_DOWN_FOLD=1 GGML_CUDA_MWR_FOLD=0
GGML_CUDA_DISABLE_MWR=1 GGML_CUDA_DISABLE_FUSED_ADDMUL=1`), `llama-perplexity --kl-divergence`, wikitext-2,
`-c 512`, 10 chunks, 1 GPU.  **The unfused base logits file is byte-identical on both builds**
(sha256 `0a4a69973ab8027fefcff4c5e046a301cb6d9c66cbc6f2cb749c167b40215912`, base PPL 7.1177), so the reference is
the same object and the difference is entirely the fused paths:

| build | `-ub` | mean KLD | same top p |
|---|---|---|---|
| r323 | 512 | 0.006613 | 96.627 % |
| **r324** | 512 | **0.000000** | **100.000 %** |

and the same equality in text (same-seed greedy, `prompts/prose-rdna-boosts.txt`, `-n 256`, `-fa 1 -c 8192`):

| arm | r323 default | r323 unfused | r324 default | r324 unfused |
|---|---|---|---|---|
| Qwen3.6-35B-A3B Q4_K_M | `bd111389f051` | `abed0bf40d87` | `abed0bf40d87` | `abed0bf40d87` |
| Qwen3-Coder-30B-A3B Q4_K_M | `553b730d2e24` | `fc94447651c1` | `fc94447651c1` | `fc94447651c1` |
| gemma-4-26B-A4B Q8_0 | `63f491378b41` | `6faaaeff2903` | `6faaaeff2903` | `6faaaeff2903` |
| Qwen3.5-4B Q8_0 (dense) | `18d8b09cd3d3` | — | `18d8b09cd3d3` | — |

That is the substantive finding: **the r323 delivery shipped MoE decode text that is not the unfused chain's
text**, on three architecture families, and r324 makes it exact — `GREEDY-PURITY.md` §101's rule for a fold
("bit-identical to the chain it replaces"), which the weighted-reduction fold had never been measured against.

The `-ub 1` point the submitter graded the decode arm with is **too coarse to see this** (it reads ≈0 on both
builds): 512 sequential token steps over 2 chunks do not accumulate the difference the way 256 greedy tokens do.
The text arms and the census are the instruments; a short `-ub 1` KLD window is not.

## The kill switches are a true revert

| arm | text (35B-A3B Q4_K_M, 256 tok) |
|---|---|
| r323 build | `bd111389f051` (991 chars) |
| r324 `GGML_CUDA_MWR_EXACT=0 GGML_CUDA_MWR_FOLD_FIRST=0` | `bd111389f051` (991 chars) |
| r324 `GGML_CUDA_MWR_EXACT=0` alone (the contracted fold) | `0e1e59e500e8` (859 chars) |
| r324 default | `abed0bf40d87` (1002 chars) |

`EXACT=0` alone is its own state on purpose: it is what proves `GGML_CUDA_MWR_EXACT` is not inert, and it is
why the two switches are **two** rows and not one — the precedence and the arithmetic are independent claims,
while the fold's sum and the kernel's sum are not (one knob, both paths).

pp512 is flat within noise everywhere.  gemma4 is flat because its MoE decode already took the larger fold
(census: `MWR FOLD` served every armed site on r323 too there), so it only gains the arithmetic fix.

**The submitter's "Qwen3-30B-A3B is flat, the fold already ran there" does not generalise**: on
`Qwen3-Coder-30B-A3B` (same `qwen3moe` architecture) r323 takes the MUL fold on **all 238** sites and r324 is
**+2.2 %**.  Which fold wins is a per-shape property of `ne[0]`, the fold's counter span and `moe_cache` state,
not of the architecture.

## Limits

* **NVIDIA / nvcc not built or run.**  nvcc ignores the pragma, so both kernels compile as before there and
  `GGML_CUDA_MWR_FOLD_FIRST` defaults **off** outside HIP (with the switch on, nvcc's fold would be the *less*
  exact of the two candidates).  Nothing changes on a CUDA build.
* **RDNA3 / gfx1151 and Windows not run here.**  The pragma is a long-standing clang feature and the Windows HIP
  toolchain is clang, but neither was exercised this session.
* The removal of one fma per term *could* in principle be slower on the standalone kernels.  pp512 shows no change
  beyond noise on three models; the kernel was not timed on its own.
* The `MWR FOLD DECLINE` arm cannot fire on this box (every fleet MoE has `n_embd` 2048-2816, all RDNA parts are
  warp-32).  It is the check that would catch a warp-64 (CDNA) or `n_embd > 8190` mis-arm; here it only proves
  nothing is refused.
* A multi-slot server arm is not covered by the new gate; `gate-server-arms.sh` (host-expert multi-slot DFlash
  acceptance) is the detector for that class and its recorded hash set is re-recorded at r324.
