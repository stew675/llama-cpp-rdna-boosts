# 2026-09-17 — PR #28549 (`Enable CUDA graph for MTP draft`) on the delivery, isolated A/B

**Question.** Upstream `2f3fd0252` (#28549, "Enable CUDA graph for MTP draft") was picked up by the
2026-09-17 re-base onto `ebbb18522`.  It was the largest MTP-facing upstream change in that range, so
we measured whether it actually helps the delivery's `draft-mtp-adaptive` path.

**Answer: yes, a small but consistent win that scales with draft depth.**  +0.3 % (reasoning, mean
len 2.95) to +1.4 % (verbatim recall, mean len 11.13) generation throughput, with identical
acceptance and mean accepted length on every axis.

## What the PR does (and why depth scaling is the expected signature)

It is host-side `llama_context` bookkeeping only (`src/llama-context.{cpp,h}`, no kernels/backends):
`gf_res_prev` becomes `std::array<llm_graph_result_ptr, 2>` indexed by `n_outputs > 0`, plus a
`gf_res_prev_active` guard so `can_reuse()` only hits for the active arena.

The MTP draft context (`common/speculative.cpp`, `ctx_dft`) alternates two graph shapes on the *same*
context: `process()` (ingest `embeddings_nextn`, `common_batch_add(..., 0)` -> `n_outputs == 0`) and
`draft()` (propose, `common_batch_add(..., true)` -> `n_outputs > 0`).  With one shared arena, every
alternation tripped `res->reset()` -> `ggml_backend_sched_reset` -> reallocation -> `properties_changed`
-> the backend graph could never warm up and replay.  Two arenas keep each shape's allocations stable,
so the draft graph warms up and replays.  More draft steps per generation -> more draft decodes ->
more savings, hence the monotonic depth scaling below.  It is backend-neutral and needs no HIP-specific
work (`GGML_HIP_GRAPHS=ON` by default; ROCm's `hipStreamBeginCapture` is used as on CUDA).

## Cell and commands

* 2x R9700 (`gfx1201`), ROCm 7.14, GPUs **1,2** (`-sm tensor -ts 1/1`), f16 K/V — the recorded
  2026-09-15/16 adaptive-MTP reference cell.
* Model `/llm/models/Qwen3.8/27B/Q8_0/Qwen3.8-27B-Q8_0.gguf`; drafter = the built-in MTP head
  (`qwen35.nextn_predict_layers = 1`), **no `-md`**.
* Prompts (sha256): `prompts/reasoning.txt` `242f5e6f…`, `prompts/prose-rdna-boosts.txt` `fabdec65…`,
  `prompts/code-python.txt` `53da7f23…`, `prompts/recall.txt` `4e11ce3c…`.
* `--reasoning on` for R, `off` for P/C/K; `-n 3000 --seed 42 --temp 0 --single-turn
  --no-display-prompt -c 32768 -b 2048 -ub 2048 -ctk f16 -ctv f16 -fa auto -ngl 99 -lv 4`;
  `--spec-type draft-mtp-adaptive --spec-draft-n-max 12`.

**Isolation.** `rev` = the same re-based tree with `git revert 2f3fd0252` (only `llama-context.{cpp,h}`
change), `new` = the delivered tree.  Paired interleaved runs (`rev`, `new`, per axis), acceptance and
mean length are byte-identical between the two arms on every axis, so only timing differs.

## Results (generation t/s)

| axis | mean len | rev (no #28549) | new (with #28549) | Δ |
|---|---:|---:|---:|---:|
| reasoning (R) | 2.95 | 60.3 | 60.5 | **+0.3 %** |
| prose (P) | 5.10 | 80.3 | 80.5 | **+0.25 %** |
| code (C) | 7.11 | 94.07¹ | 94.87¹ | **+0.85 %** |
| recall (K) | 11.13 | 135.27¹ | 137.20¹ | **+1.43 %** |

¹ mean of 3 paired runs (one interleaved pass over all four axes + a second pass over C and K, each
alternating `rev`/`new`).  Single-run pairs: code 94.3/94.9, 94.0/94.7, 93.9/95.0; recall
135.5/137.3, 135.0/138.1, 135.3/136.2.  Acceptance/mean len identical in every pair.

For context, the delivered tree also reproduces the 2026-09-16 recorded cell within ~1-2 %
(R 60.5 vs 60.7, P 80.1 vs 80.9, C 94.0 vs 95.1, K 134.9 vs 137.5), so the win is on top of an
unchanged baseline.

## Takeaway

Keep the PR.  It is a free ~0.3-1.4 % on every `draft-mtp` workload (largest where drafting is
deepest), correctness-neutral (acceptance/mean-len unchanged, plain == `draft-mtp` purity unaffected),
and it is what makes the draft context's HIP/CUDA graph actually warm up.  It does **not** address the
~2 % adaptive-vs-pinned-per-round residual noted in `2026-09-15-adaptive-mtp-tuning.md` — that is a
depth-dependent graph-shape invalidation (`n_tokens` changes with the draft depth), whereas this PR
only separates the `n_outputs == 0` arena from the `n_outputs > 0` arena.
