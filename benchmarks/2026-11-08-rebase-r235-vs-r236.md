# r235 (shipped) vs r236 (re-based) — first performance comparison

**Date:** 2026-11-08 · **Box:** primary, 3 × R9700 (gfx1201, 32 GiB), Ryzen 9950X3D, 91 GiB RAM, ROCm 10.1.0
**Method:** `llama-bench`, interleaved arms (r236, r235, r236, …), one benchmark at a time, nothing else on the
box.  Both trees built by `~/bin/build-llama-rocm` with the campaign's canonical flags
(`-DGGML_HIP_NO_VMM=OFF`), each in its own build directory at the **same source path** (`build-rocm` = r236,
`build-rocm-r235` = the `rdna-boosts` branch, i.e. block 15 on the old base).  `-p 512`, `-ngl 99`; `tg128`
unless stated.  Reps are llama-bench's own (`-r 3` unless stated), rounds are separate processes.

## Results (t/s)

| arm | r236 | r235 | delta |
|---|---|---|---|
| dense **4B** Q8_0, 1 GPU — pp512 | 8461 / 8361 / 8225 | 8510 / 8366 / 8212 | **−0.2 %** (noise) |
| dense 4B Q8_0, 1 GPU — tg128 | 103.70 / 103.75 / 103.61 | 103.78 / 103.62 / 103.52 | **+0.1 %** |
| **30B-A3B** Q4_K_M, 1 GPU — pp512 | 4323 ± 31 / 4321 ± 58 (`-r 5`) | 4459 ± 49 / 4472 ± 40 | **−3.2 %** |
| 30B-A3B Q4_K_M, 1 GPU — tg128 | 174.37 / 174.35 / 174.35 | 174.28 / 174.19 / 174.18 | +0.08 % |
| **35B-A3B** Q8_0, 3 GPU `-sm tensor` — pp512 | 5120 / 5268 | 5227 / 5371 | **−2.0 %** |
| 35B-A3B Q8_0, 3 GPU — tg128 | 139.82 / 140.09 | 140.00 / 140.16 | −0.1 % |
| 27B Q8_0 dense, 1 GPU — pp512 | 1462 | 1482 | −1.4 % |
| 35B-A3B Q8_0, 1 GPU `-ncmoe 30` (host experts) — pp512 | 585 | 581 | +0.7 % |
| **Flash-Next GSQ-IQ3_XXS**, 3 GPU, `-ncmoe 48` — pp512 / tg64 | **396.8 / 74.4** | **aborts** | r235 cannot run it |

Every r236 row is the *same tree the R16 rung validated* (`2aac85e78`), and every r235 row is the shipped set on
the old base.  Decode is flat everywhere (±0.1 %); a **MoE prefill delta of −2 … −3 %** is the one systematic
difference, and it is *not* in the 4B and *not* where the experts live on the host.

## Localising the MoE prefill delta (30B-A3B Q4_K_M, 1 GPU, pp512)

| switch | r236 | r235 | delta |
|---|---|---|---|
| default | 4323 | 4459 | −3.2 % |
| `GGML_CUDA_MMB=0` | 4404 | 4563 | −3.5 % |
| `GGML_CUDA_DISABLE_MMQ=1` | 4334 | 4479 | −3.2 % |
| `GGML_CUDA_DISABLE_FUSION=1` | 3863 | 3928 | −1.6 % |

So it is not the MMB path, not MMQ, and not the fusion dispatcher: the gap survives turning each of them off, and
its *absolute* size is roughly constant (~130-160 t/s) rather than proportional, which points at a per-launch or
per-batch cost in the device-resident-expert path rather than at one kernel.  Not localised further; a profile of
the two binaries on this arm (or a rung-level bisect across the 16 rungs) is the next step, and is owed before
r236 is claimed "no slower" on MoE prefill.

## Correctness finding that the comparison depends on

**r235 aborts where r236 runs.**  On this box r235 asserts in `ggml_cuda_pool_vmm::free`
(`ptr == pool_addr + pool_used`) on the Flash-Next field config (`-sm tensor`, `-ncmoe 48`), i.e. the shipped set
cannot run that arm at all with the campaign's canonical VMM build; r236 completes it.  The same r235 abort was
seen on fingon (gfx1100) with a plain 9B `-p 512` bench and on halo (gfx1151) with a plain 4B run.  That is the
pool-ordering class `TODO` #298 records (R13's `hc_combine_norm` rule); the re-base fixed the sites that r235
trips.

## Not measured here (and why)

* **fingon (gfx1100)**: correctness is fine (dense 9B, Flash-Next `-ncmoe 48` → `7a8734a9f1a6`, Flash-Next + MTP
  byte-identical to the no-drafter arm), but the box rebooted three times under load and its 9B pp128 reads
  spread 2.5× (2265 / 901 / 920), so its timings are not usable.  Also note: fingon needs
  `-ncmoe 44 --lazy-mode auto` for Flash-Next + a drafter (with `--lazy-mode off` the 28 GB of PLE weights
  cannot fit and the box OOMs).
* **halo (gfx1151)**: the pool is rejected there now (`TODO` #300), so the pool arms cannot be timed.
