# 2026-10-30 — PR #252's third patch (the GDN small-projection gather) ships in r180

Contributor `@briansp2020`, PR [#252](https://github.com/stew675/llama-cpp-rdna-boosts/pull/252), patch 0003
of `wip/graph-order-r176`.  Its siblings (the V/K rotate and the RDNA4 row concat) shipped in r177; this one
was **declined, not refuted** (`TODO` #119) because it needs a **quantized `<= 256`-row** weight and every
Qwen3.6-35B GGUF we held keeps the GDN `ssm_alpha`/`ssm_beta` at **F32** (the unsloth UD quants) or `Q8_0`
(the Q8_0 quant, which the pass deliberately skips).  The submitter then supplied the exact file.

## Why the reorder is safe, and the guards a future edit must keep

The pass only **reorders** nodes: it moves a candidate `MUL_MAT` earlier, behind an anchor `MUL_MAT` it
shares an activation with, across nodes that a valid topological order guarantees cannot read the moved
node.  Its sources are the anchor's activation (already before the anchor) and its own leaf weight, so no
reader is skipped and no buffer lifetime shortens.

Two guards protect positional fusions, and both are load-bearing:

* **never a `MUL_MAT` whose output feeds a `CONCAT` within 8 nodes** — `ggml_cuda_ssm_conv_in_try_fuse`
  returns `j - i` and the nodes in that window are never executed, so a node moved into it would silently
  never run;
* **never a `Q8_0` weight** — `ggml_cuda_ssm_prescan_try_fuse` matches its 16-node chain by position
  (`alpha_w` at `i + 7`, `beta_w` at `i + 13`) and only fires when both GDN small weights are `Q8_0`, so
  moving one out of the window would drop the whole conv + l2-norm + gate/beta fusion.

The pass is arch-gated (RDNA3_0 / RDNA4) because it is a tuning pass; the fusion it feeds carries its own
gate.

## Scope

It cannot fire where the GDN small projections are `F32` (unsloth's UD quants, and even their "True" Q3_K_M
keeps them `F32`) or `Q8_0` (skipped by design).  So the win is real on llama.cpp-quantized files
(lmstudio-community's are) and inert on the GGUF set this box mostly holds; the release notes say so.

## Also found this session (NOT part of this PR, and not shipped)

`--fit on` (the default) **aborts on any multi-device `-sm tensor` run** in r178 and r179: the new
`common/fit.cpp` KV probes (`fit_buft_is_kv_region` / `fit_kv_*` in block 15) call
`ggml_backend_dev_backend_reg(dev)` on the **Meta** device, which has no backend reg (`device->reg == NULL`),
so `ggml_backend_reg_get_proc_address(NULL, …)` asserts.  Reproduced with the plain r179 binary on two
models; `--fit off` works.  The PR arms above therefore used `--fit off` for the 2- and 3-device runs.  The
null-reg guard is with the `archive/work/kv-residency` campaign (`fit-meta-reg-guard.patch`); the maintainer is
handling the multi-GPU/KV interaction separately.
