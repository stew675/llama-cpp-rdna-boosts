# The dense MMQ residue (`TODO` #303): it is the base commit, not the delivery — closed

**Date:** 2026-11-08 · **Box:** primary, 3 × R9700 (gfx1201, 32 GiB), Ryzen 9950X3D, ROCm 10.1.0
**Closes** `TODO` #303 and supersedes its premise.  Related: [`2026-11-08-rebase-r235-vs-r236-localisation.md`](2026-11-08-rebase-r235-vs-r236-localisation.md)
(#301/#302), `INVARIANTS.md`, `RUNGS.md` `P7`.

**The item as filed.** After #301 and #302, the dense 27B Q8_0 prefill arm was still **−1.3 … −1.6 %** against the
shipped r235, and a single `rocprofv3 --kernel-trace` said the residue was `mul_mat_q` **+1.4 %** at the *same*
template instantiation, grid and launch count, with VGPR **232 → 216**.  The filed hypothesis was "the re-base's
own `mmq_args`/`tile_spec` re-expression (R01/R08/R09) changed the dense body".

**What it actually is.**  The dense kernel on r236 is **bit-for-bit upstream's**, and three quarters of the gap is
upstream's own change between the two fork points.

## 1. The arm, and what the kernel census could and could not resolve

Wall clock, `llama-bench -p 512 -n 0 -ngl 99 -r 5`, `HIP_VISIBLE_DEVICES=0`, interleaved arms, 3 rounds per
session (two sessions, same box state): r236 vs r235 **−1.08 / −1.28 / −1.23 %** and **−1.16 / −1.22 / −1.29 %**.
That is the trustworthy number — the arm is 1.1-1.3 % behind.

**The single-run census cannot resolve this item, and the earlier record read too much from it.**  Two
consecutive traces of the *same* binary gave dense-`mul_mat_q` totals of **521.26 and 527.11 ms** — a **±1.1 %**
run-to-run floor, larger than the effect.  Every per-kernel number in this file is therefore **2 interleaved
rounds**, and the claim "VGPR 232 → 216" was never a mechanism: VGPR is an allocation artefact that tracks the
*body*, and the body turned out to be upstream's either way (§2).

## 2. Attribution: four builds, 2 interleaved rounds each, one kernel

`void mul_mat_q<(ggml_type)8, 128, false, (ggml_prec)30, false[, has_gate]>`, 27B Q8_0 pp512, **794 launches**,
**identical launch geometry in all four builds** (workgroup `(32,8,1)`, the same six `Grid_Size_Y` values
1088/320/640/384/768/64 and the same count per grid, template `J = 128`).  So there is no runtime `J`/`ntj`/
`nthreads` difference to chase — hypothesis (a) of `HANDOVER-303.md` is dead — and this is a body/codegen question
only.

| build | round 1 | round 2 | mean | static instrs | VGPR |
|---|---|---|---|---|---|
| `6050b467c` **unpatched** (r235's fork point) | 520.40 | 522.23 | 521.32 ms | 1432 | 216 |
| **r235** = 6050 + delivery | 518.77 | 520.09 | **519.43** | 1476 | 232 |
| `a691b2345` **unpatched** (r236's fork point) | 527.20 | 529.08 | 528.14 ms | 1436 | 216 |
| **r236** = a691 + delivery | 527.79 | 529.48 | **528.64** | 1436 | 216 |

* **the base commit costs +1.31 %** (a691 vs 6050, both unpatched; the round ratios are 1.307 % and 1.311 %);
* **the delivery's old-base win was −0.36 %** (6050 → r235) — the 232-VGPR body, not worth anything recoverable;
* **the delivery on the new base is +0.09 %** — neutral.  And the decisive static fact: **r236's kernel is
  instruction-for-instruction identical to unpatched `a691b2345`'s** (normalised mnemonic+operand sequence, 0 diff
  lines, 1436 instructions).  The delivery has **no code presence** in this kernel; there is nothing of ours to fix
  inside it.

Instrument: the gfx1201 code objects are unbundled out of `libggml-hip.so` (`unbundle` → `llvm-objdump
--disassemble-symbols`) and compared as normalised instruction sequences — exact, noise-free, and it answers "same
template name, different registers" in seconds.  Tool: `archive/work/upstream-rebase-261108/isa-kernel-diff.py`.

## 3. The two candidate fixes, both refuted at ISA level before any measurement was spent

1. **Drop the per-tile `min()` from the dense column range** (r235's pre-`#31047` `col_diff - jt*J - 1` shape).
   Provably equivalent (the write-back only tests `j < j_sup`, so any `j_sup >= J` never clamps and a
   past-the-end tile yields `j_sup <= 0` either way) and it compiled in — **1436 → 1435 instructions, VGPR
   unchanged at 216**.  Wall clock with it: −1.16 / −1.22 / −1.29 % vs r235, i.e. nothing.  Reverted.
2. **Put the NVFP4 scale plumbing back behind `if constexpr`** — exactly the restructuring `a691b2345` introduced
   (`offset_y_scale`, `y_scale_tile`, `x_scale_tile`/`gate_scale_tile` moved out of `if constexpr` into
   unconditional selects).  Compiled in, and the Q8_0 kernel's ISA came out **byte-identical** to the unfixed one:
   the compiler was already folding all of it.  Reverted.

So the remaining difference between the fast and the slow body is **four static instructions**: `v_cmpx_ge_i32` ↔
`v_cmpx_gt_i32` (the `j >= j_sup` rewrite), one `s_min_i32`, and four FMAs that stop pairing into `v_dual_fmac_f32`.
Nothing to remove.

## 4. Why it is not a fixable delivery defect

* the delta is **proportional to work, not to block count** — the smallest geometry (`Grid_Size_Y = 64`, 76 µs per
  launch) shows **+0.9 %** and the largest (`1088`, 950 µs) **+1.3 %**, so it is inside the main loop, and the main
  loop's instruction stream is unchanged (32 × `v_wmma_i32_16x16x16_iu8`, same 69 `global_load_b32` /
  64 `global_store_b32` / 34 `ds_store_b32` in the old body's shape);
* it is not specific to this kernel: on the same two unpatched builds the **FA kernel is +8.2 %** (7.27 → 7.87 ms)
  and `__amd_rocclr_fillBufferUnAligned` goes **0.79 → 2.64 ms** (+1.85 ms of per-pass buffer fills), for a whole-trace
  +1.47 %.  Two builds of the same source shape, differing by 318 upstream commits, and several kernels move
  together — that is a base-level characteristic (graph/allocation layout), not a defect in our copy of one kernel;
* the delivery is *protective*, not additive: the whole-trace kernel total goes 690.82 → 701.00 ms (+1.47 %) on the
  unpatched pair but 643.84 → 649.60 ms (**+0.89 %**) with the 16 blocks applied.

## 4b. Levers tried later the same session (all null, all at instruction level)

After the item was first closed, four more levers were tried because the delivery owns per-shape tuning and the
dense path was one arm away from parity.  None moved the code:

| lever | result |
|---|---|
| `__launch_bounds__` occupancy 2 → 1 for the Q8_0/J=128 row (`mmq-config-rdna4.cuh`) | kernel **byte-identical** — the register cap is not binding, so there is nothing to trade there |
| the J (column tile width) knob — the per-shape decision this repo already owns | **J=128 is optimal**: J=64 = **−4.3 %** (1486.12 / 1480.67 vs 1552.07 / 1546.93 t/s), J=96/48 are not instantiated for Q8_0 (the run aborts) |
| the delivery's own dense path (block 06 MMB, `MMB_DENSE=1 MMB_DENSE_TYPES=q8_0`) | **−0.15 %** (1541.06 / 1536.75 vs 1543.67 / 1538.55) — no win, consistent with gfx1201 having `mmb_dense_flag()` off and Q8_0 out of its RDNA4 dense mask |
| a probe with the whole ids branch compiled out of the kernel | the dense loop **still** comes back 62 dual-FMA + 52 dual-MUL + 4 unpaired (vs the old body's 64 + 54 + 0): the ids machinery is not what shifts the allocation, so a `has_ids` template split would buy nothing |

Six levers in total (with §3's `min()` removal and NVFP4 gating), six null.  Combined with §2's byte-identical
ISA, the conclusion is that the delta is not reachable from this repo's side of the fence.

## 5. Disposition

`#303` is **closed, no delivery change**.  The delivery is verified clean on this kernel (bit-identical to
upstream on the new base, neutral in time), the two recoverable-looking shapes were refuted at ISA level, and the
one live lever — the r235 body's 232-VGPR allocation, worth 0.36 % of one kernel — was **dropped by the
maintainer's decision (2026-11-08)**: recovering it means re-introducing a semantically dead construct to steer
ptxas, for ~0.3 % of an arm, under a ±1 % measurement floor.  The arm stands 1.1-1.3 % behind r235 as an
**inherited, understood cost**.

**Corrections to the earlier record** (they were wrong, not merely stale):
* the run is **794** dense `mul_mat_q` launches — **986** is the *total* `mul_mat_q` launch count on that arm
  (794 dense `J=128` + 192 ids);
* `VGPR 232 → 216` is not a signal (see §2): the shipped r235 body was a *pre-`#31047`* body, so it was never the
  same code with a different allocation;
* a single-run `rocprofv3` census cannot resolve a 1.4 % kernel delta (±1.1 % floor); use 2+ interleaved rounds,
  and prefer the arm wall clock for anything that has to be argued.

**What does not change:** `patches/`, `release.json` and the fork's `rdna-boosts` are untouched (they are cut at
R17), and the delivery's absolute win over unpatched upstream on this arm is unaffected (the 27B dense arm is
~+8 % over `a691b2345`).
