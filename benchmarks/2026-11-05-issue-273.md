## 1. The dispatch stall is real, but its shape decides whether the pad pays

`archive/work/rdna4-grid-stall-pad/graphgap.hip`, extended to large grids: 2000 dependent trivial kernels
inside a captured HIP graph, 256 threads per block, gfx1201, µs per kernel (`/tmp/graphgap273`):

| blocks | 256 | 257 | 512 | 513 | 1024 | 1025 | 1536 | 1537 |
|---|---|---|---|---|---|---|---|---|
| us | **12.63** | 2.34 | **13.63** | 2.71 | **11.62** | 3.32 | **6.42** | 4.21 |

| blocks | 2048 | 2049 | 4096 | 4097 | 8192 | 8193 | 16384 | 16385 | 32768 | 32769 | 65536 | 65537 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| us | 5.08 | 4.83 | 7.54 | 7.52 | 12.71 | 12.76 | 24.41 | 24.49 | 46.06 | 45.86 | 90.64 | 90.84 |

The stall is a **fixed ~10 us** added to a launch whose block count is a multiple of 256 (or whose
work-item count is a multiple of 65536).  Up to ~1536 blocks it dominates a short kernel, which is why
the reporter's 256-block grids measure 15.5 / 15.8 us against 10.1 / 2.4.  **From ~2048 blocks on the
kernel's own runtime is larger than the fixed cost and adding a block changes nothing** (16384 against
16385: 24.41 against 24.49).  So the pad is worth what the reporter measured on *their* model's grids and
is neutral on a grid that is already large; both are bit-identical either way.

`rocprofv3 --kernel-trace`, Qwen3.8-27B UD-Q4_K_XL + DFlash2-Q4_K_M drafter, `-c 16384`, 10.5K-token
prompt, one GPU:

| kernel | grid | blocks | per launch |
|---|---|---|---|
| `rms_norm_scale_pair_f32<256>` (decode/verify) | (8192, 2, 1) | 16384 | 2.5 us median |
| `rms_norm_scale_pair_f32<256>` | (8192, 6, 1) | 49152 | 2.2 us median |
| `rms_norm_scale_pair_f32<256>` (prefill rows) | (8192, 512, 1) | 4194304 | 53.5 us median |
| `flash_attn_stream_k_fixup_uniform<256,4,8>` | (1024, 4, 8) | 32768 | 10.9 us median |
| `flash_attn_stream_k_fixup_uniform<256,32,2>` | (6144, 32, 2) | 393216 | 11.2 us median |

Both grids **do** hit the documented condition on this model too, but at this model's row/channel counts
they are large (16384 blocks rather than 256), so there is no stall left to remove here.  The pad is applied
anyway because it is arithmetic-free and the reporter's configuration is the one that pays; on this box it
is neutral (see the end-to-end table below).

## 2. `seq_rm` with a parked idle slot: 42.1 -> 1.36 us per call

Public-API harness (`/tmp/rm273.cpp`, the same source run against both libraries): unified cache
`n_ctx = 131072`, `n_seq_max = 2`, q8_0 KV, seq 0 holds 4096 cells, seq 1 holds 64 cells and is **parked**
(`llama_memory_seq_park`) so its cells sit at the top of the cache; 400 timed
`llama_memory_seq_rm(mem, 0, p0, p0)` calls past the live sequence (no cell matches: the scan cost alone).

| arm | us/call |
|---|---|
| r215 | **42.127** |
| r217 (scan stops at `park_bound()`) | **1.358** |

31x.  The harness also asserts the equivalence the narrowing relies on: the parked sequence keeps its 63
positions through a range removal **and** through a full removal of seq 0, seq 0 empties, and seq 1 unparks.
`scripts/gate-park-idle-slots.sh` is the end-to-end arbiter (PASS, 6 park moves + 2 unpark, park ==
lazyoff on all four requests, parkoff still differs).

## 3. The per-step prompt copy: 28.8 us per step at 110K tokens

The code the server no longer runs, in isolation (reserve + a filtered `push_back` loop over the prompt,
then the assignment into `slot.spec_prompt`): 2.8 us/call at 10 494 tokens, **28.8 us/call at 110 187**
(plain `std::vector` copy 0.5 / 4.4 us).  That is 0.17 % of a 16.5 ms step on this box, and the reporter's
~0.1 ms at 52.8 ms/step (0.19 %) on a 3900X.

| Flash-Next + MTP, `-ncmoe 40` | `GGML_CUDA_MMB_TYPES` | 22 913 | 1 |
| | `GGML_CUDA_SLAB_STATS` | 15 552 | 1 |
| | `GGML_STAGE_TRACE` | 240 | 1 |

Cost of one call on this box: **21.74 ns** (`getenv` of a name that is not in the environment, i.e. the
full `environ` scan) against **0.18 ns** for a latched `static`; on Windows it is documented to be far
worse (it takes the CRT lock).  `MMB_TYPES` alone was 22 913 calls in a single Flash-Next run.

The tree now has **425 `getenv` call sites over 371 variables and no line reads the same name twice**
(129 such lines before), and no delivery variable is read on a per-op, per-batch or per-step path.  The
only remaining multi-reads are one per **template instantiation** (`GGML_CUDA_DISABLE_MMQ_ROUTED` 25x in
`mmq.cuh`, `GGML_CUDA_GRID_STALL_PAD` 5-6x in `common.cuh`), which a function-local static cannot share by
construction, and one-shot init/argument reads.

## 5. End to end (the reporter's own shape)

One R9700, Qwen3.8-27B UD-Q4_K_XL + DFlash2-Q4_K_M drafter, `-c 245760 --parallel 2 --kv-unified
-ub 2048 -fa on -ctk q8_0 -ctv q8_0 --spec-type draft-dflash --spec-draft-n-max 5`, llama-server, one
request at a time, greedy 512 tokens, a warm request first so the idle slot is parked, arms alternated
O N N O (2 runs each):

| prompt | before ms/token | after ms/token | delta |
|---|---|---|---|
| 10 494 tok | 12.978 / 12.855 | 12.938 / 12.911 | +0.06 % (noise) |
| 110 187 tok | 16.576 / 16.527 | 16.504 / 16.489 | **-0.33 %** |
| prefill 10 494 | 1262.9 / 1267.9 pp t/s | 1256.0 / 1260.0 | flat |
| prefill 110 187 | 803.6 / 803.9 pp t/s | 804.3 / 803.1 | flat |

Generated text identical in all runs (`sha 3a9db54dc13c76c4`), i.e. the JSON `content` hash of the 512-token
completion.  -0.33 % is inside this box's run-to-run spread (~0.3 %) but matches the reporter's -0.25 %.

**Why this box cannot resolve items 2-4 end to end:** the reporter's step is 42.4 ms with 52.8 % of it
host-side at 110K; ours is 16.5 ms with the same absolute host work (a 110K `seq_rm` was 0.157 ms there,
~0.08 ms here; the prompt copy 0.10 against 0.029 ms).  The GPU work shrank faster than the host work did,
so the same absolute saving is 0.25 % of a step there and 0.3 % of ours -- at the noise floor.  The
per-piece measurements above (42.1 -> 1.36 us, 28.8 us, 21.7 -> 0.18 ns) are the statement of record.
