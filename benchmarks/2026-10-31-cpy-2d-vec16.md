# 2026-10-31 — `cpy_2d_vec16`: a vectorised fallback for the 2-D copy the r183 guard refuses (r189)

**Question:** r183's driver-refusal guard in `ggml_cuda_cpy_as_memcpy_2d` sends a refused 2-D block copy to
`cpy_scalar` (an element-per-thread kernel, three divisions and three modulos per element).  Is that fallback
pathologically slow on a copy the delivery actually makes, and does a vectorised fallback fix it without
touching the guard?

**Answer:** the refused path is reachable in the delivery — qwen4exp (`Flash-Next`) with a **quantized indexer
key cache** makes one refused copy per layer per prefill chunk — and it cost **1010 ms → 637 ms** of the deep
prefill's copy time.  On the delivery's own arms that is **below the wall-time noise** (prefill and decode both
measure flat); the large *decode*-side cost the KV campaign recorded (5.20 ms/token) is on its sparse/pool shape,
which I could not reproduce on a delivery-only build.  Shipped as `v16-6050b467c-r189` (block 10) because it is
a regression fix in a shipped path, bit-identical, with the guard untouched.

## What the guard does, and the new fallback

r183 keeps `cudaMemcpy2DAsync` only while a copy's **padded** span (`height*pitch`, including the last row's
padding) fits the tensor's own allocation — a conservative proxy for a driver `invalid argument` on a 2-D copy of
a mirrored slab weight's view.  Its false positive is any padded destination, and the old fallback was
`cpy_scalar<cpy_1_scalar<float,float>>`.

r189 adds `cpy_2d_vec16`: when the guard refuses a 2-D copy of two **F32** tensors whose width and pitches are
multiples of 16 B (and both pointers are 16-B aligned), copy the same block with **one 16-byte unit per thread**,
the row index taken from the grid (no division).  Bit-identical by construction; every other type/geometry and
every copy the guard allows is unchanged; **the guard itself is untouched**, so the r183 load fix stands.

One hardening over the campaign's original cut (`f8e47e392`): "the guard refused" is signalled by an explicit
`guard_refused` out-parameter, not inferred from `width != 0`.  `width` is also written before the
`spitch < width || dpitch < width` rejection, which is a *different* refusal (self-overlapping rows need the flat
element mapping); inferring from `width != 0` would route that geometry to a row-per-row copy.  See
`GREEDY-PURITY.md` §76.

## Where it is reached (gfx1201, measured with a debug build)

(a throw-away debug build that logs every guard refusal — not shipped) Flash-Next GSQ-IQ3_XXS,
`-ctk/-ctv q8_0`, 105k-token prompt:

| geometry | calls | when |
|---|---|---|
| `w=512 h=576..26304 sp=2048 dp=512` | 48 per chunk (48 layers) | **prefill** (h = the QSA index-block count, `h = n_blocks = n_kv/4`) |
| `w=2 h=10240 sp=8 dp=2` | ~28 per run | the r183 case itself (`blk.1.ple_conv1d.weight` column view) — too narrow for vec16, stays on `cpy_scalar` (20 KiB/call) |
| `w=3840 h=105 sp=15360 dp=3840` | 12 per run | prefill |

Every `w=512` and `w=3840` call takes the vec16 path (w % 16 == 0); the `w=2` one correctly does not.  **No
decode-phase refused copy appears** on the resident arm *or* with `LLAMA_KV_RESIDENT_CELLS=2048` (block 15's
windowed KV) — the copies stay prefill-phase, which is where the delivery's reach is.

## Copy cost, deep prefill (105k prompt, `-n 8`, rocprofv3)

| kernel | r188 | r189 |
|---|---:|---:|
| `cpy_scalar<cpy_1_scalar<float,float>>` | **1433.75 ms** / 12428 calls | 423.91 ms / 2732 calls |
| `cpy_2d_vec16` | — | 636.77 ms / 9696 calls |
| refused-copy total (the difference) | ~1010 ms | **~637 ms** (1.6x) |
| whole run, all kernels | 329.16 s | 329.28 s |

The campaign measured ~2.8x (`5.20 -> 1.83 ms/token`) on its arm; the ratio is geometry- and occupancy-dependent
(our copies are pure prefill, `w=512` = one 16-B unit per lane per row), so quote *its* number with its arm.

## Wall time on the delivery's arms (1 GPU, `-ncmoe 48`, q8_0, 3 interleaved rounds where applicable)

| test | r188 | r189 |
|---|---:|---:|
| `llama-bench -p 16384 -n 0` | 339.30 / 339.37 / 339.34 | 339.37 / 339.32 / 339.34 |
| `llama-bench -n 64 -d 49152` (tg) | 26.69 / 26.74 / 26.75 | 26.70 / 26.06 / 26.79 |
| deep arm 105k prompt (`llama-cli`) generation | 30.9 t/s | 30.4 t/s |

So: **flat**, as expected from the copy being prefill-phase and ~0.3 % of the prefill's kernel time.  The fix's
value is (a) the campaign's sparse/pool decode arm, where the same copy is made per step, and (b) not leaving a
4x-slower fallback under a guard that a padded destination can trip.

## Purity

* greedy text **byte-identical**: qwen4exp q8_0 at 4k (`905 chars sha=6b9e214d3b59`) and at **105k depth**
  (`94 fe7775042f82`); 3-GPU `-sm tensor -ncmoe 48` qwen4exp (`611 15561552e5d1`); dense 27B Q8_0 3-GPU
  `-sm tensor` (`678 692c3f7ca639`).  Every arm with `ROCBLAS_USE_HIPBLASLT=0`.
  (Without it, one fresh process read `953 chars sha=46bd85e08529` — the per-start hipBLASLt solution pick of
  issue #67, `GREEDY-PURITY.md` §44, not a change: the same arm re-run with the env set reproduces the hash.)
* prefill logits: qwen4exp q8_0 **0.000000 KLD / 100.000 % same-top-p** (8 chunks, 512 ctx, base recorded on the
  r188 build) and the canonical dense 27B Q8_0 gate **-0.000000 / 100.000 %**.
* `test-backend-ops -o CPY` **251/251**; no GPU faults.
* **The r183 load fix still holds:** Flash-Next GSQ-IQ3_XXS, 3 GPUs, `-sm tensor -ncmoe 48` loads and generates
  (this is the arm that aborted at load on r182 and earlier — the guard is untouched).

## Verdict

Accepted and shipped (r189, block 10).  It is a pure improvement on a reachable path with zero numerics risk.
Record it as a **regression fix**, not a perf win: nobody should expect it to move our numbers.
