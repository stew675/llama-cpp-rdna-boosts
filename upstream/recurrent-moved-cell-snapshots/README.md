# recurrent-moved-cell-snapshots — a moved recurrent cell keeps its rollback snapshots

Written by Claude (AI).  `UPSTREAM-PR-recurrent-moved-cell-snapshots.patch` is cut against plain `ggml-org/llama.cpp` **`6050b467c`** (the delivery base; applied tree `322e440c`), sha256 `b4bd5abd6f7ce549ec1c9872aa696c1f46182fc0d7b8fbaf15aed07ab369f57f`. Contributor: overdoingism.

**What.**  From 3 cells on, `find_slot` can move a cell out of the range of a later ubatch of the same decode after it verified a draft.  `build_rs` copies only plane 0 of such an extra state, so a rollback of that sequence reads the snapshot planes another sequence left at the new row.  The patch also copies planes 1..n_rs_seq of the extra states (input `s_copy_extra`), gathered before the ubatch writes its snapshots.  With 2 cells or fewer the graph does not change.  llama.cpp's own tests stop at 2 sequences.  llama.cpp issue #28286 (`--parallel 4` with speculative decoding, replies mixing content, closed as stale without a cause) reads similar; not shown to be the same.

**Validation** (plain `6050b467c`, Qwen3.8-2B Q8_0): three sequences, one verified, moved, then rolled back, against the order that rolls back first.  Largest logit difference of that sequence: CPU 10.52 -> 0, ROCm (gfx1201) 10.31 -> 0; its state differs -> same.  The server-level results are in `wip/recurrent-moved-cell-snapshots/README.md`, measured on the rdna-boosts tree, not on plain llama.cpp.

**Not validated:** the server scenario on plain llama.cpp; other backends than CPU and ROCm; the patch on master beyond `git apply --check`; speed and memory with 3+ slots.  Re-run the validation on current master before filing.
