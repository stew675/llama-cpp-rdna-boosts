# MANIFESTS — apply order and verification contract

**What this file answers:** in what order the blocks apply, what "verified" means for each one, and what to
do when an apply fails.  The current release identity (fork point, tip/tree, block count, per-artifact
sha256) is [`release.json`](release.json); the dated record of every release and re-validation is
[`WORKLOG.md`](WORKLOG.md).  Dated validation records from the pre-V2.0 era (the 16-block set, its
per-block table and its release-by-release narrative) are preserved in
[`archive/docs/validation-history.md`](archive/docs/validation-history.md) and do **not** describe the
current delivery.

## Current delivery

17 blocks (`block 00` + `blocks 01-16`) against `release.json.base`, canonical chain `release.json.tip` /
`.tree`.  `scripts/validate-set.sh` is green (checksums, then a strict 17/17 apply on a fresh tarball,
tree equality, a conflict-marker/subject scan of every block tree, then the Windows portability lint of
the files the set adds — issue #231).  **Block 14 is temporary** (`-sm relaxed-tensor`, a local relaxation of an upstream rule,
not a supported feature) -- keep it separate and expect to drop it.  Each block is **one** `git am` commit and the series is **linear**: apply in order, never
reorder, never insert.

## Apply (fresh checkout at the fork point)

```bash
git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp
git checkout "$(jq -r .base /path/to/rdna-boosts/release.json)"
bash /path/to/rdna-boosts/scripts/apply-all.sh .     # strict 16/16 git am, tree checked vs release.json
```

`scripts/apply-all.sh` is the only supported flow.  **Do not `git apply` the concatenated series** — it
silently drops hunks (measured: 30 files / 2483 lines instead of 35 / 6094).  The script:

1. refuses a dirty tree or an existing `rdna-boosts` branch;
2. applies the whole series with strict `git am` (one commit per block, original subjects);
3. on failure, aborts and retries the series **once** with `git am -3` (3-way against the recorded blob
   ids), warning that the merged tree may differ from the canonical one;
4. on the strict path, asserts the applied tree equals `release.json.tree` — a stale fork point or a
   partially regenerated patch set fails here — and prints the applied **tip** (`release.json.tip`, the
   commit the personal fork's `rdna-boosts` branch carries).  `apply-all.sh` pins the committer
   identity/date, so a re-cut on a real checkout of `.base` reproduces that tip; `validate-set.sh`
   itself cannot compare it (it builds `.base` from the commit tarball, so its commit ids differ by
   construction) — `scripts/fork-refresh.sh` does that comparison.  The `.tip` rule is in `AGENTS.md`.
   partially regenerated set fails here rather than at the build;
5. `--include-optional` then steps through `optional/*/*.patch` on top of the *verified* tree and asks
   `[y/N]` for each one (`N` is the default), applying the accepted ones with strict `git am`, one commit
   each (an optional artifact is cut against exactly this tree, so the script refuses a 3-way merge);
   `--include-optional-all` applies every one without asking, which is what a scripted or headless apply
   must use.  `--include-beta` then applies `beta/*/*.patch` the same way.  Either flag leaves the checkout
   **not** the release tree, which the script reports; optional artifacts are not covered by the gates
   below (`optional/README.md`).

## Release gates (all mandatory, recorded in the release's `WORKLOG.md` entry)

**Where the gates run.**  There are three tiers, and which one a change hits is what keeps the cheap gate
cheap:

| tier | where | what | trigger |
|---|---|---|---|
| 1 | `.github/workflows/validate.yml` (hosted, no GPU) | `validate-set.sh`: strict apply on a fresh tarball, tree/count, per-artifact sha256, the Windows path + portability lints, and a conflict-marker/subject scan of every block tree | every push and PR, ~20 s |
| 2 | `radiance` (`scripts/validate-gpu.sh`, cron every 30 min) | re-applies the set at `origin/main` from scratch, `gate-per-block-build.sh --fast`, the seven op oracles, then `gate-prefill-logits.sh` (records a base on a fresh box, compares after) | every new `origin/main` commit, unattended |
| 3 | a GPU box, by hand | the release flow: `all` build, coherence, MTP Protocol A, arch sweeps | before a tag |

Tier 2 exists because almost every block is a CUDA/HIP kernel change and a hosted runner has no ROCm, so
tier 1 cannot compile any of it.  It is the automation behind "a re-base is a decode AND prefill change"
(`INVARIANTS.md`).  It holds its own `flock` and **skips while a container build holds the watcher's lock**,
so the two worker jobs never contend; summaries land in `~/.cache/rdna-validate/runs/<sha>/summary.txt`, and
a rev is retried at most `MAX_ATTEMPTS` times (3) before the script stops and names the `failed-<sha>` file
to remove.  The release container images are built **off-host by the worker** and are not a CI tier
([`CONTAINERS.md`](CONTAINERS.md)).

`scripts/validate-set.sh` covers patch integrity only (checksums + a fresh-tarball strict apply) and runs
in CI.  The model-level gates are manual:

1. **Coherence** — same-seed `llama-cli` output identical to a known-good build (dense and, for a change
   that touches the MoE path, a host-expert config).  `GGML_CUDA_ALLREDUCE=nccl` is not a bit-identical
   reference under `-sm tensor`; treat it as a smoke comparison.  **A change to the host-expert scheduler hook
   (`ggml_backend_sched_copy_input`'s routing paths, or a `moe_cache_remap`/`_gather`/`_update` iface member)
   owes both kill-switch arms** (`GGML_MOE_DEVREMAP=0`, `MOE_HOST_POOL_COLD=0`, `--host-experts pool`) plus a
   sequentially driven 2-slot server arm, and **never** a *concurrent* two-slot text diff as the oracle
   (`GREEDY-PURITY.md` §38/§82: the unchanged eager build reads two text basins run to run on this box).  Since
   r221 a remap arm also owes **the exit report's `device remap: N tables served` line** -- a member that is
   never offered, or always declined, measures nothing (`INVARIANTS.md` r221 fact 6).  **A
   change that touches a cache-*quantizer*
   fusion also needs a `-ctk/-ctv q8_0` arm** (the fusions key on the q8_0 `SET_ROWS` and are inert on an f16
   cache: r187's five folds are worth +13.4 % tg128 on that arm and nothing at all at f16), on **1 and 2+
   device** `-sm tensor`/`-sm layer` arms — the submitter's own r187 matrix stopped at one card.
2. **MTP** — the adaptive-MTP four-axis gate, `-n 3000` (2000 floor), `--reasoning on` for R and `off` for
   P/C/K, plus the stock-relative `llama-batched-bench -npl 1,4,8` arm.  Protocol:
   [`benchmarks/mtp-adaptive-methodology.md`](benchmarks/mtp-adaptive-methodology.md).
3. **The UMA GTT expert store** — `scripts/gate-uma-experts.sh` (block 16): same-seed
   greedy text byte-identical across the arena, placement, kill-switch, lock-clamp, cold-cache, fault, no-host-buffer
   and prefill arms; the arena census non-vacuous (`tables > 0`, `evictions > 0`, **0 arena releases**); both shape
   directions (a budget below the set -> arena, a budget that covers it -> placement); the `-lme`-absent **refusal**
   on a model that cannot fit; the prefill **read bytes below "fetch every used expert"**; and P4e's recorded answer
   (no fill worker -- no demand fill ever waits >= 1 ms).  It is a prefill-path change, so **`gate-prefill-logits.sh`
   is mandatory alongside it**, and a discrete box owes `scripts/gate-host-pool.sh` (the tier must be inert there:
   zero GTT census lines with the envs forced on).  Every arm freezes the heat-map prior
   (`MOE_EXPERT_HEATMAP=load`).  Pass `--kld` to run the KLD gate inside it.
4. **Prefill logits** — `scripts/gate-prefill-logits.sh`: mean KLD <= 0.005 and same-top-p >= 98 % against
   a recorded known-good base.  **Required for any change to a prefill kernel** (GDN/SSM chunked, FA,
   MMQ/MMVF/MMB, MoE prefill) or to a default-on approximate path.  Protocol:
   [`benchmarks/prefill-logit-methodology.md`](benchmarks/prefill-logit-methodology.md).
   **An all-reduce arm is a prefill-numerics change too** (block 01): it is only reachable on >= 2 devices
   with a `tensor` split, so pass `--sm tensor --device 0,1,2` (r165; a single device has no comm layer and
   the default `layer` split needs no all-reduce, so the bare gate passes a swapped arm as if nothing
   moved).  **A change whose reach is a rank COUNT needs that count's arm too** (r272): the copy-engine
   2-rank form is unreachable at 3 devices, so its gate is `--device 0,2 --sm tensor` with the base
   recorded from the previous form, and the 3-device arm is the proof that the untouched path did not move.
   The base meta records `device=` and `sm=` and the gate refuses a mismatch -- a 1-device base is not a
   reference for a 2-device `tensor` arm.  The base arm is the previous arm via `--ab "GGML_CUDA_ALLREDUCE=hybrid"`.
   The default arm is an **f16 KV cache**, which skips the quantized-cache prefill paths (the F16 FA staging
   arena, `GGML_CUDA_FA_KV_NATIVE`'s tile read); a change to those also needs `--kv q8_0` (its own base file,
   r156).
   **A change to a decode-band fusion owes two more arms (r201, `GREEDY-PURITY.md` §81):** the same
   `--ab "<fusion kill switch>=off"` at `--ub 4` (a verify width) as well as at `--ub 1`, and
   `test-logits-width-probe P=4096` on the arms.  `--ub 1` alone is **vacuous** where another single-token
   fusion owns the same nodes (the SSM pre-scan fusion does exactly that on qwen3.5/3.6/3.8), which is how
   the gate/beta softplus rounding survived r183..r200.  Quote both arms.  **Judge the fused arm against
   `GGML_CUDA_DISABLE_FUSION=1` (the chain), never against the default** (r202, issue #263): a fusion whose
   kill switch covers only part of the band (`GGML_CUDA_FUSE_GATE_BETA_VERIFY` gates the verify band only)
   is width-uniform and wrong in the default arm, and only the chain shows it.
   A **kernel-family switch** (a new tile/WMMA head cap, e.g. block 05's RDNA3_0 head-512 rows) uses the
   script's `--family-switch` mode, which judges the same absolute limits **at a point inside the gate's
   calibrated domain** and always prints a same-kernel reordering control measured on the spot:
   `--record --ab "<feature-off env>" --family-switch --model <head-256/512 model> --corpus
   prompts/fa-family-switch-gemma4-26B-A4B.txt --ctx 2048 --chunks 10`, then the same command without
   `--record` (`--candidate-env` selects the arm, so a single switch can be judged against a fully-tile
   base).  The absolute limits stay the criterion; `--allow-control-pass` is an explicit opt-in for a
   switch that provably cannot meet them, so an insensitive point cannot pass a bad change.  The mode refuses a point whose base PPL is above `--family-max-ppl` (default 10): at a
   point the model is not confident about, *every* reordering measures far outside the limits (a benign
   `-ub 512` vs `-ub 256` same-kernel change measures 0.105 / 85.0 %, so such a point cannot decide the
   question — `GREEDY-PURITY.md` §46, `archive/work/fa-rdna3-head512-purity/RESOLUTION.md`).
   The `FA_DBG_NMSE` op-level accuracy reference (`test-backend-ops` error magnitude vs the CPU backend at
   the model's own prefill shape) is the second, deterministic leg of a family-switch judgement.
5. **Per-block build** — `scripts/gate-per-block-build.sh` on a clean `all` build per commit (bisection and
   review walk the blocks individually, so every block must build on its own).  Use `--changed-from` to
   rebuild only the blocks a release changed.  **Run it against the long-lived checkout** (its default
   `--repo`, or `scripts/scratch-tree.sh gate`): ccache keys on the source path, so a per-arm worktree makes
   the first block a full cold build (measured: 5m56s / 85 CPU-min at a new path vs 8.6s for the same
   content at the established one).  The gate prints each commit's build time and the run's total; a first
   block that takes minutes on an otherwise unchanged tree means the path was new.
6. **GPU faults** — `scripts/check-gpu-faults.sh` on the run's journal + log (never grep a log by hand).
7. **Idle-slot parking** — `scripts/gate-park-idle-slots.sh`: drives a park/unpark request sequence
   (a long prompt on slot 0, a short one on slot 1, a return to slot 0, a launch on slot 2) and requires the
   parking arm to be **byte-identical** to `LLAMA_SERVER_LAZY_IDLE_SLOTS=0`, with the moves traced and no
   refusal.  Required for any change to the parking path: the KV-cache park API, a memory type that carries
   a second cache, or the server's park scheduling.  **Gates 1-3 never reach parking** — it is inert in
   `llama-cli`/`llama-bench`/`llama-perplexity`, so a server-only defect is invisible to them (issue #227
   shipped in r136 and survived r136-r145 on this fact).
8. **qwen4exp hyper-connection fusions** — `scripts/gate-hc-fusions.sh MODEL.gguf`: runs the **four**
   mix/combine arm combinations (`LLAMA_FUSED_HC_MIX` x `LLAMA_FUSED_HC_COMBINE`, selected independently)
   plus the CUDA-side chain fusions, and requires every hard arm to be **byte-identical to the unfused
   chain**.  The DSV4 HC pre/post pair are **numeric arms, sha-anchored** (r236, `TODO` #292): those two ops own
   the HC16 bf16 producer slots and are a documented numeric re-baseline, so `LLAMA_FUSED_DSV4_HC_PRE=0` swaps
   the producer precision as well as the fusion and byte-identity is **not** expected on any class.  Measured
   on the BF16-hc class (3 devices `-sm layer`, wikitext 512 x 40, base PPL 2.8489): pre op **0.013217 /
   96.392 %** and post op **0.013198 / 96.186 %** against their own chain.  Because each arm is deterministic
   per class, its own text is the anchor instead: the gate defaults `SOFT_EXPECT` to the fused-mixer class's
   recorded shas (`dsv4_pre_chain=dsv4_post_op=6a102dbc62d6`, 449 chars) and **FAILs when one moves**, which is
   the regression signal a "reported" arm used to swallow.  (Historical, for scale only: the IQ4_NL class read
   0.027936 / 96.471 % at base PPL 1.7888 in the gate's own r156 record and 0.021542 / 95.814 % in gate 11's
   r148 row -- different points, neither is a target.  The r148 row's "BF16-hc 449 chars `6a102dbc62d6`" is
   the *chain* of that date; the chain now reads `d62340fbf566`, which is what #292 mistook for drift.)
   Required for any change to `build_hc_mix`, `build_hc_combine`,
   `GGML_OP_HC_MIX` / `GGML_OP_HC_COMBINE` (kernel, CPU reference or op definition) or a matcher that fuses
   either.  **Run it once per hc-down weight class** — Q8_0/BF16 `hc_attn_down` takes the fused mixer, any
   other quant takes the chain (`--types MODEL.gguf` prints the class).  The defect class it exists for only
   shows on the arms where the two halves disagree, and `test-backend-ops` cannot see it: it compares each
   op against a CPU reference that can share the op's mistake.  Issue #228 was invisible to gates 1-6 for
   the same reason (a wrong combine feeds every residual stream the same value, so text stays coherent on
   the arms that happen to be self-consistent), and it silently degraded every non-Q8_0/BF16 qwen4exp quant
   for ten releases.

9. **Batched state save / restore** — `scripts/gate-state-pipe.sh`: drives the server's **in-memory prompt
   cache** (`--cache-ram`), i.e. the path a real chat turn pays for, in four arms (`LLAMA_STATE_PIPE_GROUPS=8`,
   `=1`, `LLAMA_STATE_ASYNC_READ=0`, and `LLAMA_STATE_ASYNC=0`), and requires (a) every arm's restored greedy
   text to be byte-identical to the **synchronous** arm cycle by cycle, (b) the arm that differs in one
   direction only to reproduce the other (`read1` isolates the save bytes, `pipe` the restore), (c) the run to
   have actually restored (`prompt_n` <= 32), and (d) no abort and no GPU fault.  Required for any change to
   `llama_io_write_host` / `llama_io_read_host`, `state_stage`, the state pipelining or its events.  **No
   other gate reaches the host path**: `llama-cli`/`llama-bench` never save a state, and the file-based slot

   shape of the issue #274 follow-up) / `MOE_HOST_POOL_SINK=1` (the eviction demote: an admitted miss copies its
   arena victim into a free pool slot, and the arm must actually demote or it is vacuous) /
   `MOE_HOST_POOL_SINK=1 MOE_HOST_POOL_SINK_FAULT=1` (every demote copy fails, so the arm proves the #274 rule
   holds for the demote too: **`0 demoted`** with `copy-error` declines > 0 -- a failed demote declines and is
   never published as a resident victim, which would serve stale bytes for the life of the run) /
   `MOE_HOST_POOL_PIN_FAULT=late` (r229, issue #278: the platform **latches the pinned tier off** after the pools
   and the arena exist -- the Windows shape at the adapter's shared-segment ceiling -- and the latch must stop the
   tier GROWING, not throw away pinned memory the run already owns: the census must report
   `N expert fills were served from a host pool built BEFORE the refusal` with N > 0, measured 7 060 against 0
   with the pre-r229 lookup order, which also turns 110 failed fills into 1 587).  Every arm runs
   with `MOE_EXPERT_HEATMAP=load`, so the arms are compared across one prior.  It **fails** unless the three healthy arms are byte-identical with a
   real pool (slots > 0, MiB pinned > 0) and no fill failure, the disk-tier arms are not vacuous, and the two
   failure arms are still byte-identical with `FAILED fills: N`, `the slot is NOT resident` per table and

   runs after `main` and llama-server's async log is gone (r227, the reporter's clean Ctrl+C printed every
   teardown line except the census).  Two rules it exists for: a fill must never require a tier the platform may

21. **Narrow-row norm fusion aliasing** — `scripts/gate-norm-rows-alias.sh` (r225, issue #276): the
   `RMS_NORM -> MUL(w)` fusion (and its sigmoid-gated `-> MUL_MAT -> SIGMOID -> MUL` form) reads `x`, `w`
   and the gate output `z` while it writes `dst`, but the gated form dispatches the gate `MUL_MAT`
   **itself**, ahead of the launch.  In graph order `x` is dead as soon as the `RMS_NORM` has consumed it
   and the gate output has exactly `x`'s shape, so the allocator's best fit for it is `x`'s own block.
   The gate drives the fusion **without a scheduler** (`scripts/norm-rows-alias.cpp` calls
   `ggml_backend_graph_compute()` directly, i.e. none of the alloc deps the sched's optimize pass
   registers exist) and forces each aliasing shape by pointing a tensor at another one's buffer after
   allocation: `alias_gate` (gate output == `x`) and `alias_dst_row` (fused output == `x` + one row) must
   be **declined**, `alias_dst_exact` (fused output == `x` exactly, a read-then-write of the same address
   by the same thread) must still **fuse**, and every arm must reproduce `ref` byte for byte and equal
   the driver's own `--no-fuse` (chain) digest.  It then drives the **delivery path** on a real gated
   GGUF (Ling-3.0-tiny, `-c 8192` over the 5256-token `prompts/prose-rdna-boosts.txt`) and fails unless
   the gated form **fused** (>= 1 `norm-rows: ... fused=1 gated=1` line, so the text comparison cannot be
   vacuous), **nothing was declined** (the scheduler's alloc deps still hold `x`/`w` for the fused
   launch: this is the assertion that catches a dropped or renumbered dep, which is silent -- the text
   stays correct because the guard falls back), the fused and `GGML_CUDA_DISABLE_NORM_ROWS=1` arms are
   byte-identical, and neither arm aborts or faults a GPU.  `GGML_CUDA_NORM_ROWS_DEBUG=1` is the
   diagnostic that makes the decision observable.  A **third** arm (r238, GitHub issue #285) drives a
   **SILU**-gated hybrid (Qwen3.5-4B Q8_0) instead: the gated matcher records the gate `MUL_MAT` and then
   declines there (the `UNARY` is not `SIGMOID`), so it is the only arm that exercises "a declined gated
   match followed by the plain match", and it fails unless the PLAIN form fused, **nothing was declined**
   and the text equals the kill-switch arm.  A sigmoid-gated model cannot stand in for it (its gated match
   succeeds, which is why the Ling arm passed before and after that fix).  Required for any change to
   `norm-gated.cu`, to the norm-rows alloc-dep registration in `ggml-cuda.cu`, or to the fusion's dispatch
   order; every release (no other gate reaches this code, and `test-backend-ops` cannot: the fused kernel
   is compared against a chain, not against an allocator).

22. **gfx1201 grid-stall pad** — `scripts/gate-grid-stall-pad.sh` (r226, issue #277, extending #273): the
   pad is DEFAULT ON and is a *launch-shape* change at six sites, so two properties have to be observed
   rather than assumed: a padded launch must not change a byte (a wrong row guard or grid-stride bound
   computes a row twice and can still read plausible on the shapes that do not pad), and the pad must
   actually FIRE at the site it claims to cover.  **A1** runs the `GET_ROWS` op oracle in both arms on
   four shapes added for this (block 08: vec float `(1,1,256)`, plain float `(1,4,64)`, the sub-block
   dequantizing path and the super-block k-quant path, the last two `(1,4,64)`) so every one of the four
   `get_rows` launches is dispatched at a pad-able 256-block grid, and requires the CUDA backend to match
   the **CPU** reference in both arms plus a `get_rows_*` pad line for each site in the pad arm and none
   with `GGML_CUDA_GRID_STALL_PAD=0`.  **A2** runs `MUL_MAT_ID` (a MoE expert-cache remap gathers with
   `grid.x = 16384`, so one extra y row would add 16384 blocks and stay a multiple) and requires the
   refusal branch to be reached: the helper must DECLINE that pad instead of launching a block row that
   cannot help.  **B** requires same-seed greedy text to be byte-identical between the pad arm and the
   kill-switch arm on a dense 1-device arm, a `-sm tensor` 3-device arm and a MoE `-ncmoe` arm, with a
   verbose 1-token probe of each arm proving the pad fired (pad arm) and never fired (kill-switch arm).
   `GGML_CUDA_GRID_STALL_PAD_DEBUG=1` is the diagnostic all of that rests on.  Required for any change to
   `ggml_cuda_grid_stall_pad()` or a call site of it, and every release (the site that was missing is what
   issue #277 reported: `get_rows` was unpadded from r46 to r225).

23. **The one-command verdict for a re-base (r236)** — `scripts/gate-rebase-release.sh`.  A re-base has to answer
    "did we lose performance, and are the numerics still pure?" in one place; this orchestrates the gates that own
    the rules (build per block, prefill-logit KLD, the `MUL_MAT_ID`/`MUL_MAT` op suites, the coherence texts, the
    host-expert multi-slot DFlash acceptance arms (`scripts/gate-server-arms.sh`, below), the interleaved
    performance A/B against the shipped build, and the GPU-fault scan scoped to the run's own start)
    and prints a single PASS/FAIL with exit `0`/`1`.  It adds no thresholds of its own beyond `--tolerance`
    (default 1.0 % per `llama-bench` arm) and `--text-tolerance` (default 3.0 % for the real-text prefill arm).
    **It FAILS rather than skips**: a step that cannot run is a FAIL, so a missing build,
    model or recorded hash cannot look like a pass.  **Step 5b (`--only textprefill`) is a real-text prompt-eval
    against the shipped build, and it is not redundant with the `llama-bench` perf arm**: `llama-bench` builds its
    prompt from `std::rand() % n_vocab` (uniformly random token ids), so every ubatch routes over every expert and
    the expert arena is measurably inert there (pp1450 = 414.1 / 414.5 / 414.5 / 414.5 t/s at
    `MOE_EXPERT_CACHE_MIB` 0 / 4096 / 8192 / auto) while the same arm on the shipped prose prompt reads
    401.6 / 583.6 / 676.9 / 1063.6 t/s.  A `llama-bench`-only perf step therefore cannot see the arena or the
    host-expert transport, which is where this repo's prefill risk lives (`TODO #273`, `#296`).  `--quick` drops the build ladder and the KLD gate while
    iterating; `--perf-only` is the A/B alone and is also the answer to a `#279`-class "is this still worth
    implementing on the new base?" question (the arm it guards is the decode arm).  Run it before a tag and paste
    its verdict into the release's `WORKLOG.md` entry.

    **Step 5c (`--only server`) delegates to `scripts/gate-server-arms.sh`** (`TODO` #295): three two-slot
    `llama-server` arms with a DFlash drafter on host-resident experts (`-ncmoe` 24 and 10 on Flash-Next GSQ
    + DFlash2, 10 on 35B-A3B Q8_0 + its DFlash2), `-sm layer`, greedy, the shipped prose prompt in both slots.
    It exists because every other step in this ladder — and the MTP four-axis protocol — runs a SINGLE
    sequence, so a draft regression on a `-ncmoe` multi-slot run is silent (acceptance -> ~0 while the text
    stays correct); that is the guard R13 dropped, and this is its detector.  HARD: the server comes up, both
    slots draft, per-slot acceptance is not a collapse (`ACC_FLOOR`, default 0.5 x baseline) and has not drifted
    past `ACC_TOL` (default 0.10), and the two generated texts match the recorded hash set.  R13's own numbers
    (0.53793/0.51678 etc.) are **not** the criterion: its invocation was never recorded and they do not
    reproduce, so the baselines are measured at r236 and reproduce to the digit (0.72269/0.74359 on Flash-Next
    at both `-ncmoe` levels, 0.44720/0.59124 on 35B-A3B).

24. **Fusion-window leaf-copy aliasing** — `scripts/gate-fusion-alias-copy.sh` (r239, issue #287):

25. **An hc base copy is released per statement, and one BF16 src1 block per graph** — `scripts/gate-hc-base-copy.sh`
    (r240, issue #290).  The `hc_combine_norm` [repeat] matcher reads the base from a **pool copy** when `add`
    or `mulg` reuses its buffer; r236 registered that copy on the device `pool_stack` *before* the window's

    reporter's 259.6k-token OOM).  The two per-graph activation caches (BF16 src1, MMB) had the same class of

    matcher also prints 0, which is why the copies-made floor exists), `bf16 <= 1` and `mmb <= MMB_LIVE_MAX`

26. **The node budget vs the graph** -- `scripts/gate-node-budget.sh` (r267, GitHub issue #302): a
    **quantized** KV cache carries the Hadamard rotation, and since upstream #31073 the rotation constants are
    per layer on the device, so every layer adds 12 nodes and 2 leafs that `graph_max_nodes()`'s per-tensor
    heuristic does not model.  A model with few matmuls per layer (phi-4: 40 layers, 243 tensors, fused QKV) then
    needs more entries than the scheduler's table has, and the `split_only` probe path has no size assert, so it
    aborts with a bare `ggml-impl.h:337` instead of saying why.  The gate runs four seeded greedy arms on one
    model (quantized K/V at `-ub 2048` and `-ub 512`, `f16` K/V, and the quantized arm with
    `LLAMA_ATTN_ROT_DISABLE=1`) and requires every arm to create a context, generate text and log **no**
    "over its node budget" line, plus a GPU-fault scan of its own window.  `--rotation-ref` additionally requires
    the quantized arm's text to equal the rotation-off arm's (the rotation is an identity).  **It is the only gate
    that builds a graph tight enough to reach the budget**: coherence and MTP use one KV type on models with a 20x
    margin, `test-backend-ops` never builds a llama graph, and the per-block gate only compiles.  Negative-tested
    2026-11-12 on unpatched `a691b2345`: the two quantized arms abort (exit 134), the `f16` and rotation-off arms
    pass.  Required for any change to `graph_max_nodes()`, the scheduler's sizing, a memory module that adds graph
    nodes/leafs, or anything that changes a graph's node count per layer.

## Failure handling (agent instruction)

Apply in the order above, to a branch from `release.json.base`, with `scripts/apply-all.sh`.  If a block
fails to apply:

1. Let the script's `git am -3` retry run; if the merged tree differs from `release.json.tree`, **stop** —
   the checkout was not at the recorded base, or the set is stale.
2. For a true conflict, resolve the hunks **in the block that owns the code** (never in the last block),
   then regenerate the set (`scripts/make-patches.sh`) rather than leaving a hand-edited patch.
3. Do not skip a block.  The series is linear and each block assumes its predecessors; there is no
   supported "apply a subset" flow (including for the k-quant block — see `GREEDY-PURITY.md` §8).
4. Record what happened in `WORKLOG.md`, with the base/tip/tree you ended up with.

## Known notes (working)

- **`test-backend-ops.cpp` is shared by several blocks** (03/04/05/07/08/10/11).  Their hunks sit in different
  case regions, so a re-base is local to the failing file — but grep every patch that touches the file
  before concluding a case is missing.
- **Block 08 is one diff on purpose.**  Its matchers and the `mmvq` / `mmq` / `norm` / `quantize` kernels
  they dispatch to co-developed over one kernel region; do not try to split it.  (The `ggml_cuda_try_fuse`
  translation unit itself is block 10's.)
- **Blocks own their code.**  A fix goes into the block whose surface it changes, even if that means
  amending an early block; appending it to the last block is what made the per-block build gate necessary.
- **The set must apply whitespace-clean.**  `apply-all.sh` prints no git whitespace warnings; a warning is
  a regeneration bug, not a cosmetic issue.
- **Keep UPSTREAM's identifiers in `src/llama-model.{cpp,h}`** — most blocks touch that file, so a local
  rename is paid on every re-base.  Since r128 the loader parameter is `ml` again (the delivery had
  renamed it `ml_l` to silence clang's `-Wshadow`, which re-skinned every conflict in the file — TODO #101);
  the 9 standing `declaration shadows a field` warnings that buys are documented in `src/CMakeLists.txt`
  and are expected.
- **Block-number collisions in old records:** documents written before 2026-10-13 use the
  pre-V2.0 16-block numbering ("block 12" = hybrid all-reduce there, but "block 10" = the k-quant
  umbrella).  `WORKLOG.md`, `archive/` and the dated notes in `archive/docs/patch-notes-history.md` are
