# MANIFESTS — apply order and verification contract

**What this file answers:** in what order the blocks apply, what "verified" means for each one, and what to
do when an apply fails.  The current release identity (fork point, tip/tree, block count, per-artifact
sha256) is [`release.json`](release.json); the dated record of every release and re-validation is
[`WORKLOG.md`](WORKLOG.md).  Dated validation records from the pre-V2.0 era (the 16-block set, its
per-block table and its release-by-release narrative) are preserved in
[`archive/docs/validation-history.md`](archive/docs/validation-history.md) and do **not** describe the
current delivery.

## Current delivery

16 blocks (`block 00` + `blocks 01-15`) against `release.json.base`, canonical chain `release.json.tip` /
`.tree`.  `scripts/validate-set.sh` is green (checksums, then a strict 16/16 apply on a fresh tarball,
tree equality, a conflict-marker/subject scan of every block tree, then the Windows portability lint of
the files the set adds — issue #231).  **Block 14 is temporary** (`-sm relaxed-tensor`, a local relaxation of an upstream rule,
not a supported feature) -- keep it separate and expect to drop it.  Each block is **one** `git am` commit and the series is **linear**: apply in order, never
reorder, never insert.

`rdna-boosts-all.patch` (repo root) is the entire net as ONE patch.  It is a convenience for a one-off
build at the fork point; it is **not** the reviewable increment and not a substitute for the per-block

## Apply (fresh checkout at the fork point)

```bash
git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp
git checkout "$(jq -r .base /path/to/rdna-boosts/release.json)"
bash /path/to/rdna-boosts/scripts/apply-all.sh .     # strict 16/16 git am, tree checked vs release.json
```

`scripts/apply-all.sh` is the only supported flow.  **Do not `git apply` the concatenated series** — it
silently drops hunks (measured: 30 files / 2483 lines instead of 35 / 6094).  The script:

1. refuses a dirty tree or an existing `rdna-boosts` branch;
2. applies the whole series with strict `git am` (one commit per block, original subjects);
3. on failure, aborts and retries the series **once** with `git am -3` (3-way against the recorded blob
   ids), warning that the merged tree may differ from the canonical one;
4. on the strict path, asserts the applied tree equals `release.json.tree` — a stale fork point or a
   partially regenerated patch set fails here — and prints the applied **tip** (`release.json.tip`, the
   commit the personal fork's `rdna-boosts` branch carries).  `apply-all.sh` pins the committer
   identity/date, so a re-cut on a real checkout of `.base` reproduces that tip; `validate-set.sh`
   itself cannot compare it (it builds `.base` from the commit tarball, so its commit ids differ by
   construction) — `scripts/fork-refresh.sh` does that comparison.  The `.tip` rule is in `AGENTS.md`.
   partially regenerated set fails here rather than at the build;
5. `--include-beta` then applies `beta/*/*.patch` on top of the *verified* tree (one commit each).  The
   checkout is then **not** the release tree, which the script reports.

## Release gates (all mandatory, recorded in the release's `WORKLOG.md` entry)

**Where the gates run.**  There are three tiers, and which one a change hits is what keeps the cheap gate
cheap:

| tier | where | what | trigger |
|---|---|---|---|
| 1 | `.github/workflows/validate.yml` (hosted, no GPU) | `validate-set.sh`: strict apply on a fresh tarball, tree/count, per-artifact sha256, the Windows path + portability lints, and a conflict-marker/subject scan of every block tree | every push and PR, ~20 s |
| 2 | `radiance` (`scripts/validate-gpu.sh`, cron every 30 min) | re-applies the set at `origin/main` from scratch, `gate-per-block-build.sh --fast`, the seven op oracles, then `gate-prefill-logits.sh` (records a base on a fresh box, compares after) | every new `origin/main` commit, unattended |
| 3 | a GPU box, by hand | the release flow: `all` build, coherence, MTP Protocol A, arch sweeps | before a tag |

Tier 2 exists because almost every block is a CUDA/HIP kernel change and a hosted runner has no ROCm, so
tier 1 cannot compile any of it.  It is the automation behind "a re-base is a decode AND prefill change"
(`INVARIANTS.md`).  It holds its own `flock` and **skips while a container build holds the watcher's lock**,
so the two worker jobs never contend; summaries land in `~/.cache/rdna-validate/runs/<sha>/summary.txt`, and
a rev is retried at most `MAX_ATTEMPTS` times (3) before the script stops and names the `failed-<sha>` file
to remove.  The release container images are built **off-host by the worker** and are not a CI tier
([`CONTAINERS.md`](CONTAINERS.md)).

`scripts/validate-set.sh` covers patch integrity only (checksums + a fresh-tarball strict apply) and runs
in CI.  The model-level gates are manual:

1. **Coherence** — same-seed `llama-cli` output identical to a known-good build (dense and, for a change
   that touches the MoE path, a host-expert config).  `GGML_CUDA_ALLREDUCE=nccl` is not a bit-identical
   reference under `-sm tensor`; treat it as a smoke comparison.  **A change to the host-expert scheduler hook
   (`ggml_backend_sched_copy_input`'s routing paths, or a `moe_cache_remap`/`_gather`/`_update` iface member)
   owes both kill-switch arms** (`GGML_MOE_DEVREMAP=0`, `MOE_HOST_POOL_COLD=0`, `--host-experts pool`) plus a
   sequentially driven 2-slot server arm, and **never** a *concurrent* two-slot text diff as the oracle
   (`GREEDY-PURITY.md` §38/§82: the unchanged eager build reads two text basins run to run on this box).  **A
   change that touches a cache-*quantizer*
   fusion also needs a `-ctk/-ctv q8_0` arm** (the fusions key on the q8_0 `SET_ROWS` and are inert on an f16
   cache: r187's five folds are worth +13.4 % tg128 on that arm and nothing at all at f16), on **1 and 2+
   device** `-sm tensor`/`-sm layer` arms — the submitter's own r187 matrix stopped at one card.
2. **MTP** — the adaptive-MTP four-axis gate, `-n 3000` (2000 floor), `--reasoning on` for R and `off` for
   P/C/K, plus the stock-relative `llama-batched-bench -npl 1,4,8` arm.  Protocol:
   [`benchmarks/mtp-adaptive-methodology.md`](benchmarks/mtp-adaptive-methodology.md).
3. **Prefill logits** — `scripts/gate-prefill-logits.sh`: mean KLD <= 0.005 and same-top-p >= 98 % against
   a recorded known-good base.  **Required for any change to a prefill kernel** (GDN/SSM chunked, FA,
   MMQ/MMVF/MMB, MoE prefill) or to a default-on approximate path.  Protocol:
   [`benchmarks/prefill-logit-methodology.md`](benchmarks/prefill-logit-methodology.md).
   **An all-reduce arm is a prefill-numerics change too** (block 01): it is only reachable on >= 2 devices
   with a `tensor` split, so pass `--sm tensor --device 0,1,2` (r165; a single device has no comm layer and
   the default `layer` split needs no all-reduce, so the bare gate passes a swapped arm as if nothing
   moved).  The base arm is the previous arm via `--ab "GGML_CUDA_ALLREDUCE=hybrid"`.
   The default arm is an **f16 KV cache**, which skips the quantized-cache prefill paths (the F16 FA staging
   arena, `GGML_CUDA_FA_KV_NATIVE`'s tile read); a change to those also needs `--kv q8_0` (its own base file,
   r156).
   **A change to a decode-band fusion owes two more arms (r201, `GREEDY-PURITY.md` §81):** the same
   `--ab "<fusion kill switch>=off"` at `--ub 4` (a verify width) as well as at `--ub 1`, and
   `test-logits-width-probe P=4096` on the arms.  `--ub 1` alone is **vacuous** where another single-token
   fusion owns the same nodes (the SSM pre-scan fusion does exactly that on qwen3.5/3.6/3.8), which is how
   the gate/beta softplus rounding survived r183..r200.  Quote both arms.  **Judge the fused arm against
   `GGML_CUDA_DISABLE_FUSION=1` (the chain), never against the default** (r202, issue #263): a fusion whose
   kill switch covers only part of the band (`GGML_CUDA_FUSE_GATE_BETA_VERIFY` gates the verify band only)
   is width-uniform and wrong in the default arm, and only the chain shows it.
   A **kernel-family switch** (a new tile/WMMA head cap, e.g. block 05's RDNA3_0 head-512 rows) uses the
   script's `--family-switch` mode, which judges the same absolute limits **at a point inside the gate's
   calibrated domain** and always prints a same-kernel reordering control measured on the spot:
   `--record --ab "<feature-off env>" --family-switch --model <head-256/512 model> --corpus
   prompts/fa-family-switch-gemma4-26B-A4B.txt --ctx 2048 --chunks 10`, then the same command without
   `--record` (`--candidate-env` selects the arm, so a single switch can be judged against a fully-tile
   base).  The absolute limits stay the criterion; `--allow-control-pass` is an explicit opt-in for a
   switch that provably cannot meet them, so an insensitive point cannot pass a bad change.  The mode refuses a point whose base PPL is above `--family-max-ppl` (default 10): at a
   point the model is not confident about, *every* reordering measures far outside the limits (a benign
   `-ub 512` vs `-ub 256` same-kernel change measures 0.105 / 85.0 %, so such a point cannot decide the
   question — `GREEDY-PURITY.md` §46, `archive/work/fa-rdna3-head512-purity/RESOLUTION.md`).
   The `FA_DBG_NMSE` op-level accuracy reference (`test-backend-ops` error magnitude vs the CPU backend at
   the model's own prefill shape) is the second, deterministic leg of a family-switch judgement.
4. **Per-block build** — `scripts/gate-per-block-build.sh` on a clean `all` build per commit (bisection and
   review walk the blocks individually, so every block must build on its own).  Use `--changed-from` to
   rebuild only the blocks a release changed.  **Run it against the long-lived checkout** (its default
   `--repo`, or `scripts/scratch-tree.sh gate`): ccache keys on the source path, so a per-arm worktree makes
   the first block a full cold build (measured: 5m56s / 85 CPU-min at a new path vs 8.6s for the same
   content at the established one).  The gate prints each commit's build time and the run's total; a first
   block that takes minutes on an otherwise unchanged tree means the path was new.
5. **GPU faults** — `scripts/check-gpu-faults.sh` on the run's journal + log (never grep a log by hand).
6. **Idle-slot parking** — `scripts/gate-park-idle-slots.sh`: drives a park/unpark request sequence
   (a long prompt on slot 0, a short one on slot 1, a return to slot 0, a launch on slot 2) and requires the
   parking arm to be **byte-identical** to `LLAMA_SERVER_LAZY_IDLE_SLOTS=0`, with the moves traced and no
   refusal.  Required for any change to the parking path: the KV-cache park API, a memory type that carries
   a second cache, or the server's park scheduling.  **Gates 1-3 never reach parking** — it is inert in
   `llama-cli`/`llama-bench`/`llama-perplexity`, so a server-only defect is invisible to them (issue #227
   shipped in r136 and survived r136-r145 on this fact).
7. **qwen4exp hyper-connection fusions** — `scripts/gate-hc-fusions.sh MODEL.gguf`: runs the **four**
   mix/combine arm combinations (`LLAMA_FUSED_HC_MIX` x `LLAMA_FUSED_HC_COMBINE`, selected independently)
   plus the CUDA-side chain fusions, and requires every hard arm to be **byte-identical to the unfused
   chain**.  The DSV4 HC pre/post pair is **reported, not hard** (r156): those two ops own the HC16 bf16
   producer slots and are a documented numeric re-baseline, so `LLAMA_FUSED_DSV4_HC_PRE=0` swaps the producer
   precision as well as the fusion (IQ4_NL class: mean KLD **0.021542 / 95.814 %** against the chain at the
   standard 40-chunk point, the same order the combine+norm fusion always showed).  Required for any change to `build_hc_mix`, `build_hc_combine`,
   `GGML_OP_HC_MIX` / `GGML_OP_HC_COMBINE` (kernel, CPU reference or op definition) or a matcher that fuses
   either.  **Run it once per hc-down weight class** — Q8_0/BF16 `hc_attn_down` takes the fused mixer, any
   other quant takes the chain (`--types MODEL.gguf` prints the class).  The defect class it exists for only
   shows on the arms where the two halves disagree, and `test-backend-ops` cannot see it: it compares each
   op against a CPU reference that can share the op's mistake.  Issue #228 was invisible to gates 1-6 for
   the same reason (a wrong combine feeds every residual stream the same value, so text stays coherent on
   the arms that happen to be self-consistent), and it silently degraded every non-Q8_0/BF16 qwen4exp quant
   for ten releases.

8. **Batched state save / restore** — `scripts/gate-state-pipe.sh`: drives the server's **in-memory prompt
   cache** (`--cache-ram`), i.e. the path a real chat turn pays for, in four arms (`LLAMA_STATE_PIPE_GROUPS=8`,
   `=1`, `LLAMA_STATE_ASYNC_READ=0`, and `LLAMA_STATE_ASYNC=0`), and requires (a) every arm's restored greedy
   text to be byte-identical to the **synchronous** arm cycle by cycle, (b) the arm that differs in one
   direction only to reproduce the other (`read1` isolates the save bytes, `pipe` the restore), (c) the run to
   have actually restored (`prompt_n` <= 32), and (d) no abort and no GPU fault.  Required for any change to
   `llama_io_write_host` / `llama_io_read_host`, `state_stage`, the state pipelining or its events.  **No
   other gate reaches the host path**: `llama-cli`/`llama-bench` never save a state, and the file-based slot
   save/restore (`POST /slots/N?action=save|restore`) goes through `llama_io_write_file` / `read_file`, which
   call `ggml_backend_tensor_get`/`set` per tensor and never touch the stage.  A torn state is a silent wrong
   answer, not a crash, which is why the reference is the synchronous path and not "the text looks fine".
   The **device** class (`llama_io_write_device` / `llama_io_read_device`,
   `LLAMA_STATE_SEQ_FLAGS_ON_DEVICE`) is a different path and this gate does **not** reach it: it is covered
   by `tests/test-llama-context`, whose `cp_d` restores a sequence over the device io path and compares the
   replayed logits and `cp_d_s` compares the restored KV blob byte for byte (`-sm tensor`, 2 GPU).  Run that
   binary for any change to those two classes or to `state_stage`/`llama_state_copy_staged` (r157).

9. **Speculative verify-batch alignment** — `scripts/gate-spec-align.sh`: drives a **two-slot** server
   (`--parallel 2 --kv-unified`) with two prompts of different acceptance, so the adaptive controller holds two
   different draft depths, and requires (a) the concurrent pair to recover at least 10 % with `LLAMA_SPEC_ALIGN`
   on versus off, (b) the equal-length arm (two identical prompts) not to regress, (c) every **single-slot**
   request's greedy text to be byte-identical on/off, (d) `n_seq == 1` `llama-cli` text byte-identical, and
   (e) the control arm to have actually split decode steps (read from the recurrent memory's `RSPREP` trace)
   while the fixed arm splits none — of the **draft-length** kind, and with the **single-row** kind counted
   separately and bounded (`TAIL_MAX`, default 2): a slot that cannot draft at all (its last token, or a full
   context) presents one row and that step still splits, deliberately (`TODO.md` #111, analysed and declined —
   that second ubatch carries the neighbour's genuine draft rows, so the pass count is equivalent), and the
   count is what makes a regression visible — a change that *manufactures* single-row ubatches fails the gate
   instead of being invisible as it was while they were excluded, and (f) a **mixed-drafter** arm
   (`--spec-type ngram-mod,draft-dflash` with a
   DFlash2 draft, the reporter's own case) to stay within 2 % of its knob-off self with identical draft counts,
   because r153's generic `min` cut shipped a -6 % regression on exactly that chain.  It runs at 2 **and** 3 GPUs
   plus a host-expert (`-ncmoe`) arm, because the penalty scales with the number of devices the duplicated pass
   spans.  Required for any change to
   `common_speculative_draft()`, a drafter's per-sequence depth, the server's step/draft scheduling, or the
   hybrid memory's ubatch split.  **No other
   gate reaches this code**: the coherence, prefill-logit and four-axis MTP protocols all run ONE sequence,
   where there is nothing to align.  The two-slot pair's text is reported, not gated: any fix here changes some
   slot's verify width, so the two arms are two configs — and per-config determinism is a **single-slot**
   statement (2026-10-28: one unchanged binary lands in two text basins on the two-slot pair at 3 GPUs), so judge
   a change by the split count, the single-slot text identity and the pair's aggregate t/s, never by a two-slot
   text diff (`GREEDY-PURITY.md` §63).

10. **Graph replay census** — `GGML_CUDA_GRAPH_TRACE=1` on one decode arm, and read the exit line:
   a healthy decode is `direct` ~= 0, `replay` ~= the call count and `properties_changed` in the tens; a
   large `direct` **with a matching `properties_changed`** means the replay identity is churning and
   `GGML_CUDA_DISABLE_GRAPHS=1` will measure the same speed (which is how you tell the two apart).  `capture`
   is the number of **distinct keys** (one graph per layer per width: hundreds), so a large `capture` with a
   near-zero `properties_changed` is normal and is *not* churn.  Required for any change to the graph cache,
   its key, the property comparison or anything that hands a captured graph a raw device pointer (the expert
   cache's table buffers).  Then compare `GGML_CUDA_DISABLE_GRAPHS=1` against the default: once replay works
   it is the **control**, not an equal (r149: 37.3 vs 42.8 t/s on the Flash-Next `-ncmoe` arm,
   `benchmarks/2026-10-26-graph-replay-keys.md`).

11. **Context-checkpoint reuse** — `scripts/gate-ckpt-reuse.sh`: drives a hybrid/recurrent server (a long
   prompt, then three that resume from a cached prefix) in the two `LLAMA_SERVER_CKPT_REUSE` arms and requires
   (a) every request's greedy text to be byte-identical, (b) the keep arm to have kept a restored checkpoint
   and never superseded one while the eager arm did the opposite, (c) the keep arm to create fewer checkpoints,
   (d) no abort and no GPU fault, and it **SKIPs** (rather than passing vacuously) when the config makes no
   usable checkpoints or when the keep path is unreachable (a dense/SWA target restores at `pos_max`, one token
   before the checkpoint's `n_tokens`).  Required for any change to the server's context-checkpoint path
   (`create_checkpoint()`, the restore selection, `common_prompt_checkpoint`) or to the state save/restore it
   uses.  **No other gate reaches it**: the coherence, prefill-logit and MTP protocols never create or restore
   a checkpoint, and the state gates drive the prompt cache instead.  A wrong keep is a wrong answer on the
   *next* resume, not a crash (r155, PR #236).

12. **Speculative-checkpoint location** — `scripts/gate-spec-ckpt-device.sh`: on a hybrid/recurrent target the
   server's *speculative* checkpoint (saved before a verify whose draft is longer than `n_rs_seq`, restored on a
   partial acceptance) now lives in device memory when one GPU has room (`LLAMA_SERVER_SPEC_CKPT_DEVICE`, r184).
   The device arm is **not a byte image** (the metadata is in `data_tgt`, the payload in the context's per-seq
   staging buffer), so a restore whose save it does not match is a *silent* wrong answer.  Three arms on one
   binary (host `=0`, device, `-nkvo`) and the gate requires: the device arm to take the device path and to
   really create checkpoints, the kill-switch arm never to, the `-nkvo` arm to take the host path with its own
   reason (`the context's state is not offloaded`), every request's greedy text plus the drafted and accepted
   counts to be identical between the host and device arms, and no abort or GPU fault.  The `-nkvo` arm is
   excluded from the text comparison on purpose (moving the KV cache off the GPU selects different kernels).
   It **SKIPs** when the device path is not reachable (a multi-GPU split, the state too large for state plus
   512 MiB, or no checkpoint taken).  Required for any change to `spec_ckpt*`, `use_ckpt_tgt`'s
   `update_tgt`/`load_tgt` or the state io classes' use there.  **No other gate reaches this code**:
   `tests/test-llama-context`'s `cp_d` covers the io class, not the server's use of it, and `gate-ckpt-reuse.sh`
   covers a different object (r184, PR #254).

13. **Speculative verify width** — `scripts/gate-spec-width-band.sh` (r185): the aligned draft depth is bounded
   by a verify **width** so the batch stays inside one kernel family.  On a host-expert config that width is the
   expert-cache band (unchanged); on a band-0 config it is `LLAMA_SPEC_ALIGN_WIDTH_BAND` (default 16), because
   r176 made `band` answer only for a model with host-resident experts and a multi-slot `draft-mtp-adaptive`
   draft was therefore **unbounded** there (4 slots at `n_max 7` = ~28-32 rows).  The gate drives a band-0 3-GPU
   server at 1, 2 and 4 concurrent slots on one binary and **fails** unless: the bound really fires on the
   4-slot arm (`aligned draft depth ... -> 3` with `width band 16`, and never on the knob-off arm), the 4-slot
   aggregate is >= `RECOVER` (default 10 %) of the knob-off arm, the 1- and 2-slot arms are **inert** (no bound
   line at all, byte-identical text, within `REGRESS` 3 %), every arm generated its full token budget, and no
   arm aborts with no GPU fault.  **No other gate reaches this code**: the coherence, prefill-logit and
   four-axis MTP protocols run one sequence (16 / 1 - 1 = 15 is above any `n_max`), and `gate-spec-align.sh`
   runs two or fewer drafting sequences on arms whose depth sits at or below 7, where the bound is inert too --
   it is a *four-slot* property, which is why it went unseen until PR #169's numbers were re-measured on r184
   (+14.2 to +31.8 % on three shapes).  Required for any change to `align_draft_caps()`, the band/width inputs
   or `LLAMA_SPEC_ALIGN_WIDTH_BAND`; every release.

14. **GDN direct-conv fold width purity** — `test-logits-width-probe MODEL prompts/prose-rdna-boosts.txt P

15. **MTP draft window** — `scripts/gate-spec-draft-window.sh` (r200, issue #264): the MTP draft context's KV
   is a sliding window (`LLAMA_SPEC_DRAFT_WINDOW`, default on), and under `--kv-unified` the one draft cache
   holds every sequence, so it must be sized per sequence — `(win + one batch) x n_seq_max` — by
   `llama_spec_draft_kv_cells()`, which is also what the slab's draft reserve and `common`'s "is a window
   active" test call.  The gate drives 2 slots through 6 requests (the first slot fills its window, the second
   slot's own batch is the #264 failure, then both slots are re-prefilled with the other slot's prompt so both
   rings wrap, then re-used from cache) and **fails** unless: every request answers on both slots (the bug is
   an HTTP 500 `decode() failed: failed to process speculative batch` on the second slot), the windowed arm's
   draft cache really is `(win + ub) x n_slots` cells (a window the cache declined makes the text comparison
   vacuous, and the r193-r199 shape is exactly half), and the windowed arm's text is byte-identical to
   `LLAMA_SPEC_DRAFT_WINDOW=0` on **every** step.  **No other gate reaches this code**: the coherence,
   prefill-logit and MTP protocols run one sequence, where the geometry is unchanged (and identical to
   r198's), and the park/ckpt/state gates drive one slot at a time.  Required for any change to the draft
   window's sizing, `llama_spec_draft_kv_cells()`, `create_memory`'s MTP branch or the derived draft reserve;
   every release that touches block 15.

16. **The windowed KV across a tensor split** — `scripts/gate-kv-window-split.sh` (r204, `TODO` #124): the
   resident window is one VMM region **per child device** of a `-sm tensor` split, every child committing the
   same `W` cells of its own slice, with the grow fanned out to every child and `--fit` sizing it against the
   split's per-device budget.  Three failure modes make a text comparison vacuous or dangerous, and each has an
   arm: a window that never really spills (the map unit quantises the boundary, so a small slice can sit at 0),
   a grow a child does not answer (the CUDA hook returns 0 = "not a region buffer" for a Meta buffer — a silent
   success on unmapped VA that page-faults the GPU on the next batch), and a fit that sizes against aggregate
   free VRAM instead of the per-device budget.  The gate **fails** unless: `win3 == ref3` (3 devices, small
   model) and `win2 == ref2` (2 devices, 27B, a 5246-token prompt so the boundary slides) byte for byte, the
   window is enabled **once** per cache and one region is reserved **per device**, every device really slid its
   window (`FLIP device <i>` in a debug re-run) with no `refusing to flip`, a 1 MiB map unit changes no token
   and slides more often than 4 MiB, `draft-mtp` on the windowed split is byte-identical to the no-window arm
   **and** to plain (with identical draft acceptance), a `-c 1048576` split (64 GiB of f16 KV) runs only because
   of the window, the single-device and `-nkvo` arms are unchanged (the r197 contract), the fit reports a
   WINDOWED cache on the split and keeps the pinned `-c`, `auto` decides, the pinned-RAM ceiling widens the
   window where it can and drops it where it cannot, and `LLAMA_KV_REGION=0` says nothing about a window.
   `scripts/gate-state-pipe.sh` with `LLAMA_KV_RESIDENT_CELLS` set is the required companion arm (the batched
   state save/restore of a windowed split; that is where the 2-D D2H of a mixed host/VRAM backing failed).
   **No other gate reaches this code**: the coherence/prefill-logit/MTP protocols run no window, and the
   single-device window arms do not build a Meta buffer type at all.  Required for any change to
   `ggml_backend_meta_kv_region_*`, the region buffer type/vmm region, `llama_kv_cache`'s region selection,
   the split branch of `common/fit.cpp` or `llama_model::kv_cache_split_mirrored`; every release that touches
   block 15.

17. **KV residency** — `scripts/gate-kv-residency.sh` (r206, the archive plan's phase **P0**,
   `wip/kv-residency-cleanup/` §2.1): for the **window** and the **attendance pool**, a resident arm and a
   deliberately under-sized arm, on one binary.  A residency defect is a *wrong answer*, not a crash, so the
   oracle is same-seed text (plus the drafter's acceptance) -- and that is only an oracle if the arm provably
   LEFT the resident placement, which is why the gate fails when the two arms report the same residency.  Window
   arms (4B, `-c 16384` f16, 5 246-token prompt): `wref` (no knob), `wres` (`W=8192`, above the run depth:
   **must** never flip a mapping nor map a host byte) and `wspill` (`W=2048`: **must** do both, `FLIP device 0`
   > 0 and `of which host` > 0), text byte-identical on all three.  Pool arms (Flash-Next GSQ-IQ3_XXS + its MTP
   sidecar, 1 GPU, `-ncmoe 48`, q8_0, `-c 32768`, 25 763-token prefix, MTP depth 4): `pref` (no pool, the
   SPARSE arm the pool replaces), `pres` (`LLAMA_KV_REGION_POOL=32768` = the whole cache, 8 192 pages) and
   `pfloor` (`=512`, **floored** to one decode band = 4 104 pages, with `LLAMA_KV_POOL_VERIFY=1`); text and
   `draft_n`/`draft_n_accepted` identical across all three, `bad 0`, claims/resolves/hits non-zero, `pres`
   holding exactly `-c/4` pages, and on the SAME resolve count `pfloor` claiming more per resolve and hitting
   less.  `REUSE=1 KEEPOUT=<dir>` re-grades a run; it also prints a per-cache **KV accounting** block from the
   log (cells, bytes, the buffer the placement got, host-backed MiB, pool geometry, the counters line).
   **The counters that cannot be asserted are in the script header**: `hits %` can never read 100 % (a block
   claimed by the same launch is neither hit nor miss) and a resident pool does not reach ~0 misses (the claim
   cursor is round-robin and the top-k selection moves) -- at `-c 32768`, depth 25 763 and 8 192 pages,
   144 claims/resolve is the resident arm's floor, and the floor-vs-resident delta is what the gate compares.
   **Negative-tested**: an off-by-one pool slot in `kv_pool_map_fill_kernel` (a wrong-page resolve) diverges the
   text and the acceptance, and the gate FAILs.  Required for any change to the window/region provider, the
   pool, `is_streaming()`, the sparse decode arm, block 15's `--fit` interaction or `memory_breakdown()`'s KV
   accounting; every release that touches block 15.  ~15 s (`--window-only`), ~5 min (`--pool-only`).

Run the GPU gates **alone**: two concurrent GPU jobs change the arena/band layout and invent failures.

## Failure handling (agent instruction)

Apply in the order above, to a branch from `release.json.base`, with `scripts/apply-all.sh`.  If a block
fails to apply:

1. Let the script's `git am -3` retry run; if the merged tree differs from `release.json.tree`, **stop** —
   the checkout was not at the recorded base, or the set is stale.
2. For a true conflict, resolve the hunks **in the block that owns the code** (never in the last block),
   then regenerate the set (`scripts/make-patches.sh`) rather than leaving a hand-edited patch.
3. Do not skip a block.  The series is linear and each block assumes its predecessors; there is no
   supported "apply a subset" flow (including for the k-quant block — see `GREEDY-PURITY.md` §8).
4. Record what happened in `WORKLOG.md`, with the base/tip/tree you ended up with.

## Known notes (working)

- **`test-backend-ops.cpp` is shared by several blocks** (03/04/05/07/08/10/11).  Their hunks sit in different
  case regions, so a re-base is local to the failing file — but grep every patch that touches the file
  before concluding a case is missing.
- **Block 08 is one diff on purpose.**  Its matchers and the `mmvq` / `mmq` / `norm` / `quantize` kernels
  they dispatch to co-developed over one kernel region; do not try to split it.  (The `ggml_cuda_try_fuse`
  translation unit itself is block 10's.)
- **Blocks own their code.**  A fix goes into the block whose surface it changes, even if that means
  amending an early block; appending it to the last block is what made the per-block build gate necessary.
- **The set must apply whitespace-clean.**  `apply-all.sh` prints no git whitespace warnings; a warning is
  a regeneration bug, not a cosmetic issue.
- **Keep UPSTREAM's identifiers in `src/llama-model.{cpp,h}`** — most blocks touch that file, so a local
  rename is paid on every re-base.  Since r128 the loader parameter is `ml` again (the delivery had
  renamed it `ml_l` to silence clang's `-Wshadow`, which re-skinned every conflict in the file — TODO #101);
  the 9 standing `declaration shadows a field` warnings that buys are documented in `src/CMakeLists.txt`
  and are expected.
- **Block-number collisions in old records:** documents written before 2026-10-13 use the
  pre-V2.0 16-block numbering ("block 12" = hybrid all-reduce there, but "block 10" = the k-quant
  umbrella).  `WORKLOG.md`, `archive/` and the dated notes in `archive/docs/patch-notes-history.md` are
  historical and keep their numbering; `patches/README.md` and this file use the current (V2.1) numbers,
  and the block subjects are the table above.  **r109 split the old block 10 in two:** the infrastructure
