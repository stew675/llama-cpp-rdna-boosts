# 2026-11-18 — first measurement pass: the window has MOVED, and it is bigger than expected

**Verdict: the campaign's premise was right about the size and wrong about the mechanism.**  There is up to
**~50 % of a host-expert prefill's wall** recoverable on a partial-residency arena (much larger than the
1-3 % a naive read of the cache census suggests), but the carrier is **no longer an asynchronous H2D copy
with the SMs idle** — the delivery's own device gather (r-era `GGML_SCHED_DEVGATHER`) turned it into a
**link-bound kernel**.  That changes which of §4's mechanisms can work: **(C)/(D) co-scheduling, not the
copy-stream reordering of (A)**, and it means the first thing to build is a test of whether a decode step
co-scheduled with the gather is free.

Arms, all on 1 x R9700 (gfx1201), ROCm 10.1.0-gfx120X, `-c 8192 -b 2048 -t 8`, the 4908-token
`prompts/kld-corpus-35b-in-domain.txt` prefix (`/tmp/p4k.txt`, first 200 lines), `-n 1`:
`runs/arm.sh` (runner) + `runs/summ.sh` (re-parse) + `runs/*.log` (raw).  Sequential, never parallel.

## 2. The four findings

### 2.1 A fully resident arena makes the host-expert tier free — the design already works
`-ncmoe 40` with the whole set in the arena reads **5409 t/s against 5558 t/s for the same model with no host
tier at all** (−2.7 %), with `h=0.0000 (0/0 reaches)` — no reach ever misses.  This is r258/r266/r297's
in-place band plus the covering pinned mirror doing exactly what they were built for.  **There is nothing to
overlap at 100 % residency**, so any interleave work must be gated on residency, not shipped as a default that
"helps everywhere".

### 2.2 The cost of a partial arena is large — and it is the campaign's real budget
42 % residency costs **−56.5 %** of prefill (2415 vs 5409).  That is the pool of time a productive interleave
has to attack, and it is ~20x larger than the 1-3 % the cache's own `expert H2D traffic` census reports for
the same runs (572.7 MiB on P1, 790.0 MiB on H2) — **because that census counts arena fills only; it does not
count what the gather moves.**

### 2.3 The carrier moved from an async copy to a link-bound gather kernel
`GGML_SCHED_DEVGATHER=0` on the identical config (P1c) reads **1085 t/s against 2300 t/s** — the device gather
is worth **2.12x** on prefill, and with it the gather is what moves the bytes now
(`device gather: 468 calls (468 pool-backed), 0 … (neither tier)`), *not* the staging ring: there is not one
`H2D staging`/`stage_*` line in any arm, and `MOE_EXPERT_PREFILL_IN_PLACE=0` is inert here (2296 vs 2300)
because the in-place decision is not what feeds the prefill on a pool-backed table.

**Why this matters:** an async `cudaMemcpyAsync` on the compute stream is an SM-idle window (the original
thesis).  A gather *kernel* is not: the SMs are occupied, and the wall is lost to memory-latency stalls
inside a link-bound kernel.  The window did not disappear — it moved onto the SMs, where a co-scheduled
decode step can still fill it (concurrent kernels, and a link-bound gather leaves real occupancy for a
compute-bound second kernel) — but it cannot be filled by reordering copies, and **(A) is now the wrong first
mechanism**.

### 2.4 The old staging path is 2.1x worse and must not be re-proposed as a baseline
P1c is what the pre-r-era path did: whole-table uploads, 4.5 s against 2.1 s.  Any future arm that measures
"the staging path + an interleave" is measuring a path the delivery no longer takes for a pool-backed table at
any width.  Recorded so the campaign is not re-litigated on it.

## 3. What this does to the campaign

* **The thesis survives; the mechanism ordering changes.**  The window is `F_res ≈ (t_resident −
  t_partial)/t_resident` (up to **0.57** here when the arena covers 42 % of the set), not the copy census's
  fraction of the wall, and it is spent **inside the gather kernel**.
* **New mechanism (D), which now comes first: co-schedule a decode step with the gather.**
  No layer split, no suspension, no copy-stream reordering.  The gather launch is already a host control
  point inside `graph_compute`; a decode step submitted on a second sched's stream *after* the gather launch
  and *before* the consuming `MUL_MAT_ID` runs concurrently with it.  The condition is the same one §5.5
  named: the decode must be **fill-free** (`GGML_MOE_DEVREMAP` band, resident/identity tables) or it competes
  for the same link.
* **(A) copy-stream lookahead is demoted** — it does not apply to a kernel-mediated transfer.
* **(B) layer-chunk interleave keeps its value for a different reason**: it is the server-side control point
  for *how many* decode steps per unit of prefill, whatever the mechanism underneath.
* **(C) op-level yield** is subsumed by (D) and is now the simplest place to try it.

## 4. The next test (the one that decides (D))

**Is a decode step co-scheduled with the gather free?**  Two arms, no new policy, one build:

1. `G0` — the P1/H2 config alone: prefill t/s (baseline).
2. `G1` — the same prefill, with one decode step of a second resident sequence submitted at the gather launch
   (a debug hook, `MOE_PROBE_PF_OVERLAP=1`, single hard-coded step, `n=1`).
   * **PASS**: prefill within 3 % of `G0` **and** the decode token completes.
   * **FAIL**: prefill stretches by ≈ the decode step's own time (additive, i.e. no spare capacity).
3. `G2` — control: `G1` with the decode step's tables forced non-resident
   (`MOE_EXPERT_CACHE_MIB` on the second context) — must be *worse* than `G1`, or the arm is vacuous.

The instrument for `G1` is the archived `MOE_PROBE_132` decomposition re-derived for the prefill side (per-call
timers around the gather launch and the consuming op) — it is not needed for `G0`, only to attribute the wall.

## 5. Open questions this pass creates

1. Is the gather's occupancy really leaving SM headroom (a link-bound kernel) or is it already saturating the
   SMs?  One `rocprof`/`GGML_CUDA_OP_TIMING` reading of the gather kernel's achieved bandwidth against
   28.7 GB/s answers it, and if it is *not* link-bound then (D) has no window either and the campaign stops.
2. Every partial-arena arm here was driven by an **explicit** `MOE_EXPERT_CACHE_MIB` cap, i.e. the shallow-arena
   deployment.  Should the campaign target that band only (a box whose VRAM cannot hold its expert set), and
   say so in the README, rather than pretending it helps a saturated split?  (The 3-GPU field shape is
   100 % resident, so it is out of scope by §2.1.)
3. `-lme 8` (P3) is 1043 t/s and also shows `0 (neither tier)` — a sub-complement pool still never falls
   through to the pageable mapping on this shape, so the disk tier is not being exercised.  A disk-backed arm
   is a different campaign (block 12's transport), not this one.
