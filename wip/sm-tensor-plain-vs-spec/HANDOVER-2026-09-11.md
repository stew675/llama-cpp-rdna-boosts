# Handover — `-sm tensor` plain-vs-spec divergence (qwen35 hybrid)

**Status:** OPEN.  Found 2026-09-11 on the GFX1201 box while validating the
GDN chunked-prefill fix.  **Not** the GDN chunked-prefill issue (that one is
fixed, opt-in, in `block 02` — see
`../issue-25-mtp-batch-width/GDN-CHUNKED-PREFILL-FIX.md`), and **not** the
original issue #25 (FA `parallel_blocks`, fixed by block 00).
**Owner box:** GFX1201 (3x R9700) — the fast box.  **Do not** hand this to the
gfx1151 box: it is a 2/3-GPU tensor-split issue (and one cheap 4B repro exists
on 1 GPU).

## UPDATE 2026-09-11 — ROOT-CAUSED AND (mostly) FIXED

**The batch-width defect is an MMVQ kernel-dispatch mismatch, now fixed as a
block-13 amendment.**  The first row-0 divergence (found with a per-node
dump) is a dense `MUL_MAT` with `K = n_embd < 4096`: llm.cpp's
`mul_mat_vec_q` dispatch put `ncols_dst == 1` dense rows on the block-13
**item-split** kernel while the `ncols_dst 2..8` verify dispatch
unconditionally uses the **ksplit** kernel (only `K >= 4096` ncols==1 already
used ksplit).  The two accumulate K in a different order, so a single-token
decode row is not row-identical to the same row in a verify batch — ~1e-6 at
the first projection, amplified by the recurrent GDN into greedy flips.  That
is why **Qwen3.5-4B diverges on 1 GPU** (n_embd 2560 < 4096) and **Qwen3.8-27B
diverges only under `-sm tensor`** (per-GPU K shard 5120/2 = 2560 < 4096).
Fix (block 13, `mmvq.cu`): `!has_ids || ncols_x >= 4096` for the ncols==1
ksplit gate — dense rows always ksplit; `MUL_MAT_ID`/MoE keeps the item-split
(its multi-token kernel is `mul_mat_vec_q_moe`).  Perf neutral.

**The `-sm tensor` default-config text equality needs ONE more, existing
opt-in piece:** with `GGML_CUDA_GDN_CHUNKED` on (the default) the prompt
prefill runs with the K-dependent chunked-GDN boundary (K = `n_rs_seq+1`),
so `none` (K=1) and `draft-mtp` (K=n_max+1) get different post-prefill SSM
states.  That is the block-02 `GGML_CUDA_GDN_ALIGN_BOUNDARY=1` gate, which
stays opt-in because it costs ~2-2.6% prefill.  With **both** (this fix +
the gate), 27B 2-GPU and 3-GPU `-sm tensor` are byte-identical
(none == n1 == n2 == n4).  Measured: chunked-off + mmvq fix → clean;
chunked-on + mmvq fix → none `3ddc0296` vs spec `5037ef2e`; chunked-on +
mmvq fix + gate → clean.  Canonical mmvq + gate only → still diverges, so
the mmvq fix is required too.

**Known residual (separate, not the reported symptom):** the qwen35**moe**
model still has a small batch-width divergence in a **graph-level fusion**
(not mmvq): `GGML_CUDA_DISABLE_FUSION=1` makes it bit-identical, but
`DISABLE_WEIGHTED_DOWN` / `DISABLE_MOE_MMQ_FUSION` / `PAIR_OFF` do not, and
neither do the `_moe`/ksplit/item-split dispatches.  It does **not** depress
the MoE MTP gate (0.675 / 153 t/s measured).  Investigate separately.

Instrumentation used (not in the tree): `/tmp/lw-dump2.cpp`
(`wip/sm-tensor-plain-vs-spec/`-worthy) — runs one decode width per process
and prints the token-0 logit hash with **no** `cb_eval` callback.  NB the
`llama_context_params.cb_eval` callback itself changes MoE numerics
(callback-on: W1==W3; callback-off: W1!=W3), so a `cb_eval`-based op dump is
**not** a valid instrument on MoE.

## TL;DR

Under `-sm tensor` on 2/3 GPUs, `--spec-type none` and `--spec-type
draft-mtp` (any n-max, including 1) produce different greedy text on the
qwen35 hybrid models (Qwen3.8-27B, Qwen3.5-4B).  The underlying defect is a
**batch-width dependence of the logits** — the single-token decode batch
(`n_tokens == 1`) and a multi-token verify batch (`n_tokens == 3/5`, i.e. row 0
of a wider batch) disagree on **row 0**, even though row 0 sees the same
context.  It is **independent of `n_rs_seq`** (K), **independent of the GDN
chunked kernel**, and **specific to the hybrid GDN path** (a pure-attention
model is clean).  First decode/verify-width divergence since block 00 that is
not FA `parallel_blocks`.

Performance constraint for any fix (from the maintainer): **must not force a
slower or less-accurate default** — the current default is deliberate.  Prefer
a width-invariance fix in the kernel/dispatch selection, not a global
pin-to-sequential or a forced tensor-off.

## The decisive measurement

`logits-width-tensor.cpp` (this directory; = the gfx1151 `logits-width.cpp`
plus a `SPLIT=tensor|layer|row` model-param override).  It prefills `P` tokens,
then decodes a batch of `W` tokens and prints `max|logit|` for row 0 (same
context for every `W`).  `RS` pins `n_rs_seq`; `RS=from_w` sets
`n_rs_seq = W-1` (the MTP-faithful case).

27B Q8_0, `P=256`, row 0, GDN chunked **off** unless noted:

| split | `RS` | `W1-W3` | `W3-W5` |
|---|---|---|---|
| `none` (1 GPU) | `from_w` | **0.000000** | 0.000000 |
| `layer` (2 GPU) | `from_w` | **0.000000** | 0.000000 |
| `tensor` (2 GPU) | `from_w` | **0.133178** | 0.000000 |
| `tensor` (2 GPU) | `0` (all K=1) | **0.133178** | 0.000000 |
| `tensor` (2 GPU) | `2` (all K=3) | **0.133178** | 0.000000 |
| `tensor`, chunked **on** | `from_w` | 0.137030 | 0.163328 |
| `tensor`, chunked on + `GGML_CUDA_GDN_ALIGN_BOUNDARY=1` | `from_w` | 0.164030 | 0.000000 |
| `tensor` + `GGML_CUDA_DISABLE_GRAPHS=1` | `from_w` | 0.133178 | 0.000000 |
| `tensor` + `GGML_CUDA_NO_PEER_COPY=1` | `from_w` | 0.133178 | 0.000000 |
| `tensor` + `ALLREDUCE=nccl` / `internal` / `meta` | `0` | 0.164807 / 0.163031 / 0.169452 | 0.000000 |

**Read this carefully.**  `W1` uses `n_rs_seq=0`; `W3`/`W5` use `n_rs_seq=2`/`4`.
`RS=0` forces K=1 on **all** widths and `RS=2` forces K=3 on **all** widths —
and `W1-W3` stays `0.133178` in every case.  Therefore the divergence is the
**batch width** (`n_tokens==1` vs `n_tokens>=3`), **not** K.  `W3-W5 = 0`
because both are multi-token batches.

The GDN chunked gate only fixes the `W3-W5` component (the K-dependent
chunk/sequential boundary); the `W1-W3` component survives the gate.

## Model isolation (row 0, `RS=0`, chunked off, row-0 logit diff)

| model | split | `W1-W3` |
|---|---|---|
| Qwen3.8-27B (hybrid qwen35) | `tensor` (2 GPU) | **0.133178** |
| Qwen3.8-27B | `none` / `layer` | 0.000000 |
| Qwen3.5-4B (hybrid qwen35) | `none` (1 GPU) | **0.147862** |
| Qwen3.5-4B + `FA=0` (1 GPU) | `none` | 0.170979 |
| Qwen3.5-4B + `FA=0` + chunked off | `none` | 0.170873 |
| gemma-4-31B Q8_0 (**pure attention**) | `tensor` (2 GPU) | **0.000000** |

Two things to take from this:

1. **Pure-attention gemma is clean under tensor split** → the generic
   tensor-parallel MUL_MAT / FA path is *not* the culprit; it is specific to
   the **hybrid qwen35 GDN path**.
2. **The 4B reproduces the same width dependence on 1 GPU** and it survives
   `FA=0` and chunked-off — so this is a **cheap 1-GPU repro of the same class
   of defect** (the 27B just happens to be width-consistent on 1 GPU).  Use the
   4B for fast iteration, the 27B under `-sm tensor` for the real symptom.

## Ruled out (with evidence above)

- **GDN chunked kernel / its K-dependent boundary** — chunked off gives the
  same `W1-W3`; the block-02 gate does not remove it.
- **`n_rs_seq` / snapshot count K** — `RS=0` and `RS=2` both diverge.
- **block-15 V3 derived kq mask** — `LLAMA_KQ_MASK_DERIVED=0` unchanged.
- **graphs / CUDA-graph capture** — `GGML_CUDA_DISABLE_GRAPHS=1` unchanged.
- **peer copy** — `GGML_CUDA_NO_PEER_COPY=1` unchanged.
- **one specific AR backend** — persists under `nccl`, `internal`, `meta`
  (magnitudes differ, so the AR is *involved* in the numerics, but is not the
  discriminator).
- **FA `parallel_blocks` (block 00)** — block 00 is present in every build
  used here; FA off on the 4B changes nothing.
- **generic tensor-parallel matmul** — gemma is clean.

## Lead: the GDN fused-op split by batch width

`src/models/delta-net-base.cpp` selects a different *fused op* for the GDN
purely on whether the batch is single-token:

```cpp
// build_delta_net()  (K == 1 path), ~line 403
if (n_tokens == 1) res->add_fused_node({LLM_FUSED_OP_GDN_AR, result, il});
else               res->add_fused_node({LLM_FUSED_OP_GDN_CH, result, il});
// and the same choice again in build_recurrent_attn() (K > 1 path), ~line 578
```

- `LLM_FUSED_OP_GDN_AR` ("autoregressive", `n_tokens_per_seq = 1`) is the decode
  op; `LLM_FUSED_OP_GDN_CH` ("chunked", `n_tokens_per_seq = 16`) is the verify /
  prefill op.  Definitions: `src/llama-context.cpp:59-69`,
  `src/llama-graph.h:47-48`.
- These are the *only* place in the graph where a GDN decision keys off the
  batch width, so they are the prime suspect for a width-dependent numerics
  difference on a split model.  The fusion is supposed to be perf-only (same
  math), so the suspicion is that one arm changes the operand layout /
  row-split assignment / reduction order under tensor split.
- There is currently **no env to disable the GDN fusion** (only
  `LLAMA_FUSED_HC_MIX` / `LLAMA_FUSED_HC_COMBINE` for hyperconn,
  `LLAMA_GRAPH_REUSE_DISABLE`).  Adding a temporary
  `LLAMA_FUSED_GDN=0`-style kill-switch is the obvious first experiment.

## Suggested next steps (cheap → expensive)

1. **Confirm the fused-op split is the discriminator.**  Add a temporary
   `getenv` kill-switch around the `LLM_FUSED_OP_GDN_{AR,CH}` `add_fused_node`
   calls (or force both to `GDN_CH`), rebuild, and re-run the probe:
   `SPLIT=tensor RS=0 GGML_CUDA_GDN_CHUNKED=0 ./lw-tensor 27B …`.
   If `W1-W3 -> 0`, the fusion is it.  (Keep it opt-in; the maintainer does
   not want a forced-slow default.)
2. **Bisect the width dependence inside the fused op.**  With the 4B 1-GPU
   repro (`SPLIT=none RS=0 GGML_CUDA_GDN_CHUNKED=0`), it is a *single-GPU*
   divergence, so no tensor-split machinery is needed to debug — compare the
   `GDN_AR` vs `GDN_CH` intermediate tensors (norms / conv / projections /
   the GDN op output) with a debug dump (`GGML_CUDA_DEBUG`, or temporarily
   disable the fusion and diff fused vs unfused per-op output).
3. **Check the GDN kernel's grid/thread mapping vs `n_tokens`.**  In
   `gated_delta_net.cu` the sequential kernel loops `for t in n_tokens` with a
   fixed grid over `(H, n_seqs, S_v/…)`; a `warp_reduce_sum` over a
   width-dependent lane mapping would explain it.  Verify token 0's output is
   bit-stable when only the *tail* of the batch changes (`n_tokens = 1` vs
   `n_tokens = 1` + padding/dummy tokens).
4. **Check the row-split operand split for the GDN projections** under
   `-sm tensor` — i.e. whether the fused GDN's surrounding matmuls get a
   different `nrows_split` for `ne[1]==1` vs `ne[1]>1`.
5. **Only then** decide the fix: a width-invariant kernel/launch selection
   (like block 00's `ntiles_dst_eff` / block 08's `ncols1` guard) is the goal;
   a global "force `n_tokens>1` config" or "disable tensor GDN fusion" is the
   fallback and needs the maintainer's sign-off because it trades perf.

## Acceptance gate for a fix

- 27B, 2-GPU **and** 3-GPU `-sm tensor`: `--spec-type none` == `draft-mtp`
  (n-max 1/2/4) byte-identical (currently not).
- Probe, `SPLIT=tensor RS=0` and `RS=from_w`, chunked **on and off**:
  `W1-W3 == 0` and `W3-W5 == 0` (currently `W1-W3 = 0.133`, `W3-W5 = 0.163`
  chunked-on).
- `-sm layer` and 1 GPU stay clean; block-00 `none == n2 == n4` must not
  regress.
- Delivery coherence gate + `benchmarks/mtp-adaptive-methodology.md`
  (acceptance >= ~0.45, MTP >= plain), and **no prefill/decode regression**
  (the maintainer will reject a fix that forces the slow/clean path).
- Re-run `test-backend-ops -o GATED_DELTA_NET` (46/46) and, if the GDN fusion
  is touched, the fused-op gates.
