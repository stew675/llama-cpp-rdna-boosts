# gfx1201 port — S13: the F32 policies, and HC16 is inert (2026-09-21)

Session S13 of `gfx1201-porting.md` §13.  **Headline: the F32 split tile had been bundled into
`mmb_dense_flag()` (which is off on RDNA4) and its predicate also swallowed the tiny-M kernel, so
turning one off killed both.  Separated, both are wins and the split tile *scales with depth* — which
takes qwen4exp from +4.9/+5.2 % to +6.7/+6.5 % shallow and +6.2 % at 64k/98k.  The HC16 producer
family, by contrast, is measurably INERT on gfx1201 and stays default-off.**

## 1. What was wrong

```cpp
const bool f32cand = src0->type == GGML_TYPE_F32 && mmb_f32split();   // mode 0 kills everything
...
const bool f32w = f32cand && (mmb_tiny_m_f32_ok(K, M) ||
                   (mmb_dense_flag() && (... M >= min_m && K >= min_k)));   // dense flag gates the tile
```

Two defects:

* **`GGML_CUDA_MMB_F32SPLIT=0` disabled the tiny-M kernel too**, because `f32cand` required
  `mmb_f32split()`.  They are unrelated kernels for unrelated shapes (`M <= 8` warp-per-token vs the
  `M >= 128` tile).
* **The split tile was gated behind `mmb_dense_flag()`**, which is off on RDNA4 — so S7 had bundled
  the F32 *shape* policy with the quantized *dense geometry* policy and the split never ran on
  gfx1201 at all.

Now the two are independent policies:

```
tiny-M kernel   <-  mmb_tiny_m_f32_ok(K, M)                       only
split tile      <-  mmb_f32split_mode() / f32split_min_m / _min_k  only
```

## 2. The measurement that matters: the split tile scales with depth

Flash-Next IQ4_XS, 3-GPU tensor, `-b/-ub 2048`, interleaved r=3, both configs with the tiny-M kernel
on and routed off — so the **only** difference is the split tile:

| depth | split OFF (`MMB_F32SPLIT=0`) | split ON (landed) | delta |
|---|---|---|---|
| pp8192 | 2853.85 | 2844.97 | **−0.3 %** |
| pp32768 | 2862.96 | 2889.61 | **+0.9 %** |
| pp65536 | 2725.18 (avg of two rounds) | 2752.31 (avg) | **+1.00 %** |
| pp98304 | 2585.55 (avg) | 2616.95 (avg) | **+1.22 %** |

The two deep rounds agreed to 0.1–0.4 % (`split-OFF` 2730.85 / 2719.51 at 64k, 2584.92 / 2586.18 at
98k).  **The split tile costs a fraction of a percent at the start of a run and pays >1 % once the
context is deep** — and for a long-context session it is the deep regime that decides throughput, since
the shallow part is over in seconds.  (This is why the S13 shallow-only readings — "the split is within
noise" — were the wrong conclusion to draw from pp8192/pp32768 alone.)

The tiny-M kernel, for contrast, is the *larger* but *flatter* win: with neither F32 path on
(`MMB_TINY_M=0 MMB_F32SPLIT=0` vs off: 2721.30 / 2722.47 vs 2731.81 / 2721.12), the baseline is
unchanged, so the tiny-M kernel carries ~+4.5 % at pp8192 and ~+5.2 % at pp32768 — and since the total
at depth is +6.2 %, its share shrinks as the split's grows.

Landed (both on): **qwen4exp +6.7 % pp8192 / +6.5 % pp32768** (S12: +4.9 / +5.2), **+6.2 % pp65536 /
+6.2 % pp98304**.

The mechanism, from the profile of the landed build on Flash-Next (`rocprofv3`, 3-GPU):

| kernel | delivery | landed |
|---|---|---|
| `Cijk_Alik_Bljk_S_B_Bias_..._MT64x64x16` (rocBLAS F32) | 1.923 s | **0.242 s** |
| `mmb_tiny_m_f32_kernel<4,1,false>` | -- | 0.429 s |
| `mmb_f32split_kernel<128,128,32,64,false>` | -- | 0.306 s |

i.e. the F32 GEMMs move off rocBLAS — and on qwen4exp (routed off, dense types IQ3_S-only) those two
kernels are the *only* MMB device work at all.

## 3. gfx1151 is the opposite way round

The gfx1151 record (`HANDOVER.md`) has the `M=512` router winning **2.4x** on the split tile and the
long-K hc-inject pair being *worse* on the tiny-M kernel.  That is the inverse of the RDNA4 result, and
it is why these are per-arch defaults (`mmb_f32split_mode`, `mmb_tiny_m`) rather than one arch-neutral
verdict.  gfx1151 semantics are unchanged for the default mode 1; the **only interface change is that
`GGML_CUDA_MMB_F32SPLIT=0` now disables just the split tile** instead of all F32 MMB (use
`GGML_CUDA_MMB_TINY_M=0` for the other half).

## 4. HC16 is inert on gfx1201

`GGML_CUDA_MMB_HC16`, `GGML_CUDA_MMB_DOWN16`, `LLAMA_HC_BLK16` and `LLAMA_HC_RES16` are host-side
graph marking that lets a producer write BF16 instead of F32 (killing `mmb_cvt_f32_bf16`).  Measured on
both the model they were written for and a model where their consumer actually runs:

| model / depth | base | HC16 | HC16+DOWN16 | BLK16 | RES16 |
|---|---|---|---|---|---|
| Flash-Next, pp8192/32768 | 2893.13 / 2897.62 | 2940.36 / 2893.15 | 2923.45 / 2906.66 | 2902.88 / 2899.23 | 2880.39 / 2891.63 |
| Flash-Next, pp32768/65536 | 2903.74 / 2757.03 | 2900.91 / 2755.87 | 2902.36 / 2753.76 | -- | -- |
| 27B UD-IQ3_S, pp8192/32768 | 930.97 / 854.86 | 931.22 / 855.09 | 930.87 / 854.79 | 931.20 / 855.22 | 931.04 / 854.97 |

All within a **0.03 %** spread on the dense model and within run-to-run noise on qwen4exp.

Note the 27B UD-IQ3_S row is the *hard* test: the quantized dense path **does** run there (it is the
S10 IQ3_S win) and the conversion stream **is** live — `LLAMA_MMB_CVT_LOG=1` reports **178 `MMB_CVT`
lines** — and yet HC16 changes neither the count nor the speed.  On Flash-Next the knobs are inert for
a simpler reason: their consumer is the quantized dense GEMM, which does not run there (routed off, and
the dense types are IQ3_S-only while Flash-Next's dense weights are not).

So the lever exists, is wired correctly, and has **no measurable payoff on RDNA4** — it stays default 0
as an unused opt-in.  This is a case where "measured and left off" is the deliverable.

| knob | values tried | result |
|---|---|---|
| `GGML_CUDA_MMB_TINY_TT` | 1 (default), 2, 4 | within ±1 %, no ordering — keep **1** |
| `GGML_CUDA_MMB_CACHE` | 4 (default), 32 | within ±0.5 % (3-GPU) — keep **4** |

(The `cache_max` result is mildly surprising given the ~1 % `mmb_cvt_f32_bf16` tax S10 noted on the

## 7. The landed RDNA4 default

`MMB_CFG cc=0x1001201 dense_geom=1 … f32split=1(min_m=128,min_k=0) … tiny_m=1/1 … routed=0`

| workload | vs the delivery |
|---|---|
| **qwen4exp** (Flash-Next IQ4_XS, 3-GPU tensor) | **+6.7 % pp8192 / +6.5 % pp32768 / +6.2 % pp65536 / +6.2 % pp98304** |
| IQ3_S-heavy dense (27B UD-IQ3_S, 1 GPU) | +0.54 / +0.49 % |
| IQ-heavy MoE (35B UD-Q3_K_M, 1 GPU) | neutral (+0.13 / −0.11 %) |
| same-seed text | byte-identical to the delivery on every model |

The qwen4exp number has now gone +3.1/+3.4 (S7) -> +4.9/+5.2 (S12) -> **+6.7/+6.5 (S13)** — each step
from removing a gate that S7 had put in front of a path that actually wins on RDNA4.

## 9. The pattern worth carrying to S14

Two of the three "measured losers" S7 had gated off on RDNA4 turned out to be **wins that were never
run** (the IQ3_S dense tile at a real geometry, and the F32 split + tiny-M paths), and the third (the
routed MoE) was a genuine loss.  In every case the gate was the thing under test, not the kernel:

> **When a path is disabled by a policy flag, measure the path *with the flag overridden* before
> concluding the path loses.**  S7 recorded several "loses on RDNA4" verdicts that were really
> "was never enabled on RDNA4".

The other lesson is depth: the split tile reads −0.3 % at pp8192 and +1.22 % at pp98304.  **A shallow
A/B is not a verdict** for a long-context workload — measure at 64k+ before disabling anything.
