## 3. RDNA4 gating — the constraint is already satisfied

**All FP8 execution is RDNA4-gated**, both at compile time and runtime:

* `fp8.cuh`: `#if defined(GGML_USE_HIP) && defined(RDNA4)` guards the gfx12 WMMA intrinsics
  (`__builtin_amdgcn_wmma_f32_16x16x16_fp8_fp8_w32_gfx12`) and the hardware fp8 encode.
* `vendors/hip.h:216` defines `RDNA4` from the gfx target.
* `fp8.cu:129`: `if (GGML_CUDA_CC_IS_RDNA4(cc)) { ...wmma or dot4 gemv...; continue; }` — otherwise it
  falls through to **`mul_mat_fp8_scalar`**.
* `quantize_fp8_warp` (barrier-free, hardware encode) is RDNA4-only; the block-reduce `quantize_fp8`
  is the fallback.

**Open policy item for promotion:** on non-RDNA4 the scalar fallback is *correct but very slow*.  We
should decide whether an fp8 GGUF on RDNA1/2/3/3.5 should (a) run scalar (current), (b) be rejected at
load, or (c) be dequantized to f16/bf16.  Nothing reaches the delivery before that is settled.

## 4. No CPU oracle for FP8 `MUL_MAT`

`ggml/src/ggml-cpu/ggml-cpu.cpp` deliberately returns false for `F8_E4M3` on every op except
`GET_ROWS` ("no CPU kernels, requires native FP8 hardware").  So `test-backend-ops` reports
`not supported [CPU]` and cannot validate the fp8 GEMM.  **Correctness must be established at the
model level** — PPL + greedey generation, as the cllm record did (PPL 6.2250 vs Q8_0 6.2464) — or
against an external vLLM-fp8 oracle.  This is a campaign gate, not a bug.
