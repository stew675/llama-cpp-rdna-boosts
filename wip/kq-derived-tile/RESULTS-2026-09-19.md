# V3 derived KQ mask on the tile kernel: implementation + validation

Date: 2026-09-19.  Status: **LANDED as `v16-ebbb18522-r9`** (block 15 amendment).  The decode cost
that §4 describes was removed by hoisting the derived test out of the KV loop (§6), so the planned
template split was not needed and the build time is unchanged.
Builds: `~/llama.cpp` on soar (dev), halo, fingon.

---

## 1. What was implemented

Four files, ~60 lines.  The mechanism and the three traps from `HANDOVER.md` §3 were all live
(confirmed by reading the graph code: `build_attn_mha` sets `kq_mask = nullptr` for a derived op, so
`dst->src[3]` **is** null and both "`mask != nullptr` means there is a mask" assumptions break).

| file | change |
|---|---|
| `fattn-common.cuh` | `kq_derived_t` moved here from `fattn-mma-f16.cuh` so both kernels share one definition |
| `fattn-mma-f16.cuh` | struct removed (single-line pointer to the new home) |
| `fattn-tile.cuh` | the derived arm (below); the three `flash_attn_tile_iter` call sites pass `derived`; `launch_fattn_tile_switch_ncols2`'s `use_gqa_opt` now uses the MMA kernel's `has_mask` notion (`mask != nullptr \|\| KQV->src[5] != nullptr`) |
| `fattn.cu` | `ggml_cuda_flash_attn_ext_supported` now accepts derived on TILE as well as MMA_F16 (VEC stays rejected: it is decode/verify-only and unreachable for a derived op) |

The tile arm itself, inside the one mask read site (`fattn-tile.cuh`, the "Apply logit softcap + mask"
loop):

```cuda
// inside the jc0 loop (hoisted: constant across the i loop below)
const int derived_tok_lo = derived.cell_pos != nullptr ? derived.tok_lo[j] : 0;
const int derived_tok_hi = derived.cell_pos != nullptr ? derived.tok_hi[j] : 0;
...
if (!oob_check || i_KQ < k_VKQ_sup) {
    float mask_val;
    if (derived.cell_pos != nullptr) {
        const int cell_p = derived.cell_pos[k_VKQ_0 + i_KQ];
        mask_val = (cell_p >= derived_tok_lo && cell_p <= derived_tok_hi) ? 0.0f : -INFINITY;
    } else {
        mask_val = (ncols2 > 1 || mask) ?
            slope*__half2float(mask[j*stride_mask + k_VKQ_0 + i_KQ]) : 0.0f;
    }
    KQ_acc[...] += mask_val;
    ...
}
```

Notes that matter for a reviewer:

* **The derived branch is tested before the `(ncols2 > 1 || mask)` guard, not folded into it.**  That
  guard was trap 1: with `mask == nullptr` and `ncols2 == 1` it evaluated false and dropped the mask
  entirely (silent unmasked attention).  Restructuring this way makes the derived case independent of
  `ncols2`, so the trap cannot come back through the GQA-optimised variants.
* The `INT32_MIN` sentinel needs no explicit test: positions are >= 0, so an empty/foreign cell is
  below every `tok_lo` and falls out of the compare into -INFINITY, exactly like the packed entry.
* The `slope` multiply is skipped in the derived arm on purpose: `kq_mask_derivable()` rejects ALiBi,
  so `slope == 1.0f`.  (Multiplying would be *worse* than skipping under a hypothetical zero slope:
  `0.0f * -INFINITY` is NaN.)
* Unlike the MMA kernel, the tile kernel reads the mask **straight from global memory** (no shared
  staging), so the derived arm needs no loader/staging changes at all - it is a pure substitution at
  the read site.

## 2. Correctness: bit-identical, on every arch, including naturally-selected tile

`LLAMA_KQ_MASK_DERIVED=1` vs `=0`, same-seed greedy text via `scripts/extract-generated.py`:

| platform | model / config | KV types | result |
|---|---|---|---|
| gfx1201 (3x R9700) | 9B, tile forced (`GGML_CUDA_FA_WMMA_256=0`), 3-GPU layer | **all 8** (f16 bf16 q8_0 q4_0 q4_1 q5_0 q5_1 iq4_nl) | IDENTICAL |
| gfx1201 | Gemma4 E4B (head 512, SWA 512), tile forced | f16 | IDENTICAL |
| gfx1151 (halo) | **Gemma4 12B, tile selected naturally** (no env) | f16 bf16 q8_0 q4_0 | IDENTICAL |
| gfx1100 (fingon) | **Gemma4 12B, tile selected naturally** (no env) | f16 bf16 q8_0 q4_0 | IDENTICAL |

Two controls make the above non-vacuous:

* On gfx1201 the same model with the WMMA cap left alone (derived -> MMA, the pre-existing path)
  gives `d1 == d0` **and a different text from the tile runs** (708 chars `0229d81902b8` vs 701 chars
  `cc9d5ce277d4`) - so the two kernel families really do differ numerically and the tile path really
  was taken in the tile runs.  A pure "derived == packed" result with identical kernels would have
  proved nothing.
* The SWA gate is covered: Gemma4 is a sliding-window model (`swa` 512-1024), and the window is
  carried in `tok_lo`/`tok_hi`, which the host fill (`set_input_kq_derived`) already handles.

And the headline behavioural change: on gfx1151 and gfx1100 a head-512 Gemma4 **now enables the
derived mask with no environment variable** (`derived kq mask flash attention enabled`), where r8
printed the "not supported, set to disabled" warning.  That is the entire point of the change.

Read: the win tracks the mask size (`n_kv x n_q`), so it is ~zero at a shallow context and grows with

`n_kv x n_q x 2` bytes on **both** device and host (it is a host-buffer input by design - the same

compute buffer 184.02 -> 88.39 MiB device and 112.02 -> 16.40 MiB host at `-c 98304`, ub 512;
scales with the ubatch (the ~800 MiB figure needs ub ~2048).

## 4. Decode: a real regression, and where it does *not* appear

Decode/verify **always** takes the tile kernel (the chooser's WMMA branch requires `Q->ne[1] > 8`), so
the tile kernel is on the latency path in every configuration - including ones that get no benefit
from this feature (a head-256 model uses MMA for prefill and tile only for decode).  Measuring
`LLAMA_KQ_MASK_DERIVED=1` vs `=0` in one build therefore **cannot** detect a codegen cost; this is a
baseline-build A/B (r8 with vs without the diff), ccache making the two-state rebuild ~1 s on soar:

| platform | model | tile instance | tg128 d0 | tg128 d16384 | verdict |
|---|---|---|---|---|---|
| gfx1201 | 9B | dkq256, gqa4 (ncols2=4) | -0.10% | **-0.79%** | cost |
| gfx1201 | Gemma4 E4B | dkq512, gqa4 (ncols2=4) | **-0.48%** | - | cost |
| gfx1100 | 9B | dkq256, gqa4 (ncols2=4) | -0.19% | **-0.69%** | cost |
| gfx1100 | Gemma4 12B | dkq512, gqa2 (ncols2=2) | +0.21% | +0.44% | flat |
| gfx1151 | Gemma4 12B, 9B | tile | -0.03..-0.12% | +0.07..0.00% | flat |

The gfx1201 rows are 3 alternating rounds of `-r 10` (within-state spread ~0.1%, between-state gap
~4x that, non-overlapping sets), so they are real.  Prefill on those runs is flat-to-positive
(9B pp512 d0 -0.96% on the r5 pass was before the repeat measurement; the repeated 9B prefill is
unchanged, and 9B prefill uses MMA, which the diff does not touch).

**Diagnosis (superseded - see §6).**  The cost was the per-iteration *test*, not the branch target:
with `derived.cell_pos != nullptr` evaluated inside the unrolled KV loop, the compiler rematerializes
the extra parameters instead of keeping them in registers, in a kernel that is register-bound by
design.  The pattern fits that: the cost appears only on the `ncols2=4` instantiations and grows with
depth (more KV iterations), and it vanishes on `ncols2=2` and on gfx1151.  The obvious hypothesis -
that the three extra live pointers raised the kernel's register count - was **wrong**: hoisting the
test to once per query row recovered the performance without changing the register count.

## 5. Build cost of the current (runtime-branch) shape

None beyond the normal: the three pointers were already in the kernel signature (unnamed), so the
ABI is unchanged.  Clean `ggml-hip -j16` on soar is unaffected (soar has ccache, so the two-state A/B
took ~1 s per swap).

## 6. Resolution: the test is hoisted, not templated

The tax was not inherent.  Moving the `derived.cell_pos != nullptr` test out of the unrolled KV loop
(to once per query row, at the `jc0` level, with the two loop bodies written out) removes it entirely
and costs no build time:

| state | 9B `tg128` @d16384 (gfx1201) | E4B tile `tg128` @d0 (gfx1201) |
|---|---|---|
| baseline (r8, no derived arm) | 57.039 | 77.552 |
| per-iteration test (first cut) | 56.649 (**-0.68%**) | 77.184 (**-0.47%**) |
| hoisted test (**landed**) | 57.047 (+0.01%) | 77.605 (+0.07%) |

Three alternating rounds of `-r 10` per state; the within-state spread is ~0.1% and the between-state
gap is 4-7x that, so the per-iteration row is a real regression and the hoisted row is
indistinguishable from the baseline.  Confirmed on the target arches by the same baseline-vs-final
A/B: gfx1100 9B @d16384 **+0.02%**, gfx1151 flat, gfx1100 gemma4-12B tile -0.07%.

The `use_kq_derived` **template split** (the plan that was approved) was therefore **not needed**, and
the reason is worth recording: the "only the prefill combos need a twin" estimate behind its cost was
wrong.  `cols_per_block` varies with `(n_tokens, ncols2)` for a derived op - 9 tokens takes
`cols_per_block = 32` at `ncols2 = 8` but 16 at `ncols2 = 1`, and 8 at `ncols2 = 2` - so the twin set
would have covered most of the chain, not a third of it.  With the hoist the build time is unchanged.

Prefill is unaffected by the hoist (it still wins): derived on vs off on the tile path, gfx1201 E4B
pp512 **+2.30% @d0**, gfx1100 gemma4-12B **+1.18% @16k**, gfx1151 **+1.60% / +1.72% @16k**.

The r8 diagnostic note in `src/llama-context.cpp` and the "MMA only" claims in `README.md` /
`patches/README.md` / `MANIFESTS.md` / `AGENTS.md` were fixed in the same pass; the delivery record is
the r9 entry in `WORKLOG.md`.
