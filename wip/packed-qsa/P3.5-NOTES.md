# Packed-QSA — P3.5 notes (2026-09-15)

**Status:** P3.5 measured.  Verdict: **the packed path cannot win on gfx1201 in the canonical
serving configuration.**  The whole P3 end-to-end conclusion was drawn in the wrong split mode
(`-sm layer`); re-measured under the canonical `-sm tensor` the packed path is *worse*, and the
ceiling even with a free merge descriptor is +0.8 %.  The packed attention kernel itself is at
**parity** with the VEC kernel in the canonical geometry (not 1.35x — that was a layer-split
artifact).  See §4 for the decision.

Fork `packed-qsa` @ `32d148ec4` + these notes' levers (rebased 2026-09-15 onto the r5 delivery tip
`65001ac96`, tree `d735d6c1`).  Delivery `packed-qsa` rebased onto `main` @ `a0d1de7` (r5).

## 1. The benchmarking-mode error (the central fact)

The P1–P3 record (and the handover's §1.4 scoreboard) used `-sm layer`.  For qwen4exp the canonical
serving config is **`-sm tensor`** and it is dramatically faster:

| config | pp8192 (IQ3_XXS, f16 KV) |
|---|---:|
| `-sm layer` (handover's config) | 874 t/s |
| `-sm tensor`, default ub | 1606 t/s |
| `-sm tensor`, `-b/-ub 2048` | **2289 t/s** |

`-ub 2048` matters again on top of the split: the P1 pack is rebuilt per ubatch over the whole
growing cache, so fewer/larger ubatches reduce the total pack traffic ~3.4x.

The P1 author chose `-sm layer` because the packed path **aborts** under `-sm tensor` (the P1 meta
assertion, §3).  So the campaign was never evaluated in the config that is served.

## 2. Canonical scoreboard (gfx1201, 3x R9700, `-sm tensor -b/-ub 2048`, pp8192)

| arm | pp8192 | vs pure VEC |
|---|---:|---:|
| pure VEC (no pack) | 2289.18 ± 10.32 | — |
| **P1 pack only** (no merge, VEC attn) | 2286.27 ± 12.69 | **−0.1 %** (pack is free) |
| pack + **P2 merge** + VEC attn | 2177.92 ± 8.69 | **−4.9 %** |
| pack + merge + **P3 WMMA** (full) | 2185.97 ± 15.91 | **−4.5 %** |
| pack + merge(no rows kernel) + VEC† | 2307.17 ± 1.24 | +0.8 % |
| pack + merge(no rows kernel) + WMMA† | 2298.97 ± 12.97 | +0.4 % |

† `GGML_CUDA_QSA_MERGE_NOROWS=1` is **incorrect** (see §3) — the row is there only to bound the
upside: with the expensive half of the merge removed the packed path is still only ~break-even, and
the WMMA kernel is ~0.4 % *slower* than VEC.

At ub=512 (`-sm tensor`) the same ordering holds and the full path is −7.2 % (1606 / 1533 / 1490).

**So the entire overhead is the P2 merge descriptor build, and even removing it does not make the
packed path win.**  The P1 pack is free; the P3 kernel adds nothing.

## 3. Root cause: `qsa3_rows_kernel` (merge kernel A)

`rocprofv3 --kernel-trace` on the `pack+merge+VEC` arm (pp4096, ub2048, tensor) — kernel time sums
are inflated ~1.8x by the profiler and are useful for shares only:

| kernel | calls | total | per call | share of all kernels |
|---|---:|---:|---:|---:|
| `flash_attn_qsa<256,f16>` (VEC reference) | 96 | 805.6 ms | 8.39 ms | 8.0 % |
| **`qsa3_rows_kernel`** (merge A) | 96 | **244.5 ms** | **2.55 ms** | **2.4 %** |
| `qsa3_merge_kernel` (merge B) | 96 | 19.6 ms | 0.20 ms | 0.2 % |
| `indexer_topk_*` (all) | — | 87.7 ms | — | 0.9 % |

The merge build (A+B) is ~5 % of the pass end-to-end; **kernel A is 12x kernel B**.  Kernel A walks
all `n_q * ns` index entries to (a) sentinel-normalize, (b) test ascending, (c) rank-sort any
unsorted row.  It is the same O(n_q·ns) pass the attention itself makes, with none of its reuse.

Two facts that constrain the fix:
* **The rows are not always sorted.**  `GGML_CUDA_QSA_MERGE_CHECK=1` reports `rows_sorted=1` at
  ub2048 (it was 0 in the old ub-default runs) — one row in 2048 took the sort path.  Dropping
  kernel A (`GGML_CUDA_QSA_MERGE_NOROWS=1`) makes the descriptor mismatch the host oracle
  (12 fields) and fails the synthetic self-test (8247 mismatches).  So kernel A cannot simply be
  deleted; the ascending assumption has to be established elsewhere (e.g. make the indexer emit
  ascending keys) or the merge made order-agnostic.
* The merge kernel B alone is ~free (+0.8 % arm is within noise of pure VEC), so a *correct* kernel
  A that costs nothing would leave the packed path at ~parity, not ahead.

## 4. Decision

* **P4 (tensor-split support) is feasible and was implemented/validated**: the packed shadows split
  consistently with the K/V kv-head axis (keys axis 3, values axis 2; device1 = head0's blocks,
  device2 = head1's).  The P1 "must be mirrored" assertion was over-conservative; the relaxation in
  `ggml-backend-meta.cpp` is kept.  A/B under `GGML_CUDA_QSA_ATTN_CHECK=1` gives the same
  `rel ≈ 3.9e-5` as layer split.
* **P3.5 does not reach a win on gfx1201 in any measured config.**  The 1.35x op-level figure was a
  `-sm layer` artifact; the canonical geometry puts the kernel at parity and the merge A kernel
  costs ~5 %.  The best-case (free merge A) is +0.8 % over pure VEC.
* Recommendation: **park the packed-QSA campaign for gfx1201.**  If it is continued it must be on
  **gfx1151** (Strix Halo), where the QSA op is ~14 % of the pass and the VEC kernel is the slow
  reference this design was built against — but the ~5 % merge A cost is architecture-independent
  and must be dealt with there too.  Any further gfx1201 kernel tuning (Track B in the old
  handover) cannot pay: with a free merge and a *2x* kernel the ceiling is ~+7 % QSA share × … i.e.
  ~4 % of the pass, and the kernel is currently at 1.0x.

## 7. ubatch sweep — large ubatch is NOT the missing piece (2026-09-15)

pwilkin ran ~24–32K ubatches on Strix Halo; the hypothesis was that the packed win only appears
when the ubatch is large enough to amortise the pack.  Tested on gfx1201:

**VRAM ceiling.**  For this 176B model on 3x 32 GB R9700, `-sm tensor` fits up to **`-ub 6144`**
(`pp8192`; 6656+ aborts in `ggml_backend_meta_buffer_type_alloc_buffer`).  `-sm layer` fits
`-ub 8192` (and a `-ub 16384`/`pp8192` batch), but not a `pp16384` context, and its single-ubatch
numbers are very noisy (±70–95 t/s, means drifting >5 % between runs — one `-r3` run showed the
full path **+4.1 %**, the `-r5` re-run **−5.5 %**).  The tensor-split numbers are stable (±8–20).

**The decisive measurement is the op-level speedup** (`GGML_CUDA_QSA_ATTN_CHECK=1`, x20, first op):

| split | n_q | ns | packed | VEC | speedup |
|---|---:|---:|---:|---:|---:|
| tensor | 1024 | 1024 | 1.95 ms | 2.15 ms | 1.10x |
| tensor | 2048 | 2048 | 6.19 ms | 8.04 ms | **1.30x** |
| tensor | 4096 | 2051 | 13.96 ms | 16.89 ms | 1.21x |
| tensor | 6144 | 2051 | 24.25 ms | 25.67 ms | 1.06x |
| layer  | 8192 | 2051 | 72.15 ms | 70.12 ms | 0.97x |
| layer (P3) | 2756 | 2051 | 16.47 ms | 21.99 ms | 1.35x |

**The packed kernel's advantage peaks at n_q ≈ 2K / ns ≈ 2K (1.30–1.35x) and *declines* as n_q
grows** — at n_q 8192 it is already slower than VEC (0.97x).  So a larger ubatch is the opposite of
a fix on gfx1201: it moves the op past its optimum *and* the merge overhead is at best only ~1.25 %
there (12 calls/ub, since pp8192 is a single ubatch), not enough to matter when the op itself is
slower.

Combined with §2/§3 the ceiling is: op 1.30x at its best ubatch × QSA share (~8 % profiled) gives
~1.8 % if the merge were free; the merge is ~5 % → net negative.  **Large ubatch does not change the
gfx1201 verdict.**

*Caveat for gfx1151:* the decline here is against the *RDNA4-tuned* VEC kernel (block 04).  On
Strix Halo the VEC reference is much weaker, so the trend could invert there and pwilkin's large
ubatches may be exactly what the packed path needs.  That box (128 GB unified) can hold the 24–32K
ubatch; this one cannot.  Test the hypothesis there, not here.

## 9. gfx1151 validation — the approach DOES win (2026-09-15, `halo`)

Ran **pwilkin's own `strix-halo` branch** on the Strix Halo box (gfx1151, UMA) — his kernel is the
gfx11 reference this port targets, and his QSA A/B isolates exactly the packed-WMMA kernel (both
arms carry the same `LLAMA_QSA_SPARSE/WHOLE_ATTN/BLOCK_SELECTION/COMPACT_METADATA/DENSE_SHORTCUT/`
`DIRECT_INDICES/PACK_KEYS/PACK_VALUES/SCORE_BOUNDS/NO_DENSE_MASK` stack; only `LLAMA_QSA_FA_V3`
differs).  Model `Qwen3.8-Flash-Next-UD-IQ4_XS` (87 GiB), `-ngl 99 -fa on -ctk f16 -ctv f16`,
`pp8192`:

| ubatch | base (`FA_V3=0`) | packed (`FA_V3=1`) | delta |
|---|---:|---:|---:|
| 2048 | 583.72 ± 49 | 636.82 ± 50 | **+9.1 %** |
| 8192 | 613.34 ± 0.35 | 706.71 ± 0.21 | **+15.2 %** |
| 16384 | 614.09 ± 3.06 | 711.51 ± 1.17 | **+15.9 %** |

So the design wins on UMA, and the win **grows with ubatch** in the regime pwilkin uses.  The
`soar`/gfx1201 negative result is therefore **not** a property of the approach.

### 9.1 Why our gfx1201 port does not reproduce it — the merge share, and the gfx12 kernel

Two gfx1201-specific effects, both consistent with §2–§7:

1. **The P2 merge is a fixed absolute cost, so it is a much larger *fraction* of a faster pass.**
   The merge kernels are the same code; on gfx1151 the pass is ~14 s (583 t/s) so a ~180 ms merge
   is ~1.3 %, while on gfx1201 the pass is ~3.6 s (2289 t/s) so the same ~180 ms is ~5 %.  The
   packed path is thus structurally disadvantaged on the faster box, *and* kernel A (the rows
   kernel, §3) is the dominant part of that cost.
2. **The gfx12 WMMA D layout is much worse for this softmax than the gfx11 one.**  gfx11's
   `wmma_f32_16x16x16_f16_w32` gives each lane 8 columns of **one** row, so the row softmax reduces
   over 2 lanes (one `shfl_xor(...,16)`); gfx12's `..._gfx12` gives each lane 8 **different rows**
   at one column (`m = 8*(lane>>4)+e`), so our kernel must do 8 rows x 4 shuffle steps = **32
   shuffles per chunk** for the max and again for the sum.  Our P3 kernel is also the
   correctness-first variant: LDS P-transpose (not pwilkin's shuffle network) and no K/V prefetch.

That is why the op-level A/B says 1.30x on gfx1201 while the end-to-end says the packed kernel is
at/below parity: the gfx11 kernel is genuinely faster, ours is not (yet).

### 9.2 Revised conclusion / next steps on gfx1201

The approach is validated; the remaining work is to make the **gfx12 kernel** efficient:

* transpose the 8-row D vector across the wave so the softmax reduces once per step instead of 8x
  (make each lane own a row, as gfx11 already does in hardware);
* replace the LDS P transpose with a shuffle network;
* prefetch the next chunk's K/V (and descriptor) — pwilkin does;
* reduce the P2 merge A kernel cost (~5 % on gfx1201) — e.g. have the indexer emit ascending keys
  so kernel A can be dropped, or fold the sortedness check into the merge kernel.

A gfx1201 win at `ub 2048` is plausible once (a) kernel A is cheap and (b) the gfx12 softmax is
cheap; the fix for (b) is worth ~2-4x on the op's shuffle work alone.

## 10. Levers added this session (all default-off, no delivery impact)

| env | effect |
|---|---|
| `GGML_CUDA_QSA_PACKED_MERGE=0` | build the P1 pack but skip the P2 merge entirely (isolates the pack cost) |
| `GGML_CUDA_QSA_MERGE_NOROWS=1` | skip merge kernel A (and `srow`) — **BREAKS correctness** (rows are occasionally unsorted); diagnostic only |
