## UPDATE 2026-09-02 (night): indexer-pipeline depth falloff - fused op + radix tuning

### GGML_OP_INDEXER_TOPK (commits 483f77fae, 9dff5cc4f on qwen4exp)
The indexer materialized the full [n_kv, n_tps] F32 expanded tensor
(512MB at 64K, mirrored on every GPU) per QSA layer just to feed TOP_K:
GET_ROWS 1.4 + CONT 6.78 + F16->F32 mask cast ~1.5 + ADD 2.7 + TOP_K 8.3
= ~21ms/layer. The new fused op computes value[c] = score[cell_blk[c]] +
mask[c] on the fly in each radix pass (src0=score [n_blocks, n_tps,
n_stream] F32, src1=cell_blk [n_kv, n_stream] I32, src2=mask F16/F32,
param k). Output [k, n_tps, 1, n_stream] I32 - same layout the QSA op
consumes, so the downstream reshape disappeared too.

KEY gotchas (both cost real debugging time):
- Do NOT ggml_reshape_3d(kq_mask) per layer as the additive: that
  materializes 13 x 256MB F16 copies at 64K (compute buffer 2040 ->
  4856 MiB, OOM). Pass the raw 4D [n_kv, n_tps, 1, n_stream] mask; the
  size-1 dim is a no-op stride so the kernel's 3D indexing is identical.
- The smem histogram init/accumulate in the radix only zeroed the first
  BLOCK_SIZE bins - latent bug for NBINS > BLOCK_SIZE. Fixed to zero all
  NBINS bins. (An 11-bit radix attempt using this code path faulted;
  RB=11's overlapping bit-10 pass is not worth the risk - reverted.)

Radix tuning: blocks_per_row capped at 8 (was up to 64). Histogram
buffer 134MB -> 16MB at 64K, select pass work 8x less. INDEXER_TOPK at
64K: 10.17 -> 7.61 ms.

## UPDATE 2026-09-02 (late night): prefill investigation - MoE 3x gap ROOT-CAUSED

### pp8192 baseline + op-timing methodology
- pp8192 (ub=2048, 3 GPU, warm): 2006.9 -> 1992.4 t/s (cold->warm). ~= pp16384's 1970:
  per-ubatch wall is depth-constant (~1.03s/ubatch at ub=2048 for 8K..64K).
- GGML_CUDA_OP_TIMING inflates every op by a per-op sync constant (~47-180us
  depending on run). Real op time = measured - sync. Solve sync from
  (measured_sum - wall)/n_ops. Big single ops (QSA, MUL_MAT_ID) are near-real.
- IMPORTANT harness fact: llama-bench -ub N is clamped to n_batch (default
  2048). `-b 8192 -ub 8192` CRASHES in context creation (hard cap). So ub>2048
  is unreachable; per-expert batch experiments via -ub are dead.
- Real per-GPU-ubatch budget (4112ms/run wall, ub=2048):
  MoE MUL_MAT_ID (down 12.9% + fused gate 12.9%) = 24.6% | QSA 10% | hc ~12.6%
  (LoRA GEMMs + F32 elementwise) | long tail ~53% (norms, muls, adds, delta-net
  [2560x15x2048], indexer, shared expert, graph gaps). The R9700 memory
  bandwidth is only ~640 GB/s: F32 elementwise ops at 340-575 GB/s are 55-90%
  of BW, NOT slow. Nothing is bandwidth-starved except decode.

### Model weight types (unsloth "UD-Q4_K_XL" name is misleading)
- NAMING: "UD-Q4_K_XL" = "Unsloth Dynamic" - a mixed-quant assembly, NOT a new
  quant type. Mostly Q4_K_M-ish with higher-quality quants (Q5_K/Q5_1/Q8_0/F32)
  for critical blocks. There is no Q4_K_XL quant format.
- MoE ffn_gate_exps/ffn_up_exps: Q4_K (47) + Q5_K (1) per layer. The merged
  gate_up tensor is created at LOAD time by create_tensor_gate_up_exps.
- ffn_down_exps: Q5_1 (43) + Q8_0 (5) - the DOWN experts are Q5_1 (worst
  possible for RDNA4 dequant; dense Q5_1 thin-K = 12.5 TFLOPS vs Q4_K 31.6).
- hc LoRA (attn/ffn down+up): Q8_0. hc_inject + ffn_gate_inp (router): F32.
- attn_q/k/v/output: Q8_0 (+ some F32). token_embd: iq4_nl/q8_0. NO Q8_1, NO
  Q4_K_XL anywhere. GGUF tensor type enum: Q8_0=8, Q8_1=9 (do NOT trust 7/8).

### ROOT CAUSE of the MoE 3x gap (the big finding)
- moe_fat (10 experts x 2048 rows each, same total MACs): 80.2 TFLOPS Q4_K /
  56.2 Q5_1 - FASTER than dense! The ids machinery is fine.
- 512 experts x 40 rows: 11.1 TFLOPS. The kernel's J-tile = 128 rows (selected
  from ncols_max=20480), each expert has ~40 -> 88/128 rows are GARBAGE
  (vec_dot computes ALL J rows; tile_y_max_j guards only the WRITE-BACK, not
  the dot). 3.2x wasted compute + garbage y reads pollute L2 (raw rate drops
  80 -> 35.4 TFLOPS).
- J-sweep 16..128 (env GGML_CUDA_MMQ_ID_J): FLAT ~6.1ms. Small J is
  latency-bound (raw 13.5), large J is compute-bound with 3.2x waste (raw
  35.4) - net equal. No J-based fix works.
- stream_k: false everywhere in mmq-config-rdna4.cuh (all types). It is NOT
  the lever: (a) GGML_ASSERT(!has_gate) - fused gate+up only instantiated for
  the non-stream-k path; (b) the MoE gap is not wave-tail (10240 useful blocks
  over ~96 slots = ~107 full waves, ~1% tail). Verified by J-invariance +
  block-count analysis. Leave it off.
- M=1 tail graphs: hc LoRA up [10240x320x1] = 71ms once per run (~1.7% wall,
  graph-context mmvq pathology, NOT reproducible standalone). Ignore for
  prefill; matters only if decode ever routes there.

### THE FIX DESIGN (next session - implement + verify)
Sequential-experts-per-block in the mmq ids path: each block covers ~3 experts
(512/3 = 171 groups x nty I-tiles = ~1710 blocks = the fat-case count), looping:
  for each expert e in group:
    zero sum; for kb0 in K-blocks: stage y_e rows 0..rows_e-1 (from compact
    row0_e, contiguous) + zero pad rows_e..aligned-1; load_tiles(x_e) with
    x_e = x + e*stride_channel_x; vec_dot(x_e, y, sum, k00, j_len=aligned);
    write_back(sum, ids_dst[row0_e..], dst, i_max, j_max=rows_e-1)
- vec_dot typedef gains `const int j_len`; all 14 implementations in
  mmq-vec-dot.cuh bound `for (j0 < J)` -> `for (j0 < j_len)`. Dense path
  passes j_len=J (constexpr fn-pointer call -> full unroll preserved).
- process_tile restructured for the per-expert loop; write-back guard
  unchanged (j_max handles pad rows); no ids_dst=-1 needed.
- Expected: 67.1 GMAC @ ~60-80 TFLOPS = 0.85-1.1ms vs 6.07 (gate_up), similar
  for down -> MoE 24.6% -> ~8-10% wall. Re-verify: /tmp/mmq_bench A/B, then
  logitdump top-1 11/11, then full depth curve.
- ALTERNATIVE (fallback if the vec_dot change is too invasive): zero-pad the
  compact src1 to 128 rows/expert in the mmid helper (removes L2 pollution;
  compute waste stays 3.2x - half the win at 1/10th the risk). Test the raw
  rate recovery first with that.
