## 2. THE TASK: eliminate the MoE redundant dot compute (2.2-2.6x waste)

### The mechanism (fully measured this session - trust this, not older notes)
- clock64 phase profile of the mul_mat_q K-loop (baseline kernel, per block
  of 10 K-iters, steady state):
    x load (load_tiles) ~25K cyc (20%) | y staging ~30K (20%) |
    vec_dot ~85-110K (55-65%) | post-load barrier wait ~5-10K (3-7%)
  => NOT waiting on data at the barriers (the earlier "latency-bound" model
  was WRONG for the MoE). The vec_dot dominates because EVERY block dots the
  FULL J-row tile regardless of the expert's real row count.
- Dense M=20480 has the identical per-block phases (~74K dot); the MoE just
  runs 3.2x more blocks (one full-tile block per expert) because the J-tile
  grid is sized from ncols_max=20480 while experts have few rows each.
- Measured REAL routing (pp2048, ub=2048, expert_bounds dump): 362/512
  experts used, Zipf-like (one expert 1077 rows; 34 experts >128 rows;
  ~110 experts <=8 rows). Exact dot-row waste:
    J=96  (fused gate): 2.18x | J=128 (down): 2.59x | aligned-16 floor: 1.17x
  The synthetic uniform 512x40 bench (3.2x) OVERSTATES the real waste.
- Expected win: dot phase ~60% of block drops ~2x (53120 -> 23920 dot-rows),
  stage drops ~2x (guarded staging), load stays (weight-bound, irreducible).
  MoE wall share 24.6% -> ~11-13% -> pp8192 ~2250 t/s.

### THE CRUX (why the previous attempt failed - do not repeat blindly)
The full packing scaffold was implemented and REVERTED this session (see
handover-2026-09-02.md "UPDATE ... MoE packing experiment"). It failed ONLY
because the runtime-bounded j0 loop does NOT make the MMA skip:
- j_len=48 vs full-J A/B measured 6.42 vs 7.05ms = 9% savings (expected 2.7x).
- Cause: `#pragma unroll` on the runtime-bounded j0 loop emits the full
  J/16-group body with only the ACCUMULATION guarded; the B-loads and MMA
  still run for all groups.
- Removing the pragma made it WORSE (6.75ms) - a naive dynamic loop cannot
  pipeline the ldmatrix+mma chain across the unknown trip count.
- The J-sweep flatness (16..128 all ~6.1ms) is explained by the config
  coupling (I and nthreads scale with J) + the J-independent load+stage.

### The fix: compile-time J_LEN templating (the actual design)
1. Add a template param `int J_LEN` to the vec_dot implementations used by
   the MoE (start with `ggml_cuda_mmq_vec_dot_q8_1_q8_1_mma` in
   mmq-vec-dot.cuh - serves BOTH Q4_K and Q5_1) and bound the j0 loop with
   the CONSTEXPR J_LEN: `for (int j0 = 0; j0 < J_LEN; j0 += ntx*tile_C::J)`.
   The constexpr bound gives the compiler the EXACT trip count -> full
   unroll -> the MMA genuinely shrinks. The y/sum pointer offsets stay the
   caller's business (rows [0, J_LEN) of the given pointers).
2. In process_tile, dispatch the runtime j_len to the compile-time
   instantiations: a switch over the classes {16, 32, 48, 64, 80, 96, 112,
   128(=J)} calling the J_LEN-specialized vec_dot. Limit the instantiation
   set to the classes that occur (j_len = (rows_p+15)&~15, capped at J) to
   bound the template blowup. VERIFY the mma skip FIRST via the micro-bench
   j_len A/B: the synthetic 512x40 gate should drop 6.07 -> ~2.5-3ms (a
   real ~2.2x, not 9%).
3. Re-apply the packing scaffold on top (all in the 09-02 handover record;
   the reverted diffs were: mmq.cuh + mmq-vec-dot.cuh + mmq-config-rdna4.cuh):
   - process_tile per-expert/pass loop (sequential experts per block, pad
     rows zeroed, j_len = min(aligned(rows_p), J), write-back j_max guard
     unchanged, ids_dst reload guarded by j < rows_p - the M=128 empty-
     expert fault came from an unguarded reload in that experiment).
   - kernel ids branch: zt = expert group of MMQ_MOE_EXPERTS_PER_BLOCK=4,
     grid.y=1, offset_x without the zt term (per-expert + e*stride_channel_x).
   - launch: packed_ids grid (nty, 1, ceil(nchannels/E)) when ids_dst &&
     !stream_k. Keep the J at 96/128 (the ntiles heuristic) - do NOT add
     the J=64/I=64 configs (they faulted on the real model this session -
     likely a separate pre-existing small-tile issue).
4. Correctness gate BEFORE any perf claims: logitdump A/B (see section 4).
   Expected: bit-identical or near (per-row K-accumulation order unchanged).
   Known small-M baseline faults (M<256 MoE OOB in ids_dst fill) are PRE-
   EXISTING upstream bugs, not from this work (relevant if testing small M).
5. Measure pp8192 (warm) A/B. Target: ~2250 t/s (from ~2000).

## UPDATE 2026-09-03 late: dot-redundancy theory TESTED and REJECTED - the real limiter is the x-weight stream

The prescribed J_LEN experiment was run as a clean probe (compile-time J_LEN=48
bound + `#pragma unroll 1` on the q8_1 mma j0 loop, so the executed WMMA count
truly dropped 8->3 groups, verified in SASS). Results (mmq_bench, 1 GPU):
  moe_gate_up 512x40:  5.576 ms  (baseline 5.586)  -> 0%      <- dot is FULLY hidden
  moe_down Q5_1:       4.333 ms  (baseline 5.109)  -> +15%
  dense M=20480:       2.010 ms  (baseline 2.030)  -> 0%
  moe_fat:             0.855 ms  (baseline 0.841)  -> 0%
CONCLUSION: the mma work is NOT the bottleneck for the long-K Q4_K gate; the
"3.2x redundant dot" framing and the clock64 phase profile that suggested
dot-dominance were WRONG (the probe directly contradicts the phase data - trust
the probe). The earlier j_len A/B "9%" and the "codegen doesn't skip" story
were chasing a phantom.

New mechanism (measured): the MoE time is M-INDEPENDENT. M=512 uniform 512exp
= 5.31 ms vs M=2048 = 5.65 ms (x fixed at ~840MB both, y 4x smaller at M=512).
=> the x (per-expert weight) stream dominates at ~155 GB/s effective (1 GPU,
24% of the 640 GB/s peak). The real-model fused gate achieves ~300 GB/s because
it loads TWO weight streams per barrier (2x the bytes in flight) - the
effective BW scales with the per-barrier burst, not the mma.

Other probes this session (all NEGATIVE for the gate):

## UPDATE 2026-09-03 end: register/unroll tradeoff MEASURED - occupancy is a trap

The register question was answered directly. `#pragma unroll 1` on the q8_1
mma j0 loop (full J, only change):
  moe_gate_up: 5.59 -> 11.95 ms (2.1x WORSE)   moe_down: 5.11 -> 7.85 ms
The unrolled mma pipeline (240 VGPRs) does essential intra-warp latency
hiding; reducing it exposes the ldmatrix->mma->accumulate chain. 240-256 VGPRs
are well-spent. Occupancy stays 2 (smem 41.5KB/block AND registers both cap
it; the occ=3 launch_bounds hint was ignored - compiler kept 240 VGPRs rather
than spill the 64-float accumulator). Reconciliation: full unroll + row-cut =
0% (hidden); unroll-1 + row-cut scales with groups (8grp=12ms, 3grp=5.6ms).
CONCLUSION: occupancy is NOT the gate's limiter; do NOT chase it via unroll
reduction (measured 2x regression) or I=64 (faults). The remaining untested
lever for the fused-gate x-stream (~300 GB/s vs ~640 peak) = bytes-in-flight
per barrier: ITER_K 256->512 (halve K-iters/barriers, double the per-barrier x
burst). Pair with the smem check (x tile 35.8KB->71.6KB at I=128 -> 1 block/CU
unless I is also reduced - but I=64 faults, so expect 1 block/CU and verify
whether the burst doubling outweighs the occupancy drop - this is the test).

## UPDATE 2026-09-04: vec_dot removal probe - the dot phases cost ~50% of every case

Raw-pattern probes (standalone hipcc kernels replicating the exact MoE x-read
pattern: stride-10 144B q4_K blocks, 8x4B/warp, nibble expansion, smem stores,
per-K-iter barriers, occ=2 via 41KB smem, full-block reads): ALL variants hit
950-1000 GB/s on 944MB - the DRAM scatter pattern is NOT a hardware ceiling.
The contiguous-linear control was SLOWER (633 GB/s). => the ~155 GB/s in the
real kernel is 100% kernel structure, 0% DRAM/pattern.

Then the decisive probe: commented out ONLY the 4 vec_dot calls in process_tile
(kept load_tiles, y staging, all barriers, both gate+up streams). mmq_bench:
  moe_gate_up: 5.586 -> 2.774 ms  (dots = 50% of the time)
  moe_down:    5.109 -> 2.256 ms  (dots = 56%)
  dense M=20480: 2.030 -> 0.943   (dots = 54%)
  moe_fat:     0.841 -> 0.761     (dots = 10% - full tiles, L2-hot)
The no-dot skeleton ALONE runs the gate at ~303 GB/s (2x the full kernel).
Reconciles with the J_LEN probe (mma cut 8->3 groups = 0%): the dot phase is
NOT mma-issue-bound - it is the k01-loop instruction stream (A-frag b128
ldmatrix-equivalents + 16 dmA half2 (8B) ds_reads per k01 + B + mma + the
64-float sum accumulate chain at 240 VGPRs). Per-warp per-K-iter the dmA
(scale/dequant) reads are the largest single ds_read count.

TWO levers, both real kernel work, quantified ceiling ~2.8ms on the gate
(5.59 -> ~3.0-3.5 realistic):
  A. OVERLAP: double-buffer the x tile in process_tile so K-iter k+1's loads
     issue during K-iter k's dots. Smem: x tile doubles (38.9KB -> 77.8KB at
     I=128) -> exceeds the ~64KB/block limit -> must pair with I=64 (x 19.5KB
     x2 + y + ids ~= 48-55KB, 2 blocks/CU) - but I=64 faults on the REAL model
     (bench-only OK). OR split the dot to overlap only the y-stage.
  B. CHEAPER DOT: cut the vec_dot instruction stream - the dmA half2 reads
     (16 per k01 per warp) dominate; would need an x_dm smem layout change to
     widen, or hoist/reuse across the j0 groups (already done) - hard.
Recommendation: A is the cleaner target (it attacks the serialization proven
by this probe); do it in the bench first (I=64 configs are bench-valid), then
solve the I=64 real-model fault separately. Expected: fused gate 504ms ->
~300ms, MoE wall 24.6% -> ~19%, pp8192 ~+5-6%.
Tree clean at 9dff5cc4f. mmq.cuh/.cuh probes all reverted. Bench baselines
unchanged (gate 5.586, down 5.109, dense 2.030, fat 0.841).

## UPDATE 2026-09-04b: y-staging guard experiments ALL NEGATIVE - do not re-try

Three variants of skipping the MoE pad-row y staging (experts have ~40 of the
128 tile rows; the pad rows' sums are discarded at write-back so skipping
their staging is output-safe):
  1. int4 (16B) vectorized copy + row guard:  gate 5.59->5.96 (+7%), down
     5.11->4.23 (-17%!), dense 2.03->2.32 (+14%). The dense (full rows, guard
     inert) isolates the vectorization as a pure regression: the scalar loop's
     20 independent loads/thread gave deep MLP; 1-2 int4 loads/thread killed it.
  2. Guard-only (predicated loads inside the compile-time-bound loop):
     gate 6.78 (+21%), down 4.97 (+3%), dense 3.32 (+64%). The runtime
     predicate destroyed the full unroll/load pipelining even when always-true.
  3. Guard-only with dynamic loop bound: not measured separately (variant 2
     covers the codegen trap).
Interpretation: the y staging reads are L2-resident and NOT the bottleneck;
the M-independence (5.31 vs 5.65 for 4x y) already said so. Every structural
tweak to the staging costs more in codegen than it saves. The pad-row "waste"
is free (hidden), like the dot-row waste. REVERTED, tree clean at 9dff5cc4f.
Bench baselines stand: gate 5.586, down 5.109, dense 2.030, fat 0.841.
Remaining unpursued lever: the vec_dot's per-k01 x-side (A-frag + dmA half2
smem reads) - the one part of the dot phase that does NOT scale with the j0
group count (J_LEN probe) and is therefore the only consistent candidate for
the ~8.5-11K cycle/iter dot phase (removal probe: dots = ~50% of every case).
