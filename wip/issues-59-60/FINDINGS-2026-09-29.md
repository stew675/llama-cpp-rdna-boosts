## 2. Reporter results — issue #60: **retraction + a new blocker**

**Retraction.**  They re-ran r3 vs r5 interleaved on a freshly booted box against the 196K profile
(single `llama-bench -p 196608 -n 0`, q5_1 KV, ub 256): **both PASS** (916 / 919 t/s).  The original
r5-OOM was a marginal/noise artifact, consistent with the static proof that the r4/r5 band is
RDNA4-only and r3 == r5 on gfx1100.

**New blocker — the candidate's *unfused* default does not fit their 196K context.**

| build | 196608 prefill | note |
|---|---|---|
| r3 | **PASS** 916 t/s | |
| r5 | **PASS** 919 t/s | |
| r17 (their qsa3-off) | **PASS** 880 t/s | |
| r20 (pre-fix) | **FAIL** | SIGABRT ~12 s, qsa3 F16 packs OOM the CUDA pool |
| **wip default** | **FAIL** | ROCm0 graph reserve grows 425 → 430.45 MiB, `cudaMalloc` OOM, `res=-2` |
| wip + `GGML_CUDA_FA_KV_NATIVE=0` | **FAIL** | same → **not** the staging arena |
| wip + `GGML_CUDA_QSA3=1` | **FAIL** | SIGABRT (same as r20, the qsa3 packs) |
| **wip + `…_INDEXER4_GFX1100=1`** | **PASS** 869 t/s | but not bit-exact |
| wip default @180000 | **PASS** 968 t/s | threshold between 180K and 196K |
| 131072 | PASS on every config | |

* Baseline VRAM after load at ctx=196608 is identical across r3/r17/wip (~24052-24077 MiB used of
  24560, ~480 MiB free/card), so the difference is the **compute-graph reserve**, not baseline memory.
* They do not use `--fit`, so the new arena accounting does not affect this profile; `FA_KV_NATIVE=0`
  changing nothing confirms the staging arena is not it.
* **Their root cause:** the #59(b) bit-safe choice (fused 4-head prefill score OFF on RDNA3_0 → the
  unfused `mul_mat+relu+head_sum` chain) needs a **larger compute-graph reserve at deep prefill** than
  the r3/r17 fused `lightning_indexer` chain, and it crosses the ~480 MiB headroom.  Turning the fused
  path back on fits and runs 869 t/s.
* **Their ask:** make the gfx1100 default fit long ctx as well — reduce the unfused chain's reserve at
  deep prefill, select the fused path when the context is large, or give a knob.  Until then they keep
  196K on r3.  They note the qsa3 part is a real improvement (r20 cannot do 196K at all).

### WI-2 — Make the gfx1100 default fit 196K (the actual open fix)
The #59(b) gate traded the unfused chain's speed for the fused path's smaller reserve.  Both matter, so
the real fix is one of:
1. **Reduce the unfused prefill-score reserve.**  Look at `build_qsa_top_k`'s `compute_score` in
   `src/models/qwen4exp.cpp` — the `score_mem` chunked branch already exists for `>128 MiB` score
   tensors; find why the deep-prefill reserve still grows past ~425 MiB (strip size? `n_blocks`
   bounds? the `GGML_OP_INDEXER_TOPK` block-path buffers? the derived bias?) and shrink it.  This is
   the preferred fix because it keeps the faster, bit-safe chain.
2. **Select the path by context/geometry.**  Keep `ggml_cuda_lightning_indexer_supported` returning
   true for the generic 4-head case (so the fused op remains available), and choose fused-vs-unfused
   in `use_wmma` from a reserve budget: e.g. use the fused path once `n_kv` (or the estimated
   unfused score bytes) exceeds a threshold, or when free device memory would not hold the unfused
   reserve.  This changes the #59(b) gate from "unsupported on RDNA3_0" to "policy on RDNA3_0", which
   also restores `LLAMA_QSA_SCORE_WMMA` as a working knob on gfx1100.
3. **A knob for the 196K deployment** if 1/2 need longer: a `LLAMA_QSA_*` switch that forces the fused
   path (the reporter's `…_INDEXER4_GFX1100=1` works today but is not bit-exact; the generic-vec fused
   path *is* text-bit-exact — see the #59 purity note).
