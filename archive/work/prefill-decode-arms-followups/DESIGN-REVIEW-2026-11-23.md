# Design review — `beta/prefill-decode-arms/prefill-decode-arms.patch` (2026-11-23, r353 beta)

**Status: REVIEW ONLY. No code was changed, nothing was built, nothing was run.**  This is a reading of the
6 000-line beta artifact against the reported symptom set (*corrupted output, memory shortage, crash under
multiple concurrent slots with MTP*), plus an evaluation of the maintainer's proposal: *keep the single-context
server's setup and memory entirely, and make only the decode **execution context** independent.*

Reference points: the patch as it sits in `beta/` (line numbers below are `patch:LNNN`), the r353 delivery
(`~/llama.cpp` @ `089f90067`) for every base-side claim, `beta/prefill-decode-arms/README.md` (the block's own
record), `wip/prefill-decode-arms-followups/README.md` (W1-W9), `INVARIANTS.md` r346/r347/r350/r351,
`GREEDY-PURITY.md` §63/§89/§105/§107.

---

## 0. Verdict in one paragraph

The maintainer's instinct is right about **where** it went too far, but the boundary is one level lower than
"decode runs on its own thread": **the server-side split is already close to what was proposed** (the prefill
arm keeps prompts, checkpoints, the prompt cache and the response lifecycle; the decode arm only steps and
emits).  What went all-in is the **memory model**: the second context was built as a **co-owner of a *viewed
copy*** of the prefill arm's memory — its own `llama_kv_cache`, its own `llama_memory_recurrent`, shared cells,
a second allocation owner bolted on, an apply lock bolted on, and a device-to-device **state handover** to move
the recurrent half between the two copies at every request boundary.  Every one of the three reported symptom
classes is generated by that decision, not by the two threads.  Replacing it with **one memory object that both
contexts use** (a second *user*, not a second *owner*) removes roughly a quarter of the patch and all three
symptom classes' root causes, and it needs exactly one piece of real work that upstream already has on its own
TODO list (contextifying `llama_memory_recurrent`).

## 2. The design fault, stated precisely

Upstream already had the concept of a second context that **views** another context's KV:
`llama_kv_cache::other` (a *mirror*; the shared-NextN MTP draft uses it, `llama-context.cpp:1004`).  A mirror
never allocates and never mutates — it reads the owner's cells and appends its own batches *after* them.  The
two-arm server needs more than that (its slots' positions interleave with the prefill arm's), so the patch
promoted the mirror into a **co-owner**: a second `llama_kv_cache` object whose `v_cells` *is* the owner's and
whose mutable paths run.  That single promotion forces three parallel universes to stay in agreement:

1. **one cell map, two objects, two cursors** → a per-ubatch **reservation bitmap** (`struct llama_kv_alloc`),
   `alloc_head_pull/copy/set` mirrors at five sites, `alloc_sync()` across the module taxonomy, and a
   `LLAMA_KV_ALLOC_SHARED` kill switch.  Needed only because the *objects* are two.
2. **one cell map, two threads** → the `apply_mutex` group lock, the `init_batch`/`apply`/`state_*` coverage,
   and the Meta view-slot / split-state-cache partitioning keyed on a *role* (`ctx_other != nullptr ? 2 : 0`).
3. **one hybrid, two recurrent modules** → the whole handover: a batched D2D take, a serialised fallback, a
   `can_take_batched` capability probe, a Meta `cpy_tensor_n` written *for the take*, a `RECR_ONLY` state flag,
   `seq_rm_recr()`, an indexer-pool invalidation hook, and `slot.dec_state`.

**The alternative is one line of intent: `ctx_dec` borrows `ctx_tgt`'s `llama_memory_i` object.**  Then the
taxonomy problem (1) is "one cursor, no bitmap", (2) is "one lock, one owner", and (3) **does not exist** —
there is nothing to move.  The prefill arm remains the single owner of every module, exactly as proposed.

## 3. Mapping the reported symptoms to mechanisms in this patch

| symptom | mechanism that produces it here |
|---|---|
| **corrupted output** under concurrency + MTP | (a) the recurrent state is *copied* at each boundary, and a copy that is not byte-faithful is fluent-but-wrong text — the patch itself says so and ships `LLAMA_RS_VERIFY_TAKE`, a second `Meta` copy path, and a serialised fallback to keep it honest; (b) a **failed forward take is treated as success** (D1); (c) the decode context is a **different graph shape** than the single-context decode (1..12 rows, `n_ubatch = n_parallel·(n_max+1)`), so every index/shape-keyed kernel decision (band FA split, KV pad, MTP draft ring) can differ per shape — "identical to single-context" is therefore an empirical per-shape claim, not a structural one (`GREEDY-PURITY.md` §38 is exactly this class); (d) qwen4exp's derived indexer pool is laid out *from cells* and must be invalidated on every boundary (a new hook, one more thing to forget) |
| **memory shortage** | (a) the second context is a **full `llama_context`**: its graph reserve is charged to the arena as a hand-tuned constant (`3584 MiB + 1536..2048 MiB`, `patch:243`) because it cannot be derived, taking 5 GiB from the expert arena; (b) that reserve is charged whenever `--prefill-decode-arms` is *set*, even when `create_decode_arm()` will refuse or `auto` will fall back (**D2**) — a refused pair silently shrinks the arena; (c) two *late narrow compute views* now coexist (decode ctx + the prefill arm's post-prefill re-reserve), which is what `TODO` #366's tier exists to absorb; (d) per-slot `spec_ckpt` on the *decode* arm when the seq-rm class is `FULL`, i.e. a full state snapshot per slot per draft round |
| **crash** | the six shared-memory fault classes W9 records (KV cell map, Meta split-state cache, async-input ring, VMM peer grant, default-stream coupling, apply lock) are all *consequences of two contexts on two threads*, and are correctly identified — but the fix set is one patch per symptom; the view-slot partition is **keyed on a role, not a context** and collides with the MTP draft context (**D3**) |

Note what is *not* on that list: the two threads themselves.  Nothing in the symptom set is caused by decode
running on its own thread.

## 4. Concrete defects found (severity, then location)

**D1 — a failed forward state take is installed as success (HIGH, correctness).**
`decode_arm_loop` phase (2), `patch:5210-5222`: `taken` is logged but the slot is set `dec_state = true` and
`arm = DECODE` **whatever `taken` was**.  `llama_memory_seq_state_take()` returns `false` both for "nothing to
move" (a dense model — the correct answer) and for "the move failed" (a hybrid).  Only the *reverse* path
disambiguates (`take_state_back` checks `llama_model_is_hybrid`); the forward path does not.  On a hybrid the
decode arm then generates from an empty recurrent state — fluent garbage.  This is the single most likely
explanation for "corrupted output" that survives a correct handover.

**D2 — the decode-arm arena reserve is charged for a pair that is never created (HIGH, memory).**
`patch:343`: `has_arms = has_host_experts && params.prefill_decode_arms != 0 && n_parallel >= 2`.  It does not
consult `create_decode_arm()`'s refusal list (mmproj, TTS/realtime, embeddings/decision, LoRA, sleep-idle,
backend sampling, the five layer-input drafter families, gemma4-assistant).  Consequence: `--prefill-decode-arms
-mm …` (or `-mode auto` on any refused shape) reserves ~5 GiB of the arena and then *refuses* (or falls back).
A memory shortage with the pair "off" is then attributed to the arena, not to the reserve.  Also note the
reserve's `ub` term is keyed on `params.n_ubatch` (the *prefill* width) while the decode context's own width is
`n_parallel·(n_max+1)` — two different quantities in one fudge factor.

**D3 — the Meta view slot is derived from a role, not from a context (HIGH latent, crash).**
`meta_bind_view_slot()`, `patch:2071`: `slot = (cparams.ctx_other != nullptr ? 2 : 0) + alt`.  Four slots for a
world that has **three** contexts: `ctx_tgt` (0/1), `ctx_dec` (2/3) and `ctx_dft` — the MTP draft, which also
has `ctx_other` set and therefore also maps to **2/3**.  Today that collision is benign only because
`ctx_dft` and `ctx_dec` are used sequentially on the same thread (different `thread_local` *values* do not give
different *containers* — `stc_compute[2]` and `split_state_cache[2]` are one container per buffer context).
It is one scheduling change away from the exact userland abort the comment describes
(`ggml_backend_meta_buffer_simple_tensor()` → null).  The discriminator should be a per-context id, not a role.
This is r350's (spec-on-pair) new participant meeting r347's two-role design.

**D4 — `m_spec` is one-sided; the prefill arm's draft path is unlocked (MEDIUM latent, crash).**
`m_spec`'s own comment (`patch:4369`, `4406`) says both arms' speculator use is under it.  It is not: the main
thread's draft assembly and `common_speculative_draft()` (`server-context.cpp:4385-4452`) are untouched by the
patch, while the decode arm's mirror of the same code is locked (`patch:5248`).  It is currently *masked*
because `post_decode` hands every prompt-finished slot to the decode arm in the same step, so the prefill arm's
`drafting` set is always empty — i.e. the masking depends on an undocumented server invariant, not on a lock.
Any change that lets a slot keep generating on the prefill arm (per-slot arm choice, a handover retry, a future
`-np 1` special case) turns this into two threads driving one `llama_context` (`ctx_dft`).  Fix is two lines
(`m_spec` around the base draft block) and it should be taken regardless of what happens to the rest.

**D5 — `ctx_dec_seq_rm_type = ctx_tgt_seq_rm_type` is justified by an argument that the design contradicts (MEDIUM).**
`patch:4498`: "the memory is the same, so the answer cannot differ".  Under the *viewed* model the attention
cells are the same but the **recurrent modules are two distinct objects** — the class (`FULL`/`RS`) decides the
speculative checkpoint protocol, and that protocol is per recurrent module (`rs_idx`, `n_rs_seq`, the rollback
plane).  The copy happens to be right because both contexts were built from the same `cparams`; the recorded
justification should say that instead.  Probing `can_seq_rm()` on `ctx_dec` is correctly avoided (it clears the
cache) — but that means the class is an **assumption**, and the assumption is worth an assert/census rather
than a comment.

**D6 — `arms_quiesce()` is not the barrier it claims to be (MEDIUM latent).**
`arm_step_guard` brackets only the *compute*: `dec_in_step` is set for phase (3), the `llama_process(ctx_dec)`,
and nothing else.  Two other blocks mutate the shared state **outside** it:

* phase (2), the **state take** (`patch:5208`) — mutates both recurrent cell maps and issues device copies;
* the **accept round** (`accept_draft_round`, `patch:5394`) — calls `spec_seq_rm()` (a shared-cell mutation through
  `llama_memory_seq_rm`) and `ckpt.load_dft(ctx_dft)` before the stop is declared.

So `arms_quiet` does not exclude them; what keeps two of them from overlapping today is that the main thread
*sequences* the takes (`hand_over_to_decode` waits for its own post; the reverse take runs at the top of
`update_slots`) and that `arm_release`/`finish_returned_slots` only act on a slot the decode arm has released.
That is an invariant held by call-site ordering, not by the barrier, in a block whose own documentation says
"a request boundary must run when NEITHER arm is inside `llama_process()`".  And
`llama_memory_seq_state_take` is deliberately unlocked (`patch:2283`) *because* that barrier is believed to
cover it.  Either the guard moves out to cover (2) and the accept round, or the invariant needs to be stated as
the contract (and the take should take the memory lock).

**D7 — hypotheses I checked and eliminated (so nobody re-derives them).**
* the decode-arm **failure** path is consistent: the only producer of `dec_failed` also clears `dec_state` and
  returns the slot to `SLOT_ARM_PREFILL` (`patch:5380-5392`), so the `failed` branch in `finish_returned_slots`
  never inherits a stale "state is on the decode arm".  `destroy()` not resetting `dec_state` is cosmetic.
* `arm_release`'s wait cannot deadlock against the decode arm's three phases: phase (1) prefers `dec_abort` over
  `dec_posted`, and both publish under `m_arms` before notifying.
* the reservation bookkeeping's failure path is complete: `find_slot()` only reserves after it has placed every
  sequence, so a failed search leaves no mark, and `prepare()`'s rollback releases every earlier ubatch and
  restores the first ubatch's cursor.
* `common_speculative_n_max(&params)` is the *configured ceiling* for `draft-mtp-adaptive` (not 0), so the
  decode context really is sized for the verify width and the per-slot `min(get_n_draft_max(), n_spec_max)`
  clamp is a safety net, not a silent disable.

**D8 — the handover blocks the main loop once per slot, not once per step (LOW, latency).**
`hand_over_to_decode()` is called from inside `post_decode`'s per-slot lambda and ends in
`wait_handover_taken()`, so N slots finishing prompts in one step cost N post+wait round trips.  Correct, but
it is the same shape of serialisation the campaign elsewhere went to lengths to avoid.

**D9 — `LLAMA_KV_ALLOC_SHARED=0` is a kill switch with no gate arm (LOW, process).**
`INVARIANTS.md`/`GREEDY-PURITY.md` require a kill switch to be exercised by a gate or to be a bisect knob that
says so.  `gate-arms-*` does not run the legacy two-cursor path, and the "control" it would provide (the
duplicate-cell bug) is a *silent wrong answer*, not a hash difference.

**D10 — doc drift that will mislead the next session (LOW, records).**
`wip/prefill-decode-arms-followups/README.md` still opens with "Block 17 … shipped in `v18-919794500-r346`",
with W1/W2/W3/W9 marked DONE, and never mentions the **r352 withdrawal**; the block's current record is
`beta/prefill-decode-arms/README.md`.  A cold session reading the campaign index will believe the feature is
delivery.  (TODO.md is correct; only this index is stale.)

**D11 — the decode arm's entire job could be expressed as "prefill arm with no prompts" (observation).**
Because `post_decode` hands a slot over the moment its prompt ends, the prefill arm **never** has a
`SLOT_STATE_GENERATING` slot in the pair (verified against every `SLOT_STATE_GENERATING` assignment).  The
`slot_arm_of(...) != SLOT_ARM_PREFILL` guards in `pre_decode`, the batch builder, the `-ib` decode-active test
and the spec-accept iterate are therefore *dead-but-defensive*: the single-context decode/draft code paths are
unreachable in the pair.  That is the "two arms are more independent than they need to be" observation in its
most concrete form — the pair is not the same server with a helper thread, it is a different server mode whose
prefill arm only prefills.  It also means the *single-context* code paths silently rot (D4 is a symptom).

## 5. The proposed design, in code terms

> *"Do the pre-two-arm approach for setting everything up and allocating memory and slots — keep the entire
> existing single-threaded setup. The only thing that changes is that decoding is handled by the separate
> decoding context thread."*

That is implementable, and it is **smaller** than what the patch does.  Concretely:

```
llama_context (ctx_tgt, owner)                llama_context (ctx_dec, borrower)
  memory = create_memory(...)      ◄─── same object ────►   memory = ctx_tgt's llama_memory_i *
  cparams.n_batch/n_ubatch: prefill width                     n_batch = n_ubatch = n_parallel·(n_max+1)
```

Two changes at the bottom, everything else untouched:

1. `llama_context` gets a *borrow* instead of a private `llama_memory_ptr` (a raw `llama_memory_t memory_own` +
   `memory_borrowed`, or make the field a `shared_ptr`; the create-site is one place, `llama-context.cpp:1004`).
2. The relationship gets its **own** `llama_context_params` field (`memory_owner` / `borrow_memory_from`)
   instead of reusing `ctx_other`, which already means three unrelated things (MTP target, gemma4 assistant
   view, eagle3 `token_embd` donor) and needed `ctx_other_share_memory` as a disambiguator.

### What disappears (≈ 1 500 lines, and the three root causes)

* `struct llama_kv_alloc` + `alloc_release/head_pull/head_copy/head_set/alloc_sync` + `LLAMA_KV_ALLOC_SHARED`
  + the `prepare()` rollback bookkeeping + `v_alloc_active` — one object has one cursor; keep only the
  per-ubatch **reservation bitmap** (two threads racing `prepare()`/`apply()` still need it) and nothing else.
* `other_coowner`, `is_mirror()`, `mem_other` threading through `llama_model::create_memory` + six modules, the
  identity `layer_share_cb` wiring, `mem_other_used` and the "implements no shared view" warning.  The campaign's
  own **P0** (a module that implements no shared view leaves the decode arm on an empty cache while the log says
  "KV shared") becomes **impossible by construction** — there is no per-module view to implement.
* `llama_memory_recurrent::seq_state_take()`, `can_take_batched()`, `llama_memory_seq_state_take()`, the
  `LLAMA_RS_*` diagnostics, `LLAMA_STATE_SEQ_FLAGS_RECR_ONLY`, `seq_rm_recr()`, `llama_memory_hybrid_idx::
  seq_state_take_note()`, `slot.dec_state`, `take_state_back()`'s whole premise, and `TODO` #365's Meta
  per-child `cpy_tensor_n` (350 lines written to make a copy that would not need to happen).
* The forward/reverse handover at the request boundary — the recurrent state simply stays where it is, which is
  also *why* the prefix-reuse half (`685 ms → 33 ms`) works: nothing to put back.

### What does NOT disappear (be honest)

* **Two `llama_context`s** and therefore two graphs, two schedulers, two compute-buffer sets → the graph-reserve
  constant stays (but it becomes one late context, not "one late context plus a handover transport").
* The backend/concurrency fixes (host stream, VMM peer grants, the Meta view-slot partition) — two concurrent
  contexts need all of them, and they are independently good bug fixes.
* The `apply_mutex` — genuinely needed (two threads on one cell map) — and it *gets simpler*: one lock on the
  one object, no `apply_mutex_share()` plumbing.
* The server-side arm bookkeeping (`slot.arm`, the ownership flag, the barrier).  Inherent: tokens must be
  emitted promptly, so the decoding thread must touch the slot.

### The one real piece of new work

`llama_memory_recurrent` keeps **per-batch derived state in the module**: `mem->head` (moved by `find_slot`),
`mem->n`, `mem->rs_z`, and the `src`/`src0`/`tail` rollback plane, all read by
`llama_memory_recurrent_context::get_head()/get_n_rs()/get_rs_z()/s_src()`.  Two contexts sharing one recurrent
module would read each other's placement.  The header already says so:

> `// data needed for building the compute graph for the current ubatch:`
> `// TODO: extract all the state like `head` and `n` here`

`llama_kv_cache` is already contextified (`get_n_kv(sinfo, n_tokens)`, `llama_kv_cache_context` holds the
`slot_info`), which is why the attention half can be shared *today* with only a lock.  So the clean design's
prerequisite is **finishing upstream's own refactor for the recurrent module** — a contained change (~150-250
lines, 4 accessors + `find_slot`'s writes) and a far better place to spend effort than a device-to-device state
transfer protocol.  Until it is done, sharing one memory object is only safe for a **non-hybrid** model: use the
dense shapes to validate the new shape, then land the recurrent contextification, then turn on the hybrids.

## 6. The speculator (r350) is the part that should stay off

`--spec-type` was **refused** by the pair from r346 to r349 for good reasons, and r350 lifted the refusal by
adding: a second registered target context, `common_batch::ctx`, a decode context wide enough for a verify
batch, the prefill arm's draft ingest under `arms_quiet`, the slab reserve changed from `max` to `sum`, a
per-slot spec reset at both boundaries, and a `m_spec` lock.  That is five new cross-thread contracts for a
feature the pair is not the reason for.  D3 and D4 are both in it, and D5's "the answer cannot differ" is only
true because the two recurrent modules were built identically.

Recommendation: **re-refuse `--spec-type` on the pair** in the next iteration of the artifact (one guard, no
new code), and re-admit it only after the memory model is the shared-object one *and* the prefill arm's decode
path is either deleted or locked.  Nothing in the pair's measured win (ITL 47-49 ms p50 through a 2-5 s
prefill for −21…−24 % prefill) depends on the speculator.  This also removes the need for a *third* context in
the Meta view-slot budget.

An intermediate shortcut that avoids stage 2 entirely: keep the recurrent module **owned by the prefill arm**
and let the decode arm only *advance* it by keeping the whole generation on... no — that is the single-context
design.  There is no shortcut; the contextification is the price of "the same memory for both arms", and it is
smaller than the handover it replaces.
