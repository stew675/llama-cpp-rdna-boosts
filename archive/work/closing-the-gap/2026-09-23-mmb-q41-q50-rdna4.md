# 2026-09-23 — MMB WMMA quant coverage on RDNA4: Q4_1 and Q5_0 are dense wins

**Work item 1 of [`gfx1201-closed.md`](gfx1201-closed.md) §12.1** ("MMB WMMA quant coverage on
RDNA4 (`0017`/`0018`)").  Box: 3× Radeon AI PRO R9700 (gfx1201), ROCm 7.14.  Build: campaign
`closing-gfx1201` (r13 + `beta/mmb-general` + the 25 closing patches), 1 GPU, MMB enabled.

## TL;DR

The S5–S7 "Q4Q5 group loses" conclusion is **not uniform**.  Enable **Q4_1** and **Q5_0** in the
RDNA4 MMB masks; keep **Q4_0** out (it loses, as the beta found).  `MXFP4`/`NVFP4` could not be
produced by this box's quantizer and `IQ2_*` needs an imatrix this box does not have for a matching
model, so those stay untested/unenabled.  The change is folded into closing patch `0017`; the set
re-applies 25/25 to tree **`b8700a6c2dcda216adb14cb215839c4e5d5f2b20`**.

## Method

Models were produced by requantizing the box's Qwen Q8_0 GGUFs with `--pure` so every linear weight
is the tested type (the worst case — a real mixed quant fires MMB only on its few Q4_1/Q5_0 tensors):

```sh
llama-quantize --allow-requantize --pure <Q8_0> <out>-<TYPE>-pure.gguf <TYPE> 16
```

A/B (interleaved, one GPU, warm): `llama-bench -m <model> -ngl 99 -p 8192,32768 -n 0 -b 4096 -ub 4096 -r 3`
with `GGML_CUDA_MMB=0` vs the type force-enabled through the existing env
`GGML_CUDA_MMB_TYPES=iq4_nl,iq3_s,iq4_xs,iq3_xxs,<type> GGML_CUDA_MMB_DENSE_TYPES=iq3_s,<type>`
(`MMB_CFG`/`MMB_DENSE_TYPE=...` confirmed each launch; `GGML_CUDA_MMB_LOG=1` showed the `type=q4_1`
dense launches).

## Correctness gates

* **Op oracle** (`test-backend-ops -o MUL_MAT -p type_a=<t>`, `GGML_CUDA_MMB_MIN_T=1` to force MMB at
  every test shape, default mask): **q4_1 47/47**, **q5_0 14/14**, 0 FAIL (CPU comparison).
* **PPL parity** (`llama-perplexity -c 512 -b 512 --chunks 8`, wikitext, 27B, MMB off → on):
  Q4_1 6.7657 → 6.7785 (**+0.19 %**, inside the ±0.37 CI); Q5_0 6.7946 → 6.7925 (**−0.03 %**).  A
  dequant/layout error would move this by orders of magnitude.
* **Text** (27B, `-c 8192 -n 64` greedy, prose prompt, `--reasoning off`, MMB off vs on):
  `plain` is **byte-identical off↔on** for both types (`8b430ee90e5d` Q4_1, `b2464aa2021a` Q5_0).
  So MMB's BF16 weight rounding did not change the greedy text at this length.
* **`plain == draft-mtp`** (intra-build, MMB on): Q4_1 holds (`8b430ee90e5d` both).  Q5_0 differs
  (`b2464aa2021a` vs `42bcf22d89d7`) — but so does MMB **off** (`b2464aa2021a` vs `d20b650cea3f`), so
  it is pre-existing (`q5_0` is in the relaxed coarse-quant set, `GREEDY-PURITY.md` §36) and MMB
  does not introduce it.  4B Q4_1 also holds (`7287067a1c94` both).

## Width-probe caveat (do not misread this)

`test-logits-width-probe` at P=1024 on the `--pure` models:

* 4B qwen35 Q4_0: MMB off PASS, MMB on **PASS**.
* 4B qwen35 Q4_1/Q5_0: MMB off PASS, MMB on **FAIL** (worst 0.27–0.29).
* 9B qwen35: **FAILs with MMB off too** (0.32–0.42) — the hybrid GDN decode band is already
  width-sensitive at this length on this box.
* gemma4-12B (standard transformer) Q4_1: FAIL both arms, worst ~1e-6 (the documented coarse-quant
  near-tie relaxation; MMB on is not worse: 9.5e-7 vs 1.4e-6).

MMB is gated `T >= 512` and only fires in the prefill (verified: `MMB_DENSE ... T=512` only); the
decode/verify band `W = 1..8` never takes it.  The probe's per-W divergence is therefore the
documented **logits-level** coarse-quant relaxation (a magnitude-1e-6-class decode-band sensitivity
exposed by MMB's prefill rounding), not a kernel error — which the oracle + PPL + byte-identical
greedy text all support.  The real contract for Q4_1/Q5_0 is the **text** gate, which holds.

## Unreachable types

* `MXFP4` / `NVFP4`: this box's `llama-quantize` only emits MXFP4 through the `MXFP4_MOE` file type
  (a MoE layout) and has no NVFP4 path, so a dense test model cannot be produced here.  Untested.
* `IQ2_S` / `IQ2_XS` / `IQ2_XXS`: `llama-quantize` requires an imatrix; the only imatrix on the box
  does not match a loadable model (asserts in `ggml_quantize_chunk`), so a valid requant failed.
  Untested.  Dense IQ2 is also a rare workload; IQ2 is mainly a routed-expert type, and RDNA4's
  routed MMB path is off by policy (`routed=0`), so the value would be low.

## Change folded into the set

`ggml/src/ggml-cuda/mmb.cu` (closing patch **0017**, commit `5c3bb41c5`):

* `mmb_wtype_mask()` RDNA4 row becomes `IQ_FAMILY | Q4_1 | Q5_0` (`RDNA4_SET`).
* `mmb_dense_tmask()` RDNA4 row becomes `IQ3_S | Q4_1 | Q5_0`.

`GGML_CUDA_MMB_TYPES` / `GGML_CUDA_MMB_DENSE_TYPES` still override both masks for future per-type
re-tunes without a rebuild.

reproduce the campaign tip tree **`b8700a6c2dcda216adb14cb215839c4e5d5f2b20`**.  The `0018` patch
