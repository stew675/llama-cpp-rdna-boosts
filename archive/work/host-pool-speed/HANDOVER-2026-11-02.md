# HANDOVER — what the 1-GPU host learned, and what it means for `--host-experts pool`

**Written 2026-11-02, from the 1-GPU host, after the parallel `host-expert-pinned-window` campaign was closed.**
Read this after `README.md` and before touching code.  It does not restate the campaign's charter (§§1-9 of
`README.md` are authoritative); it records (a) the constraint the other campaign violated and re-established,
(b) two mechanisms from it that are **sound under §7 and worth taking here**, (c) the three questions the
maintainer asked when this was handed over — *does the gather work with pool, is it portable to `-sm tensor`,
and how does any of it compare with `pinned`* — and (d) the session setup and gates.

---

## 1. The constraint, now measured rather than assumed

`hipHostRegister` gives **addressability**, not **residency**.  On a no-XNACK GPU a kernel read of a page that is
not present is fatal — no fault, no retry.  The window campaign built on the opposite assumption and died of it:
`window -ncmoe 44` on a 93 GiB model in 98 GB **aborted** (`mul_mat_vec_q_moe` → `Page not present`), and a
partly-lockable range **hung** with the GPU at 100 %.  Holding the pages (`mlock`) fixes it and turns the mode
into pinning.  Record: `INVARIANTS.md` (device-visible host memory must be resident), `WORKLOG.md` 261102.012/.013,
`../archive/work/host-expert-pinned-window/RESOLUTION.md`.

**Why this matters to this campaign.**  §7 of `README.md` already says the right thing — *the intermediary
guarantees the pages are pinned **and** resident before it hands the go-ahead back to the GPU*, with a residency
check before the read is released and no fallback that copies from pageable memory.  That is now backed by
measurement, and the primitives are known to work on this ROCm line:

| primitive | status here | use |
|---|---|---|
| `mlock(range)` | works once `RLIMIT_MEMLOCK` is raised (`sudo -n prlimit --memlock=unlimited -- …`, or `/etc/security/limits.d/`) | the hold |
| `mlock2(range, MLOCK_ONFAULT)` | works | the hold **without** faulting the whole range in at bind |
| `madvise(MADV_POPULATE_READ)` | works | the resident check / the populate, per range, host-side |
| `hipMemPrefetchAsync`, `hipMemAdvise` | accepted on a registered host range, and **useless** | never rely on them: a hint is not a hold |
| `MADV_PAGEOUT` as a test instrument | **insufficient** | a hot 8 MiB window is never evicted; a test that cannot fail is not evidence |

**The pool is already the safe shape** — a bounded pinned (`cudaHostAlloc`) slot per expert a GPU may read, so an
in-place read of a *pool slot* is sound and needs no hold.  What pool lacks is §7's other half: the *source* pages
being resident before the copy, which is what §4.1 of `README.md` already covers.

## 2. Take these two mechanisms (they are sound under §7)

### 2.1 CE copies out of a registered mapping instead of the per-table bounce `memcpy`

The window campaign's `moe_cache_upload_pageable` change: when a range belongs to a table whose master is
registered (`host_dev != nullptr`), stage it with **one D2D copy from the alias** instead of `memcpy` into the
per-table bounce + pinned H2D.  It is a *copy*, so the copy engine's recover-from-reclaim behaviour applies — the
CE refills a reclaimed registered page instead of faulting (the asymmetry `../archive/work/host-expert-pinned-window/
probe-cold-read.cpp`'s header states, and Avalon's `moe_split_copy_by_kernel` comment implies).

Measured there: `MOE_EXPERT_WINDOW_ALIAS_FILL` (the fill arm) took prefill **375.9 → 532.6 t/s** and **−6.7 GB
RSS** (the bounce ring was a second pinned copy of the host set).  Avalon prices the same trick independently at
**fills 115 → 61 µs**, and warns that a copy ending *outside* a registered range goes through ROCm's staged path
(**prefill −8 %**), while one registration per expert (73 728 of them) costs **−25 %** — so register per *tensor*,
page-rounded, merging overlapping ranges.

**For pool this replaces the bounce**, which is exactly the `memcpy` a pool miss pays today.  It does not change
any in-place read; `pool` keeps copying into pinned slots, which is the point.

### 2.2 The arena-aware gather, re-pointed at the pool slots

The window campaign made the device gather use the *arena*: a routed expert that is resident is copied from its
arena slot, only a miss goes to the host.  That took `pinned` prefill **735 → 1036 t/s** on the persistent-server
cell (the whole non-resident set was being re-read ~8.7× per request, 132.6 GiB; the gather moves ~8 of 256 experts
per table per ubatch instead).

It is gated on a **hold**, which is why `pool` cannot use it as written: a pool-backed table has
`host_dev == nullptr`, so `moe_cache_gather_ok()` says no.  See §3 for what to change.

> **Corrected in §6a:** at `efaa60db0` there is no `moe_cache_gather_ok` predicate to make pool-aware (that
> was window-campaign code); the gather is opt-in via `GGML_SCHED_DEVGATHER=1`.  The mechanism below was
> implemented as `patches/0003` and measured — `README.md` §14.4.

## 3. Does the gather work with pool?  Yes — with one kernel change, and it is the right shape

Today's gather kernel resolves one source per routed expert: the arena slot, else the host master.  The pool
campaign needs a **third** source, and the delivery already has the encoding for it:

* the staging kernel's residency map (`prs`, built by `prs_refresh_locked`) already encodes **both** tiers:
  `>= 0` = arena slot, `<= -2` = pool slot `(-v - 2)`, `-1` = in neither;
* the pool's device alias (`pool->base_dev + slot * pool->host_bytes`) is **pinned**, so an SM read of it is
  sound by construction — no hold, no mlock, no XNACK;
* the bounce buffers (`t.bounce[].host`) are `cudaHostAlloc`'d, so they are safe reads too — meaning the "in
  neither tier" expert can be gathered from the bounce after the fill, still without any pageable read.

So the change is: pass `(pool_dev, pool_stride, prs)` into `moe_cache_gather_kernel`, resolve
`slot >= 0 → arena`, `slot <= -2 → pool`, else `bounce`, and **drop the "read the mmap'd master" branch from the
pool path entirely** (that branch is the window mode's, and it is the one that cannot be made safe).  Then
`moe_cache_gather_ok()` becomes `arena_ok || pool_present` rather than "master is readable", and pool mode gets
the whole byte saving: only the routed experts cross PCIe, and the ones already in VRAM or the pool do not cross
at all.

**Expected gain**: pool's prefill today stages the whole non-resident set per ubatch.  This is the same ~8.7×
re-read the gather removed from `pinned` (where it was worth +41 %), except that for pool it also removes the
per-miss host `memcpy` for experts already in the pool — the double cost §9.2 of `README.md` complains about.

## 4. Is it portable to `-sm tensor`?  Yes, and it must be proved, not assumed

* **Pool itself is already `-sm tensor`-native** (r15: one pool slice and one table per device; 2-GPU
  `-sm tensor -ncmoe 48` measured 88.0 t/s MTP against `-sm layer`'s 76.2).  Unlike the window mode, pool has no
  cross-device registration to share and no `host_dev` to alias, so the whole registration/refcount problem that
  made window a multi-GPU unknown simply does not exist here.
* **The gather under a split** goes through the meta backend: `ggml_backend_meta_moe_cache_gather` forwards to
  every simple backend and returns true only if **every** device takes it, and the scheduler now asks a
  capability predicate (`moe_cache_gather_ok`, forwarded the same way) *before* it skips whole-table staging.
  That predicate is the thing to make pool-aware; if it answers "no" after the split has skipped staging, the
  split falls back to the host path — measured at **49.6 t/s** on the first request in the equivalent simple-
  backend case, i.e. a silent 5-10× prefill collapse.
* **Not portability-safe today, and the delivery is honest about it**: `MOE_HOST_POOL_COLD` (the in-place read of
  a resident pool slot) declines when `device_count != 1`.  The gather does not need it — it reads the pool slot
  from a kernel, no cold encoding involved — so the gather is the portable way to get that win.
* **The one gate that decides it** is the 3-GPU `-sm tensor` arm on `soar`, with `-p 2048+` (not a 32-token
  smoke: a short prompt cannot exercise eviction, and a big-RAM box cannot reproduce a residency fault at all).
  Assertion: gather arm ≥ staging arm per split mode, and `check-gpu-faults.sh` clean.

> **Corrected in §6a:** the `pool` 285.3 / 48.8 row below is withdrawn (a window-beta artefact).  On the
> delivery + campaign-patch tree the same srv cell reads 641-647 prefill, and 832-878 with mechanism (b).

## 5. How pool compares with `--host-experts pinned` (measured, and where it has to get to)

| cell | `pinned` | `pool` | note |
|---|---|---|---|
| persistent server, Flash-Next GSQ IQ3_XXS, 1× R9700, `-ncmoe 48`, req3 | **734.5 prefill / 59.5 gen / 68.6 GB RSS** | **285.3 / 48.8 / (pool-sized)** | pool is 2.6× behind on prefill and 18 % on decode |
| same, with the arena-aware gather | **1036.3 / 59.1** | n/a (gather declines) | gather worth +41 % to `pinned` |
| this campaign's own reference arm (`README.md` §9.1) | 22.33 t/s decode | **17.76 (-20.5 %)** | large model, sub-residency, demand disk reads |

The gap is **not** the design: it is (a) the per-miss host `memcpy` into the bounce — §2.1 removes it, (b) the
whole-table staging per ubatch — §2.2/§3 removes it, and (c) demand disk reads on a sub-full pool, which is §4.1
of `README.md`.  The acceptance criterion in `README.md` (pool ≥ PR #267's `--host-experts mmap`) is reachable
without any registration-with-in-place-reads, which is why §7 stands as written.

**One consequence for the maintainer's plan to revert PR #266.**  This campaign's P0 is
`GGML_MOE_DEVREMAP` on pool-backed tables (+8.1 % decode ceiling on the r203 cell).  Pool slots are pinned, so
that in-place read is **sound** — it is the one piece of #266 whose removal costs real throughput.  If #266 is
reverted, re-implement the remap over pool slots rather than dropping the capability.

Instruments to reuse rather than rewrite (they live in the archived campaign dir and work as-is by path):

* `archive/work/host-expert-pinned-window/srv-test.sh` — persistent `llama-server`, prompt cache off, three
  sequential requests, per-request `/proc/<pid>/io` read_bytes + RSS + timings + a server-path text hash.  This is

* `probe-aperture.cpp` / `probe-pollution.cpp` — aperture bandwidth and registration tax, both measured equal, so
  do not re-derive them.
* `scripts/gate-prefill-logits.sh`, `scripts/check-gpu-faults.sh` — as `MANIFESTS.md` requires.
* **Reading a routing sidecar**: the campaign's own `archive/work/moe-cache-coverage/tools/heatmap-audit.py`
  is **MHT1-only** and rejects today's sidecars (`not an MHT1 sidecar (magic b'MHT2')` — every `.moe-heatmap`
  under `/llm/models` is MHT2).  Use `scripts/moe-trace-replay.py --seed sidecar:<path>` (it reads MHT2: two
  arrays per table, `all` then `dec`), or teach the audit tool v2 before relying on it for the coverage curve.

**Traps that cost this host a run each** (all recorded in `WORKLOG.md` 261102.008-.013):
a below-floor auto arena silently disables the whole expert cache (`tensors=0`, decode 24.5 t/s — pass
`MOE_EXPERT_CACHE_MIB` or shrink `-c`); a killed `sudo` wrapper leaves the server holding VRAM, so the next load
fails with `unable to allocate ROCm0 buffer`; `pkill -f llama-server` also matches the shell that launched it;
and measuring `pool` straight after a `pinned` arm is not comparable (the pinned arm's allocation evicts the page
cache pool lives in).

## 6a. Corrections from the 1-GPU host's Phase 1 session (2026-11-02, session 3) — the code wins

Three claims above did not survive contact with the tree (`README.md` §14.4-§14.6 has the numbers):

1. **`moe_cache_gather_ok()` does not exist at `efaa60db0`.**  It was window-campaign code (WORKLOG
   261102.010/.011).  The delivery's scheduler tests only `iface.moe_cache_gather == NULL` plus
   `GGML_SCHED_DEVGATHER`, which is **default off**.  So §3/§4's "the predicate must be pool-aware" is not a
   patch to an existing predicate: the pool path has to *serve* (which is what mechanism (b) now does), or a
   future `-sm tensor` arm re-introduces the decline.  The multi-device arm is still unrun (§4's gate stands).
2. **§2.1's numbers do not transfer to pool mode.**  `moe_cache_upload_pageable` is pool mode's *fallback* (the
   pool staging path does not use it), so its exposure is 56.4 MiB over a 3-request srv-cell run and 3664 MiB
   on the 122B (0.26 % of wall clock), with a 43 MiB-1.2 GiB bounce ring — not the window arm's -6.7 GB and
   +42 % prefill.  Recommendation: drop §2.1 from the pool scope.
3. **The pool's `285.3 / 48.8` srv-cell reference (§5) is withdrawn** — it was measured on the window *beta*
   tree, whose staging dispatch WORKLOG 261102.008 records as a regression for the pool arm.  On the delivery
   + campaign-patch tree the same arm reads **641-647 t/s prefill / 53.5 gen**, and with mechanism (b) 832-878
   prefill, i.e. **ahead of `pinned`'s 739**.  Pool's prefill gap was never 2.6x.

What §5 got right, confirmed: pool is still behind `pinned` on **decode** (srv cell -10.8 % at FRAC 80; 122B
-22 % at FRAC 100), and the gather is the portable replacement for `MOE_HOST_POOL_COLD` — measured, `COLD=0`
goes 15.54 -> 19.57 t/s on the 122B with the gather on.

## 7. What this handover does **not** decide

The order of work, the re-base itself, and whether the gather lands before or after the `RAM_PCT`/coverage work
are the maintainer's calls (`README.md` §9).  What it does assert is the constraint: **no kernel reads a pageable
page, ever** — pool copies into pinned slots, and anything that reads in place reads a pool slot, an arena slot or
a bounce buffer.
