# Pass 3 (same day) — T0 built: ONE allocation owner, and the tier's "§89 class" was a harness race

**Verdict.** T0 exists as its own artifact ([`enabling-0003-shared-kv-allocator.patch`](enabling-0003-shared-kv-allocator.patch),
7 files, +386/−10, `~/llama.cpp` `386b7dd48`, the 6th commit of `wip/prefill-overlap`) and it does what the
maintainer asked for: **per-ubatch reservation through ONE shared owner with a handshake**, not a unilateral
prefill-side decision.  With it the two-arm run is **bit-identical to the single-context reference in every rep,
on both shapes, with no harness control at all** — and the warm-rep divergence that pass 2 attributed to a
`GREEDY-PURITY.md` §89 "residency class" turns out to be **an ordering bug in the instrument**: a stale
`handover_done` flag let the next prompt be prefilled *while the take was reading the prefill arm's recurrent
metadata*.  With that fixed and T0 in, the host-tier arms read the reference too.

## 1. What T0 is (the shape the maintainer approved: per-ubatch, two-sided)

`struct llama_kv_alloc` (`llama-kv-cache.h`), shared by the pair exactly like `v_cells_impl`:

| step | where | what |
|---|---|---|
| **reserve** | `find_slot()` | searches from the pair's **one** cursor (`alloc->heads[strm]`), marks the chosen cells `reserved`, advances that cursor.  A reserved cell is invisible to **any** search, on either arm.  Granularity = one ubatch (what `prepare()` works at) |
| **commit** | `apply_ubatch()`, real apply only | clears the marks, installs the cell metadata as before.  `prepare()`'s trial apply passes `trial=true` and does **not** consume the reservation — the dry run is rolled back, the reservation is not |
| **release** | a failed `prepare()`, or `~llama_kv_cache_context` | clears the marks of ubatches that were never applied, and restores the pair's cursor on failure — a cancelled step cannot shrink the cache |
| **handshake** | `llama_memory_alloc_sync(mem, tag)` | the request-boundary check either arm may call: reports reservations nothing applied (a leaked prepare) instead of letting them shrink the cache silently; prints the reserve/commit/release census |

The mutex is held across the search and the bookkeeping only — microseconds at a ubatch boundary, **never across a
compute** (the campaign's 2.85 s starvation was a lock held across a decode step).  `LLAMA_KV_ALLOC_SHARED=0` is
the A/B kill switch (legacy two-cursor path); it goes into `ENVIRONMENT.md` when this becomes delivery-bound.

**Every** other place that moves a cursor moves the pair's one cursor too, or the layout would again depend on
which arm moved last: `seq_rm`/`seq_keep`'s pull-back to a freed hole, `seq_cp`'s stream copy, `seq_add`, a
whole-cache restore (`state_read_meta`) and `clear()`.  The pull-back was the one that mattered in practice: it is
why the single context restarts every rep at cell 0, and without it the pair's cursor marched forward and warm reps
placed a prompt at 703–1214 while the reference used 0–511.

## 3. What `b79e73e3fe9f` actually was — an instrument ordering bug (pass 2 §3 refuted)

The instrument resets a request's flags at each rep boundary but did not reset `handover_done`, so from rep 1 the
prefill arm's wait returned immediately and the next prompt was prefilled **while the take was still reading that
arm's recurrent metadata** — the exact ordering rule `HANDOVER.md` §4.2 states ("only one prompt in flight on the
prefill arm, and it waits for the handover to complete").  The visible trace: R1's prefill landed in recurrent cell
**1** instead of **0** (`[TAG_RS_CELLS] find_slot head=1 ... cells=1:p511/s1`), and the take appeared *after* it.

| arm | what it shows |
|---|---|
| tier, T0 on, instrument fixed | reference, all reps |
| tier, T0 on, **`ARMS_NO_WAIT_TAKE=1`** (the race, deliberately) | rep 0 R1 **`b79e73e3fe9f`** |
| tier, `ARMS_RESET_CACHE=1`, legacy cursors, instrument bug present (pass 2) | rep 1 R1 `b79e73e3fe9f` |

`ARMS_NO_WAIT_TAKE=1` is now a named control arm in the instrument, precisely so this cannot be re-derived as a
design property.  Both fixes are needed to get the tier match: the ordering (instrument) and the allocator (T0).

**Corrected attribution of every warm-rep divergence this campaign has chased**:

| value | cause | how it was proved |
|---|---|---|
| `b79e73e3fe9f` (full residency) | the **hipBLASLt** path | `ROCBLAS_USE_HIPBLASLT=0` makes 480/480 rows bit-identical (pass 2 §2) |
| `b79e73e3fe9f` (host tier) | the take **racing** the next prompt | `ARMS_NO_WAIT_TAKE=1` reproduces it; T0 + the fix removes it |
| `e05c6e16a136` / `abe253ea957a` | the two allocation **cursors** (a scatter) | `LLAMA_KV_ALLOC_SHARED=0` reproduces it on both shapes; T0 removes it |
| `58945dce9598` / `3d59e8f5c116` (seen transiently this pass) | T0's cursor not yet mirrored at `seq_rm`'s pull-back | fixed in `386b7dd48`; after the fix the census is identical to the reference |

## 1. What was built (the as-built code points)

| piece | as built |
|---|---|
| `ctx_dec` | created in `load_model()` right after the prefill context's model is up (`create_decode_arm()`), from `common_context_params_to_llama(params_base)` with `n_batch = n_ubatch = n_parallel` (one row per generating slot), `ctx_other = ctx_tgt`, `ctx_other_share_memory = true`.  **Sized for decode, never for prefill** (a prefill-sized second context is what does not fit).  Freed in `destroy()` **before** the model |
| the second batch | `server_batch batch_dec`, initialised in `load_model()` with `llama_n_batch(ctx_dec)` rows |
| the arm flag | `server_slot::arm` (`SLOT_ARM_PREFILL` / `SLOT_ARM_DECODE`) plus `dec_posted` / `dec_stopped` / `dec_failed` / `dec_abort`, all written only under one `m_arms` mutex; `slot_arm_of()` is the reader for the per-step loops.  **One mutex for the transition** (T2-SERVER-CUT §4 allows "the queue's ordering" instead of a mutex per slot) |
| the handover | `post_decode()` samples the prompt's LAST row on `ctx_tgt` (its logits live there) and then `hand_over_to_decode()`: allocation handshake -> post the slot -> **wait for the take**.  The decode thread runs `llama_memory_seq_state_take(mem_dec, mem_tgt, id)` at the top of its next pass (device to device, ~1 ms) and only then marks the slot ACTIVE |
| the decode step | `decode_arm_loop()`: collect (aborts, handovers, active) -> **one token per active slot in ONE batch** -> `llama_process(ctx_dec, DECODE)` -> `llama_synchronize` -> `slot_step()` per row |
| the step | `post_decode()`'s sample/stop/emit factored into `slot_step(ctx, batch, slot, row)` -- **the two arms share it** (the prefill arm runs it for the row that ends a prompt, the decode arm for every generated token) |
| the return | on stop the decode arm calls `llama_memory_seq_rm(mem_dec, id, -1, -1)` -- **the shared cells are freed once, there** -- marks the slot PREFILL and wakes the main loop; `finish_returned_slots()` (top of `update_slots`) owns the response's lifecycle: `print_timings` / `send_final_response` / `prompt_clear` / `release` |
| the boundary handshake | `arms_boundary_sync(tag)` calls `llama_memory_alloc_sync()` on **both** memories at every request boundary (handover + return) and **asserts it is clean**.  A reservation is legal while a ubatch is prepared-but-not-applied, so the check holds both arms out of `llama_process()` for its duration (`arms_quiet`, `arm_step_guard`) |
| the guards | refused at start-up: a speculator, mtmd/TTS/realtime audio, embeddings/rerank (any pooling), a decision model, LoRA adapters, `--sleep-idle`, backend sampling.  **`-np 1` warns and stays single-context** |
| main-thread-only | `slots[]`, `batch`, `ctx_tgt`, `spec`, checkpoints, the prompt cache, the response lifecycle.  The decode arm never calls `prompt_save/load`, `common_speculative_*`, or anything in that list |

Two additions beyond the scoped cut, both required to make the measured ordering rule hold in a server:
`wait_handover_taken()` at the top of `pre_decode()` (a second line of defence for "no prompt starts while a take
reads this arm's recurrent metadata"), and `arm_release()` (a cancel / abort / error on a slot the decode arm owns
hands it back first -- the memory is freed by the arm that owns the sequence -- then releases it on the main loop).

## 4. New landmine: the 2-row decode graph, and the knob that makes the pair fit

The first measurement attempt (arena 5000, `-c 16384 -ub 512`, the campaign's ~5900-token prompt) **died at the
second handover**, i.e. exactly when the decode arm first had to run a **2-row** batch:

```
ggml_cuda_device_malloc: 741.48 MiB allocation failed on device 0 while the movable-boundary slab holds the VRAM;
  the arena cannot yield physical back to the driver
ggml_backend_sched_alloc_splits: failed to reserve graph buffers
decode arm: the decode step failed (n_tokens = 2, ret = -2)
```

That is landmine 8's 741.47 MiB reserve, seen from the server: it is **per active-slot width**, it is only paid when
the *second* slot starts decoding, and at arena 5000 next to a grown prefill graph it does not fit.  A 1-row decode
step had been running fine for 5.5 s immediately before it.

**Fix (the maintainer's): `GGML_CUDA_SLAB_HEADROOM_MIB=1536`** -- the documented knob for exactly this failure mode
(`ENVIRONMENT.md` §1.3: VRAM left outside the slab; default `1152 + 128 x n_gpu` = 1280 MiB on one GPU).  With it
the same shape runs clean (**shape C** above, 0 OOM lines).  So the T4 gate's VRAM rule has a second lever beside
"size the arms for their own batch": *the headroom the slab leaves free must cover the widest decode graph the pair
will ever reserve*, and a partial arena is what makes that tight.

## 5. Two defects the cut itself produced (both fixed, both the kind that reads as "physics")

1. **A self-deadlock on the arm mutex.**  `slot_arm_of()` takes `m_arms`; a blanket rename put it *inside* a block
   that already held `m_arms` (`finish_returned_slots`), so `update_slots()` deadlocked on the very first request
   with the GPU idle and ~32 GiB still resident.  Diagnosed with `gdb -p` (`finish_returned_slots` blocked in
   `pthread_mutex_lock`, the decode thread parked in `cv_arms.wait`).  Rule: *the flag is read directly when the
   mutex is already held*.
2. **`server_queue::post()` asserts `task.id != -1`.**  A `NEXT_RESPONSE` posted from the decode arm (to wake the
   main loop when a slot is handed back) must carry `queue_tasks.get_new_id()`; without it the server aborts.  Hence
   `wake_main_loop()`.

Neither is a design property, and both are recorded so the next session does not re-derive them as one.

## 6. Why -24…-27 % and not the instrument's -14.1 % (the honest reading)

The cost is `charge per decode token / the decoder's in-window ITL`.  Measured, same arena, same model:

| arm | standalone decode step | charged per decode token | in-window ITL | prefill cost |
|---|---|---|---|---|
| instrument, pass 1 (arena 5000, `-c 24576 -ub 2048`, 4932 tok) | 10.9 ms | **7.7 ms** | 53.7 ms | **-11.3 / -14.1 %** |
| two-arm server (arena 5000, `-c 12288/16384 -ub 512`, 2900-5900 tok) | 16.9 ms | **11.8-12.5 ms** | 47-49 ms | **-24…-27 %** |

The server's standalone decode step is ~1.6x the instrument's (server-side slot bookkeeping per step, and a 2-row
batch where the instrument's `dec-alone` arm is one request), so at the same arena it draws ~1.6x the charge per
token; and because the smoothing holds the ITL at ~48 ms instead of the instrument's ~54, *more* tokens fit into the
same window.  Both push the same way.  The knob that trades one for the other is the charge (arena depth / residency
-- the retired campaign's own sweep: 7.7 ms at h=0.66, 12.8 ms at h=0.40, 16.0 ms at h=0.32), and the one policy
knob we thought might be free (`-ib 0`, i.e. an unchunked prefill) measured **inert** (-25.8 %, shape B), which fits
the campaign's established result: the cost is resource sharing, not step granularity.

**Not claimed:** that -14 % is reachable on the server.  The next measurement that could reach it is a shape with a
*slower* standalone decode step or a decodable band that is more resident -- both are T4/T5's question, on hardware
with more VRAM than this 32 GiB card at arena 5000 with two contexts.

## 7. One behavioural limitation of the cut (deliberate, documented)

When generation ends the decode arm frees the slot's shared cells, and `finish_returned_slots()` clears the slot's
prompt: a **later request on the same slot re-prefills from scratch** (no cross-request prefix reuse on the arms
path).  Keeping it would need the recurrent state to move *back* to the prefill arm at the return, which the scoped
design does not do (T2-SERVER-CUT §2) -- the reference server keeps the KV and *does* reuse it.  It costs nothing in
the oracle (the gate sends `cache_prompt:false`), and it is the first thing to fix if this is ever promoted.

             .   |   |   |   .   .   .   .   .   .   .   .   .

Read it as the user does:

* **the document lands 1.6x sooner on the two arms** (2.81 s vs 4.46 s, 1252 vs 797 t/s) — the single-context server
  pays twice for the interleave, because its prefill is chunked by `-ib` *and* it still stalls the decoder;
* **the reply never freezes on the two arms**: its worst gap inside the window is **95 ms**, against 390 ms, and
  its p95 62 ms against 300 ms — the difference between "text keeps coming" and "the chat hangs, then jumps";
* **what it costs is rate, not liveness**: the reply runs at 22-35 tokens/s while the document prefills instead of
  its ~60/s alone (`gap p50` 44 ms vs 18 ms).  That is the same trade pass 5 §6 measures as prefill throughput, seen
  from the other side of the wire, and it is the whole claim: a **bounded** stall in exchange for a **bounded**
  rate.

## 4. The cost target is CLOSED as a decision, not a miss

The `<= ~14 %` figure this campaign carried was a **pre-analysis prediction**.  The maintainer's ruling on the
measured **-24…-27 %**: acceptable — it is far better than the **~-75 %** the old workaround (a smaller ubatch, which
cost prefill throughput) implied, and the point of the campaign is the **smoothness**: no freeze, no burst (§3 above:
worst gap 95 ms against 390 ms).  Recorded so a later session does not re-open the cost as unfinished business;

# The ubatch answer — `-ib` was a single-context hack, and the pair prefers a BIG ubatch (the maintainer's question)

**`-ib` / `--interactive-batch-size` exists for one reason**: in a single-context server a step that carries
prompt tokens is the slow one, so a decoding slot's inter-token latency *was* the step length.  `-ib` caps the prompt
tokens a step may carry while a decoder waits, which bounds that stall.  On the arms path a decoding slot waits for
nothing: its latency is the decode arm's own step.  So the question is what the prefill looks like with the ubatch
free — and the answer is *much* better, in both directions.

## 1. Measured: prefill vs ubatch (arena 5000, `-c 16384`, ~3700-token prompt, warm, both pins, 1 GPU)

| `-b` / `-ub` / `-ib` | `lone` (one context) | **two arms** | cost | decoder in the window p50 / p95 / max |
|---|---|---|---|---|
| 2048 / **512** / unset (the shape the VRAM rule forced) | 1440.0 t/s | 1056.3 → **1142.0** after §3 | -26.6 % → **-20.7 %** | 49.0 / 71.0 / 114.3 ms |
| 2048 / **2048** / 2048 | 3041.2 t/s | **2454.5 t/s** | **-19.3 %** | 40.9 / 61.1 / 66.0 ms |
| 4096 / **4096** / 4096 | 3884.2 t/s | **3245.5 t/s** | **-16.4 %** | 46.2 / 56.7 / **63.3 ms** |

* **a bigger ubatch lifts the prefill 2.7x** (1440 -> 3884 t/s on the reference arm) and the *relative* overlap cost
  falls with it: **-26.6 % -> -19.3 % -> -16.4 %**.  The maintainer's prediction ("we may end up close to the -14 %
  figure with 4096") is nearly there, and the residual is the per-step link contention, not a policy: the trend is
  the retired campaign's own (it measured 2529 t/s at `-ub 2048` and 2977 at arena 8000 for the same design).
* **the decoder gets *smoother*, not worse**: p95 71.0 -> 56.7 ms and worst gap 114.3 -> 63.3 ms, because a decode
  step is now a smaller fraction of the prefill's work and the driver fills the gaps of one long step.
* **and it fits now**: `-ub 4096` at arena 5000 / `-c 16384` with two contexts runs clean (`reserve=1.50 GiB`,
  no OOM), which pass 1's landmine 8 recorded as *not* fitting ("at arena 5000 / `-c 16384` / `-ub 2048` the pair
  does not fit ... `-ub 512` does").  That note is **superseded by r343**: the +256 MiB slab headroom is exactly the
  741 MiB 2-row decode-graph reserve that used to fail, so the shape the campaign was forced out of is back.

## 2. Measured: the user-facing number at each ubatch (`interactive.py`, reply streaming + document pasted)

| `-b`/`-ub` | arm | the document | the reply's worst gap inside the prefill |
|---|---|---|---|
| 2048 / 512 | single context | 4463 ms, 797 t/s | **390 ms** |
| 2048 / 512 | **two arms** | **2807 ms, 1252 t/s** | **95 ms** |
| 2048 / 2048 | single context | 1854 ms, 1961 t/s | **615 ms** |
| 2048 / 2048 | **two arms** | **1448 ms, 2430 t/s** | **86 ms** |
| 4096 / 4096 | single context | 1291 ms, 2854 t/s | **878 ms** |
| 4096 / 4096 | **two arms** | **1131 ms, 3111 t/s** | **60 ms** |

The single-context server's *stall grows with the ubatch* (390 -> 615 -> 878 ms: one step is longer, and a decoder
waits the whole step) while the two arms' stays flat (~60-95 ms) and its prefill keeps improving.  **So on the arms
path the big ubatch is not a trade at all: it is better on both axes at once**, and the two columns diverge further
the larger the ubatch.

## 3. The leftover that made `-ib` matter at all: `decode_active` counted the decode arm

The prefill arm's step cap keyed on "some slot is GENERATING" — including slots on the **decode arm**, which no
longer wait for this arm.  So with `-ib` unset the arms' prefill was still chunked to `n_ubatch` whenever the
decoder was busy.  At `-ub 512` that cost **8.1 %** of prefill (1056.3 -> **1142.0 t/s**, 10 steps of 420 ms ->
5 steps of 1088 ms, same prompt, same arm); at `-ub >= 2048` the cap equalled the ubatch and was already inert.
Fixed: `decode_active` only counts a **prefill-arm** slot now (`slot_arm_of(slot) == SLOT_ARM_PREFILL`), with the
reason in the code.  **Tier 1 re-run after the change: PASS, both slots `459865c93d55cbaf` / `7dc20b0ce0bac255`**
(`runs/server-oracle-r343b/`) — as expected, since the ubatch *composition* is unchanged, only how many ubatches one
step carries.

## 4. What this means for the design (T4)

* **`-ib` is inert on the arms path** and should not be set for it; the campaign's earlier advice to run the pair at
  `-ub 512` was a **VRAM** workaround, and r343 removes the reason.
* **`-ub`/`-b` is the knob**: bigger is better for prefill *and* for the decoder's worst case, up to whatever the card
  fits.  `-b 4096 -ub 4096` measured here (arena 5000, `-c 16384`); the delivery's own `-ub 2048` default is already
  most of the win (-19.3 % vs -16.4 %).
* The campaign's **cost figure of record should be read at the shape it is quoted for**: -26.6 % at `-ub 512`
  (a VRAM-forced shape), **-16.4 % at `-ub 4096`**, and the decoder's smoothness *improves* as the ubatch grows.
  That is closer to the pre-analysis -14 % than pass 5 could see, and it was only visible once r343 made the pair
  fit at a real prefill shape.

# Where 8192 lands — and a CORRECTION to "the ubatch answer": the falling cost was a one-step artifact

The maintainer asked for `-ub 8192`.  It was measured, and it forces a correction to the previous section: the cost
that appeared to fall with the ubatch (`-26.6 % -> -19.3 % -> -16.4 %`) was **mostly an artifact of the prompt
fitting in one step**.  At a prompt that needs several steps at *every* ubatch the relative cost is **flat at
-21…-24 %**, and the ubatch buys **absolute prefill rate** instead — which is the real prize.

## 1. The artifact, stated plainly

The sweep in the previous section used a **~3700-token** prompt.  At `-ub 4096` and `-ub 8192` that prompt fits in
**one** step, so the "cost" measured there is one contended step against a one-step reference — a different
experiment from the two–four-step sweeps at 512/2048.  Same shape, same arena (5000), same prompt (~3700 tok):

| `-ub` | `lone` | two arms | cost | steps at `-ub` | decoder p50 / p95 / max |
|---|---|---|---|---|---|
| 512 | 1440.0 | 1056.3 | -26.6 % | 8 | 49.0 / 71.0 / 114.3 |
| 2048 | 3041.2 | 2454.5 | -19.3 % | 2 | 40.9 / 61.1 / 66.0 |
| 4096 | 3884.2 | 3245.5 | **-16.4 %** | **1** | 46.2 / 56.7 / 63.3 |
| 8192 | 3859.4 | 3159.9 | -18.1 % | **1** | 45.2 / 62.3 / 62.6 |

Note 4096 -> 8192 *does not* improve once both are one step (and the 8192 graph is bigger for the same work).

## 2. The honest measurement: a prompt long enough to need several steps everywhere

A **~8300-token** prompt (`reps 570`), `-c 20480`, both pins, warm, ubatch set per arm via `LLAMA_ARG_UBATCH`:

**arena 5000** (the campaign's):

| `-ub` | `lone` | two arms | **cost** | steps | decoder p50 / p95 / max |
|---|---|---|---|---|---|
| 4096 | 3625.4 t/s | 2866.3 t/s | **-20.9 %** | 3 | 37.8 / **50.2** / **95.1** ms |
| 8192 | 3836.6 t/s | 2997.3 t/s | **-21.9 %** | 2 | 32.7 / 63.5 / 124.5 ms |

**arena 4000** (a shallower tier, for the 2048 point and a second copy of the trend):

| `-ub` | `lone` | two arms | **cost** | decoder p50 / p95 / max |
|---|---|---|---|---|
| 2048 | 2954.6 | 2278.9 | -22.9 % | 39.4 / 61.5 / 104.0 |
| 4096 | 3525.6 | 2779.9 | -21.2 % | 38.1 / 54.2 / 101.5 |
| 8192 | 3799.5 | 2892.7 | -23.9 % | 34.5 / 74.0 / 131.4 |

**So: the relative cost is ~-21…-24 % at every ubatch from 2048 up, and the ubatch does not change it.**  What the
ubatch changes is the prefill's *absolute* rate — `lone` 2955 -> 3526 -> 3800 t/s and the pair 2279 -> 2780 -> 2893
from 2048 to 8192 (**+29 %**), which is the 2.6x over the `-ub 512` shape that the VRAM workaround had forced.

## 3. Where 8192 lands: a small prefill gain for a slightly worse worst case

* **prefill**: +8 % over 4096 on both arms (lone 3836.6 vs 3625.4, arms 2997.3 vs 2866.3) at arena 5000;
* **the decoder's worst case gets worse**: p95 **63.5** and max **124.5 ms** at 8192 against **50.2** and **95.1** at
  4096.  The cause is visible in the step census: an 8192-token step takes **2.2 s** (`pf_step_max` 2225 ms), and
  the driver cannot always fill a queue that long — the retired campaign's "a phase-locked decoder waits ~600 ms"
  effect starts to reappear as a *tail*, not as the median (p50 is fine at 32.7 ms);
* **VRAM**: both fit at arena 5000 (`-c 20480`, twice the KV of the gate shape) with `reserve=1.50 GiB` and no OOM,
  which is again r343's headroom doing the work.

**Recommendation: `-ub`/`-b` 4096 is the sweet spot** — within 8 % of 8192's prefill, −1 pt better on cost, and a
materially better decoder tail (95 ms vs 124 ms).  8192 is a legitimate choice only where prefill rate is worth more
than the tail.

## 4. What survives of the previous section

* **`-ib` is inert on the arms path** (and the `decode_active` leftover is fixed): unchanged, and independently
  confirmed — every arm here set `-ib` = `-ub`, so `-ib` never bound.
* **`-ub 512` was a VRAM workaround, not a property of the design**: unchanged, and now emphatically so — the pair
  runs 2.6x the prefill at 4096 on the *same arena*.
* **"a bigger ubatch is better on both axes"**: **REFUTED at a multi-step prompt.**  Bigger is better for absolute
  prefill; the *relative* cost is flat and the decoder's tail degrades past 4096.  The earlier claim was an artifact
  of a single-step measurement and is corrected here, in place, as `README.md` §3 asks.

## 5. User-facing numbers at these shapes (for the record)

At `-ub 4096` with the ~3700-token document (`interactive.py`): single-context **1291 ms TTFT / 878 ms reply freeze**;
two arms **1131 ms / 60 ms** (`runs/interactive-2611h/`).  The multi-step prompt does not change the picture — the
freeze is what grows on the single-context arm as the ubatch grows, and it is what the arms remove.

# Full residency — no host tier, no arena, nothing to hide: the arms are STILL better on both axes

The last case, and the one that cannot be explained away by a link: **all 21.1 GiB of 35B-A3B Q4_K_M resident in
VRAM** (`-ngl 99`, no `-ncmoe`, no `-lme`, no `MOE_EXPERT_CACHE_MIB`, so no expert arena and no gathers).  Here the
two arms compete for the same SMs, compute against compute — the retired campaign's own note said this is where "the
prefill decodes at −11 % with the decoder 2.1x slower, nothing hidden".  Measured on the *server* (`-c 16384
-b 2048 -ub 2048`, warm, `ROCBLAS_USE_HIPBLASLT=0`):

**`smooth.py`** — a ~3700-token prompt with a decoder generating throughout:

| arm | prefill | wall | decoder tokens in the window | in-window ITL p50 / p95 / max |
|---|---|---|---|---|
| `lone` (prefill alone) | **6320.8 t/s** | 0.6 s | — | — |
| `single` (one context, both streams) | **4129.2 t/s** (**-34.7 %**) | 0.9 s | 32 | 8.8 / 46.8 / **327.3 ms** |
| **two arms** | **4792.0 t/s** (**-24.2 %**) | 0.8 s | **53** | 14.6 / 16.0 / **34.9 ms** |

**`interactive.py`** — the reply streaming while a ~3600-token document is pasted:

| arm | the document | the reply's worst gap | tokens in the window |
|---|---|---|---|
| `default` (single context) | 924 ms at **4029 t/s** | **327 ms** | 32 |
| **two arms** | **737 ms at 4786 t/s** | **33 ms** | **50** |

## What it means

1. **The arms win at full residency too, on both axes.**  Against the single-context server: **+16 % prefill**
   (4792 vs 4129 t/s), **a 10x tighter worst-case stall** (33-35 ms vs 327 ms), **66 % more decoder tokens** through
   the prefill window (53 vs 32), and the pasted document arrives **20 % sooner** (737 vs 924 ms).
2. **The single-context server is the one that does badly here**, and for a mechanical reason worth knowing: with a
   decoder running, its prefill is served in many small steps (`pf_steps` 34 against 4 for the arms, step p50 8.7 ms),
   so it re-pays the per-step fixed cost throughout — **-34.7 %** — *and* each of its steps still stalls the decoder
   (the 327 ms spike is one prefill step).  The arms pay one contended step per 2048-token chunk and stall the
   decoder only by the amount the hardware genuinely shares.
3. **The retired campaign's "no window at full residency" is a statement about the *host-tier* window, not about
   this design.**  There is indeed nothing *free* to hide behind — the compute is shared — so the cost is real
   (-24.2 %).  But "the two arms are worse than one context here" was never true on the server: they are better on
   both axes, because the single context's interleave is *itself* the expensive thing.
4. **The cost is the same order as the host tier's** (-24.2 % against -21…-24 % there), which is the reassuring part:
   the arms' price does not depend on which tier the weights are in, and the smoothness gain does not either.

## Caveats

One GPU, one model, one shape (`-c 16384 -b 2048 -ub 2048`; full residency leaves ~10 GiB for KV + two contexts, so
`-ub 4096` was not tried here), warm, sequential, `ROCBLAS_USE_HIPBLASLT=0` (a rate arm keeps the same library config
as every text arm).  `single` is the plain server (`-ib` = `-ub`, so no chunking from the interactive cap; the small
steps come from the server's own per-step admission with a live decoder).

# Pass 7 (same day) — the REVERSE HANDOVER: prefix reuse is back, and it moves no token

**Verdict.** The one behavioural regression pass 5 §7 recorded is **fixed**.  When generation ends the decode arm no
longer frees the slot's shared cells: the main thread **takes the recurrent state back** to the prefill arm (the
mirror of the forward take, under the same `arms_quiet` bracket) and **keeps the prompt**, so the sequence stays
resident and the next request on that slot reuses its prefix exactly as the single-context server does.  Measured on
the delivery's own `gate-ckpt-reuse.sh`: **3 checkpoint restores and 33 ms turns instead of 0 and 685 ms**, i.e.
identical to the single-context control.  Two new oracles say the reused state is *correct* (byte-identical text
against an arm that never reuses), including two slots reusing **concurrently** (the multi-agent case) and a
prompt that **forks below** the shared prefix.

`~/llama.cpp` `16e942d2f` (the 8th commit of `wip/prefill-overlap`), **1 file** (+94/-29,
`tools/server/server-context.cpp`); no library change was needed — `llama_memory_seq_state_take(dst, src, id)` was
already symmetric.

## 1. What changed (and what deliberately did not)

| piece | before | now |
|---|---|---|
| the decode arm's stop | `llama_memory_seq_rm(mem_dec, id, -1, -1)` — the shared cells freed once | **nothing freed**: the cells stay, the state stays on the decode arm, `dec_state = true` |
| the return (`finish_returned_slots`) | `prompt_clear()` — the prompt dropped, so no reuse | `take_state_back()`: **`llama_memory_seq_state_take(mem_tgt, mem_dec, id)`**, then print/send/`release()` — the prompt is **kept** |
| a cancel / abort (`arm_release`) | the decode arm freed the cells, then `prompt_clear()` | the same take-back, so a cancelled conversation keeps its prefix (what the single-context `release()` does) |
| a failed take | n/a | **drops the sequence** (`prompt_clear()`): an attention half with no recurrent half is an inconsistent state, and a forced re-prefill is the safe failure.  A dense model has nothing to move, so `false` there is not a failure (`llama_model_is_hybrid`) |
| the decode step's failure | cells freed, `prompt_clear()` | unchanged (a failed step's state is suspect) |

**Why the take runs on the MAIN thread.**  Its *destination* is the prefill arm's memory, so it cannot race this
arm's own prepares; its *source* is the decode arm's cell map, which `arms_quiet` holds the decode arm out of
`llama_process()` for.  The existing handshake bracket was factored into `arms_quiesce()` / `arms_resume()` and is now
shared by the allocation sync and the take.  The deadlock rule is unchanged and documented in place: the decode
arm's step guard waits for `arms_quiet` to clear before marking itself in-step, so the two waits cannot cross.

**The ordering rule is automatic here, and one new flag carries it.**  `dec_state` (under `m_arms`) says "the
recurrent state is on the decode arm"; the decode thread sets it in the same critical section that clears
`dec_posted` (which is what the forward handover waits on), and `take_state_back()` reads it under the same mutex.
A slot is only released after its take, so no request can start on a slot whose state is still on the other arm.

# Pass 10 (2026-11-22) — the P0 is TWO defects, both in the memory module, and both FIXED

**Verdict.** The open P0 — a ~70K-token prompt (five attached files) answered as if the model had seen nothing —

## 3. Defect 1 — `hybrid_idx` allocated its own cache while the server printed "KV shared"

`llama_model::create_memory()` passed `mem_other` to the plain `llama_memory_hybrid` branch only.  The
`llama_memory_hybrid_idx` branch — qwen4exp and GLM5-Next — never received it, so `create_decode_arm()`'s second
context got its own attention KV and its own indexer KV, and the pair printed
`KV shared, one allocation owner` regardless.  The decode arm then had nothing to attend to, which is exactly the
reported symptom (and why the prefill's `prompt_n` was right).

Fix (`src/llama-model.cpp`, `src/llama-memory-hybrid-idx.{h,cpp}`, `src/llama-kv-cache.cpp`):
* `llama_memory_hybrid_idx` takes `mem_other` and hands it to the base, which is what wires the **attention** cache
  (`hybrid_mem_other_attn`, the identity layer-share, `other_coowner`);
* the **indexer** cache gets the same wiring (the source's indexer cache as `other`, identity layer-share,
  `other_coowner`).  Cell j is the same token in both caches — `can_park()`/`seq_park()` already rely on that — so
  sharing the map is the design, not a shortcut;
* `alloc_sync()` now covers the indexer cache's own allocation owner (one owner per cache, so the boundary
  handshake must ask both);
* the layer-share log line no longer dereferences a NULL `v` — a **keys-only** cache (the QSA indexer store,
  `v_enabled == false`) shares layers whose `v` is null, and printing it **segfaulted on the first shared layer**;
* `mem_other_used` is set at both `hybrid_idx` sites, so the warning above can no longer be printed by a context
  that really did share.

## 4. Defect 2 — a restore moves cells behind the derived indexer pool

After defect 1 the fresh request was correct but a `cache_prompt` repeat still was not: it reported
`cache_n=6898` and answered without the first 6 898 tokens.  The arms-off server does the *same* restore (it picks
checkpoint 6898 and erases the 10990 one — a delivery property, identical on both arms) and is correct, so the
difference is the arms.  qwen4exp pools **consecutive CELLS** (`kpool_by_order`), the restore re-places the
sequence, and the derived pool is per **context**: the decode arm kept a layout built for the sequence's previous
cells.  (The 4B has no indexer — it restores 8904 tokens and is correct.  With the pool disabled,
`GGML_CUDA_QSA_INDEXER_CACHE=0`, the arms pass too — that is the acid test.)

Fix: the handover notes it on the **destination** (`llama_memory_seq_state_take()` → a new
`llama_memory_hybrid_idx::seq_state_take_note(seq_id)` → `mem_idx_stale_set(seq_id, 0)`), so the receiving arm
re-pools from the shared, authoritative raw indexer keys.  Cost: one re-pool on the first batch after a handover
(TTFT, not ITL), only on an indexer model.

* **Flash-Next does not fit on one card at arena 5000 with the pair**: the single context is fine (`h=0.49`), the pair

# Pass 14 (2026-11-22) — the decode context is DECLARED like a draft (auto, no knob), and the allocation design the question exposed

**Verdict.** The maintainer's question — *"the two-arm mode needn't be doing anything different to the one-arm mode
when it comes to memory allocations … was the memory allocation mechanism a handshake when the original shipping
allocation path was best all along?"* — is right on both counts, and measuring it produced the fix.

**What ships today is not exposed to the reserve problem**, for a reason worth stating precisely:

* the single-context server is ONE `llama_context` ⇒ ONE scheduler ⇒ ONE set of compute buffers, and its
  `sched_reserve` covers **both** layouts it will ever run, before the slab exists:
  `graph (pp bs=2048, tg bs=2): nodes = 7178 / 5145, splits = 144 / 50` → **1504.83 MiB**.  A decode step — one slot
  or many — therefore allocates **nothing new**; concurrency there means more ROWS in an already-reserved graph.
* the shipped **second** context (an MTP draft) *is* exposed to the same class, and is handled by **declaring** it: the
  slab is told a flat 3584 MiB second-context reserve *before* it is created
  (`SLAB_INIT … reserve=5.00 GiB headroom=1.50 GiB aux=3.50 GiB … va_spare=3.50 GiB`), and it pins the draft's
  compute as a narrow-2 region.  Verified working on the *same* 1-GPU `-ncmoe 48` shape.

**The pair was doing something different**, and that is the defect: its decode context (1792.00 MiB, its own
`sched_reserve`) arrives *after* the slab, with **nothing declared**, so the slab maps its whole VA (`aux=0`,
`va_spare=0`) and the arena commits the VRAM.  Worse, the reserve is partly **duplicated** — the tg layout is reserved
inside the prefill context's 1504.83 MiB *and* again as the decode context's 1792.00 MiB:

| | compute buffers | layouts reserved |
|---|---|---|
| shipped single context | **1504.83 MiB** | `pp bs=2048` + `tg bs=2` in ONE reserve |
| the pair (prefill ctx) | 1504.83 MiB | `pp bs=2048` + `tg bs=2` |
| the pair (decode ctx) | **+1792.00 MiB** | `tg bs=2` again, standalone, **after the slab** |

## The fix shipped in `~/llama.cpp` (auto, no operator input)

The decode context is now declared exactly like the draft: `common_draft_reserve_derive()` charges a second-context
reserve when the pair will run (`prefill_decode_arms != 0 && n_parallel >= 2 && the model has host experts` — so a
fully resident shape and `-np 1` are untouched), default **3584 MiB** (the same flat constant an embedded MTP head
gets; no KV term, because the pair shares one cache), overridable by `MOE_EXPERT_CACHE_AUX_RESERVE_MIB`, and a manual
`GGML_CUDA_SLAB_RESERVE_MIB` still wins.  Logged once:

```
common_init_result: slab reserve for the PREFILL-DECODE ARMS' decode context: 3584 MiB (no KV term -- it shares the
  prefill arm's cache; MOE_EXPERT_CACHE_AUX_RESERVE_MIB overrides).
```

**Verified (auto arena, no user knob, `-ncmoe 48`, marker + text compare):**

| shape | before | after |
|---|---|---|
| Flash-Next, 1 GPU, layer | **FAIL** `the decode arm's step failed` | **PASS** `h=0.78`, text identical |
| Flash-Next, 3 GPU, tensor | **FAIL** (needed `SLAB_RESERVE=8192`) | **PASS** `h=0.85`, text identical |

A partial declaration is *not* enough, which pins the mechanism: aux 2048 MiB (`reserve=3.50 GiB`, `va_spare=2.00 GiB`)
still failed, while an explicit `GGML_CUDA_SLAB_RESERVE_MIB=4096` (`reserve=4.00 GiB`) passed — a 512 MiB difference at
the same narrow-2 geometry.  So the reserve must cover the second context's graph *plus* its own slack, which is what
the 3584 MiB flat constant does.

## What is still the wrong shape (the follow-up this question earned)

The pair reserves ≈ **2.2x** the shipped path's compute buffers (3296.83 vs 1504.83 MiB), and the extra copy is the
duplicated tg layout, arriving late.  The shipping pattern — *one reserve, both layouts, sized before the slab* — is
the right one.  Two contained ways to get there, neither implemented (they touch `llama_context`'s reserve path, i.e.
the shipped single-context behaviour is in the blast radius):

1. **do not duplicate the layout**: when the pair will decode, the prefill context need not reserve its standalone tg
   layout, and the decode context need not reserve a wide pp layout.  The pair would then cost ≈ one wide + one narrow,
   like the shipped path, and the aux declaration could shrink to a residual (or go).
2. **reserve both contexts before the slab is armed** (the literal shipped pattern).  Today the slab is born inside
   the prefill context's own `sched_reserve`, so this needs the contexts' reserve split from their construction.

Until then the declaration above makes the pair work on the shapes measured, with no operator input — and
`MOE_EXPERT_CACHE_AUX_RESERVE_MIB` / `GGML_CUDA_SLAB_RESERVE_MIB` remain the manual path (documented on the option's own
help text, as asked).

# Pass 15 (2026-11-22) — the "duplication" hypothesis is WRONG: measured 0 MiB, so (1) was reverted; (2) is the declared reserve, already in

**This pass corrects pass 14.**  Pass 14 read the two `sched_reserve` sizes (prefill 1504.83 MiB with `pp bs=2048, tg
bs=2`, decode +1792.00 MiB) as *the tg layout reserved twice*, and called it a duplication bug.  **That was wrong**, and
the maintainer's instruction to fix the duplication first is what tested it: implementing "the prefill context does not
reserve the tg layout" showed the saving is **zero**.

## 1. The measurement (the fix implemented, then reverted)

`llama_context_params::ctx_no_decode_reserve` was added, plumbed through `common_params` and set by the server when the
pair will decode; `sched_reserve` then skips the tg layout (a decode that lands there still re-reserves on demand, as
any wider ubatch does).  Result — the `(pp bs=2048, tg bs=2)` pair disappears from the log, and the buffer size does
**not move**:

| shape | reserve with the tg layout | reserve without it |
|---|---|---|
| Qwen3.8-Flash-Next, `-ncmoe 48`, `-ub 2048`, np 2 | 1504.83 MiB | **1504.83 MiB** |
| Qwen3.5-4B, `-sm layer`, `-ub 2048`, np 2 | 224.57 MiB | **224.57 MiB** |

…and the Flash-Next pair **still fails** (`the decode arm's step failed`, the same 1430.16 MiB allocation) with the
declaration disabled (`MOE_EXPERT_CACHE_AUX_RESERVE_MIB=0`).  So:

* the tg layout is *entirely dominated* by the pp layout inside the per-context union — it is not a second allocation;
* the pair's extra ~1.8 GiB (Flash-Next) / ~9.5 MiB (4B) is the **decode context's own graph buffers**, which a second
  scheduler needs.  It is inherent to "two threads, two contexts", not a duplication;
* my pass-14 "2.2x, the tg layout reserved twice" reading was the error.  The *sizes* were right; the attribution was
  not.

**(1) is reverted** — not because it is incorrect in principle, but because it saves 0 MiB on the shapes measured and it
would leave the *fallback* path (pair refused / `auto` fallback / cancelled handover) without a tg layout it may need:
on a host tier that fallback would then need a late reserve, i.e. (1) would create the very failure class it was meant
to remove.  `~/llama.cpp` is back at `a7958316c` (the declared reserve only), clean, re-verified: Flash-Next 1 GPU
`-ncmoe 48`, auto arena, no knob → **PASS** `h=1.00`, text `121ff7b5af176297`, identical to the single context.

## 2. What "(2)" actually is, and why it is already in

(2) was "reserve both contexts before the slab is armed".  Two implementations exist:

* **declare the second context** (`common_draft_reserve_derive` → the existing `aux_reserve` path, pass 14) — the slab
  maps less VA and holds the amount back *before* the arena claims the space.  **Implemented and verified** on 1 GPU +
  layer and 3 GPU + tensor, auto arena, no knob (3584 MiB flat; a partial 2048 still failed, 4096-equivalent passed).
* **move the decode context's construction before the slab** — a construction-order refactor of `llama_context`
  (`sched_reserve` is inside the ctor) with the shipped single-context path in the blast radius.  It would account for
  the same VRAM, not less, so it buys nothing the declaration does not.

The honest summary for promotion: **the pair needs ~1.8 GiB more than the single context on a host tier (an inherent
second scheduler), and it must be declared before the arena takes the space.**  That is now automatic; the manual path
(`MOE_EXPERT_CACHE_AUX_RESERVE_MIB`, `GGML_CUDA_SLAB_RESERVE_MIB`) is documented on the option's own help text.  No
layout-deduplication work is owed.

# Pass 18 (2026-11-22) — does this mean MTP works now? Two answers, both measured

**Short answer: MTP works today (it always did), MTP *with the arms* does not, and neither changed — but the reserve
work had introduced a bug that WOULD have hurt MTP, now fixed (`~/llama.cpp` `9b8ac957f`).**

## 1. Shipped MTP: works, and the reserve work is inert for it

Qwen3.8-Flash-Next, 1 GPU, `-ncmoe 48`, auto arena, `--spec-type draft-mtp --spec-draft-n-max 3`, arms OFF:
**PASS** (marker found, `prompt_n=10994`), a `draft acceptance` line logged, and the slab shows `aux=3.50 GiB` — the
**draft's** own second-context reserve, exactly as before this campaign touched anything.  That path was already
verified in pass 13 (§"shipped second context"); it is unchanged.

## 2. MTP WITH the arms: still refused, by design

`create_decode_arm()` refuses the pair whenever a speculator is configured (a drafter owns its own context and a
per-slot checkpoint path that would have to cross the arms).  So:

* `--prefill-decode-arms-mode auto` + `--spec-type draft-mtp` → the pair **falls back** with a warning and MTP runs:
  **PASS**, `draft acceptance` logged, `running single-context` in the log;
* `--prefill-decode-arms` (explicit `on`) + a speculator → **refuses to start**, as documented (`HANDOVER.md` §8).

Speculative decoding *with* the arms is the follow-up campaign's item (it needs the draft's context and its checkpoint
path to cross the two arms).  Nothing in this campaign changed that.

## 3. The bug this question caught (fixed)

`common_draft_reserve_derive()` charged the arms' flat 3584 MiB reserve whenever `prefill_decode_arms != 0` — including
a run where a **speculator is configured**, i.e. where the pair is refused and the reserve would only shrink the arena
of a legitimate MTP run.  Fixed by mirroring the server's refusal (no `has_dft()`/`has_mtp()`), and verified: the
`auto` + MTP run above reports `aux=3.50 GiB` (the draft's), **not** 3584 MiB, and the arms' reserve line is absent.

| arm | slab `aux` | pair | MTP | result |
|---|---|---|---|---|
| shipped MTP, arms off | 3.50 GiB (draft) | — | runs, accepts | **PASS** |
| MTP + arms `auto` | 3.50 GiB (draft) | **falls back** | runs, accepts | **PASS** |
