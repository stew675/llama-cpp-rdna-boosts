# 2026-11-21 — pass 1: the handover exists (T1), the harness is the server's shape (T2/T3), and three landmines

**Verdict.**  T1 is **done and measured**: one sequence's recurrent state moves between the two arms
device-to-device in **0.5–0.7 ms** (36 ms serialised), and the text oracle holds byte-for-byte wherever the
shape lets it be measured (a no-host-tier model in **all** modes and reps; the campaign's 35B host tier for a
**single** handed-over request, 3/3 warm reps).  T2/T3 are **emulated outside the server** (a prefill arm and a
decode arm on their own threads, its own context each, one KV, a request queue and a handover at the request
boundary) and the campaign's physics reproduces on it.  Three things were found that the campaign did not
know, and one of them is a hard blocker for the server cut:

1. **The shared KV's cell allocator is not concurrency-safe** (`llama_kv_cache::find_slot` searches from
   `v_heads` and only `apply_ubatch` advances it — two contexts that both allocate can be handed the same
   cells).  Measured arms got away with it; it is a *silent wrong answer* class and must be fixed before two
   arms are allowed to allocate.
2. **The two-arm VRAM cost is one graph reserve per arm AND per active-slot count** — 741 MiB for a 2-row
   decode graph on 35B-A3B at `-ub 2048`, on top of the prefill graph.  At arena 5000 / `-c 16384` / `-ub 2048`
   the pair does **not** fit on a 32 GiB card; `-ub 512` does.
3. **On a partial host-expert arena the 2-slot two-arm arm is not text-stable across warm reps** (it matches
   the sequential reference in the cold rep and diverges in the warm ones, both from the reference and from
   itself), while the single-context 2-slot reference is stable.  Isolated as far as time allowed — and the
   host tier was then **refuted** as the carrier: the 35B-A3B reproduces it at full residency.  See §3.3
   (shape/graph-bucket family, not state corruption).  The consequence for the campaign's gates is concrete:
   **a cross-configuration greedy hash is not a valid oracle for this design yet** — `GREEDY-PURITY.md` §89's
   rule applies, and the T3 gate needs a pinned shape plus a KLD point.

All arms: 1 × R9700 (gfx1201), ROCm 10.1.0-gfx120X, sequential (never in parallel).  `HIP_VISIBLE_DEVICES=0`.
Source: the WIP branch `wip/prefill-overlap` in `~/llama.cpp` (built as `build-2ctx`); the two new artifacts are
[`enabling-0002-recurrent-handover.patch`](enabling-0002-recurrent-handover.patch) (this pass) and
[`enabling-0001-second-context-shared-kv.patch`](enabling-0001-second-context-shared-kv.patch) (pass 10-13 of
the retired campaign).  The instrument is [`arms/two_arms.cpp`](arms/two_arms.cpp) (`arms/build-two-arms.sh`).

## 1. T1 — the handover

### 1.1 What it is

The KV cells already belong to both arms (the co-owner work of `enabling-0001`), so the only state that has to
follow a slot is the **recurrent** state (GDN conv + SSM, `llama_memory_recurrent`).  The shipped serialised
path (`llama_state_seq_get_data_ext` + `set_data_ext`) already carried exactly that, because
`llama_kv_cache::state_write/read` **return immediately when `other != nullptr`** (`llama-kv-cache.cpp`,
`[TAG_KV_CACHE_SHARE_CELLS]`) — i.e. a co-owner context contributes no KV bytes to the stream.  So T1 was
"already possible"; what was missing was (a) a way to drop only the *recurrent* half on the arm that gives the
slot away, and (b) a transfer that does not go through host memory.

| what | measured |
|---|---|
| `llama_state_seq_get_size_ext(..., RECR_ONLY)` | **52 691 548 B (50.3 MiB)** at a 4932-token prompt (35B-A3B) |
| the whole state (attention + recurrent, `FLAGS_NONE`) | 69 481 272 B (66.3 MiB) — the 16 MiB difference is the seq's attention K/V |
| serialised handover, `RECR_ONLY` (`ARMS_HANDOVER=copy`) | **34.5 / 36.1 ms** (35B, 2 reps) — ~100 small synchronised tensor copies, latency-bound at ~1.5 GB/s |
| serialised handover, whole state | 44–50 ms |
| **device-to-device handover (`llama_memory_seq_state_take`)** | **0.45 – 0.66 ms** warm, 1.9–2.3 ms on a process's first handover |
| same, dense 512-token prompt (4B) | 0.33–2.1 ms vs 36 ms serialised |

The new code (`enabling-0002`, 7 files, +274/−2):

* `llama_memory_recurrent::seq_state_take(src, seq)` — one contiguous destination block via the same
  `find_slot()` path `state_read_meta()` uses, then **one batched `ggml_backend_tensor_copy_n`** over per-layer
  `ggml_view_2d` row ranges (a host-buffer memory takes a `memcpy` instead), then release the source rows.
* `llama_memory_seq_state_take(mem, src, seq)` — the llama-level entry (hybrid memories only).
* `llama_memory_i::seq_rm_recr()` / `llama_memory_seq_rm_recr()` — drop **only** the recurrent cells.  Needed
  because `llama_memory_seq_rm()` on the handing-over arm would free the **shared** attention cells.
* `LLAMA_STATE_SEQ_FLAGS_RECR_ONLY` — the serialised control arm (the hybrid wrapper skips its attention half
  on both sides).

### 1.2 The text oracle for the handover

| shape | mode | result |
|---|---|---|
| **4B Q8_0, no host tier** (`-c 4096`, 512 + 256-token prompts, 64 tokens each, 2 reps) | `single` / `batch-pair` / `arms` | **all identical**, both requests, both reps (`03601256ed3a`, `dbbc1b5c148b`) |
| **35B-A3B Q4_K_M, arena 5000**, one request (4932-token prompt, 32 tokens), 3 reps | `single` vs `handover` | **identical** (`7a13c4ea9e6b`), 3/3 |

thread, so it is queued behind at most one decode step — the 15–20 ms outliers are a take that landed behind a
cold-arena prefill step).

## 2. T2/T3 — the design, emulated (the instrument is the server shape)

[`arms/two_arms.cpp`](arms/two_arms.cpp): one process, one model,

* **prefill arm**: `ctx A`, `n_batch = n_ubatch = -ub`, owns the prompts, samples the prompt's last row, posts
  the slot;
* **decode arm**: `ctx B`, `ctx_other = A`, `ctx_other_share_memory = true`, `n_batch = n_ubatch = ARMS_B_BATCH`,
  owns the sampled tokens, steps **one token per active slot in one batch** (continuous batching);
* a **request queue** between them and a **handover at the request boundary** (the take runs *on the decode
  arm*, under the same mutex as its steps, and the prefill arm waits only for that one handover to complete
  before it starts the next prompt — so a take never reads a memory module the prefill arm is allocating in);
* modes `single` (text reference), `batch-pair` (one context, the same 2-slot decode loop — the
  **width-matched** reference), `arms`, `handover`, `pf-alone`, `dec-alone`; `ARMS_REPS` for warm reps,
  `ARMS_WAIT_ALL` for the no-overlap control, `ARMS_HANDOVER=device|copy`.

**Ordering matters and it is measurable**: the first version had the *prefill* thread take the mem_mutex
directly, and the decode thread's tight step loop starved it for **2.85 s** (the campaign's "queue depth, not
phase" in a new form).  Posting the take to the decode arm's loop removed it entirely.

### 2.1 The product numbers (35B-A3B Q4_K_M, arena 5000, `-c 16384 -b 2048 -ub 512`, 2 requests: a 512-token
prompt with 192 decode tokens, then a 2048-token prompt with 48, warm reps)

| arm | request-1 prefill | decoder tokens **inside** the prefill | ITL p50 / p95 inside | handover |
|---|---|---|---|---|
| `pf-alone` (no second context) | **1820.1 ms** = 1125.1 t/s | — | — | — |
| `arms` rep 1 | 2076.5 ms = 986.3 t/s (**+14.1 %**) | **38** | **53.7 / 71.6 ms** | 0.47 ms |
| `arms` rep 2 | 1980.1 ms = 1034.3 t/s (**+8.8 %**) | **37** | **49.0 / 77.7 ms** | 0.42 ms |

Read: **6.75 ms charged per decoder token** against the campaign's 7.7 ms at arena 5000 — the interleave's
price reproduces on the product shape, and the decoder keeps getting a token every ~50 ms through a 2 s

Caveats, stated: `-ub 512` (see §3.2 — the pair does not fit at `-ub 2048`), so the prefill rate is ~1000 t/s
against the campaign's 2172; `pf-alone` has no second context (the campaign measured its presence at **~3 %**,
which is inside the +8.8 % of rep 2); the p50/p95 come from 37–38 samples.

## 3. Landmines this pass adds (each is a blocker or a cost, none is theoretical)

### 3.1 The shared KV's cell allocator is not concurrency-safe

Two contexts that co-own the cells both allocate in them, and the allocator is a **two-step, unlocked**
read-modify-write:

* `llama_kv_cache::find_slot(ubatch, cont)` is **const** — it only *searches*, from
  `uint32_t head_cur = v_heads[seq_to_stream[seq_id]]` (`llama-kv-cache.cpp`, ~line 2360), and returns
  `sinfo.idxs`;
* `llama_kv_cache::apply_ubatch()` **then** advances the cursor: `head = sinfo.idxs[s].back() + 1`
  (`llama-kv-cache.cpp` ~2615).

Between those two calls the cells are *not reserved*.  Two arms that search from the same `v_heads` value are
both handed the same cells, and both publish `head = last + 1`.  The result is two sequences writing one KV
cell — fluent, wrong text, non-deterministically.  (`v_cells` is shared through `v_cells_impl`; `v_heads`,
`used`-bookkeeping and the per-context `n`/`head` are not.)

The measured arms did **not** visibly hit it (the text is stable *within* a configuration), but it is
unavoidable in principle and it is the first thing the server cut must fix.  Three candidates, cheapest
first: (a) reserve at `find_slot()` time (advance `v_heads` at prepare and make `apply_ubatch` not re-set it —
needs a rollback path for a failed/abandoned prepare); (b) **partition**: give each arm its own cell range and
bound `find_slot`'s scan to it (each arm then has a private cursor — this is the contained fix, and it also
makes the extent/`get_n_kv` a per-arm quantity); (c) a mutex across prepare→apply, which serialises the two
graphs' compute and **defeats the feature**.

### 3.2 The second arm's VRAM is a graph reserve per arm *and per active-slot width*

The campaign's figure ("a second context costs ~548–600 MiB of graph buffers + 125.6 MiB of RS") is the cost of a
context that decodes **one** slot.  The decode arm's reserve is **per graph shape**, and a 2-row decode graph on
35B-A3B asks for **741.47 MiB** (`ggml_gallocr_reserve_n_impl: failed to allocate ROCm0 buffer of size
706806016` when it does not fit — the scheduler keeps the 1-row graph *and* reserves the 2-row one).  Measured,
in order: arena 5000 + `-c 24576`/`-ub 2048` → the *prefill* graph's reserve fails; arena 4000 + `-c 8192` +
`-ub 2048` → same; arena 5000 + `-c 16384` + **`-ub 512`** → fits and runs.  So: **N generating slots cost a
per-N reserve, and the pair needs roughly one prefill-graph of headroom** on a 32 GiB card.  The server's
opt-in gate should therefore be "arena + one prefill graph + one decode graph per admitted slot width", not
"arena + 600 MiB".

### 3.3 The 2-slot two-arm text is not stable warm on a partial arena

Isolation matrix (35B-A3B, arena 5000, `-c 16384 -ub 512`, two requests, 3 reps; reference
`b0281be7c5a6` / `d5083bd41b4c`, which `single` and `batch-pair` both read in **all three** reps):

| arm | rep 0 | rep 1 | rep 2 |
|---|---|---|---|
| `batch-pair` (one context, 2 slots) | match | **match** | **match** |
| `single` (sequential) | match | match | match |
| `arms` + `WAIT_ALL` (no overlap at all) | match | `e05c6e16a136` / `abe253ea957a` | `fc7d8e55fd40` / `d5083bd41b4c` |
| `arms` (free-running) | match | `e05c6e16a136` / `abe253ea957a` | `fc7d8e55fd40` / `6f5362913a44` |
| `arms`, `ARMS_HANDOVER=copy` | match | same as device | same |
| `arms`, `GGML_MOE_DEVREMAP=0` | match | same | same |
| `arms`, `MOE_EXPERT_PREFILL_IN_PLACE=0` | match | same | same |
| 4B (no host tier) | match | match | match |
| 35B, **one** request | match | match | match |
| **35B, FULL residency** (no `-ncmoe`, no arena) | match | `e05c6e16a136` / `abe253ea957a` | — |
| 35B full residency, `LLAMA_KV_N_PAD_MIN=8192` | match | `fc7d8e55fd40` / `abe253ea957a` | — |

So the carrier is **the second context doing the decoding**, not the move (both handover implementations
agree), not the remap, not the in-place prefill path, not the overlap (`WAIT_ALL`), not the batch width
(`batch-pair` is stable at the same widths), and **not the host-expert tier**: the 35B-A3B reproduces it at
**full residency** (no `-ncmoe`, no arena), the dense 4B does not.  Cold rep → identical; warm reps →
different **and different from each other**, but from a *small set* of outcomes (`b0281be7c5a6` /
`e05c6e16a136` / `fc7d8e55fd40` for request 0), which is the signature of a **shape/graph-bucket** effect rather
than of state corruption.  Two further data points point the same way and are worth recording:

* the *single-context* reference's own text **changes with the KV pad**: `batch-pair` reads `b0281be7c5a6` at the
default pad and `649c8596467d` with `LLAMA_KV_N_PAD_MIN=8192`, stable in both.  So this fork's decode numerics do
depend on the graph's `n_kv` bucket (the `LLAMA_KV_N_PAD_*` family exists for exactly that reason);
* the two arms do **not** share a cell cursor (`v_heads` is per-context, only `v_cells` is shared), so after one
rep the two arms' KV extents and their recurrent destination rows differ from the single-context run's — even
with no overlap at all.

Two more candidates were then eliminated on the 35B-A3B at full residency, each with its own arm:

* **not the `n_kv` bucket**: `LLAMA_KV_N_PAD_MIN=8192` at `-c 8192` puts every decode graph in one bucket
  (the pad equals the cache size) and the arms still diverge (`fc7d8e55fd40` / `abe253ea957a` in rep 1);
* **not the second context's compute-buffer layout**: `ARMS_B_BATCH=512` sizes the decode context's reserve
  exactly like the prefill context's (a 2-row batch is a 2-row graph in either) and the arms still diverge
  with the *same* values.

So the earlier "arena settle / residency" reading is refuted, and so are the map, the in-place path, the
overlap, the batch width, `n_kv` and the buffer layout.  **What is left, and it fits every row above: the
physical KV cell INDICES.**  An arm allocates its sequence's cells from its own `v_heads` (`v_cells` is shared,
the cursor is not), so a slot occupies different cells in `arms` than in `batch-pair` — and this fork's tile-FA
decode launcher splits the KV extent between blocks by index (`ggml_cuda_fattn_band_wmma_split`,
`parallel_blocks` — the very thing `scripts/gate-spec-purity.sh` exists to pin).  Different indices, different
split, different numerics; the 4B's attention path is not index-sensitive, so it is immune; a cold rep starts
both configurations from cell 0, so it agrees.  That also makes the `LLAMA_KV_N_PAD_MIN` sensitivity of the
*single-context* text (`b0281be7c5a6` -> `649c8596467d`) a different instance of the same class.

The instrument that would settle it: print the cell indices a sequence holds on each arm (the `sinfo.idxs` of
its ubatches) and the resulting `get_n_kv()`/`parallel_blocks`, and diff the **logits** of the same token decoded
on A and on B.  The fix direction is then either a **shared allocation cursor across the co-owner pair** (one
counter for both arms, which the allocator fix of §3.1 wants anyway) or making the FA split index-independent.
Until then: **T3's text point must compare two runs of the SAME cell layout** — which is why the campaign's
"byte-identical to today's single-context server" is not available as a hash comparison on an MoE model.  §3.4
then **confirms the cell-index hypothesis** with a reset arm and states the fix (one allocator, the prefill arm
reserving and the decode arm consuming).

> **REVISED 2026-11-22** ([`RESULTS-2026-11-22.md`](RESULTS-2026-11-22.md) §3): "the host tier is refuted" holds
> only for the *full-residency* instance of the divergence, which pass 2 shows is the hipBLASLt path (cured by
> `ROCBLAS_USE_HIPBLASLT=0`, which these arms did not carry).  On a partial arena, **with both pins on**, the

## 4. What this changes in the campaign

* **T1 is closed** (see §1); the artifact is `enabling-0002-recurrent-handover.patch`, and the serialised
  `RECR_ONLY` path stays as the control arm of the handover's own gate.
* **T2 has a shape that is measured, not hypothesised**: post the take to the decode arm (never take a lock
  the decoder holds in a loop), step one token per active slot in one batch, and wait for the handover only at
  the request boundary.  §5 is the server cut, with the code points.
* **T3's gate cannot be a cross-configuration hash yet** (§3.3 — two arms, warm reps, MoE model: the divergence
  survives full residency and every kill switch tried, so it is a shape/bucket effect and needs the logits
diff): text on a *pinned shape* (KV pad high enough that both arms sit in one `n_kv` bucket), a
  same-configuration repetition to catch non-determinism, and `scripts/gate-prefill-logits.sh` (KLD) for the
  prefill path.
* **T4's opt-in gate needs the VRAM rule of §3.2** and the allocator fix of §3.1 before it can be default-on
  anywhere.
* Nothing was applied to `patches/`, no block was created or amended, and `~/llama.cpp` carries the changes on
  the WIP branch `wip/prefill-overlap` only (4 commits, tree clean).

## 5. The server cut (T2), in code points

The design is *not* "two servers": it is one server with **two arms**, where the decode arm owns its slots'
generation and nothing else.

1. **Contexts** (`tools/server/server-context.cpp`, `load_model`/`init`, around `ctx_tgt` at ~1134 and the
   `slot.ctx_tgt`/`slot.ctx_dft` wiring at ~1857): create `ctx_dec` after `ctx_tgt` with
   `cparams.ctx_other = ctx_tgt`, `ctx_other_share_memory = true`, `n_batch = n_ubatch = <decode width>`,
   `n_seq_max = n_parallel`, `n_outputs_max = n_parallel`.  A second `server_batch` for it.
2. **Ownership**: `slot.arm` (`PREFILL`/`DECODE`) plus a per-slot mutex.  `pre_decode()`'s slot loop skips
   `DECODE` slots; the decode thread touches only `DECODE` slots.  `slots[]` itself, `batch`, `ctx_tgt`,
   `spec`, `checkpoints` and the prompt cache stay **main-thread only** — the decode arm must never call
   `prompt_save`/`prompt_load`, `common_speculative_*`, mtmd, TTS, embeddings, rerank or decision paths.
3. **Handover** (in `post_decode()`, where the prompt's last row is sampled and the slot becomes
   `SLOT_STATE_GENERATING`): `llama_memory_seq_state_take(llama_get_memory(ctx_dec), llama_get_memory(ctx_tgt),
   slot.id)`, set `slot.arm = DECODE`, wake the decode thread.  The take must run **on the decode arm's
   thread** under its step mutex (a prefill-side take starves: §2).
4. **Return** (the decode arm finishes a slot): `llama_memory_seq_rm(llama_get_memory(ctx_dec), slot.id, -1,
   -1)` (the shared cells are freed once, here), `slot.arm = PREFILL`, and the slot goes back to the main loop
   for `release()`/`send_final_response()` — i.e. the decode arm does **not** own the response lifecycle, it
   only produces tokens into the slot's `generated`/stream path.
5. **The decode step**: `llama_process(ctx_dec, LLAMA_PROCESS_TYPE_DECODE, batch)` over one token per `DECODE`
   slot, then `common_sampler_sample(slot.smpl, ctx_dec, i)` per row and the same stop/emit logic `post_decode`
   uses (factor it into a function that takes an explicit context + batch + slot, so the two arms share it).
6. **Guards** (the opt-in gate): `--prefill-decode-arms` (or the arena+residency rule of §3.2 auto), and refuse
   when any of `spec`, `mctx`, TTS, embeddings/rerank/decision, LoRA, sleep/wake or `n_parallel < 2` is in play;
   `-np 1` stays single-context.
7. **Blockers before any default flip**: §3.1 (allocator), §3.3 (which oracle), and `scripts/gate-prefill-fairness.sh`
   / `gate-prefill-duty.sh` (the prefill arm keeps block 16's admission and the duty cycle becomes the `F ≈ 0`
   fallback).

## 3.4 The carrier of §3.3 is the TWO ALLOCATION CURSORS — measured

The leading hypothesis of §3.3 (`v_cells` shared, `v_heads` per-context, so the arms place a slot in different
cells) was tested by giving every rep the *same* allocation state as rep 0: `ARMS_RESET_CACHE=1` wipes the cell
metadata and both cursors at the rep boundary (`llama_memory_clear(mem, false)` on both contexts — nothing is
live there).  Two requests, 3 reps, `ARMS_WAIT_ALL` (no overlap), reference `b0281be7c5a6` / `d5083bd41b4c`
which `batch-pair` reads in all three reps of both shapes:

| shape | request | rep 0 | rep 1 | rep 2 |
|---|---|---|---|---|
| **host tier, arena 5000** (no reset) | R0 512 tok / 192 gen | match | `e05c6e16a136` | `fc7d8e55fd40` |
| | R1 2048 tok / 48 gen | match | `abe253ea957a` | `d5083bd41b4c` |
| **host tier, arena 5000, RESET** | R0 | **match** | **match** | **match** |
| | R1 | match | `b79e73e3fe9f` | `b79e73e3fe9f` |
| **full residency, RESET** | R0 | **match** | **match** | **match** |
| | R1 | match | `b79e73e3fe9f` | `b79e73e3fe9f` |

So: **with one allocation state the first request is byte-identical to the single-context reference in every rep,
on both shapes** — the two independent cursors are the carrier, exactly as the hypothesis said, and the residual
difference for the *second* request collapses into one stable value (rep 1 == rep 2), i.e. it is a layout/state
difference and no longer run-to-run non-determinism.

Two consequences, and they are design instructions, not just explanations:

1. **A single allocator for the pair removes this class entirely** — and it is the same change the §3.1 blocker
   needs.  For the server the shape is: **the prefill arm reserves the slot's cell run at handover and publishes
   it; the decode arm CONSUMES it and never searches or advances the shared cursor.**  That is one owner for
   every allocation decision (the layout is then a function of the request sequence alone), no lock on the
   decoder's hot path (so the "queue depth, not phase" lesson survives), no `find_slot()` scan per decode step,
   and the double-allocation hazard of §3.1 is gone by construction.  The machinery to run a batch into a
   caller-chosen cell set already exists: `llama_kv_cache::state_read_sinfo(..., sinfos_in)` — the "mirrored slot
   layout" path the draft/restore code uses.
2. **The take is not the setup.**  It moves the recurrent rows and touches **no** KV cell, so moving the take to
   the prefill thread changes nothing about this.  What the prefill arm must own is the *allocation for the
   decode arm's future tokens*; what the decode arm must own is the *mutation of its own memory module* at a step
   boundary (the take's metadata write included).  Concretely: prefill computes the reservation + the state copy
   on its own stream, **posts** it, and the decode arm applies the publish at its next step boundary — a posted
   message, never a lock the prefill thread waits on (measured: a direct mutex take starves the prefill arm for
   **2.85 s**, §2).
3. Orthogonal residual, and it is the next thread: R1 (the second concurrent slot, whose recurrent tail was moved
   by a take instead of allocated by its own prefill) still reads `b79e73e3fe9f` warm.  It is now *deterministic*,
   so it can be found by printing the cell indices (KV and recurrent) each request holds on each arm, and
   diffing the logits of one token decoded on A and on B.  The `src0`/`rs_z` surface is the first suspect.

## Reproduce

The tree must be the WIP branch (4 commits) — `enabling-0001` + `enabling-0002` are the two `src/` commits:

```bash
cd ~/llama.cpp && git checkout wip/prefill-overlap
BUILD_DIR=build-2ctx JOBS=24 ~/bin/build-llama-rocm-101     # 10.1.0-gfx120X, the line every number here is on
cd ~/llama-cpp-rdna-boosts/archive/work/prefill-decode-arms/arms && ./build-two-arms.sh
head -200 ../../../prompts/kld-corpus-35b-in-domain.txt > /tmp/p4k.txt   # the 4932-token prompt

export LD_LIBRARY_PATH=/opt/rocm-10.1.0-gfx120X/lib HIP_VISIBLE_DEVICES=0 TWO_CTX_PF_FILE=/tmp/p4k.txt
M=/llm/models/Qwen3.6/35B-A3B/Q4_K_M/Qwen3.6-35B-A3B-UD-Q4_K_M.gguf

# the host-tier shape of §2.1 (arena 5000, the ubatch the pair fits at)
export MOE_EXPERT_CACHE_MIB=5000 MOE_EXPERT_HEATMAP=load ROCBLAS_USE_HIPBLASLT=0 \
       ARMS_SCENARIO="512:192@0,2048:48@0" ARMS_B_BATCH=4 ARMS_REPS=3
for m in single pf-alone dec-alone arms; do
  ARMS_MODE=$m ./two_arms -m $M -ngl 99 -ncmoe 40 -lme auto -c 16384 -b 2048 -ub 512 -n 192 -t 8 2>&1 \
    | grep -E "^REP |^REQ |^TOTAL|^ITL"
done

# the oracle: full residency (no -ncmoe, no arena), no overlap control
# NOTE 2026-11-22: ROCBLAS_USE_HIPBLASLT=0 is MANDATORY on these arms -- without it the arms' warm text diverges on
# the hipBLASLt path alone (RESULTS-2026-11-22.md §2).  It was missing here and produced the "residual".
unset MOE_EXPERT_CACHE_MIB MOE_EXPERT_HEATMAP
export ROCBLAS_USE_HIPBLASLT=0
ARMS_MODE=batch-pair ./two_arms -m $M -ngl 99 -c 8192 -b 2048 -ub 512 -n 192 -t 8   # the reference
ARMS_MODE=arms ARMS_WAIT_ALL=1 ./two_arms -m $M -ngl 99 -c 8192 -b 2048 -ub 512 -n 192 -t 8

# the handover itself, one request, 3 warm reps (single vs handover: the hashes must match)
ARMS_SCENARIO="4932:32@0" ARMS_MODE=single   ./two_arms -m $M -ngl 99 -ncmoe 40 -lme auto -c 24576 -b 2048 -ub 2048 -n 32 -t 8
ARMS_SCENARIO="4932:32@0" ARMS_MODE=handover ./two_arms -m $M -ngl 99 -ncmoe 40 -lme auto -c 24576 -b 2048 -ub 2048 -n 32 -t 8
# ARMS_HANDOVER=copy forces the serialised path (the control arm of the take)
```

Knobs the instrument adds: `ARMS_MODE` (`single|batch-pair|arms|handover|pf-alone|dec-alone`), `ARMS_SCENARIO`
(`<prompt_tokens>:<n_predict>@<admit_ms>,…`), `ARMS_REPS` (warm reps; rep 0 pays the cold arena), `ARMS_B_BATCH`
(the decode arm's `n_batch = n_ubatch`), `ARMS_WAIT_ALL=1` (no prefill/decode overlap: the step loop holds until
every handover is done), `ARMS_HANDOVER=device|copy`, `ARMS_RESET_CACHE=1` (wipe the cell metadata and both
allocation cursors at each rep boundary — the §3.4 control: it makes every rep start like rep 0).
