## 1. Task 1 — a GENERIC second context sharing the KV (the enabling change)

### 1.1 What the change is (WIP branch `wip/prefill-overlap`, 6 files)

`llama_context_params::ctx_other` was arch-gated to GEMMA4_ASSISTANT / EAGLE3 / DFLASH / QWEN4EXP with a
literal `// TODO: more generic`.  The sharing underneath it was a **read-only MIRROR**: a drafter that reads
the target's cells.  A same-model second context is a **CO-OWNER** — it allocates cells for its own
sequences in the shared cell map and must run the mutable cell paths, or its attention reads garbage (it
did: `!!!!!!!!!!!!`, see §1.4).  The change:

* `include/llama.h` — **one new bool**, `ctx_other_share_memory` (default `false`), so sharing is opt-in and
  the MTP drafter (which names a `ctx_other` it deliberately does *not* share a KV with) is untouched.
* `src/llama-context.cpp` — the generic gate: any arch may name a `ctx_other`, and it must be a context of
  the **same model** (else throw).  The arch blocks above stay — they decide what sharing *means* for their
  arch.
* `src/llama-model.cpp` — `create_memory` offers the source memory to the two modules that implement a
  shared view (the plain attention KV and the plain hybrid wrapper) and **declines loudly** for every other
  module instead of silently handing out a private cache.
* `src/llama-memory-hybrid.{h,cpp}` — the hybrid wrapper takes `mem_other` and gives it to its attention
  cache (identity layer share: same model, same layer ids).
* `src/llama-kv-cache.{h,cpp}` — `other_coowner`: a co-owner runs `apply_ubatch` / `seq_rm` / `seq_cp` /
  `seq_keep` / `seq_add` / `seq_div` / `update` / `state_write` / `state_read` / `build_graph_shift` on the
  shared cells; a mirror still skips all of them (`is_mirror()`).

**Not shared yet, and it must be said:** the **recurrent** state of a hybrid model (Qwen3.5/3.6 is GDN + 10
attention layers, `llama_memory_hybrid`).  The second context views the attention KV (its KV buffer line
appears **once**, 160 MiB at `-c 8192`) but allocates its **own** 125.6 MiB RS buffer.  That is coherent for
the arm measured here (each sequence lives entirely in one context) and it is **not** sufficient for a
server that moves a slot between contexts — see §5.

### 1.4 The divergence is the sync-free DECODE-BAND REMAP, not residency (hypothesis refuted in place)

First reading — *"residency selects the MoE kernel set (`GREEDY-PURITY.md` §89), so a hash cannot be the
oracle here"* — **is refuted by these arms**:

* the fusion census is **identical** in the diverging and the matching arm (`prefill MoE fusions … (in_place/
  staged) mixed_lanes=0`, `decode MoE fusions … mmvq_glu=78/0 mixed_lanes=0`, `takeover=3840 get_ok=798`);
* `GGML_MOE_DEVREMAP=0` makes the two-context arm read `1e05a254e65f` **3 runs out of 3**, while its
  residency census still differs run to run (h=0.8270 vs the matching arm's 0.8095) — so a **different
  residency with the same text** is directly measured, and residency is not the carrier;
* `MOE_EXPERT_PREFILL_IN_PLACE=0` alone is **not** enough (1 of 2 runs matched).

Mechanism, read off `ENVIRONMENT.md`: `GGML_MOE_DEVREMAP` is the **sync-free** path — the scheduler offers
the split input, a kernel maps routing through the per-table expert→slot map "one call late", and the policy
"re-uploads the map only after a residency change".  That map / `slot_dirty` state is **per table, per
process**.  Two contexts that both submit decode-band work interleave their routing into the same late map,
so one of them reads the other's slots.  The bytes are wrong, the output is fluent (not garbage), which is
why only a text oracle catches it.

**Sharpened by the pf-dec arm (§4):** a *prefill* context plus a *decode* context does **not** collide (all
4 pf-dec reps read `60e6daadb89f` / `37896a97c74e`, byte-identical to their solo arms) — the remap is
decode-band only (`ne[2] <= band`), so the hazard is precisely **two contexts submitting decode-band ops
concurrently**.  The campaign's own arm is the safe pair; a *second decoder* is not.

### 1.5 `apply_ubatch` was the first bug (kept, because it will bite again)

The first `dual` run produced `!!!!!!!!!!!!`: `llama_kv_cache::apply_ubatch` returns early when
`other != nullptr` (a mirror never writes cell metadata). A co-owner must, or its own cells never get
positions/seq ids.  Hence the explicit `other_coowner` flag rather than "`other` means mirror".

## 2. The VRAM cost of the second context (measured, and it changes the arm)

At the campaign's 8 GiB arena, the **second context does not fit** on a 32 GiB card:

```
ggml_cuda_device_malloc: 547.84 MiB allocation failed on device 0 while the movable-boundary slab holds
the VRAM; the arena cannot yield physical back to the driver.
```

Even with the decode context sized for decode only (`n_batch = n_ubatch = 8`, which is all a decode step
needs), its graph buffers ask for **547.84 MiB**, and the arena + the first context's compute buffers hold
everything.  At **arena 5000 MiB** the pair fits and runs.  Facts to carry:

* the second context costs **~548-600 MiB of compute buffer + 125.6 MiB of RS** (its KV is shared, so zero);
* an 8 GiB arena + two contexts OOMs; a 5 GiB arena + two contexts runs;
* so the honest two-context arm **must** trade arena for the second context, which changes the shape (more
  non-resident experts => a *bigger* window) — every number in §4 is at **arena 5000**, and its `pf-alone`
  control is at arena 5000 too.

## 4. The first overlap numbers (arena 5000 MiB, warm rep, no gate at all)

| arm | prefill | decoder ITL (during the prefill window) |
|---|---|---|
| `pf-alone` (warm) | **2531 t/s** (1948 ms / 4932 tok) | — |
| `dec-alone` (warm, arena 8000) | — | p50 **10.9** / p95 **11.6** / max 12.0 ms |
| **`pf-dec` (warm, flat out)** | **2176 t/s** (2266 ms) = **−14.0 %** | **33 tokens** during the prefill, p50 **42.8** / p95 **51.1** / max 52.1 ms |

Read against the shipping rows on the same harness family (arena 8000, 15 k prompt, §0):

| mechanism | prefill cost | decoder lateness |
|---|---|---|
| shipping `DUTY=0` (today's default-ish) | −2 % | **one token per prefill step: p95 568 ms** |
| shipping `DUTY=16` | **−30 %** | p95 **519 ms** (p50 13.5 ms) |
| **this arm, ungated, arena 5000** | **−14 %** | **p95 51 ms**, p50 43 ms |

So the ungated interleave is already a **Pareto improvement over both shipping rows** on this shape: a
decoder that keeps getting tokens (33 of them) through a prefill rather than one burst per step, at half the
duty cycle's prefill cost.  It is **not** the handover's PASS (prefill within 5 % and p95 < 50 ms): the
decoder is **3.9x slower per token** while the prefill runs (42.8 vs 10.9 ms), i.e. it is **charged, not
hidden**.

**What that means, stated honestly.**  On the partial-arena shape the *prefill's* wall is dominated by
gathers (pass 2: 57 %), yet a real decode step is **not** free inside it (pass 4's burn kernel was: −1.2 %
to the gather).  The difference is the decoder's own work: a decode step is D≈11 ms and a gather window is
~2.5 ms, so one decode step **cannot** fit in one window — it spans 4-5 windows and is charged for the
compute phases in between (exactly the `max(fill quantum, D)` arithmetic of the README §7).  Whether a
*gated* (rate-limited) arm converts that into a better trade is the next measurement, not a conclusion.

Also measured, for the record: at **full residency** (dense 4B control, no window) the same ungated arm
charges 2.1x per decode token (10.2 → 21.3 ms) and the prefill **−11 %** (9005 → 8000 t/s) — so the partial
arena's 3.9x is *worse* than the no-window case, not better.  The window does not help a decode step that
itself uses the link.

Three things, all measured:

1. **The gate is not the lever; the submission is.** F = 0.25 is *worse* on the decoder's p95 (177.7 ms) than
   flat out (52.6 ms) at no prefill saving worth having (2333 vs 2172 t/s): a cumulative-budget gate withholds

   Rate-limiting can only decide *how many* tokens; it cannot decide *where in the prefill's phase structure*

2. **The marginal cost of a decode token here is 79 % charged, not absorbed.** Between `F = 0`
   (2007 ms) and flat out (2268 ms) the prefill pays **261 ms for ~34 decoder tokens = 7.7 ms/token**
   against a standalone decode step of **10.9 ms** (measured, `dec-alone`: 10.9 ms p50/p95 11.6).  Pass 5's
   sweep said "two-thirds absorbed / one-third charged" for an **ALU-only** burn kernel; a real MoE decode
   step is charged ~4/5, because on a shallow arena **the decode step is itself link/memory-bound** and the
   gather window leaves SM capacity, not link capacity (pass 4 measured the SM half with a kernel that
   deliberately did no memory traffic — its own note says so).
3. **A second context that does nothing costs ~3 %**: 2529.9 → 2457.1 t/s on the same prompt.  That is the
   floor every arm above carries (landmine 5's "~8 % with lanes armed" measured 3 % here).

**What survives of the campaign's number.**  The target in pass 5 was "~3550 t/s of prefill AND a tens-of-ms
ITL p95".  On this shape the interleave delivers **2172 t/s (the untouched prefill's own 2457 t/s less 11.3 %)
with a decoder p95 of 49-53 ms** — against the shipping rows on the same box, same shape family:
`DUTY=0` = one token per prefill step (**p95 568 ms**), `DUTY=16` = **p95 519 ms at −30 % prefill**.  So on
both axes the interleave is **better than both shipping mechanisms** (Pareto), and on neither axis is it the
handover's PASS (prefill within 5 %, p95 < 50 ms) — it is a **PARTIAL** by the handover's own definition, and
the maintainer has said explicitly that parity on performance with a smoothness win is a win.

**And what does not survive: "the window is ~75 free decode steps."**  A decode step is not the burn kernel.
The free-window physics applies to work that does not touch the expert tables; on a partial arena the decode
does exactly that.  The honest statement is: *the interleave converts prefill time into decode tokens at
~70-80 % of the decode's own cost, smoothly, instead of at ~86 % in one burst per step (pass 3).*  The
smoothness is the win; the throughput is a wash against the duty cycle, not a gain.

## 6. Task 2 (the submission point): the per-gather host boundary EXISTS — `splits = 120`

One `GGML_SCHED_DEBUG=1` reading on the shallow-arena shape (`-ncmoe 40`, `-ub 512`) settles the question
that decides Task 2's design:

```
sched_reserve: graph (pp bs=512, tg bs=2): nodes = 3839 / 3839, splits = 120 / 42, ...
```

**120 splits for one prefill ubatch = 3 per layer x 40 layers** — one split per `MUL_MAT_ID`, whose routed
expert table is a host tier.  Reading `ggml_backend_sched_compute_splits()` against that number
(`ggml/src/ggml-backend.cpp:3719-3769`): per split it runs `sched_stage_issue()` -> the input copies ->
`ggml_backend_graph_compute_async()`, and the MoE gather is issued inside the *input-copy* phase
(`ggml_backend_sched_copy_input()` -> `iface.moe_cache_gather`, `:3425-3440`).  So for every one of the 120
splits the host has a point **after that split's gather is enqueued and before that split's compute is
launched** — exactly the switch point HANDOVER §4.3 asks for, and it needs no change to `llama_process()`'s
public shape.

Two consequences, both load-bearing:

1. **Why the ungated two-thread arm already reads p95 49-53 ms**: the driver is free to interleave the
   decoder's kernels with those 120 gather windows; that is the smoothness measured in §4/§5.  A *gate* adds
   nothing to that (§ pass 11: F=0.25 is worse).
2. **What a real Task 2 must do that a callback alone cannot**: the CUDA backend's stream is
   `cudaStreamPerThread` (`ggml-cuda.cu:1954`), so a decode graph submitted *from the prefill's own thread*
   (the obvious callback body) lands on the **prefill's stream** and serializes behind the split.  The
   overlap needs the decode enqueued from a **different thread** (its own per-thread stream) with an
   event/condvar handshake at the split boundary: prefill signals -> decoder enqueues one step -> prefill
   launches its split.  That is ~120 host round trips per ubatch (5-20 us each, 1-2 ms of a 2000 ms prefill),
   and it is the difference between "the driver schedules the decoder when it can" and "the decoder is
   placed in the window on purpose".

**Not implemented yet.**  It needs (a) a nullable sched-level yield callback in
`ggml_backend_sched_compute_splits()` plus a `llama.h` setter so a caller can install one on a context's
scheduler, and (b) the handshake in the harness.  Both are WIP-only and neither touches the delivery.
Honest expectation from §5: placement can at best recover the 79 % charge down to the ALU-only window's
~33 % charge, so the target is prefill **-4 %** with the decoder's p95 still in the tens of ms — which would
be the handover's PASS.  That is a hypothesis to measure, not a result.

# Pass 12 (same day) — Task 2 built and measured: the per-gather yield point LOSES to free-running

Pass 11's §6 said the switch point exists and that Task 2 needs (a) a sched-level hook and (b) a handshake
with the decode on its own thread.  Both are now built and measured:

* **`ggml`**: a nullable sched yield callback, invoked once per graph split that issued a MoE device gather —
  after the gather is enqueued on the split backend's stream, immediately before that split's compute is
  launched (`ggml-backend.{h,cpp}`, `llama_set_split_yield_callback`).
* **`llama_server`-free harness**: the prefill thread OFFERS a window, the decoder thread (parked) wakes,
  enqueues exactly ONE step on its own thread/stream, reports the enqueue, and the prefill thread proceeds
  (bounded wait, `TWO_CTX_WAIT_MS`).
* **stream priority** (`llama_set_stream_priority(ctx, -1|0|+1)`): the other way to spend the window without
  competing for it — the hardware form of "give the prefill the SMs first".

Shape unchanged from pass 11 (arena 5000, 4932-token prompt, 128 decoder tokens, warm reps).

| arm | prefill | decoder during the prefill |
|---|---|---|
| `pf-alone` | **2528 t/s** (1950 ms) | — |
| flat out (free-running, no code path at all) | **2172.5 / 2175.3** (2268 ms) | **32-35 tokens, p50 41.8-43.1, p95 48.4-52.6 ms** |
| yield, F=1.0, wait 3 / 10 / 40 ms | 2406.5 / 2380.6 / 2138.1 | **3-8 tokens**, p95 604-627 ms (during) |
| yield, F=1000 (offer whenever the decoder is ready), wait 0.2 / 1 ms | **2405.8 / 2408.1** | **3-4 tokens**, p95 627-628 ms |
| stream priority: decode LOW | 2173.9 | 33 tokens, p50 41.6, p95 51.8 |
| stream priority: prefill HIGH **and** decode LOW | 2174.4 | 34 tokens, p50 41.2, p95 52.6 |

**The yield is a measured loss, and the mechanism is now understood: queue depth, not phase.**

* The prefill offers a window every **~5.6 ms** (360 gathered splits over a 2 s prefill).  The decoder's own
  step, once submitted, takes **~42 ms** while the prefill runs — so it can accept a window only once per
  ~40 ms, and the census confirms it: `skipped(not-ready)=344-348` of ~352 offers.
* Worse, a *phase-locked* step waits **~600 ms**, not 42: with the decoder holding only one small burst in
  the hardware queues, that burst is scheduled **behind the prefill's deep queue of already-enqueued
  kernels**; a free-running decoder always has work pending, so the hardware fills every gap it finds.
  Free-running = 33 tokens at 42 ms; phase-locked = 4 tokens at 600 ms.  **The host cannot place work better
  than an always-non-empty queue can.**
* The host handshake itself is not the cost (3-400 ms of prefill stall, tunable to ~1 ms at F=1000/wait 0.2 —
  and the result is the same), so this is not "the handshake is slow": it is the queue effect.

**Stream priority is a measured no-op here, and the experiment is not vacuous.**  The first attempt applied
nothing (the compute streams are created when the *context* is built, so a later setter never reached them —
the diagnostic printed `ALREADY CREATED`); the setter now re-creates them and `hipDeviceGetStreamPriorityRange`
reports a real range (`least=1, greatest=-1`).  With the priority genuinely applied (both directions) the
prefill and the decoder read **within noise of the default** (2173.9 / 2174.4 vs 2172.5 t/s; 41.6 / 41.4 vs
41.8 ms p50).  So HIP stream priority orders the *launch* of pending work, it does not preempt running grids,
and the charge is not a scheduling inversion — it is real resource sharing.

## What pass 12 settles

1. **The campaign's mechanism is "two contexts, free-running, driver-scheduled".**  Every host-side policy we
   can express (a rate gate, a per-gather placement, a priority) is either neutral or **worse** than leaving
   the decoder's queue full: the win is concurrency, and the only remaining knob is *how much* decode work is
   admitted — which is linear in the charge (pass 11: 7.7-8.6 ms per token against a 10.9 ms step).
2. **The handover's PASS is not reachable this way on this shape**, and the reason is not the switch point: it
   is that the prefill and the decode both need the same device resources (a shallow-arena decode step is
   itself link/memory-bound), so ~4/5 of the decode's own time is charged.  A PASS needs either a shape where
   the decode's band is resident and its step is link-free, or work that does not touch the expert tables.
3. The PARTIAL stands and is the campaign's result so far: **a decoder that keeps getting tokens (32-35
   through a 2.27 s prefill, p95 ~50 ms) at ~11 % of prefill**, against the shipping rows' one-burst-per-step
   p95 of 519-568 ms at 30 %.  Whether ~11 % is an acceptable price for the smoothness — and whether the
   campaign should stop at "concurrency, no policy" and hand that to the server — is a **maintainer decision**,
   not a gate outcome.

# Pass 13 (same day) — the price FALLS as the window GROWS (the arena sweep)

The link explanation of pass 11's 79 % charge makes a prediction: the charge per decode token should rise as
residency falls, because both sides then compete for the same expert link more often.  Measured on the
flat-out arm at three arena sizes (same prompt, same decoder, warm reps):

| arena | residency (warm) | `pf-alone` | flat out | prefill cost | decoder tokens during | decoder p50 / p95 during | **charged per decode token** |
|---|---|---|---|---|---|---|---|
| **3000 MiB** | h=0.32 | **2294.9 t/s** (2149 ms) | 1899.7 (2596 ms) | **−17.2 %** | 28 | 52.3 / 65.7 ms | **16.0 ms** |
| **4000 MiB** | h=0.40 | 2404.3 (2051 ms) | 2025.7 (2435 ms) | −15.7 % | 30 | 48.2 / 59.9 ms | **12.8 ms** |
| **5000 MiB** | h=0.66 | 2528.0 (1950 ms) | 2172.5 (2268 ms) | −11.3 % | 32-35 | 41.8-43.1 / 48.4-52.6 ms | **7.7 ms** |

Two readings, both measured:

1. **The charge per decode token rises as the arena shrinks** (7.7 → 12.8 → 16.0 ms) — and so does the
   decoder's own latency during the prefill (41.8 → 48.2 → 52.3 ms p50).  The two sides are competing for the
   same link budget, exactly as pass 11 concluded: the shallower the arena, the more often the *decoder's* own
   step also misses.
2. **Therefore the campaign's price and its value move in opposite directions.**  The window is worth most
   where residency is worst (pass 2: 57-71 % of the wall at 42-66 % residency) and that is precisely where the
   charge per decoder token is highest.  The Pareto win is real at every point measured (prefill −11 to −17 %
   for a decoder at a 50-66 ms p95, against the shipping rows' 519-568 ms at −30 %), but it is **cheapest
   where it is worth least**.

That closes the physics: no measured configuration gives the handover's PASS (prefill within 5 % *and* p95
under 50 ms), and the two axes are coupled by the expert link rather than by any policy we can apply.
