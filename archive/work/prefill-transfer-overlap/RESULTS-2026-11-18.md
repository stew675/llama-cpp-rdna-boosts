# 2026-11-18 — first measurement pass: the window has MOVED, and it is bigger than expected

**Verdict: the campaign's premise was right about the size and wrong about the mechanism.**  There is up to
**~50 % of a host-expert prefill's wall** recoverable on a partial-residency arena (much larger than the
1-3 % a naive read of the cache census suggests), but the carrier is **no longer an asynchronous H2D copy
with the SMs idle** — the delivery's own device gather (r-era `GGML_SCHED_DEVGATHER`) turned it into a
**link-bound kernel**.  That changes which of §4's mechanisms can work: **(C)/(D) co-scheduling, not the
copy-stream reordering of (A)**, and it means the first thing to build is a test of whether a decode step
co-scheduled with the gather is free.

Arms, all on 1 x R9700 (gfx1201), ROCm 10.1.0-gfx120X, `-c 8192 -b 2048 -t 8`, the 4908-token
`prompts/kld-corpus-35b-in-domain.txt` prefix (`/tmp/p4k.txt`, first 200 lines), `-n 1`:
`arms/arm.sh` (runner) + `arms/summ.sh` (re-parse) + `runs/*.log` (raw).  Sequential, never parallel.

## 2. The four findings

### 2.1 A fully resident arena makes the host-expert tier free — the design already works
`-ncmoe 40` with the whole set in the arena reads **5409 t/s against 5558 t/s for the same model with no host
tier at all** (−2.7 %), with `h=0.0000 (0/0 reaches)` — no reach ever misses.  This is r258/r266/r297's
in-place band plus the covering pinned mirror doing exactly what they were built for.  **There is nothing to
overlap at 100 % residency**, so any interleave work must be gated on residency, not shipped as a default that
"helps everywhere".

### 2.2 The cost of a partial arena is large — and it is the campaign's real budget
42 % residency costs **−56.5 %** of prefill (2415 vs 5409).  That is the pool of time a productive interleave
has to attack, and it is ~20x larger than the 1-3 % the cache's own `expert H2D traffic` census reports for
the same runs (572.7 MiB on P1, 790.0 MiB on H2) — **because that census counts arena fills only; it does not
count what the gather moves.**

### 2.3 The carrier moved from an async copy to a link-bound gather kernel
`GGML_SCHED_DEVGATHER=0` on the identical config (P1c) reads **1085 t/s against 2300 t/s** — the device gather
is worth **2.12x** on prefill, and with it the gather is what moves the bytes now
(`device gather: 468 calls (468 pool-backed), 0 … (neither tier)`), *not* the staging ring: there is not one
`H2D staging`/`stage_*` line in any arm, and `MOE_EXPERT_PREFILL_IN_PLACE=0` is inert here (2296 vs 2300)
because the in-place decision is not what feeds the prefill on a pool-backed table.

**Why this matters:** an async `cudaMemcpyAsync` on the compute stream is an SM-idle window (the original
thesis).  A gather *kernel* is not: the SMs are occupied, and the wall is lost to memory-latency stalls
inside a link-bound kernel.  The window did not disappear — it moved onto the SMs, where a co-scheduled
decode step can still fill it (concurrent kernels, and a link-bound gather leaves real occupancy for a
compute-bound second kernel) — but it cannot be filled by reordering copies, and **(A) is now the wrong first
mechanism**.

### 2.4 The old staging path is 2.1x worse and must not be re-proposed as a baseline
P1c is what the pre-r-era path did: whole-table uploads, 4.5 s against 2.1 s.  Any future arm that measures
"the staging path + an interleave" is measuring a path the delivery no longer takes for a pool-backed table at
any width.  Recorded so the campaign is not re-litigated on it.

## 3. What this does to the campaign

* **The thesis survives; the mechanism ordering changes.**  The window is `F_res ≈ (t_resident −
  t_partial)/t_resident` (up to **0.57** here when the arena covers 42 % of the set), not the copy census's
  fraction of the wall, and it is spent **inside the gather kernel**.
* **New mechanism (D), which now comes first: co-schedule a decode step with the gather.**
  No layer split, no suspension, no copy-stream reordering.  The gather launch is already a host control
  point inside `graph_compute`; a decode step submitted on a second sched's stream *after* the gather launch
  and *before* the consuming `MUL_MAT_ID` runs concurrently with it.  The condition is the same one §5.5
  named: the decode must be **fill-free** (`GGML_MOE_DEVREMAP` band, resident/identity tables) or it competes
  for the same link.
* **(A) copy-stream lookahead is demoted** — it does not apply to a kernel-mediated transfer.
* **(B) layer-chunk interleave keeps its value for a different reason**: it is the server-side control point
  for *how many* decode steps per unit of prefill, whatever the mechanism underneath.
* **(C) op-level yield** is subsumed by (D) and is now the simplest place to try it.

## 4. The next test (the one that decides (D))

**Is a decode step co-scheduled with the gather free?**  Two arms, no new policy, one build:

1. `G0` — the P1/H2 config alone: prefill t/s (baseline).
2. `G1` — the same prefill, with one decode step of a second resident sequence submitted at the gather launch
   (a debug hook, `MOE_PROBE_PF_OVERLAP=1`, single hard-coded step, `n=1`).
   * **PASS**: prefill within 3 % of `G0` **and** the decode token completes.
   * **FAIL**: prefill stretches by ≈ the decode step's own time (additive, i.e. no spare capacity).
3. `G2` — control: `G1` with the decode step's tables forced non-resident
   (`MOE_EXPERT_CACHE_MIB` on the second context) — must be *worse* than `G1`, or the arm is vacuous.

The instrument for `G1` is the archived `MOE_PROBE_132` decomposition re-derived for the prefill side (per-call
timers around the gather launch and the consuming op) — it is not needed for `G0`, only to attribute the wall.

## 5. Open questions this pass creates

1. Is the gather's occupancy really leaving SM headroom (a link-bound kernel) or is it already saturating the
   SMs?  One `rocprof`/`GGML_CUDA_OP_TIMING` reading of the gather kernel's achieved bandwidth against
   28.7 GB/s answers it, and if it is *not* link-bound then (D) has no window either and the campaign stops.
2. Every partial-arena arm here was driven by an **explicit** `MOE_EXPERT_CACHE_MIB` cap, i.e. the shallow-arena
   deployment.  Should the campaign target that band only (a box whose VRAM cannot hold its expert set), and
   say so in the README, rather than pretending it helps a saturated split?  (The 3-GPU field shape is
   100 % resident, so it is out of scope by §2.1.)
3. `-lme 8` (P3) is 1043 t/s and also shows `0 (neither tier)` — a sub-complement pool still never falls
   through to the pageable mapping on this shape, so the disk tier is not being exercised.  A disk-backed arm
   is a different campaign (block 12's transport), not this one.

# Pass 2 (same night) — the gather is timed, and it IS the campaign's window

Pass 1 established *that* the gather is the carrier.  This pass measures **how much of the wall it is**, with
a temporary instrument (`probe-gather-timer.patch`, applied with `git apply` to a scratch build dir
`build-probe`, **reverted from the tree afterwards**, never shipped): an event pair around
`ggml_backend_cuda_moe_cache_gather()` on the compute stream, folded with one stream synchronize per 64 calls
(`MOE_PROBE_PF_OVERLAP=1`).

| arm | arena | residency | gather calls | gather wall | prefill | **gather share** |
|---|---|---|---|---|---|---|
| `g_h1_gather_timed_100pct` | auto 18662 MiB = 100 % | no reach ever misses | **0** | **0 ms** | 904 ms | **0 %** |
| `g_h2_gather_timed` (`-ub 2048`) | 8000 MiB | h=0.658 | 468 | **1154 ms** (468 x 2.466, extrapolated past the last fold at 448) | 2033 ms | **~57 %** |
| `g_h2_gather_ub512` (`-ub 512`) | 8000 MiB | h=0.658 | 1287 | **~2750 ms** (1287 x 2.137) | 3870 ms | **~71 %** |

Three things follow, and they are the campaign's real result:

1. **The window is 57-71 % of a shallow-arena prefill's wall**, not the ~1 % the `expert H2D traffic` census
   reports.  At 2033 ms total and 904 ms for the same work at full residency, the excess (1129 ms) and the
   gather wall (1154 ms) agree to within the extrapolation — **the entire cost of a partial arena is the
   gather**, nothing else.
2. **The gate is residency, and it is sharp.**  100 % residency: zero gathers, and the host tier is −2.7 %
   against no host tier at all.  66 % reach-hit rate: 57 % of the wall.
3. **The gather is link-bound, so the SMs inside it are waiting rather than computing — which is exactly the
   property a co-scheduled decode step needs.**  The arithmetic: a 13080-slot arena is 109 slots of 256 per
   table, so 147 experts per table are not resident; at 0.607 MiB per Q4_K_M expert that is <= 89 MiB moved
   per call, and 89 MiB in 2.14-2.47 ms is **36-42 GB/s**, at or above this box's own **28.7 GB/s**
   calibrated H2D figure (so a given call moves rather fewer than 147 experts, and the rate lands at the
   link).  **The per-call cost is also nearly width-independent** (2.47 ms at `-ub 2048`, 2.14 ms at
   `-ub 512`, i.e. 4x fewer tokens per call costs the same), which is the signature of a
   bandwidth/latency-bound transfer rather than compute.

**What this does NOT yet prove**, and what `G1` must therefore answer: that the gather's SM occupancy leaves
*enough* headroom for a decode step to run in it without stretching the prefill.  A link-saturated kernel can
still occupy most warps with in-flight loads.  That is the `G0`/`G1`/`G2` test in §4 above, and it is now the
only thing between this campaign and a prototype.

**A second, cheaper line this opens.**  If the gather really is at the link rate, the prefill is spending
57-71 % of its wall moving bytes that a *bigger arena* would not have to move — so the competing answer to
this campaign is not an interleave at all but block 09's residency policy (more slots).  On this shape the
arena is VRAM-bound (28.7 GiB slab, 1.25 GiB reserve), so that path is closed here and the interleave is the
only lever — but a campaign that only pays on a *shallow* arena must say so (§5.2), because on a saturated
split the window is 0 by construction.

# Pass 3 (same night) — the baseline an interleave must beat, measured on the shallow-arena shape

Two attempts, one result, and one thing the box cannot do.

## 3.1 Two processes on one GPU: NOT FEASIBLE here (recorded so it is not retried)
The cheapest test of "is there spare capacity" would be a prefill process and a decode process side by side on
the same card.  `runs/g1-physics.sh` implements it; it **cannot run on this box**: each `-ncmoe 40` process
loads ~8 GiB of non-expert weights plus its arena, and the second process dies at load with
`ggml_backend_cuda_buffer_type_alloc_buffer: allocating 1921.34 MiB on device 0: cudaMalloc failed: out of
memory` (32 GiB card, two Q3_K_M contexts).  A smaller pairing would not be the shape under test.  **The
concurrency question therefore has to be answered inside ONE process — i.e. by mechanism (D) itself.**

## 3.2 The shipped mechanism on the same shape: `scripts/gate-prefill-duty.sh`
Run as shipped, on a **shallow arena** (`Q3_K_M`, 1 GPU, `-ncmoe 40 -lme 6`, `MOE_EXPERT_CACHE_MIB=6000`,
`-np 2`, 6000-token prompt, `--quick`):

| arm | prefill wall | prefill t/s | decode tokens during it | decoder ITL med/max |
|---|---|---|---|---|
| `DUTY=0` (baseline) | 4.25 s | 1413 | **15** | 14 / 882 ms |
| `DUTY=16` (shipped) | 6.51 s | 930 | **187** | 14 / 650 ms |

Gate verdict: **PASS**, 12.5x the decode tokens for a **1.53x** prefill stretch, lone prefill −1.3 %, text
identical, GPU clean.

**The number that matters for this campaign: 172 extra decode tokens cost 2.26 s of prefill, i.e. 13.1 ms per
token, against a standalone decode step of 15.2 ms (65.6 t/s on the same config).**  So the shipped mechanism
already converts *prefill time into decode tokens at ~86 % of the decode's own cost* — and the decoder's
*median* ITL does not move (14 ms), i.e. its resident band is served from the arena, not through the link.

**Why that is not yet a verdict on (D):** at step granularity the prefill's steps and the decode-only steps are
**serialized on one stream** — of course they add.  The measurement cannot distinguish "additive because the
software serialises them" from "additive because the device has no spare capacity", and those two have opposite
implications.  That distinction is exactly what (D) exists to test: submit the decode step *concurrently with
the gather*, in which case it either hides in the gather's SM-idle window (PASS) or it does not (FAIL).

**What pass 3 does establish** is the bar: an interleave is worth building only if it delivers more than
**12.5x tokens for 1.53x stretch** on this shape without the duty cycle's step-boundary burstiness.  The
expected shape of the win, if (D) works, is the same token count with a *smaller* stretch — the 13.1 ms/token
is the decode's own compute, so the recoverable part is whatever fraction of it the gather's link-bound warps
can absorb.

# Pass 4 (same night) — the headroom test: the gather DOES leave SM capacity, but only the gather

The prerequisite question for mechanism (D): can *anything* compute while the gather runs?  The probe's mode 2
(`MOE_PROBE_PF_OVERLAP=2`) launches a compute-bound kernel (64 blocks x 256 threads, a 2M-iteration
`__fmaf_rn` dependency chain, one store per block, **no link traffic**) on a second non-blocking stream right
after each gather, and records both walls.

| arm (`Q4_K_M`, 8000 MiB arena, `-ub 2048`) | gather ms/call | prefill | Δ |
|---|---|---|---|
| `g_h2_gather_timed` — gather alone (pass 2) | **2.466** | 2033 ms (2415 t/s) | — |
| `g_h2_burn_ub2048` — gather **+ a compute kernel co-scheduled** | **2.436** | 8677 ms (566 t/s) | gather **−1.2 %** |

**The gather is unaffected (−1.2 %) by a compute kernel running beside it — while the prefill as a whole is
stretched 4.3x.**  That is the campaign's answer in one line:

1. **The gather's window is real and free**: its warps wait on the link, so other work runs in the SMs at no
   cost to it.  A decode step *can* hide there.  This is the property pass 2 predicted from the rate
   (36-42 GB/s against a 28.7 GB/s link) and pass 4 has now demonstrated directly.
2. **Only that window is free.**  The same co-scheduled kernel stretches the prefill 4.3x, because the
   prefill's *compute* phases (the other ~43 % of the wall) are compute-bound and the co-scheduled work steals
   their SMs.  So an interleave must be **rate-limited to the gather window**, not merely "submit a decode step
   whenever the prefill is running".
3. **Therefore the ceiling is F (the gather share), not the prefill's wall**: ~57 % of a 2033 ms shallow-arena
   prefill (≈ 1150 ms) is available for a decode step's compute, i.e. ~75 tokens at this shape's 15.2 ms
   standalone step — against the duty cycle's one burst per prefill step.

**Accounting caveat, recorded so the numbers are not over-read.**  The burn kernel's own events are recorded on
a stream the drain does not synchronize, so the printed `burn=` figure is only the first fold's worth and the
per-call `burn` column is not trustworthy; the *stretch* (2033 → 8677 ms) is the honest measure of how much SM
time the probe kernel consumed.  The probe kernel was deliberately heavier than a decode step (~5 ms of
dependent FMAs); a real decode step is ~15 ms but does its own expert gathers, so its link use — not its SM use —
becomes the binding constraint once the arena band is resident (pass 3's decoder ITL was flat at 14 ms).

**The next build is therefore narrow and well-specified:** a decode step submitted at the gather launch, gated
so that at most F of the prefill's wall is given to it (the same time-bounded rule block 16's duty cycle
already implements, retargeted from step boundaries to the gather window), with the decode's band forced
resident so it does not consume the link the gather needs.

# Pass 5 (same night) — the smoothness A/B, and the work budget of the window

Two things: the A/B the maintainer named as the core benchmark, and a quantified budget for how much
co-scheduled work the gather window actually absorbs.

## 5.1 Smoothness A/B (`arms/smooth.py`, shallow arena, 1 GPU, `-np 2`, pinned slots)

`Q4_K_M`, `-ncmoe 40 -lme auto -c 32768 -b 2048 -ub 2048`, `MOE_EXPERT_CACHE_MIB=8000` (42 %-residency class),
a ~15 k-token prompt and a 600-token decode request, both fired with the prompt 0.4 s behind the decoder.
`itl_d_*` are the decoder's inter-token times **measured inside the prefill's own window** — the stall a user
feels while a prompt is being processed.  `pf_step_*` are the *prefill's* step intervals from the
`prompt_progress` events — the prefill's own smoothness.

| arm | prefill t/s | prefill wall | prefill steps | step p50 | step max | dec tokens during prefill | ITL p50 | ITL p95 | ITL max |
|---|---|---|---|---|---|---|---|---|---|
| `lone` (nothing decoding) | **3636** | 4.13 s | 10 | 514 ms | 576 ms | — | — | — | — |
| `DUTY=0` | **3552** (−2.3 %) | 4.22 s | 10 | 546 ms | 567 ms | **10** | 525 ms | 568 ms | 568 ms |
| `DUTY=16` (shipped) | **2544** (−30 %) | 5.90 s | 130 | **13.5 ms** | 590 ms | **131** | 13.5 ms | **519 ms** | 590 ms |

Read it as the maintainer described it:
* with the duty cycle **off**, the prefill barely notices the decoder (−2.3 %) but the decoder is starved:
  **one token per prefill step, 525 ms of p50 and p95 lateness** — the burstiness.
* with the duty cycle **on**, the decoder's *median* becomes excellent (13.5 ms) and it gets 13x the tokens,
  but its **p95 is still 519 ms** — because each cycle still ends with one whole prefill step — and the
  **prefill pays 30 %**.
* so the shipped mechanism cannot give both.  It is a burst trade, exactly as the campaign argued, and the
  target is now stated numerically: **~3550 t/s of prefill AND an ITL p95 in the tens of ms** — which nothing
  shipping today delivers.

## 5.2 How much co-scheduled work the window absorbs (`MOE_PROBE_PF_OVERLAP=3`)

The probe's mode 3 launches the compute-bound burn kernel only once every *N* gathers with a tunable size, so
the prefill's cost can be read against the *total* co-scheduled work.  Baseline: 2026 ms.

| iters x launches | total co-scheduled work | prefill | Δ |
|---|---|---|---|
| — (no burn) | 0 | 2026 ms | — |
| 200 k x 448 | 89.6 M | 2210 ms | **+9.1 %** |
| 400 k x 224 | 89.6 M | 2444 ms | **+20.6 %** |
| 800 k x 112 | 89.6 M | 2310 ms | **+14.0 %** |
| 2 M x 448 | 896 M | 8647 ms | +327 % |

The three middle rows are the *same total work* (89.6 M iterations) and read +9 to +21 % — one run each, so
that band is the noise floor of a single arm; call it **~+15 %**.  Converting with the 2 M row (14.8 ms of
concurrent work per launch at 448 launches ≈ 663 ms of solo work for the 89.6 M-equivalent): **roughly
two-thirds of the co-scheduled work is absorbed and one-third is charged**, which brackets the 57 % gather
share measured in pass 2 from the other direction.  Beyond the window it is charged ~1:1 (the 2 M row).

**The budget for this shape: ~1.15 s of free SM compute inside a 2.03 s prefill, i.e. ~75 decode steps at this
shape's 15 ms token.**  That is the number the interleave is worth, and it is *on top of* a prefill that keeps
its 3552 t/s — versus the duty cycle's 131 tokens at a 2544 t/s prefill with a 519 ms p95.

## 5.3 What this leaves, precisely

The physics is now measured from three directions (rate, share of wall, absorption curve) and they agree: the
window is real, it is ~57 % of a shallow-arena prefill, and a decode-shaped workload fits in it.  What does not
exist yet is the **place to submit it**: a decode step needs a `llama_context` that is not the one currently
inside `llama_process()`, i.e. a second context sharing the KV, and in `llama-server` all slots share one
context.  That is the one architectural decision the campaign needs from the maintainer (`README.md` §10.1),
and everything else is downstream of it.

# Pass 6 (same night) — the gather's cost is FIXED PER CALL, not bandwidth
> **SUPERSEDED IN PART BY PASS 7.**  The *observation* stands (the per-call cost does not scale with the
> non-resident set), but the *attribution* to host-side bookkeeping is **refuted by direct measurement**: the
> host body of `moe_cache_gather_host` is **0.037 ms per call**, 1.5 % of the 2.466 ms.  The carrier is the
> gather **kernel's own device time**, which is latency/occupancy-bound.  Read pass 7 with this section.

Pass 2 and 5 treated the gather as a link-bound transfer (36-42 GB/s of a 28.7 GB/s link, "link-saturated").
Two arms that move **2x different byte volumes at the same call count** kill that reading:

| arm | arena | non-resident experts/table | bytes per call (approx) | gather ms/call | prefill |
|---|---|---|---|---|---|
| `host_q8_default` (Q8_0, 84 % residency) | 26848 MiB | 256-215 = 41 | ~43 MiB | **2.605** | 2178 ms |
| `host_q4_8g` (Q4_K_M, 42 % residency) | 8000 MiB | 256-109 = 147 | ~89 MiB | **2.466** | 2031 ms |

Flattening the byte volume by 2x moves the per-call cost by **−5 %**.  A transfer that halved its bytes and did
not get faster is not transfer-bound.  So the ~2.5 ms per gather is **dominated by the per-call fixed work**,
and the *call count* is the cost: 448 calls x 2.47 ms = **1105 ms of a 2031 ms prefill**, i.e. the same ~55 %
share pass 2 measured, now attributed correctly.

## 6.1 What that fixed work is (read off the code, `moe_cache_gather_host`)

Per (table, ubatch) call, in `ggml/src/ggml-cuda/moe-expert-cache.cu:10017`:

1. `moe_cache_table(...)` + a **linear scan of `g_tables`** (120 entries) matching the master pointer,
   **under the cache's single global `std::mutex`** (`:10075-10099`).
2. `t.gprs_host.assign(n_experts, -1)` — a 256-entry vector rebuild, then a **loop over `t.expert_slot`**
   (`:10160-10166`).
3. a second **loop over `gpool->expert_slot`** for the pool tier (`:10167+`).
4. a `memcmp` of `n_experts` int32 (1 KiB) against `gprs_last`, with an H2D only when it changed (the H2D is
   already amortised — the *rebuild* is not).
5. **two kernel launches**: `moe_cache_gather_zero_heads_kernel` re-armed on every gather (`:10137`, r42) and
   the gather itself.

`GGML_MOE_GATHER_ONCE=1` restores a once-only head zero and is documented as an A/B arm, so item 5 is already
a measured ~3x-sensitive knob in the other direction — but nothing amortises items 1-3, which are per-call and
width-independent.  That is the same shape as the record's own finding for the *staging* path
(`MOE_HOST_POOL_STAGE_BATCH`: one launch instead of ~200 per-expert copies, worth +34 % in its day).

## 6.2 The win, and why it is a block-09/12 amendment rather than this campaign's mechanism

If the per-call fixed work went from 2.5 ms to ~0.6 ms, this shape's prefill would read **~2030 -> ~1100 ms
(~+85 %)**, and the same fraction applies to *every* shallow-arena host-expert prefill, including the ones this
campaign has been treating as "the budget for an interleave".  The estimate is an estimate: the split between
host bookkeeping and kernel time is inferred from the two arms above, not yet measured inside the call (the
probe prints only the combined stream span; the `host=` field I added does not print — see the caveat below).

It is **not** part of this campaign's interleave work: it is a change to the expert cache's gather path (blocks
09/12), it needs the delivery's own gates (byte-identical greedy text with the residency prior pinned, the
prefill-logit KLD, `gate-host-pool.sh` including the fill-fault/rollback arms, and `gate-moe-promise.sh`), and
it is a **maintainer decision** under `AGENTS.md`.  It is recorded here because this campaign found it and
because it changes the campaign's own arithmetic: **the "free window" is free because the gather is doing
per-call bookkeeping, so making the gather efficient is worth more than hiding it** — and the two are
independent (a cheaper gather shrinks the window *and* the wall).

**Caveat, recorded honestly.**  The probe's `host=` field (added for this pass) does not appear in the output —
the fprintf edit did not take, so only the combined stream span is measured.  The 2x-bytes/constant-time result
stands on its own (two arms, same call count, halved volume, same time), but "how much of the 2.5 ms is host
side" is inferred, not measured.  That is the first thing to instrument when someone picks this up: one
`ggml_time_us()` pair around the host body of `moe_cache_gather_host`, printed per call at `-lv 4`.

# Pass 7 (same night) — pass 6 REFUTED: the host work is 37 us, and the gather kernel is latency-bound

Pass 6 inferred that the gather's ~2.5 ms per call was per-call fixed *host* work, from the code path (mutex,
120-entry scan, two 256-entry map rebuilds, memcmp, two launches).  Measured directly, with a `ggml_time_us()`
pair around the host body of `moe_cache_gather_host` (`MOE_PROBE_PF_HOST`):

```
MOE_PROBE_PF_OVERLAP: gather calls=448 wall=1104.9 ms (2.466 ms/call) ...
MOE_PROBE_PF_HOST:    calls=448 host=16.4 ms (0.037 ms/call)
```

**The host body is 37 us per call — 1.5 % of it.**  The other 2.43 ms is **device time inside the gather's own
kernels**.  Pass 6's recommendation ("amortise the per-call bookkeeping, worth ~+85 % prefill") is therefore
**withdrawn**; the mutex, the scan, the map rebuilds and the memcmp together cost 1.5 % and are not worth a
block amendment.

Two further readings, both from single arms:

* `GGML_MOE_GATHER_ONCE=1` (drops the per-gather finite-head zero launch, r42's re-arm) reads **2026 ms vs
  2031/2039 ms** — no change.  So the second kernel launch is not the carrier either.
* 2.43 ms per call for a routed set of order **5-10 MiB** (the non-resident subset of one table's routed
  experts: the census's "neither tier" counter is 0, and the routed-set size per call is not printed, so this
  is an inferred range, not a measurement) is **~2-4 GB/s** — an order of magnitude below the 28.7 GB/s link,
  and it did not move when the non-resident set doubled (pass 6).  **The gather kernel is latency/occupancy
  bound**, not transfer bound.

## 7.1 What that means for the campaign (the thesis is restored, with a caveat)

Pass 2 called the gather "link-saturated" on the strength of 36-42 GB/s derived from *assumed* per-call bytes.
The measured 2-4 GB/s inverts that: the gather's warps are waiting on **memory latency**, with a lot of idle
SM capacity, which is the *best* possible case for mechanism (D) — and it is consistent with pass 4's direct
result that a co-scheduled compute kernel costs the gather only −1.2 %.

The caveat: with the gather at 2-4 GB/s, the *"cost"* of a shallow arena is not a transfer bill but a
**low-parallelism kernel** — so the cheapest win on this shape may be **making the gather kernel faster**
(occupancy, `n_split`, coalescing across the routed experts) rather than either hiding it or amortising its
bookkeeping.  That is a contained change in `moe_cache_gather_host`'s kernel — but it is a block 09/12 change,
it needs the same gates, and it needs one measurement first that nobody has taken: **the routed distinct-expert
count and the bytes moved per call**, both one counter away (print them at `-lv 4`).  With that, the kernel's
achieved bandwidth is known exactly and the win is sized instead of estimated.

## 7.2 The three levers, now correctly priced

| lever | where | what it would buy | status |
|---|---|---|---|
| **hiding the gather** (mechanism D: co-schedule the decode in the gather's latency window) | llama/server: a second context + a submission point | both objectives (§5.3): ~3550 t/s of prefill **and** a tens-of-ms ITL p95 | physics proven (pass 4), architecture missing — maintainer decision |
| **a faster gather kernel** (occupancy/coalescing) | `moe_cache_gather_host`'s launch config | up to the gather's whole ~55 % share, on every shallow-arena shape | sized only as an upper bound; needs the routed-set/bytes counter first |
| **fewer gathers** (a bigger arena ⇒ 0 calls at 100 % residency) | block 09 residency policy | closes the window entirely on a card that can hold the set (measured −2.7 % vs no host tier at all) | already shipped; VRAM-bound on a 32 GiB card with a 37.8 GiB set |

## 7.3 The lever this actually points at: ONE gather launch per layer instead of three

The call counts pin the structure: **448 calls over 3 ubatches = ~149 per ubatch for 120 host tables**, i.e.
**one gather per (table, ubatch)** — 3 per layer (gate, up, down), even though r297 merges the three roles into
ONE split and **they are driven by the same routing ids**.

And the per-call cost is nearly fixed:

| arm | bytes per call (inferred, relative) | calls | ms/call |
|---|---|---|---|
| `-ub 2048` | 1.0 | 468 | **2.466** |
| `-ub 512` | ~0.25 | 1287 | **2.137** |

A 4x smaller routed set costs 13 % less time.  So of the ~2.4 ms, **~2.1 ms is per-call fixed** (launch +
kernel latency on a small block count — the kernel comment itself says "8 chunks/expert -> ~64 concurrent
blocks for the usual 8 routed experts"), and only ~0.3 ms follows the bytes.

**Therefore the single highest-value contained change on this shape is to gather a layer's three roles in ONE
launch**, since they share the ids and (post-r297) live in one split:

* calls per ubatch: 120 → 40 (**3x fewer**)
* per-call fixed time saved: ~2.1 ms x 80 calls = **~0.67 s of a 2.03 s prefill**
* expected prefill: **~2030 → ~1360 ms (+49 %)** on this shape, and the same shape of win on every shallow-arena
  host-expert prefill (it is a per-(layer, ubatch) constant, so it also *reduces* the cost of small `-ub`/`-ib`
  chunks — which is what makes a smoothness knob affordable, §5.1).

That is a block 09/12 change (the gather path and the scheduler's split-input loop), it needs byte-identical
greedy text with the residency prior pinned, the prefill-logit KLD and `gate-host-pool.sh`, and it is the
maintainer's call.  It is recorded here as the campaign's **best throughput lead**, with the arithmetic above
and the caveat that the 2.1 ms fixed component is inferred from two `-ub` arms, not from a counter.

**What to measure to confirm it before writing it:** print the routed distinct-expert count and the bytes moved
per call at `-lv 4` (one counter), then one arm at `-ub 2048` gives the achieved bandwidth exactly.  If it lands
at 2-4 GB/s the fixed component is real; if it lands at 20+ GB/s the two `-ub` arms are hiding something and the
launch-merge idea is worth nothing.

# Pass 8 (same night) — the IDEAL scenario: no `-ncmoe` at all, and the window is exactly zero

The maintainer's question: *"a performance measurement on a fully resident expert set — no `-ncmoe` at all.  What
does the probe look like in that scenario?  There's no fetching to hide behind, but does the probe predict a
smoother prefill+decode experience with the campaign's premise?"*

`Q4_K_M` (21.1 GiB, fits a 32 GiB card), **no `-ncmoe`**, no `-lme`, `-c 32768 -b 2048 -ub 2048`, `-np 2`,
pinned slots, the same ~15 k prompt + 600-token decode.  Gates on this lens: `gather calls = 0` (there is no
host tier and no cache arena).

| arm | prefill t/s | steps | step p50 / max | dec tokens during prefill | ITL during prefill p50 / p95 / max |
|---|---|---|---|---|---|
| `lone` | **6350** | 10 | 291 / 368 ms | — | — |
| `DUTY=0` | **5996** (−5.6 %) | 10 | 315 / 382 ms | 11 | 311 / 382 / 382 ms |
| `DUTY=16` | **4293** (−32 %) | 130 | 8.1 / 383 ms | 132 | 8.1 / **141.6** / 383 ms |
| `DUTY=16`, `-ib 1024` | 3315 (−48 %) | 242 | 8.1 / 206 ms | 245 | 8.2 / 159 / 206 ms |
| `DUTY=16`, `-ib 512` | 2153 (−66 %) | 465 | 8.1 / 134 ms | 468 | 8.1 / 104 / 134 ms |

## 8.1 The three residency regimes side by side (same harness, same prompt, same settings)

| regime | `lone` prefill | `DUTY=16` prefill | duty tax | ITL p95 during prefill |
|---|---|---|---|---|
| **ideal — no `-ncmoe`** | **6350** | 4293 | −32 % | **141.6 ms** |
| host tier, arena covers the set (`-ncmoe 40`, 100 %) | 5187 | 3530 | −32 % | 369 ms |
| host tier, 42 % arena (`MOE_EXPERT_CACHE_MIB=8000`) | 3636 | 2544 | −30 % | 519 ms |

## 8.2 The answers

1. **In the ideal case the campaign's window is exactly zero** — `gather calls = 0`, so mechanism (D) has
   nothing to hide behind.  The only contention between a prefill and a decode there is **compute vs compute**,
   and pass 4 measured that to be charged ~1:1 (a co-scheduled kernel stretched the prefill 4.3x).  So *no*:
   the premise predicts no gain at full residency, and the measurement agrees.
2. **Smoothness tracks the prefill step time, not the gather**: 141 ms (step 315 ms) → 369 (383) → 519 (546).
   The ideal case is simply the smoothest because its prefill is the fastest, not because anything is being
   hidden.
3. **The duty tax is a constant ~32 % in all three regimes.**  It is a *step-granularity* trade (its cycle ends
   with one whole prefill step), not a host-tier effect — which is why it is the same number three times.
4. **Narrow `-ib` is a poor smoothness lever even in the ideal case**: p95 141 → 104 ms (−26 %) for
   prefill 4293 → 2153 (−50 %).  In the 42 %-arena case it is 519 → 284 for −59 %.  So "chop the prefill into
   small steps" is dominated everywhere; the ~10 ms ping-pong would need ~64-token prefill steps at 6350 t/s,
   where the GEMM efficiency has already collapsed.
5. **Therefore the campaign is, by measurement, a VRAM-starved-box mechanism.**  That is not a small market
   (it is every consumer card with a big MoE model) but it must be stated: the ideal shape gains nothing, and a
   *saturated* split has a 0 % window by construction.  With #1, the design implication is that the interleave
   should be **enabled by a measured residency deficit**, never shipped as a default that "helps everywhere".

# Pass 9 (same night) — the one-gather-per-layer lead: REFUTED as stated, but the launch SHAPE is a real win

Maintainer's instruction was to build one gather launch per layer instead of three.  Before writing it, the
arithmetic of pass 2/6/7 was re-derived against the *bytes*, and the merge cannot help:

* a prefill ubatch routes essentially **every** expert of each table (8-of-256 per token over >= 512 tokens
  saturates the set: 4096 draws over 256 experts covers 256), so the routed set is the same at `-ub 512` and
  `-ub 2048` — which is why the two arms' per-call time barely differs;
* the gather moves the **non-resident** subset, and that is a *volume* per (table, ubatch): Q4_K_M at 42 %
  residency = 147 experts x 0.607 MiB = **89 MiB** in 2.466 ms = **36 GB/s**; Q8_0 at 84 % = 46 x 1.06 MiB =
  **49 MiB** in 2.60 ms = **19 GB/s**;
* the three roles (gate/up/down) are three *different tables*, so merging their launches removes **no bytes**
  — and the host-side per-call work is already only **0.037 ms** (pass 7).

What the numbers *did* show is that the per-call rate depends on how much parallelism the launch exposes: 19 GB/s
when a call moves 49 MiB, 36 GB/s when it moves 89 MiB.  `moe_cache_gather_kernel`'s block count is
`n_experts * n_split` with **`n_split = 8`**, a constant chosen for the *decode* band's shape ("~64 concurrent
blocks for the usual 8 routed experts").  Swept it:

| `MOE_GATHER_NSPLIT` | Q8_0, 84 % residency (prefill wall) | Q4_K_M, 42 % residency |
|---|---|---|
| 8 (shipped) | 2134 ms (3 interleaved reps: 2133 / 2132 / 2138) | 2031 ms |
| 16 | 2000 ms | — |
| 24 | 2145 ms | — |
| **32** | **1983 ms** (1982 / 1984 / 1984) — **−7.1 %** | **1987 ms** — −2.2 % |
| 48 | 2252 ms | — |
| 128 | 2342 ms | — |

Then re-verified as a clean candidate build (`candidate-gather-nsplit.patch`, default 32, no probe code):
**1984 ms vs 2132/2139 ms with `MOE_GATHER_NSPLIT=8`**, i.e. −7.0 % twice, and the greedy text is
**byte-identical** (`103 chars sha=8261876a1e61` in both arms).

So the deliverable is **one constant plus an env override**, not a scheduler change: **`n_split` 8 -> 32** in
`moe_cache_gather_host`, `MOE_GATHER_NSPLIT=8` restoring the pre-change launch for an A/B.  The merge
(one launch per layer) is **not needed** — it would not remove a byte, and the parallelism it would add is
already obtained by the split index.

**Caveats.**  The two arms disagree on the optimum less than they agree (Q4 is flat 8..32, Q8 peaks at
16-32 and falls away after), so 32 is a safe default rather than a fitted one; a per-call volume model would
pick 16 for the high-residency end.  Also, only two volumes and one GPU were swept — a 3-GPU `-sm tensor` arm
(each device gathers its own slice, so the per-call volume is ~1/3) should be measured before this ships, and
`gate-host-pool.sh` + `gate-prefill-logits.sh` are the gates it needs.
