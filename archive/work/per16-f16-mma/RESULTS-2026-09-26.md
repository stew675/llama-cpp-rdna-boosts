# RESULTS 2026-09-26 — campaign setup + Phase-1 spike findings

**Outcome:** the per-16→F16 hypothesis is **not yet disproven, but two facts materially lower its
ceiling** and one design assumption was wrong.  No delivery code was touched; the fork tree is
clean.  The decision this raises is at the bottom — maintainer's call.

---

## 1. What was done

* Campaign branch + docs + tools (see `README.md` / `PLAN.md`).
* Baseline frozen in `MEASUREMENTS.md` (model + isolated GEMM + type landscape).  The Q6_K deficit
  reproduces exactly: pp32768 897 (Q6_K) vs 1129 (Q4_K_XL) vs 1207 (Q8_0), and 1466/1804/1955 on
  2-GPU `-sm tensor`.
* A standalone fused Q6_K→F16 WMMA spike was written (`kernel/q6k_f16_gemm.hip`) to answer the
  feasibility question before touching `~/llama.cpp`.

## 2. Finding A — the gfx12 F16 WMMA fragment is a trap for hand-rolled kernels

The gfx12 (RDNA4) `wmma_f32_16x16x16_f16` layout is **not** what a contiguous shared-memory read
suggests.  From the delivery's own `mmb.cu` shim:

> gfx12: 8 halves/lane ("two runs of four": `k = 4*hi + {0..3}` and `4*hi + 8 + {0..3}`),
> accumulator `m = 8*hi + e`; the C tile is `DATA_LAYOUT_J_MAJOR`, so `get_i`/`get_j` are swapped
> relative to the A/B tiles.

The standalone spike was still incorrect after two attempts at the layout, and ran at 0.14 TFLOPS
(a deliberately naive, unpipelined kernel — the number is not meaningful).  **Lesson for the
implementation: do not hand-roll the fragment; drive the kernel through `load_ldmatrix`/`mma` in
`mma.cuh` and/or the `mmb.cu` shim, which are self-consistent.**  This is a strong argument for the
**in-tree** Phase-1 path (the spike's fallback) rather than the standalone one.

## 3. Finding B — the 107 TFLOPS "F16" baseline is hipBLAS, not a tile kernel

`ggml_cuda_should_use_mmf()` (`mmf.cu`) returns **false for `src1_ncols > 16`**, so F16 prefill goes
straight to `ggml_cuda_mul_mat_cublas` (`ggml-cuda.cu:2364` → `:2384`).  The 107 TFLOPS measured at
`m=17408,n=512,k=5120` is therefore **rocBLAS**, and there is **no fast in-tree F16 tile GEMM for
prefill** to inherit.

Consequence: a fused Q6_K→F16 tile kernel's realistic competitor is the **int8 MMQ at 57 TFLOPS**,
not the 90-107 the README assumed.  The success gate must be "beats 57", and reaching 90 is not a
supported expectation.

## 4. Finding C — the delivery already has a fused dequant tile GEMM, and it loses

`mmb` is exactly "transform the weight once into a tensor-core-friendly form, consume with a dense
WMMA kernel" (bf16).  Forced onto Q6_K on RDNA4 it measures **639-733 t/s** vs MMQ **981 t/s**
(§3.3 of `MEASUREMENTS.md`).  Its dequant is scalar, so a *vectorized* fused F16 kernel is still an
open question — but the precedent is discouraging.

## 5. Consequence for the plan

| original assumption | corrected |
|---|---|
| a fused F16 tile kernel inherits ~107 TFLOPS | no in-tree F16 prefill tile kernel exists; the bar is 57 (int8 MMQ) |
| the standalone spike is the fast path | the gfx12 fragment layout makes it error-prone; use the in-tree `load_ldmatrix` path |
| per-16→F16 is near-certain to win | unproven; `mmb` (fused bf16) currently loses |

The **general** lever from `archive/work/q8-prefill-tuning/` is unchanged and arguably bigger: the MMQ kernel
runs at 31-34 % of the int8 issue ceiling **with no double-buffering**, so a software-pipelined MMQ
would lift *every* quant type (Q6_K included) and would not change numerics.  Per-16→F16 and MMQ
double-buffering are complementary, but the pipelining has the better risk/return.

## 6. Decision needed

Two viable next steps; both are real kernel projects:

* **(a) Continue the per-16 PoC** — implement the in-tree fused F16 path (Phase 1 of `PLAN.md`,
  using `load_ldmatrix`/`mma`), gate Phase-1 on "correct **and** > 57 TFLOPS".  If it passes, tune;
  if it fails, archive.
* **(b) Pivot to MMQ double-buffering** — attack the shared 31-34 % ceiling.  This is `archive/work/q8-prefill-tuning/`'s
  parked "real kernel project", helps all types, and keeps bit-identical output.

Recommendation: **do (a) as the Q6_K PoC the maintainer asked for**, but time-box it — the corrected
ceiling means the expected win is "57 → maybe 65-75", not a near-doubling, and (b) is the larger
prize.  Awaiting the maintainer's call before writing the in-tree kernel.
