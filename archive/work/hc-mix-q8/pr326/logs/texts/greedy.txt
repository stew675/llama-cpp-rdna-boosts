# Hash Table Collision Handling: A Detailed Technical Explanation

## 1. Introduction to Hash Tables and Collisions

A **hash table** is a data structure that maps keys to values using a **hash function**. The hash function converts a key into an index into an array (the "bucket array"). Ideally, each key maps to a unique index, but in practice, **collisions** occur when two or more distinct keys hash to the same index.

### Why Collisions Are Inevitable
- The hash function maps a potentially infinite set of keys to a finite number of buckets.
- By the **Pigeonhole Principle**, if the number of keys exceeds the number of buckets, collisions are guaranteed.
- Even with fewer keys, poor hash functions or adversarial inputs can cause frequent collisions.

### Key Metrics
- **Load Factor (α)**: `α = n / m`, where `n` is the number of stored elements and `m` is the number of buckets.
- **Collision Rate**: The frequency with which insertions result in a collision.
- **Time Complexity**:
  - Best case: O(1) for search/insert/delete.
  - Worst case: O(n) if all keys collide (degenerates to a linked list).

## 2. Collision Resolution Strategies

There are two primary families of collision resolution:

| Strategy | Description | Pros | Cons |
|---|---|---|---|
| **Separate Chaining** | Each bucket holds a linked list (or other container) of entries. | Simple, handles high load factors, no clustering. | Extra memory for pointers, cache-unfriendly. |
| **Open Addressing** | All entries are stored in the bucket array itself; collisions probe for the next empty slot. | Cache-friendly, no extra memory for pointers. | Requires careful load factor management, deletion
