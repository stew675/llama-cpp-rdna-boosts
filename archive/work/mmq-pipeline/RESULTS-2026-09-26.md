# RESULTS 2026-09-26 — Phase 1: geometry + register/LDS headroom → **GO**

**Decision: GO with design (2)** — LDS double-buffering at a smaller tile (`I=64`), which costs no
base rate and needs no extra registers.  Design (1) (register-staged prefetch at the default
geometry) is ruled out by register pressure.

Method: `test-backend-ops perf` (isolated ffn) + a one-off `--save-temps` compile of
`mmq-instance-q8_0.cu` to read the kernel resource metadata.  No delivery code changed.

---

## 1. The alternative geometry is free

`GGML_CUDA_MMQ_J_MAX=64` selects the `(nthreads=128, I=64, J=64)` config.  At the 27B ffn shape
`m=17408,n=512,k=5120`:

| type | default (`I=128, J=128`) | `J_MAX=64` (`I=64, J=64`) |
|---|---:|---:|
| Q8_0 | 83.66 TFLOPS / 1090.9 µs | **83.47 TFLOPS / 1093.5 µs** |
| Q6_K | 56.97 TFLOPS / 1602.1 µs | **57.17 TFLOPS / 1596.4 µs** |

⇒ shrinking the tile to free LDS costs **nothing** — good news, because the pipeline needs the room.

## 2. Register headroom rules out design (1) at the default geometry

`mul_mat_q<GGML_TYPE_Q8_0, J, fallback=false>` from the code-object metadata (max 256 VGPRs/thread):

| J | VGPRs | SGPRs | VGPR spills | private bytes |
|---:|---:|---:|---:|---:|
| 64 | 130 | 33 | 0 | 0 |
| 96 | 173 | 33 | 0 | 0 |
| 112 | 194 | 33 | 0 | 0 |
| **128** | **214** | 33 | 0 | 0 |

A register-staged `tile_x` prefetch at `I=128` needs ~`I*sram_stride/nthreads = 128*70/256 = 35`
extra VGPRs/thread → **> 256, guaranteed spill**.  (The `fallback=true` J=128 kernel is already at
256 VGPRs with 25 spills.)  So design (1) is dead at the default geometry.

## 3. LDS budget confirms design (2)

64 KiB/block.  At `I=64` (Q8_0 stride 70, `tile_x = I*70*4`) and `J=64` (`tile_y = J*33*4`):

| buffers | bytes |
|---|---:|
| `2 × tile_x` = 2 × 17 920 | 35 840 |
| `2 × tile_y` = 2 × 8 448 | 16 896 |
| header | 512 |
| **total** | **~53.2 KiB** ✅ |

Both the **weight and activation** tiles can be double-buffered at `I=64/J=64`.  (`I=64/J=128` with a
single `tile_y` is also 52.7 KiB, if the wider J is preferred.)

## 4. Why this is expected to pay

At the ffn shape, Q8_0 takes 1.09 ms for 45.6 G-MAC:

| component | time |
|---|---:|
| pure WMMA at the 174 T-MAC/s ceiling | 0.26 ms |
| weight DRAM read (~89 MB at ~600 GB/s) | ~0.15 ms |
| **measured** | **1.09 ms** |

**~0.68 ms (62 %) is unaccounted for** — that is the serial load→barrier→compute→barrier chain plus
issue stalls, exactly what the pipeline attacks.  (A `rocprofv3` stall-counter confirmation is still
worth doing, but the arithmetic already justifies the go.)

## 5. Plan

* Add an `I=64, J=64` config row for the target types (or reuse `J_MAX`'s) and switch the campaign
  build to it.
* Double-buffer `tile_x` (and `tile_y` if the measurement supports it), one `__syncthreads()` per
  stage, `GGML_CUDA_MMQ_PIPELINE` gate, **preserve the `vec_dot(k00=0)`/`vec_dot(k00=32)` sequence**.
* Validate bit-identity **before** the speedup (Phase 3).
* Leave the `fallback=true` (non-128-row) kernel unpipelined — it is at the register limit.
