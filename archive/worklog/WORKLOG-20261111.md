## 261111.036 (r265) -- block 16's prefill span plan read the WHOLE table minus the used residents: a 38-token prompt went 3.2 -> 26.6-29.7 t/s, and a wide prefill +9.6 %

**The report.**  A few-hundred-byte prompt in the WebUI "looks like it reads the entire set of model weights from
the drive several times" on `Qwen3.5/122B-A10B/Q5_K_XL` with `-lme 75`, even though the census says the store holds
94 % of the expert set.  It did: the prefill stream's read plan was built from the wrong set.

**Root cause (block 16, P5).**  `moe_cache_prefill_stream()` builds its coalesced spans from "`map[e] < 0`", but
`map[]` is populated only for an expert that is **both routed by this ubatch AND resident**.  So a "run of missing
experts" was a run of *"not (used and resident)"*, which also covers every expert the ubatch does not route to --
and those were read from storage, then **not counted** (the census added up the used bytes a span served), so
`MiB/span` could print *below* the smallest expert (1.02 MiB against a 2.06 MiB floor) and hide it.  On a wide
prefill the wrong set nearly equals the right one (`used ~= all`), which is why the campaign measured this shape as
clean; on a short prompt it is most of the table.

**Fix (block-16 amendment).**  The run set is `used[e] && missing(e)` (breaking at the first expert that is not used
or is resident), and `g_pf_span_bytes` is accumulated where each span's H2D is issued (its real length), so the
census cannot hide the class again.  No new environment variable, no semantic change: it fetches strictly less of
the same bytes, from the same sources, into the same destination.

**Measured (`halo`, gfx1151, 122B-A10B Q5_K_XL: 81.06 GiB expert set, 147 tables, `-lme 75` -> arena 241/256 slots
per trunk table = 78 239.3 MiB, head pinned outside; `-ub 4096 -b 4096 -ngl all --fit off --spec-type draft-mtp`,
prior frozen):**

| arm | metric | before | after |
|---|---|---:|---:|
| 38-token prompt (1 pass) | spans / span read time | 8 550 / 10 031 ms | **684 / 61 ms** |
| | hook total | 11 093 ms | **239 ms** |
| | prompt eval | 3.2 t/s | **26.6-29.7 t/s** |
| 24 576-token prefill (6 passes) | spans | 23 985 (1.02 MiB avg) | **10 353 (2.37 MiB)** |
| | read time / ring wait | 5 307 ms / 2 158 ms | **1 118 ms / 6 ms** |
| | prefill | 499.9 t/s | **547.7 t/s** |

The used / read / arena-D2D census is byte-identical in both arms (wide: `used 519 970.8 MiB`, `read 24 486.7 MiB`

## 261111.034 (docs-only, NO delivery change) -- why a `97.5 %` arena hit rate still reads **1-1.5 GB/s** off the drive on the 122B Q8_0 (the miss arithmetic of the GTT arena)

**The question (field report).** `Qwen3.5-122B-A10B-Q8_0`, `-lme 90`, one decode stream on `halo`: the per-turn
line reads `MoE arena = 0.97xx`, decode is ~11 t/s, and the drive is sustaining 1-1.5 GB/s.  "If it is missing 1 in
40 reaches, isn't that drive rate too high?"

**No -- it is exactly the miss traffic.**  The hit rate is per **expert reach**, and a miss costs a WHOLE expert:

| quantity | value | where it comes from |
|---|---|---|
| one expert (Q8_0) | 3 x 3072 x 1024 params -> **10 027 008 B = 9.5625 MiB** | `ffn_{gate,up}_exps [3072,1024,256]`, `ffn_down_exps [1024,3072,256]`, all Q8_0 (3 342 336 B each) |
| reaches per token | 8 used experts x 48 trunk MoE layers = **384** | `expert_used_count 8`, `block_count 49` (block 48 = the nextn/MTP head, pinned and resident) |
| misses per token at h = 0.975 | 384 x 0.025 = **9.6** | 1 miss per ~40 *reaches*, i.e. per ~5 layers -- not per token |
| miss bytes per token | 9.6 x 9.5625 MiB = **91.8 MiB/token** | |
| **drive rate at 11 t/s** | 91.8 MiB x 11 = **1010 MiB/s** | |

So 1.0 GB/s is the *expected* figure at h = 97.5 % and 11 t/s; 1.5 GB/s is h ~= 96.4 %.  The other direction is the
useful one: 92 MiB/token over a ~1.2 GB/s drive is **~80 ms of the 91 ms** a token takes at 11 t/s -- the miss
traffic **is** the decode budget here, which is why this box reads 11 t/s and not 20+.  Each point of hit rate is
384 x 0.01 x 9.5625 MiB x 11 t/s ~= **0.4 GB/s** of drive traffic.

**Why so many misses at `-lme 90`.**  Block 16's GTT store: the expert set is 48 x 256 x 9.5625 MiB = **114.7 GiB**
(+2.4 GiB MTP head) against a 123 GiB box, so `-lme 90` is *below* the set -> the store is the **ARENA**, not a
placement: 90 GiB / 117 GiB ~= 77 % of the *experts* resident, while the routing is skewed enough that 77 % of the
slots still catch 97.5 % of the *reaches* (the LFRU working as designed, not a contradiction).  A miss is one
buffered `pread` of the expert straight into the vacated slot (`fill_slot_direct_locked`) and it **drains the
compute stream first**, so the ~10 misses/token are serialized on the decode path.  Confirmed from the log at
`-lv 4` (`MoE expert cache: h=...`, `GTT arena tier: ...`, `direct slot fills ... MiB/s`, `fill-side overlap
headroom ... ms/fill`) and from `/proc/<pid>/io read_bytes` == misses x 9.5625 MiB.

**Levers, in order.** (1) A quant whose whole expert set fits the budget turns the store into a **placement**
(static, zero decode reads) -- Q4_K_XL's set is well under this box's 90 %-of-`MemAvailable` ceiling (~105 GiB),
which is the big one; (2) raise `-lme` toward that ceiling (`-lme 100` is legal here), worth ~0.4 GB/s per point of
hit rate; (3) the discrete knobs (`MOE_HOST_POOL_*`, `MOE_EXPERT_CACHE_MIB`) do not apply -- there is no pinned
host pool on an APU -- and `MOE_EXPERT_CACHE_TOUCH` is a documented no-op on this tier (every miss fills).

## 261111.033 (r264) -- `TODO` #300 RETIRED: the attendance pool is refused on a shared host/device pool **by design**, and `--fit` stops advertising placements that the model+device will refuse (it printed a wall of red for a feature nobody asked for)

**The report.** On `halo` (gfx1151 Strix Halo, UMA, 123 GiB) the field command
`llama-server -m Qwen3.5-122B-A10B-Q8_0 -lme auto -ub 4096 -b 4096 -c 102400` -- which **runs fine** (11 t/s, the
GTT store streaming, see 261111.034) -- printed, before the load, an ERROR block ending in **8 lines about
`--kv-window` and `--kv-attendance-pool`**: `common_params_fit_impl: two placements can buy the KV back ...`.  The
operator had not asked for either, the model is a **qwen35moe** trunk (no sparse indexer, so the pool has nothing
to serve) and the device is an **APU** (so the pool is refused anyway, r236).  The kernel of that sequence is
also in `TODO` #300 as "the pool is INCORRECT on a UMA device, the fix is owed".

**The decision: `#300` is retired, not fixed.**  The pool is a **distinct-memory** design: it buys *device* memory
back by keeping the authoritative KV in a **pinned host mirror** and caching only the indexer pages the sparse
decode selects.  That trade only exists where the host and the device are separate tiers.  On a shared host/device
pool they are one: the KV is already in the memory the GPU reads, so there is nothing to buy back, and the
two-tier resolve (MARK/CLAIM/MAP+FILL, `kv_pool_invalidate()`, the dirty-refill protocol) has no second memory kind
to be correct against -- which is exactly what r236 measured (a *fully resident* pool still verifying ~93 M
mismatched bytes against its own mirror, a different text every run).  Chasing the resolve would leave a
placement that cannot help on the one device it would then claim to support, so the item is closed as **"not
supported on a shared host/device pool, by design"** and its record moved here from `TODO.md` (which per policy
carries no closed items).

  device memory back ... here they are one ... NOT SUPPORTED on such a device, by design") instead of pointing at an

experts").  The same DRAM is touched in both shapes; only one makes the excess reclaimable.  The cap costs the

`=0` force placement) and is no longer parsed as `getenv(...) != nullptr` -- that made `=0` *enable* the tier.  The
census names the reason in both directions:

    -lme 4 [auto: -lme asks for a 4096.0 MiB cap on non-swappable expert memory against a 18662.5 MiB set, so the
             excess streams from the file-backed page cache (reclaimable) instead of becoming anonymous memory]
            -> the GTT store is the MoE ARENA
    auto: 80% of MemAvailable -> a 95584.6 MiB cap -> ... 120 tables / 30720 slots (18662.5 MiB) resident ...
            the WHOLE set                                        (placement)

the head also exists as a **separate draft model** -- `mtp-Qwen3.8-Flash-Next-shared-Q8_0.gguf` (arch `qwen4exp`,

**Answer: yes, and on UMA nothing needs pinning there — but reaching that answer found two real bugs**, both
pre-existing (P2), both in the "one region, many loads" seam:

1. **A failed carve is FATAL, and the code claimed the opposite.**  `alloc_buffer`'s comment said "a DECLINE, not
   an abort: the loader places the tensors it cannot fit in the plain device buffer".  It does not --
   `llama_model.cpp` turns a null buffer into `unable to allocate ROCmGTTStore0 buffer` and the model does not load.

   its two rows under **different expert tiers**.  `free_buffer` now returns the range to the allocator.

can still hand out; that free space is the whole budget, and the load: never sizes/grows the region (the extent is
the first model's, clamped for *that* model against `RLIMIT_MEMLOCK` and 90 % of `MemAvailable`); **never takes the

carving the head out of it drops the trunk's residency from 100 % to 69 %, measured as 2 550 of 8 192 MiB);
**adopts** the live region when its set fits free space (`open` accepts a *smaller* request, still refuses a
larger); and otherwise **declines cleanly** with a message that names the case.

**The maintainer's decision, implemented**: the nextn (MTP) head is metadata overhead read on every draft step, so
it is pinned in the GTT store and is **not** counted against `-lme N`.  Three things came out of implementing it:

* **The head is not a second model.**  An MTP draft is a `LLAMA_CONTEXT_TYPE_MTP` context on the target's own
  weights (`/*.shares_model =*/ !has_draft`), so its expert tables (`blk.40.ffn_{gate,up,down}_exps` on 35B-A3B)
  are ordinary candidates of `plan_gtt_expert_store()`.  They are now partitioned by layer (`>= n_layer_trunk`).
* **They were in the set even when never loaded.**  `weights_map` is the GGUF index, so the set was counted as

**How it is wired.**  `-lme` buys TRUNK residency; the store's extent is `min(budget, trunk padded) + head padded`.
Placement mode places the head's tables **first and unconditionally** (`host_experts_store_pinned`, named in the
census).  Arena mode passes the head's **layer indices** to `moe_cache_preflight_store()`, which sizes those layers
at `slots = n_experts`, excludes their per-expert bytes from `dev_one_bytes`, subtracts the head's bytes from the
per-device budget, and keeps head layers out of the identity-aware drop pass (they are already full, and charging
them to `remain` twice would drop trunk layers).  A model whose expert tables are *all* head keeps the uniform
arithmetic, or `-lme` would stop being a cap.

  `weight_buft_supported()` check may be applied to it**: a host master reaches the GPU through the scheduler's
  OFFLOAD path (`ggml_backend_sched_backend_id_from_cur`), not through `supports_buft`, and asking the device to
  "support" a host buft silently leaves the tensors on the device (measured: the whole 20 583 MiB model on the

* An **identity-mirror guard**: on this tier the master is pageable, so the identity fast path (mirror every

**What does NOT work, and must not be papered over.**

1. **The tier registers no tables.**  `MoE expert cache: ... tables=0, slots=0, arena=0.0 MiB` in the census of an
   arena arm that otherwise produced identical text.  Identical text therefore proves nothing: with no table, the
   op reads its own buffer and the arena is never touched.  **A text arm is not evidence for this tier** -- the
   first thing the next session must do is make `tables=` non-zero, and the place to look is why the scheduler's
   host-weight registration hook is not reached for a host-`mapped` expert weight on an APU
   (`moe_cache_register_host` / `moe_cache_pending` / `moe_cache_tables_complete_locked`).
2. **Arena mode can allocate without bound.**  It took this 123 GiB box to full memory + swap **twice**.  The

   anonymous memory.  Suspects, in order: the pageable-master fill path's runtime staging, the prefill staging
   ring (`span_buf_ensure`), and the heat/ghost mirrors.  Not diagnosed -- the box was not worth a third attempt.

**State of the branch after this entry:** with `MOE_EXPERT_GTT_ARENA` unset (the default) an APU behaves **exactly**

**Campaign-scope** (no `patches/`, no `release.json`, nothing applied to the fork, no gate owed).  The cumulative

**Landed (P3a-1): the store is an allocator, not a bump pointer.**  A first-fit over a sorted, coalesced free list

**Four seams read out of `moe-expert-cache.cu`, three of which simplify P3:**

1. **The MUL_MAT_ID interception already exists**: `ggml_cuda_mul_mat_id()` asks `moe_cache_get_table()` at its
   entry and re-dispatches with `src0c.data = arena` + the remapped ids.  Base pointer only -- no new op, no
   dispatch change, no copy.  Its `(layer, role, device)` semantic fallback is what finds a table the scheduler
   never aliased, which is exactly the APU case (the expert weight is not a host-buft input there).
2. **`access_locked()` is the residency policy already**: hit → `arena + slot*stride`, free slot → take it, full →
   LFRU victim (smallest decaying count, tie → oldest), with the `admit=value|touch` doorkeeper.
3. **The transient band is not needed for the core loop.**  `access_locked` only *rejects* a miss when a cold path
   exists; with none, its own comment says "every mode fills and the policy is a no-op".  On an APU the in-place
   cold read of a pageable mapping IS the fault (no `PageableMemoryAccess`, no XNACK), so `g_cold_uva` must be
   false for this tier and every miss evicts+fills.  Nth-touch admission becomes a priced P3b refinement instead
   of a prerequisite -- §5.1's rationale does not survive the measurement.
4. **The master is the model mapping**, and the fill must be a plain host `memcpy` into the registered slot (the
   measured warm arm, 12.8 GB/s) -- `fill_slot_from_host`'s pageable branch does `cudaMemcpyAsync(H2D)`, which is
   the delivery's known-bad path on RDNA.

So P3 is: **the store is the arena, the model mapping is the master, the cache is the policy** -- the discrete
path's own `--host-experts pool` shape with the pool replaced by the GTT store and no pinned master.  Staged
P3a-1..3 (arena, then holes) → P3b (evictions, a >RAM model) → P3c (nextn pinning); the table with each stage's
verify criterion is in `IMPLEMENTATION.md` P3.0.

## 261111.013 (wip, NO delivery change) -- probe 16: `hipHostRegister` does NOT pin, so the GTT store is reclaimable and the "budget is a reservation" claim is FALSIFIED -- `mlock` is the fix, and it is a decision

**Campaign-scope** (no `patches/`, no `release.json`, nothing applied to the fork, no gate owed).  New probe
[`archive/work/apu-expert-gtt/probe/16-reclaim-pressure.cpp`](archive/work/apu-expert-gtt/probe/16-reclaim-pressure.cpp); record
[`MEASUREMENTS.md` §15](archive/work/apu-expert-gtt/MEASUREMENTS.md); the claim it overturns is corrected in
[`README.md` §5](archive/work/apu-expert-gtt/README.md) and `IMPLEMENTATION.md` P1.2, with the open decision as README §7 Q11.

**The question.**  `README.md` §5 called the `-lme` budget "a real reservation" on the strength of probe `09`: a
registered range keeps 1 048 576 of 1 048 576 pages after `fadvise(DONTNEED)` **and** `madvise(DONTNEED)` where
the unregistered control releases all of them.  That is a *user-initiated* discard.  The kernel's own reclaim
under memory pressure is a different mechanism, and the campaign had it listed as owed.

**The measurement.**  Five arms, each in its own process inside a memory cgroup
(`systemd-run --user --scope -p MemoryMax=6G -p MemorySwapMax=4G`, `PROBE16_HOG_MIB=4096`) so the pressure is
real but contained; 2 048 MiB region + 2 048 MiB unregistered control; the **GPU read is the first touch** after
the pressure (a host read would fault the pages back and hide the case).  Every arm's pressure was real: the
control lost 17-2 048 MiB and the cgroup reached `memory.max` with 2.1-2.2 GiB in swap.

| arm | pages taken (MiB) | huge pages after | GPU read after | `Unevictable` |
|---|---|---|---|---|
| `reg` -- `mmap`+THP+`hipHostRegister(ReadOnly)`, **the GTT store's own backing** | 1.1 / 28 / 212 / 436 (0 in 2 runs) | **split every run** (2048 -> 626-1 066) | 29-36 ms when <= 28 taken, **524 ms** when 436 was | **0** |
| `reg_w` -- registered writable | 286 / 394 (0 in 1) | split (2048 -> 812-1 150) | 78 / 395 / **2 191** ms | **0** |
| `hostalloc` -- `hipHostMalloc` (a pinned allocation) | 86 (0 in 2) | never had any | 48 / 183 ms | **0** |
| **`mlock`** -- `mmap`+THP+**`mlock`**+register | **0, 0, 0, 0** | **2048 preserved** | **26-28 ms** | **2 048** |

**Four findings.**
1. **`hipHostRegister` on an `mmap` region does not pin it on this box.**  The kernel splits the THPs every run and
   swaps 0-436 MiB of a 2 GiB region out.  (`hipHostMalloc` held in 2 of 3 runs, so it is not absolute either --
   but it is never THP-backed, which is what the delivery's `ROCm_Host` master trades.)
2. **It is a slow failure, not a fatal one, and it is one-off.**  The GPU read returned the right bytes in every
   arm and run -- no `HSA_STATUS_ERROR_MEMORY_FAULT`, the driver re-faults the range at submission -- but the first
   read that touches the swapped part pays **12-37x** (524 ms and 2 191 ms against 42-59 ms), and the second read
   is back to 41-44 ms.  A swapped-out GTT store does not corrupt: it stalls.
3. **Only `mlock` is a reservation, and it is the only arm the accounting reports**: `Unevictable` / `Mlocked` /
   `smaps Locked` = 2 048 MiB there, and **0** in every other arm *while being reclaimable*.  It also keeps the
   huge pages and the read rate.
4. **THP splitting alone costs nothing measurable** (29-36 ms where 0-28 MiB was taken) -- the cost tracks the
   bytes actually swapped, not the split.

**Consequences, and what is deliberately NOT done yet.**  `-lme`'s sizing arithmetic stands unchanged
(`MemAvailable` is charged the same way), and no fill path or census field depends on this.  But P2 ships
**without** `mlock`, so `-lme` is a sizing *intent*, not a guarantee, and the docs now say so.  The fix is one
call plus one census field, and it needs the maintainer's decision because it costs `RLIMIT_MEMLOCK` (unlimited
on `halo`, **8 MiB on a stock desktop**): README §7 Q11 lays out refuse / best-effort / don't, and recommends
best-effort with `mlocked MiB / extent` in the census.

Also recorded in this entry: the naming rule (**never a bare "store"** -- always "GTT store"), the confirmation
that **the GTT store IS the expert arena** (P3 points the cache's slot allocation at it; "arena" alone still means
the slab's), and that the **nextn/MTP head's tables are pinned outside `-lme`** (P3 implements the accounting).

**Maintainer's decisions on the report (2026-11-11), recorded so they are not re-asked:**

* **Best fit, not strict fit** for `-lme N`: the extent is the budget and the carve may sit up to one expert table
  under it (6 144.0 vs 6 116.0 MiB at `-lme 6`), and that is what ships.  P3 makes the two converge on its own;
  nothing to change.
* **Linux only for now.**  Windows support is a later session.  The GTT store declines there and the run keeps
  today's behaviour, and the platform-specific part is deliberately **one** `#if !defined(_WIN32)` function
  (`gtt_store_create_locked()`) so a Windows arm replaces that function and nothing else -- the buffer type only
  needs a host-writable backing and the fill is `read_raw()` into `tensor->data`, both of which Windows has.
* **The page-cache-bound load fill is owned elsewhere**: a separate development line is adding explicit buffered
  reads instead of the mmap-only load, because the page cache chokes under low-free-memory conditions.  The GTT store
  inherits it for free -- its fill is already a buffered `pread` into the slot.
* **Naming: never a bare "store".**  It is always a **GTT store** (or "GTT expert store") in code, in the `-lv`
  census and in records -- so it cannot be read as disk storage, and cannot be confused with the slab's **arena**,

* **The GTT store IS the expert arena** (decision 2026-11-11), i.e. P3 points the existing cache tables' slot
  allocation at it instead of at the slab/`hipMalloc` arena, reusing admission, LFRU, the remap and the censuses.
  The word "arena" alone still means the slab's; say "GTT store" when you mean this one.
* **The MTP (nextn) head's expert tables are PINNED in the GTT store and NOT counted against `-lme N`** (the head's

  candidate set (35B-A3B: 123 = 40x3 trunk + 3 nextn) -- because in P2 everything resident is pinned; it moves with

  store today; it keeps its layer's device buffer, so it stays readable and text is unchanged (README §7 Q10).

**The new shape.**  The resident expert set is ONE anonymous region -- `mmap` + `MADV_HUGEPAGE`,
`hipHostRegister(Mapped|ReadOnly)`, sliced into per-expert slots -- with **no pinned master, no host pool, no
arena and no slab**.  Residency is the delivery's existing heat table + slot map; a miss drops the coldest entry
(a **table** operation) and loads straight into the vacated bytes, then continues; prefill streams per layer only
the experts that are not already resident.  The delivered host-expert tier (`-ncmoe`/`--host-experts`) stays
refused on UMA exactly as r236 left it -- this is not that tier.

**What killed the old plan is in its own probe log.**  The 2026-11-09 plan had to keep a staging/bounce ring for
every disk fill, because `pread(O_DIRECT)` into a `hipMalloc` GTT buffer is **`EINVAL`**
(`MEASUREMENTS.md` §7) -- so its headline "an eviction moves no data" only ever applied to the host tier, and
the disk tier stayed a copy.  `pread(O_DIRECT)` into an **anonymous** buffer is **3.6 GB/s** (§4).  An anonymous
registered region is therefore the only backing on which a *zero-copy load into the vacated slot* is possible at
all, and choosing it deletes the pool, the staging ring and the arena from the UMA path in one move.  The old
plan's **P1** (enable `--host-experts pool` / `-lme auto` on `IGPU` via the `ROCm_HostMap` mapping master) is
**dropped outright**; its **P0.5** survives as `MOE_EXPERT_GTT_RO` (the store is registered read-only from
creation, 230-233 GB/s against 60 writable); its **P2** survives in shape but not in memory (registered anon THP
instead of an arena slot + slab).

**Four assumptions are still unmeasured, and two of them can reshape the design** -- so `IMPLEMENTATION.md` P1.0
owes four probes before any code: (1) whether `MADV_HUGEPAGE` THPs survive `hipHostRegister` (the design is "a
mass of registered THPs"; the P0 probes counted base pages, not huge pages); (2) **`pread(O_DIRECT)` into a
registered RO region followed by a GPU read of exactly those bytes** -- the keystone, since the three halves are
measured separately and never in one program; (3) the copy-engine pull from a registered RO `MAP_SHARED` file
mapping into the registered slot (warm arm); (4) per-expert cost at the real 0.65 MiB granularity.  If (1) fails
the tier is 4 KiB pages (recorded, not fatal); if (2) fails the cold fill is not zero-copy and the design must be
re-costed before anything is built.

**Plan** (`wip/apu-expert-pool/IMPLEMENTATION.md`): **P1.0** the four probes; **P1** the integrated branch of
`moe_cache_preflight()` (`moe-expert-cache.cu:5641`) becomes a policy that *selects* the store instead of
disabling the whole cache, with the budget from `MemAvailable` (never "free VRAM": the 2026-10-19 over-commit
stays guarded) and `MOE_EXPERT_GTT=0` as the verbatim-restore kill switch; **P2** the store's allocation plus a
device-carrying **buffer type** on the delivery's KV-region pattern (`ggml-cuda.cu:10697`), so `MUL_MAT_ID` reads
it **in place** -- no new op, no per-layer copy; **P3** residency/eviction wired to `access_locked()`
(`:3495`), skipping the arena->pool hand-over, with **no `madvise` and no unregister on the hot path** (the P0
traps: `MADV_DONTNEED` on a registered region the GPU reads is a *silent zero*, and the pin survives
`hipHostUnregister` anyway while, with `iommu=off`, the registration *is* the GPU's mapping -- so an unregister
would turn a fill into a fatal fault, not a retry); **P4** the two fill arms (cold zero-copy `pread`, warm
copy-engine pull) with a fill-fault arm that must decline; **P5** prefill streaming on the existing span logic;
**P6** `scripts/gate-uma-experts.sh` (10 arms, text hashed with no `-lv`, censuses at `-lv 4`) + docs.

**Open for the maintainer** (`README.md` §7): slot granularity (per expert vs per layer-bank), whether the store
holds the hot subset or the whole expert set, LFRU vs the free "evicted but intact" second chance UMA allows,
whether a Windows carve-out APU folds into the same detection, gfx1150, and whether the directory should be
renamed to `archive/work/apu-expert-gtt/` now that the pool is gone (left as a decision: a rename touches
`CAMPAIGNS.md` and this record's own cross-links).

1. **The item's mechanism is refuted by a decomposition, not by opinion.**  A temporary probe (kept in the
