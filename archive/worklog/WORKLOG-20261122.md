## 261122.040 (r350, BLOCK-17 AMENDMENT 3: cut, validated, committed and tagged) -- `TODO` #364: a SPECULATOR on the two-arm server, three-way text-pure, and the placement trap the first gate version fell into

**`#364` is retired.**  Block 17 refused `--spec-type` (`auto` fell back to the single-context server and ran MTP,
`on` refused to start) because the decode arm owns its slots' KV and the recurrent state moves at a request
boundary, while a speculator needs a verify batch on the target plus a draft context whose KV is its own.  Nothing
about the two features was ever known to be incompatible; what was missing was (a) the verify batch on the decode
arm, (b) the drafter's target side on a second context, and (c) an oracle.  All three are now in block 17, and
`draft-mtp`, `draft-mtp-adaptive`, `draft-simple` and the n-gram family run on the pair.

### 1. What the implementation is (4 places, each a per-context binding)

* **`common_batch` carries its `ctx`.**  A drafter that reads the target's hidden rows (`llama_get_embeddings_nextn*`,
  the eagle3/dflash layer inputs) can only read them from the context that RAN the batch, so
  `common_speculative_process()` takes the rows from `batch_in.ctx`, and
  `common_speculative_add_target_ctx(spec, ctx_dec)` is what enables the nextn output on the second target context.
  A batch from an unregistered context is refused with a warning (drafting degrades, the text cannot).  With one
  target context this is bit-for-bit the old path (the batch's ctx IS `params.ctx_tgt`).
* **The decode arm is sized for the VERIFY WIDTH**: `n_batch = n_ubatch = n_parallel x (n_max + 1)` (3 slots at
  `--spec-draft-n-max 3` = a 12-row graph, `decode ctx n_batch = 12` in the log), and its output limits are raised
  to the whole width because every verify row is an output.  `n_spec_max` also clamps a round's draft so a batch
  can never overrun the width it was sized for.
* **`accept_draft_round()`** is the single-context `post_decode()` acceptance block moved into ONE function with two
  callers (the prefill arm for the row that ends a prompt, the decode arm for every later step) and an explicit
  verdict (`OK` / `REPLAY` / `STOP`), because only the main thread may touch the response lifecycle.  The rollback's
  `seq_rm` goes through the context the batch ran on (`common_memory::seq_rm_on`) and its sequence-removal class is
  the decode arm's (`ctx_dec_seq_rm_type`, taken from the prefill arm's -- probing it would clear the shared cache).
* **Cross-thread ownership**: `spec` is serialised by one mutex (`m_spec`); a slot carries no speculative state
  across a boundary (`spec_slot_reset()` on the forward handover, the reverse take and a decode-arm failure); the
  prefill arm's accept loop skips slots the decode arm owns; and the draft context's own `llama_process()` is
  bracketed by the arms handshake (`arms_quiet`), because it is a second DECODE-band context and block 17's rule is
  one in flight at a time.
* **The slab reserve is the SUM** of the decode arm's and the draft context's (`common_draft_reserve_derive`), and
  the FLAT fallback path adds the decode arm too -- that fallback is not hypothetical: the STEW675 2-part
  Flash-Next tree has an empty `params.model.path`, so every such run takes it (measured: `aux=3.50 GiB` before,
  `aux=8.50 GiB` after, the 35B-A3B and Flash-Next host tiers both still clean).  Refused with a message: the
  **layer-input** drafters (eagle3/dflash/dspark/dflash2/lilicorr) and a **gemma4 assistant** (which shares the
  target's KV instead of owning one).

## 261122.039 (r349, BLOCK-17 AMENDMENT 2: cut, validated, committed and tagged) -- r348 did not compile on Windows (`ssize_t` in block 17's state-move VERIFY), so it ships 20 minutes later as r349 with the lint that would have caught it

**r348 is tagged and released, and this supersedes it the same evening.**  Its patch set does not build with the

### 1. The fix (block 17, `(long long)` / `%lld`)

`(ssize_t) first` -> `(long long) first` and `"first at %zd"` -> `"first at %lld"`.  The value is a
never-negative byte offset, so the cast is lossless and the `(size_t) -1` sentinel still prints `-1` through it:
measured on the boundary arm with `LLAMA_RS_VERIFY_TAKE=1`, `VERIFY seq 0: 0 of 65864420 byte(s) differ (0 in the
12-byte cell metadata), first at -1; the source rows are FAITHFUL` -- i.e. the sentinel and the format are right,
and the arm still passes 9/9.

### 2. The lint that was blind to it, extended (`scripts/check-windows-portability.sh`)

The script knew two name rules (POSIX-only **calls**, and windows.h **keyword macros** like `near`/`far`) plus the
include-closure check, and PR #352's own diagnosis is why neither could see this: `(ssize_t) first` is a type in a
cast, not a call, and it is not a macro.  It is now a third rule -- **POSIX-only TYPE names** (`ssize_t`, a name
rule on the same Windows-compiled lines, comments/strings already stripped, so the fix's own explanatory comment
is not a hit).  Negative control: on the **r348 tree** the rule reports **exactly one** site,
`src/llama-context.cpp:7284`, and nothing else in 515 scanned files; on the r349 tree it is clean.  `tests/` and

`MANIFESTS.md` (the portability-gate row), `scripts/README.md` and `AGENTS.md`'s scripts row carry the rule.

### 2. `TODO` #365: the Meta buffer's per-child `cpy_tensor_n` -- 72-77 ms becomes 1.4-1.9 ms

`llama_memory_recurrent::seq_state_take()` builds its 2-D row views **out of graph**, so no `simple_tensor` container
knows them and the host paths cannot resolve them; with no copy hook on the Meta buffer, `can_take_batched()` refused
and every `-sm tensor` hybrid boundary was `state_write()` -> host -> `state_read()`: **112.57 MiB, 72-77 ms, in TTFT**
(measured, unchanged from the handover's 74.6).

The hook is per **child**: the split state of the view's ROOT (which IS registered) says which byte range of a row
belongs to which child, and each child's own buffer takes a plain copy of its rows.  **The non-obvious half:** both
sides of a copy are children of the SAME layout, so a child's covered rows are ONE contiguous range even when the
split state is segmented/repeated -- and the state of Qwen3.8-Flash-Next is one segment **repeated 3 or 5 times**
(interleaved inside the row, identically on both sides).  The first cut walked that interleaving (`nr[0]` copies per
row per child: **3.5 ms**); copying the child's range gives **1.4-1.9 ms** (3.0-3.3 ms with the verify capture; the

### A: the peer grant is best effort, which the slab already knew

`ggml_cuda_pool_vmm::alloc` granted **every** peer descriptor in ONE `cuMemSetAccess` call and wrapped it in a
`CU_CHECK`.  On a box whose MoE arena has taken the VRAM the driver refuses to build a peer mapping, so that call
returns `invalid argument` and the process aborts -- measured as `HipVMM Failure: invalid argument` in `alloc()` from
`mul_mat_q`, ~2 s into the first request, **only with the arena on** (`MOE_EXPERT_CACHE_MIB=0` clean) and **only with
the pair** (pair OFF clean).

The appliance for it already existed: `ggml_cuda_vmm_map_phys()` (the slab's mapper) grants the **owner alone, then each
peer on its own**, keeps the mask of what was granted, and lets the copy path **stage** the pairs the driver refused --
with a comment recording exactly this bug from the slab's own history ("one refused peer descriptor would otherwise
poison the whole call").  The pool never got that treatment.  So A is:

* grant the owner's descriptor alone (located **explicitly** -- the list is in device order, so for devices 1 and 2 the
  owner is not at the front; my first cut granted "the front" and CU_CHECKed a peer, i.e. reproduced the abort),
* then each peer alone, best effort: a refusal clears the error, warns once per (device, peer), and drops that device
  from the pool's `peer_mask` (intersection over every growth),
* register the pool's `[base, size)` + mask in a process-wide registry, and teach the copy predicate about it: the
  slab's `ggml_cuda_slab_peer_copy_ok()` becomes **`ggml_cuda_peer_copy_ok()`** and answers for slabs **and** pools
  (process-wide and pessimistic, exactly as the slab's does -- a wrong "yes" faults the GPU, which nothing catches).
  A refused pair now stages through pinned host memory instead of aborting.

**And one more of the same class, found on the way:** the async-input ring's origins uploaded on `cudaStreamPerThread`,
the sentinel HIP couples to the legacy default stream, so a *peer arm's* capture refused them -- measured on the host
tier as a failed `llm_graph_input_ple::set_input` at ~86 s (`operation failed due to a previous error during capture`,
then the next kernel launch failed).  The origin now owns a **private non-blocking stream**: the ordering was already
carried by events, never by a stream handle (see the note on `ggml_cuda_async_input_origin`), so nothing else changes.

### Why the single-context path does not hit it, and whether its approach is cleaner

**It is not pre-allocation of the *buffers*, it is when the *grants* are attempted -- and the pool's grant policy was
simply inconsistent with the slab's.**  Concretely:

* One context grows **one** set of pools, during load and the first reserve.  The pair grows a **second** set at
  *request* time (the decode arm's first step), after the arena has taken the VRAM.  Same free-VRAM figure at both
  moments (~2.8 GiB measured), which is why "more free VRAM" is not the fix: the refusal is HIP declining to build a
  peer mapping on a nearly-full device, and the *order* of grants decides who gets one.
* The slab has lived with that for months: its grants are best effort and the copy path stages.  The pool had no such
  path, so the *pair* only exposed the inconsistency.  Any later pool growth on a full box -- a new ubatch width, a
  wider verify batch, a third context -- would abort even with perfect timing, so A is the correctness fix regardless.

**Sharing the single context's buffers with the decode arm is not viable**, and that is structural rather than
timing: the two arms compute **concurrently** with different shapes (a 2048-token prefill vs a 3-token decode), so their
compute buffers must be separate or they overwrite each other's graphs -- which is exactly why block 17 creates a second
context and shares only the **KV cache**.  What the non-pair path *does* have and the pair should borrow is its
**timing discipline**: declare the second context's needs before the arena claims the space.  That is r346's
`MOE_EXPERT_CACHE_AUX_RESERVE_MIB` (`SLAB_INIT ... aux=`), and on this shape it is now the host tier's last blocker --
see below.  It is B in `261122.033`, and it is a **performance/headroom** work item (it keeps peer copies direct
instead of staged), not a correctness one, once A is in.

### What the pair actually shares, and what was racing

Three separate structures were being mutated from the two arms' threads with no common lock.  Each was measured, not
inferred, and each has its own fix:

1. **The KV cell map** (`261122.032`): `apply()` and `init_batch()` (whose `prepare()` snapshots the map for rollback)
   run on both arms.  **Fix: one apply lock per memory GROUP** -- `llama_memory_i::apply_mutex()`, shared through
   `create_memory()` by exactly the condition that decides the shared view, taken at the engine's memory entry points
   (`init_batch`, `apply`, `clear`, `state_write/read`, the `llama_memory_*` seq ops and park; `alloc_sync` and
   `seq_state_take` stay unlocked -- request-boundary only).  Worst critical section measured **783-1161 us**, once per
   prefill step.
2. **The Meta split-state cache** (`ggml-backend-meta.cpp`) -- the released build's SIGSEGV, and the reason the P0 was
   not just the assert.  `ggml_backend_meta_buffer_context` keeps **8 rotating versions** of a
   `unordered_map<(tensor, assume_sync) -> split-state>`, plus `cur`, `used[]` and a `tick`, and *every* tensor of *every*
   graph allocation resolves through it (~10k lookups per decode step).  It was **per buffer**, and the two arms share
   one buffer -- the **KV cache's** -- so one arm's version switch, `clear()`, or insert under the other's `find` is a
   corrupted hash table.  It surfaced as a SIGSEGV in `ggml_backend_meta_get_split_state` and in `set_tensor_async`'s
   lookup, *pre-fix and on the release*.
   **Fix: the cache is per VIEW SLOT** (`split_state_cache[4][8]`, `cur[4]`, `used[4][8]`, `tick[4]`), indexed by
   `g_meta_view_slot` -- the same discriminator the simple-tensor containers next door already use, and the reason they
   were already `stc_compute[4][2]` ("a co-owner pair runs two graphs on two threads and each needs its own pair").  A
   single context never leaves slot 0 (`sched_alt_for()` is false without `ctx_other`), so its own rotation across graph
   shapes is unchanged.
   **And the slot is now bound for EVERY graph build/alloc** (`llama_context::meta_bind_view_slot()`, called from
   `graph_reserve()` and `sched_alt_select()`): it is `thread_local`, and it used to be set only when the *alt scheduler
   state changed*, so a context's first graph -- or a `sched_reserve()` / new-shape reserve -- could run under the
   thread's default slot 0, i.e. the co-owner's slot as the owner's.
3. **The async-input ring** (`ggml_cuda_async_input_set`, the H2D staging of small graph inputs, default ON).  On the
   ring-wrap path it drained every origin and then called **`cudaDeviceSynchronize()`** -- a device-wide host
   synchronisation, which is **illegal while any capture is in flight on the device**.  The pair captures on one arm
   while the other stages, so HIP returned `operation not permitted when stream is capturing`, and every subsequent
   launch on the device failed (`operation failed due to a previous error during capture`) -- measured as a dead request
   with four `ROCm error` lines and no assertion at all.
   **Fix: wait on the ORIGINS' own streams, never the device.**  A ring slot can only be read by an origin's own
   uploads (its `ev`/`flush_ev` are recorded on its stream), so `cudaStreamSynchronize(e.stream)` per origin is exactly
   the guarantee the wrap needs, and it is not a device-wide barrier (it also no longer waits for the graph compute of
   either arm).  If even that is refused, the error is cleared, the ring is left untouched and the copy reports "not
   staged" so the caller takes its synchronous path; a later wrap, after the capture ends, resets the ring.

```
[DBG_APPLY] MISMATCH tid=<DECODE arm> n_tok=1 n_seqs_unq=1 | attn n_kv=23040 used=22921 size=204800
                                                          | idx  n_kv=24064 used=23999 size=204800 | USED-DIFFER
qwen4exp.cpp:1138: GGML_ASSERT(mctx_idx->get_n_kv() == inp->mctx->get_attn()->get_n_kv() ...) failed
```

So the two children differed by **~1078 cells, i.e. one whole peer PREFILL ubatch**, not by the 1-3 cells a pad
coincidence would need.  `H1` is right about the window and wrong about its narrowness: the peer is not a decode step
(tens of milliseconds to cross a pad bucket), it is the *other arm's 2048-token prefill apply*, so any interleaving shows
up and no boundary luck is required.  Two further facts close the alternatives: both caches report the same
`size = 204800` (H3 dead), and the mismatch lands in **`apply()`, which runs before the graph build**, so the assert is
only the messenger.

The window is exactly what the handover drew: `apply()` computes the attention child's padded extent, then applies the
indexer child; the engine takes **no lock** over that pair, and the arms' `arm_step_guard` deliberately lets both arms
run `llama_process()` at once.

### The same root cause has a second symptom, and it is a memory-safety bug

With the assert's window covered, the shape still crashed: `SIGSEGV at 18 ... libstdc++.so.6` with the faulting
instruction a red-black-tree walk (`48 8b 52 18`, i.e. `mov 0x18(%rdx),%rdx`).  The caller chain is
`llama_kv_cache::prepare()` via `memory->init_batch()`: to roll a failed placement back it **copies the whole cell map**
(`std::vector<llama_kv_cells>`, each with a `std::set<uint32_t> used`) while the peer arm's `apply_ubatch()` is inserting
into those same sets.  Pre-fix this is masked by the assert firing first; it is a real crash on the released build for the
larger shape.  **`init_batch()` is as much a cell-map mutator as `apply()`, and it was never serialised.**

### Fix A (written, validated): one apply lock per memory GROUP

- `src/llama-memory.h`: `llama_memory_i` gains `std::shared_ptr<std::mutex> mtx_apply`, `apply_mutex()` and
  `apply_mutex_share()`.
- `src/llama-model.cpp` (`create_memory()` tail): a context that VIEWS another memory's cells (`mem_other_used`, i.e. the
  same condition that decides the shared view) shares that memory's lock.  One hook, every memory module, so a future
  module cannot forget it -- the r346 lesson ("implements no shared view" must be loud) applied to the lock.
- `src/llama-context.cpp`: the lock is taken at the **engine's memory entry points** -- `init_batch()` (decode and the
  trainer), `apply()` (`process_ubatch`, `memory_update`, the trainer), the truncation `seq_rm`, `clear`, the four
  `state_write/read` sites, and the `llama_memory_*` API (`clear`, `seq_rm`, `seq_rm_recr`, `seq_cp`, `seq_keep`,
  `seq_add`, `seq_div`); `llama_memory_seq_park()` in `llama-memory.cpp`.  **Not** locked, and documented as such:
  `alloc_sync()` and `seq_state_take()` -- request-boundary only, already inside the arms' quiet window (and a take
  reads the peer's map, so a lock there would have to span two groups).
- Rationale for the engine boundary rather than per-module locks: all concurrency enters through a `llama_context`, the
  sites sit in one contiguous API layer of one file, and a composite memory's children are covered as a unit (a leaf
  lock cannot make `attn read -> idx apply` atomic).  Cost measured, not assumed (below).

**Cost:** the critical section a peer arm can be held out by is `init_batch()` for a 2048-token prefill ubatch =
**783-1161 µs** (44 occurrences in a 55 s run, the worst 1.16 ms).  `apply()` itself is far smaller.  Against the pair's
contract (`r346`: p50 47-49 ms / p95 64-78 ms decode through a prefill) that is noise; it is one short wait per prefill
step, and the arms' *compute* is untouched.

**No delivery patch changed, no tag.**  A user-facing abort in the shipped block 17, reproduced by the maintainer while
running `/llm/models/Qwen3.8/Flash-Next/STEW675-IQ4_NL/runme` (that script's own shape: `-c 204800 --parallel 3
--kv-unified -sm tensor`, 3 x R9700, `q8_0` K/V, `-ub 2048`, `--prefill-decode-arms-mode auto`, the 94 GB STEW675 IQ4_NL
model fully on the cards).  Log and backtrace: `/llm/models/Qwen3.8/Flash-Next/STEW675-IQ4_NL/server-logs`.

**The abort.**

```
/home/stew675/llama.cpp/src/models/qwen4exp.cpp:1138: GGML_ASSERT(mctx_idx->get_n_kv() ==
    inp->mctx->get_attn()->get_n_kv() && "the indexer cache must track the attention cache cell for cell") failed
```

`ggml_abort` <- `llama_model_qwen4exp::graph::graph` <- `build_arch_graph` <- `build_graph` <-
`llama_context::process_ubatch` <- `decode` <- `update_slots()`, i.e. on the **prefill arm's** thread.  At the time: slot
0 decoding, slot 1 prefilling **70 986** tokens, slot 2 prefilling **23 003** tokens; the abort came ~0.4 s after slot 1
printed `progress = 1.00`, so at the **request boundary** where its sequence was handed to the decode arm.

**The assert is upstream, not ours** (`git log -S` on the message: `6c84c7d5d`, "model: add Qwen3.8-Flash-Next
(qwen4exp) (#27742)", 2026-08-27, carried in by block 11).  So this configuration violates an invariant the model has
always had; the pair is what makes it reachable.

**Mechanism (leading hypothesis, with the evidence for it).**  `get_n_kv()` is the PADDED extent the attention views use,
`max over streams of min(size, max(pad, PAD(used, pad)))`, where `pad` is 256 normally and `LLAMA_KV_N_PAD_PREFILL` =
**8192** by default on a multi-device split for prompt-sized ubatches.  The two children of `llama_memory_hybrid_idx`
compute that value **separately and in sequence**, each right after its own `apply_ubatch` (see
`llama_memory_hybrid_idx_context::apply()`: the attention child applies and computes, then the indexer child applies and
computes).  Single-context, nothing runs between those two reads.  **With the pair they are two threads on one shared
cache**, so the decode arm can publish cells in between, and the two values then differ exactly when the movement crosses
a pad boundary.  That explains the shape of the report: it needs a LARGE prefill (70K of cells puts `used` next to an 8192
multiple) AND a request boundary (the moment the decode arm gains a sequence and starts applying), which is why it is rare
and why nothing in the gate set has hit it.  Corroborating details from the log: only one `handshake clean at the
'handover' boundary` line precedes the abort; parking is declined on this cache (`idle slot parking: not supported by this
KV cache`), so the park bound is not involved; and both children are built from the SAME `sinfos` and `ubatches`
(`heads_idx = heads_attn` in `init_batch`), so the inputs are identical and only the timing can differ.

**Discriminator and repro hint.**  The same 3-slot workload with `--prefill-decode-arms-mode off` settles whether the arms
are required.  `LLAMA_KV_N_PAD_MIN=256 LLAMA_KV_N_PAD_PREFILL=0` shrinks the pad buckets and turns smaller timing
differences into a visible mismatch, so it should make a repro more likely rather than less.

**Fix direction.**  Derive the indexer's `n_kv` from the attention's for the pair rather than computing it twice: the
invariant already states they are equal, and `init_batch` already gives the indexer the attention's slot layout, so making
the value follow the layout removes the disagreement by construction.  If some case legitimately needs them independent,
hold the arms' quiet window across BOTH children of `apply()` instead.  Either way a gate arm is owed: three slots, two
prefills in flight and one decode, on a qwen4exp hybrid, pad buckets shrunk, repeated N times.

**Severity.**  An abort, not silent corruption, and **opt-in only** (block 17 is default off and the shipped
single-context server has no second thread to race), so `v18-919794500-r346` stands.  It is a P0 for the feature and a
blocker for any default-on decision.  Recorded as `TODO` #373 and campaign `W9`.

## 261122.030 (no delivery change) -- the premise history behind W8 corrected: prefill multi-slot batching arrived WITH block 16's fair share, and the shortest-prompt droop is default-off tuning, not dead code

**No delivery patch changed, no tag.**  A correction to the framing of `WORKLOG.md` 261122.029 (which described the
current behaviour without saying when it began), recorded because the history is the part a future reader will get wrong.

**Before r300** `update_slots()` added the decode tokens and filled the rest of the batch **in slot index order**: the
lowest slot took the whole window and every other prompt waited for that slot's **entire** prompt.  The fairness gate's
own header carries the measurement (a 7-token prompt behind a 13204-token one waited **1.91 s**) and the note that `-b`
does not help, because it changes the grab size, not the order.  So prefill steps carried **one** sequence and every step
re-read the whole weight set for that one slot's chunk.  Several sequences per ubatch was always *possible* (it is the
parallel-request machinery) but the scheduler never composed it for prefills.

**r300 (block 16)** replaced the fill order with `share_prompt_budget()`, and that is what makes the multi-slot prefill
batch exist.  So "this delivery supports batching on prefills" is true, and it is a consequence of the serialisation fix,
not a separate capability.  261122.029's statement that the slots already share the weight pass is correct for the current
code and was wrong before r300; the campaign's W8 section now carries the history.

**The two things that were bundled into "the fix" have different status**, which is the part worth remembering:
`share_prompt_budget()` itself (every active prompt admitted to every step, one-token floor, rotating tie-break) is **on by
default** with `LLAMA_SERVER_PREFILL_FAIR=0` as its kill switch; the **shortest-prompt-priority droop**
`LLAMA_SERVER_PREFILL_SKEW` is a live knob with **default 1 = the plain equal share**, i.e. off.  It is not dead code:
measured on four prompts of 6000/3000/1500/400 tokens at `-np 4`, mean TTFT is **1.401 s at 1**, 1.082 s at 5 and 1.040 s
at 20, and the longest prompt improves too (2.201 -> 1.975 s) because short slots retire and stop competing.  Its job
changed rather than disappearing: "which slot gets to run" became "who gets the larger share of one window", a
TTFT-versus-throughput tuning that was never promoted to a default because the pathological serialisation was what needed
fixing.

## 261122.029 (no delivery change) -- design answer: multi-slot prefill is ALREADY batched per ubatch, so "layer-major across slots" is the `-ub` knob, not a new schedule (`TODO` #372)

**No delivery patch changed, no block created or amended, no tag.**  A design question from the maintainer, answered from
the code and the measurements, and recorded as campaign item `W8`.

**The question.**  With several slots prefilling concurrently, "each slot scans through the full set of layer weights per
ubatch chunk"; would processing the prefill **layer by layer**, with each active slot handling its ubatch for the active
layer, batch them for better prefill throughput?

**The answer: within one step the slots already share the weight pass.**  `share_prompt_budget()`
(`tools/server/server-context.cpp`, block 16's fair share) gives **every** slot that still has prompt tokens a share of the
step's window, with its own stated goal: "nobody fills n_batch first and every active prompt is admitted to every step".
That one `llama_batch` is split into `n_ubatch` chunks, and **each chunk is one graph**, so the linear ops see a single 2-D
tensor of all rows in it and the weights are read **once per chunk for every slot in it**, not once per slot.  On the arms
path the chunk cap that could shrink a slot's contribution is inert by construction (`-ib` bounds a step only when a decoder
is waiting on that arm, and a slot on the decode arm is not).

**What is left is the SPLIT, and that is the `-ub` knob.**  A step whose admitted tokens exceed `n_ubatch` becomes several
chunks, each re-reading the whole weight set.  Measured on the pair: `-ub` 512 -> 2048 -> 4096 reads **1440 -> 3041 -> 3884
t/s**, and 8192 buys +8 % more prefill for a worse decoder tail (124.5 vs 95.1 ms).  A layer-major schedule across *chunks*
would need several chunks' activations live at once, which is the definition of a bigger ubatch, so the idea degenerates
into the knob the delivery has already tuned.

**Three things the item does owe.**  (1) A **composition census**, because the fair share admits every prompt but does not
make them *arrive together*: `LLAMA_KV_DEBUG_CELLS=1` prints one line per sequence per ubatch, so grouping those lines says
whether real ubatches hold one sequence or several; if they hold one, the headroom is scheduler-side.  (2) A **two-slot
aggregate-scaling table** at four ubatches on a dense model and on a host-expert MoE, where a routed expert read amortises
the **union** of the experts its rows route to and batching is therefore superlinear.  (3) A recorded **"do not"**: merging
the two **arms'** layer passes (decode rows plus prefill rows in one weight read) would halve the weight traffic and would
also put the decode row's latency back inside the prefill layer's work, which is precisely the 300-880 ms stall block 17
exists to remove.

Record: campaign `archive/work/prefill-decode-arms-followups/` §W8, `TODO` #372, and the note that W6 and W8 must be measured as ONE
curve ("worst in-window gap against prefill rate"), since they pull the same axis in opposite directions.

### The finding

`moe_cache_gather_kernel`'s grid is `n_experts * n_split` blocks, and every block scanned the WHOLE routing
(`n_used * n_tok` ids) to answer one question -- "is MY expert routed?" -- so a call paid up to
`n_experts * n_split` redundant scans.  The copies shrink with `n_split`; the scans do not, which is why a deep
split lost at low residency.  Issue #350 reports the shape (Flash-Next IQ3_XXS, 55 % arena residency, Windows):
`MOE_GATHER_NSPLIT` 32 is 466.5 t/s of prefill against 504.1 at 8 and 554.7 at 4, and it "stops changing at 4 and

40012.5 MiB host experts): 32 -> 1671.7 t/s against 1719.3 at 4, -2.8 %.

bitmap, one atomic per word, not one per routed id -- a direct global atomic per id measured 0.11 ms per call),

volume it replaces (`n_experts * n_split * n_used * n_tok` ids) reaches `1e8`: below that the pass is latency on
the critical path that buys nothing (measured -1.2 % at 6.7e7 ids, -2.3 % in one 16-split arm), so `n_split` 4-8

magnitude below the threshold) never adds a launch.
