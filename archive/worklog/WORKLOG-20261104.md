## 261104.008 (r215) -- `--load-mode mmap` reaches `listening` 1.6x faster than `--load-mode none`: the host pool's mirror FILL and its pinned BACKING

**Delivery change: `patches/0000`-`0015` (16 blocks, block 09 AMENDED and block 12 AMENDED), release
`v16-6050b467c-r215`, tip `790686b53`, tree `19200174f`.**  Reported symptom: on Qwen3.8-Flash-Next
GSQ-RCO-IQ3_S (`-ncmoe 48`, the `runme` config) a `--load-mode mmap` start takes ~1.5x as long to serve as
`--load-mode none`.  It is not a loader difference and it is not more work: both arms move the same 48 GiB of
host-expert weights into RAM (`/proc/PID/io read_bytes` 54.6 GiB in both, 1 and 2 devices).  It was two costs
in the pinned host pool (`ggml/src/ggml-cuda/moe-expert-cache.cu`), both of which only a mapped load pays.

### 1. Cold measurements (page cache dropped with `POSIX_FADV_DONTNEED`, same command line)

| arm | 1 device | 2 devices (`0,2`) |
|---|---|---|
| `--load-mode mmap`, r214 | 26.30 s | 30.76 s |
| `+` the mirror fill (1) | 22.31 s | — |
| `+` the THP backing (2) = **r215** | **15.19 s** | **19.27 s** |
| `--load-mode none` | 16.70 s | 19.91 s |

The `runme` itself: **26.3 s -> 15.17 s** to `listening`, attendance pool active, 43 t/s decode.  mmap is now
*faster* than `none`, because the PLE tensor stays lazy-read.

### 2. The two costs

1. **The mirror fill.**  With the budget covering the whole host expert set (`-lme auto` in the fitting band) each
   per-tensor pool is a **mirror** (`slots == n_experts`), and the prewarm filled it with one `host_bytes`
   (256-900 KiB) `memcpy` per heat-ranked slot out of the demand-faulted model mapping: ~4.5 GB/s, and it faulted a
   *second* 48 GiB into the page cache that cannot be kept beside the 48 GiB pinned mirror.  A mirror holds every
   expert, so the fill ORDER is content-free and its memory is one contiguous `n_experts * host_bytes` allocation
   whose layout is exactly the GGUF expert-major stride: the whole mirror is now **one sequential read of the
   tensor**, the same `pread` mechanism `--load-mode none` uses for its pinned master.  48 GiB 10.8 s -> 7.4 s.
2. **The backing.**  `cudaHostAlloc(Portable|Mapped)` of 48 GiB cost **5.4 s**: it pins page by page and pins a zero
   page per 4 KiB page, every one of which the fill immediately overwrites.  An anonymous `mmap` + `MADV_HUGEPAGE`
   region (2 MiB pages) pinned with `cudaHostRegister` **after** the fill costs ~1 ms of explicit pin plus page
   allocation the fill had to do anyway.  `Mapped` is required — `Portable` alone leaves it unreachable by the
   in-place cold read (a GPU page fault at block 09, which is how it was found) — so `vendors/hip.h` and
   `vendors/musa.h` gained the `cudaHostRegisterMapped` mapping.

### 3. Release and recycling (the maintainer's constraint)

`cudaHostUnregister` alone does **not** return the pages on this stack (the pin is tied to the VMA —
`archive/work/host-expert-eager-push/` P4 §5), so block 12's `pool_free_locked` does `unregister` + `munmap`.
Verified: `AnonHugePages` 48.97 GiB while running -> **0** after teardown, `MemAvailable` back to baseline.  A pool
SLOT is index bookkeeping inside that one allocation, so recycling never pins/unpins: with an 8 GiB partial pool
and **35 559 slot fills**, **144 `hostRegister` / 144 `hostUnregister`** (exactly one per host tensor).

## 261104.007 (r214) -- `TODO` #143 FIXED: the slab's narrow-2 (MTP draft compute) region is MAPPED for its whole extent, and the draft reserve stops guessing the compute term

**Delivery change: `patches/0000`-`0015` (16 blocks, block 09 AMENDED and block 12 AMENDED), release
`v16-6050b467c-r214`, tip `e76491d89`, tree `5de3ff716`.**  The r213 report (`WORKLOG.md` 261104.004) left one
pre-existing defect open: a 2-device `-sm layer` Flash-Next at `-c 204800` faults the GPU during the first prefill.
It was not block 15 (it reproduced with `LLAMA_KV_REGION_POOL=0`), not the PLE host read, and not a use-after-evict.

### 1. The defect: a slab region handed to a graph with no physical behind its top

`ggml_cuda_slab_narrow2_pin_locked()` pins the MTP draft's compute region (narrow-2) at the **top** of the slab's
reserved VA: `off = size - nf2`.  `ggml_cuda_slab_narrow2_commit_locked()` had two branches:

| condition | what it did |
|---|---|
| `off >= mapped` (the region fits the unmapped spare) | maps `nf2` physical at `off` |
| `off < mapped` ("taken from the arena") | evicts the tables in `[off, mapped)`, caps the arena -- **maps nothing** |

When the region **straddles** `mapped` (`off < mapped < off + nf2`) -- the documented shortfall case, the one r106
added the arena-yield branch *for* -- nothing above `mapped` is ever mapped, yet the draft's compute buffer occupies
the whole region.  On a no-XNACK part the first access past `mapped` is an unrecoverable fault.  Every arm's slab
accounting separates the classes exactly (from the `SLAB_INIT` / `narrow-2` lines):

| arm | slab `size` / `mapped` | narrow-2 `off` | branch | mapped part of the region | |
|---|---|---|---|---|---|
| 1 dev, `-c 204800` | 23.19 / 21.88 | 21.94 | spare | 1.25 GiB (all) | clean |
| 2 dev, `-c 131072` | 25.75 / 24.62, 27.81 / 26.69 | 24.75, 26.81 | spare | 1.00 GiB (all) | clean |
| 2 dev, `-c 204800` | 25.62 / 24.25, 27.69 / 26.38 | **24.12, 26.19** | **arena** | **0.13 / 0.19 GiB**, 1.37 / 1.31 GiB **absent** | **fault** |

Attribution (temporary `norm.cu` instrumentation, reverted): the faulting launch is `rms_norm_f32<1024,1,...>` over
`ROCm1#mtp_h_state-48#0` = `reshape_3d(inp->h, n_embd, hc, n_tokens)` (`src/models/qwen4exp.cpp:1223`), `src0`/`dst`
both in the 1536 MiB `ROCm1` compute buffer = **exactly** the narrow-2 region (`slab_base + 24.12 GiB`).  The fault
address lands `0x21E000` past `dst`, i.e. just above the mapped boundary, which `/proc/<pid>/maps` confirms: the
`---s /dev/dri` mapping of the slab ends there and a 1408 MiB `---p` (the slab's `va_spare`) begins.  So the crash is
inside the *draft's* compute buffer, not the residual stream and not host memory (both `buft=ROCm1, host=0`).

**Fix (block 12, 12 lines of logic):** `narrow2_commit` maps **whichever part of `[off, off+nf2)` has no physical
behind it** -- the whole region when it is above `mapped`, or just the tail when it straddles -- then sets
`s.mapped = off + nf2`; the arena-yield and the `arena_free` drop for `[off, mapped)` are unchanged.  Addresses are
untouched (the region was already handed to the graph allocator), so this moves no tensor.  The comment above
`ggml_cuda_slab_arena_limit()` is corrected: the `min(mapped, ceiling)` clamp is **load-bearing**, not defensive,
because `mapped` now ends up *above* `narrow2_off` in the straddle case.

### 2. Why it only showed at a deep context, and the reserve's compute term (block 09)

The region is `size - off` large and the spare is `size - mapped`.  The spare is the draft-context estimate the slab
holds back **before** the draft exists, and its `compute` term was a 512/768 MiB tier measured at `-c 16384`.  The
draft's compute buffer is **not** a constant: it is read back measured (`sched_reserve`'s per-backend size, the number
`slab_narrow2_floor` is given) and it grows with the draft's **context** in 256 MiB lumps.  Measured here (gfx1201,
Flash-Next GSQ-RCO IQ3_S + its shared `mtp-...-Q4_K_M`, `-ub 4096`, q8_0 KV, per device):

| `-c` | 32768 | 65536 | 98304 | 131072 | 163840 | 196608 | 204800 | 229376 | 262144 |
|---|---|---|---|---|---|---|---|---|---|
| 2 GPUs | .75 | .75 | 1.00 | 1.00 | 1.25 | 1.25 | 1.50 | 1.50 | 1.75 GiB |
| 1 GPU | | | | | | | 1.25 | | |

So the estimate was 2-3.5x short at any context this config is run at -- which is precisely what puts the region across
`mapped`.  The term is now the **measured minimum** (768 MiB, +256 above a 4096 ubatch) and *stays a floor*: a shortfall
is harmless now (the commit maps it), while an over-estimate is not free either (on a box with no VRAM left
`slab_extend` cannot reclaim it, so it stays unmapped).  Correcting it converts the repro arm from the arena-yield
branch to the clean spare branch, and it is a strict VRAM improvement: 32.82 / 33.11 GB used against 32.89 / 33.24 GB
with the straddle, 1.50 GiB pinned either way.

## 261104.006 (docs) -- `TODO` #135 re-scoped: an even-split guard at load, not a host-expert perf hunt

**No delivery change** (`patches/`, `release.json` and the fork are untouched; the release stays
`v16-6050b467c-r213`).  Follow-up to the audit in 261104.005, at the maintainer's correction of what #135 actually is.

**The finding is a limit, not a defect to tune.**  35B-A3B has **no even `-sm tensor` split above 2 GPUs**, so a 3-device
arm is degenerate (r209: ~20 t/s against ~55 on 1 GPU and ~52 on 2, while all-VRAM on the same three devices gives
138 t/s), and the ~20 t/s figure is the *symptom of a zero/uneven per-device share* — not something a host-expert path
can recover.  It is the same class as the accepted limitation already recorded for `gemma-4-E4B-it` at 3 devices (2 KV
heads < 3 devices, the split-state ratio-consistency assert).

**So the item is re-scoped to the guard it implies:** a **load-time check** that decides whether the requested device
count can split *this model's* tensors evenly and, when it cannot, **refuses to offload that far** with a message naming
the constraint and the supported counts — the vLLM TP-validation behaviour.  It must be derived from the model's own
geometry (head / expert counts), never a hard-coded model list.  The r209 measurement is kept only as the evidence that
the degenerate configuration is silent today; the row no longer asks for an attribution of the number.

## 261104.004 (r213) -- block 15 amended: the attendance pool works on a multi-device `-sm layer` split

```

  ggml_backend_sched_split_graph <- llama_context::graph_reserve <- resolve_fused_ops <- sched_reserve
```

A node no backend claims.  Instrumenting the split (all of it reverted) showed `op=KV_POOL` for a layer on device 1 with

1. **The mirror buffer type had no device in its NAME.**  `ggml_backend_cuda_kv_pool_mirror_buffer_type_name()` returned

## 261104.003 (r212) -- the host pool's fill mode mirrors `--load-mode` (a mmap is a request for the page cache, not a RAM guess)

**Delivery change: `patches/0000`-`0015` (16 blocks, block 12 AMENDED), release `v16-6050b467c-r212`, tip `5f3e6ffee`,
tree `0c76a1eb`.**  Found while answering a user question about `llama-server` maxing the disk during prefill on a 113 GB
Flash-Next (`-ncmoe 48 -lme 60`, 2 devices).

**The finding.**  `MOE_HOST_POOL_DIO=auto` decided the pool's fill mode from `planned_pool + host_total > MemAvailable`, which
on a tight box is always O_DIRECT -- so the operator's `--load-mode mmap` (an explicit request for the page cache) was being
silently overridden, and the pool's POPULATION -- the one read that cannot be avoided -- went to the drive.  Measured on that
config (host expert set **71.7 GiB**, pool 60 GiB = 428 of 512 slots/table = 84 %, `per_layer_token_embd` 26.8 GiB
host-resident, arena 66.3 %):

| pool fill mode | fills | fill time | effective | drive traffic |
|---|---|---|---|---|
| O_DIRECT (the old auto) | 97 692 storage reads | **35.8 s** | 2 785 MiB/s | 95.20 GiB off the drive |
| buffered (the new auto, mirroring `--load-mode mmap`) | 97 692 mapping memcpys | **24.8 s** | 4 062 MiB/s | none |
| `MOE_HOST_POOL_DIO=1` on a mapped load (the override still works) | 97 692 storage reads | 36.1 s | 2 708 MiB/s | 95.20 GiB |

**Policy (the maintainer's call):** the fill mode **mirrors `--load-mode`**, because the load mode IS the operator's caching
decision.  A pool only exists on a *mapped* load (its master is the model mapping; `--load-mode dio`/`none` log "NOT APPLIED: a
pool needs a mapped load" and use the whole-tensor pinned master instead), so in practice auto = buffered and O_DIRECT fills are
an explicit request.  The MemAvailable numbers are still computed and printed *as a note* on the decision line when they cannot
hold the pool AND the set, naming `MOE_HOST_POOL_DIO=1` as the memory-tight arm (the regime r112 tuned it for).  The old
heuristic survives only for a consumer that never reports a load mode.

**Implementation.**  One new device-iface entry, `moe_cache_set_host_fill_mode(dev, direct)`, **APPENDED at the end of
`ggml_backend_device_i`** (the documented positional-initializer rule -- inserting in the middle would alias every other
backend's entries, which is exactly what bit the block-09 repair in r211); the loader reports `use_direct_io` from its own
resolved `--load-mode`, once, in `llama_model_loader`'s constructor; the cache stores it and `pool_decide_dio_locked` applies
env-force → mirror → heuristic in that order.  Every backend other than CUDA leaves the entry zero-initialized.

### 1. The blocker: the eager take-over declined every routed op on a covering pool

`llama-batched-bench -npp 512 -ntg 128 -npl 8` on 2 devices gave the pool tier **49.2 tg** against 270.5 for a
pinned master.  The cause is **not** the prefill staging path the r210 handover hypothesised (that hypothesis is
refuted below) but the eager take-over's completeness guard in `moe_cache_update_host`:

```c
if (!table_cold_ok(t) && t.slots < (int) (n_used * n_tok)) { g_decline_all++; return false; }
```

`table_cold_ok()` is `g_cold_uva && t.cold_safe && t.host_dev != nullptr`, and `host_dev` is **null for every
pool-backed table** (a pageable master).  So the guard bounded the pool tier by the **arena**: 8 tokens x 8
routed experts = 64 ids against **56** arena slots at `-npl 8` -> every routed op declined (`decline_all=1920`,
`takeover=0` in the census) and the whole run read the pageable mapping.  `-npl 4` is 32 <= 56, which is exactly
why the 4-slot row never moved (193.5 vs 191.9).  r209 shipped the pinned tier, so block 09's numbers never met
this; r210 made the covering pool the default and inherited it.

The guard is about **representability** ("can every expert be expressed as a remap id"), not about the arena, and
a pool whose capacity COVERS the tensor has the pinned master's own property: every expert is pool-resident, so
`id = n_res_slots + slot` is a valid cold id for all of them.  **Fix: `pool_covers_table()`** (same translation
unit, next to `pool_cold_geometry_ok`), `pool_cold_geometry_ok() && pool->slots >= n_experts` plus an O(1)
re-check that every expert is resident, and the guard becomes
`!table_cold_ok(t) && !pool_covers_table(t) && t.slots < n_used * n_tok`.  Nothing else changes: no
`region`/`region_dev` field and no rebind of `t.host` (it keys `g_host_pools`/`g_host_src` and is shared by every
per-device table of one tensor) -- the cold encoding already IS "a slot index into one pinned base", which is P6
§1's whole point.  It is static per shape (the pool's slot count is fixed at the first build and the surplus
layout never un-loads an expert when `slots >= n_experts`), so a CUDA-graph replay cannot see it flip.
