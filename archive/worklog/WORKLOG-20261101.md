## 261101.016 (r204) -- the windowed KV across a `-sm tensor` split: `TODO` #124 closed, and four path defects fixed with it

**Delivery change.  Block 15 amended** (the streamed KV), fork point unchanged (`6050b467c`), new tip
**`aaf30b6b4`**, tree **`6260370949c1975c1ec5cb085bf5e937a2677cf1`**, release **`v16-6050b467c-r204`**.
`TODO` #124 is **retired**: the release is its record, the gate is `scripts/gate-kv-window-split.sh`, and the
numbers are in [`benchmarks/2026-11-01-kv-window-tensor-split-124.md`](benchmarks/2026-11-01-kv-window-tensor-split-124.md).

**What #124 was.**  Block 15's resident window (`LLAMA_KV_RESIDENT_CELLS`) was single-device only: the window is
one VMM region per device, a Meta (tensor-split) device has no backend reg of its own, so the region proc
addresses were unreachable through it and the cache declined with one message (the r181 crash fix).  The design
note (`archive/work/kv-residency/A6-TENSOR-SPLIT-WINDOW.md`, five changes C1-C5) was written against a
one-GPU box and never implemented.  This box has three R9700s, so it was implemented and measured.

**The change (block 15).**  `ggml_backend_meta_kv_region_buft/is_kv_buft/grow` (new, `ggml-backend.h`): the Meta
buffer type over the per-child region buffer types (all children or nothing), the is-a-region predicate `--fit`
needs, and a grow that fans out to every child and **refuses** (-1) where a child cannot be reached -- the CUDA
hook returns 0 for "not a region buffer", and for a Meta buffer that 0 was a silent success on unmapped VA, i.e.
a batch that page-faults the GPU.  `llama_kv_cache` resolves capability/buft/budget/link through the Meta side,
declines a MIRRORED cache (dsv4/HRM: `llama_model::kv_cache_split_mirrored()`, `n_devices x` cost and an
under-booked pinned spill) with its own message, and `common/fit.cpp` sizes the window for the split in the
tensor-split branch: charged at its physical `W x cell_bytes`, checked against `min_i(target_i / ratio_i)`, with
the Meta entry's margin now the **sum** of the children's (it was child 0's, so `(n_devices - 1) x -fitt` vanished
from the budget).  The corrected KV term applies **only** where a window is asked for -- a run without the knob
keeps the branch's old arithmetic exactly, and the split's pre-existing `n_devices x` KV over-count is left for
its own item.

**Four defects found by the arms, all fixed here** (each one would have shipped a lie or a crash):
(a) the init-time window commit was rounded up past the tensor's extent, and on a split each child is its own VA
reservation -- the last tensor's inflated window was refused (`the KV window (4.00 MiB) could not be committed in
VRAM on device 1/2`, twice per 4B/split run); it is now clamped to the region end in whole units (clamping to the
tensor's own extent is wrong: it leaves a short mapping off the grid and the next slide refuses to flip);
(b) `ensure_span` refused a request covering several whole mappings -- one batch can advance the boundary by more
than one unit and a 1 MiB unit is floored to the driver's 2 MiB granularity, which aborted the batch on
`win2fine`; whole mappings now flip one at a time, a *partial* coverage is still refused;
(c) the **batched state save** issued a 2-D D2H per device, and `hipMemcpy2DAsync` fails (`invalid argument`) when
the range begins in a spilled region's pinned host mapping -- the tensor-split checkpoint save aborted
(`cache_k_l64 (view)`, 1024 B x 4782 rows, found on the `draft-mtp` arm); the region-backed directions now fall
back to the region buffer's own copy, ordered behind the compute stream (without that wait the save is torn);

**The defect (issue #264, reported on r195 by `DanoPTT`).**  Since r193 the MTP draft context's KV is a
sliding window (`LLAMA_SPEC_DRAFT_WINDOW`, default ON).  Under `--kv-unified` that ONE draft cache holds every

sequence had filled its window the only free cells left were the `n_ubatch` + 256 headroom cells — which is
exactly where that sequence's own ring writes — and `find_slot`'s SWA reclaim frees a cell by its **owner's**
newest position, so an idle sequence's cells are never reclaimable by another.  A second sequence's first
batch therefore had no contiguous run: `W decode: failed to find a memory slot for batch of size 1024`, then
`E spec process: llama_process(ctx_dft) failed` and HTTP 500 `decode() failed: failed to process speculative
batch` on every request on that slot.  `LLAMA_SPEC_DRAFT_WINDOW=0` worked, and the target KV has room — only
the drafter's cache was starved.

**The fix.**  `llama_spec_draft_kv_cells()` (new, `src/llama-ext.h`) is the one geometry function:
`(win + one batch) x n_seq_max` cells for a unified cache (capped at the context), today's exact per-stream
expression for `--no-kv-unified`.  `create_memory`'s MTP branch, `common_draft_reserve_estimate` (the slab's
draft reserve) and `common`'s "is a window active" test all call it, so the reserve can no longer under-charge
an allocation.  `llama_spec_draft_window_cells()` stays the policy (a per-sequence window).  The window is
**declined**, not lowered, when `win + n_ubatch > n_ctx_seq / n_seq_max`: a window that small would save one
batch of cells per sequence and mask the drafter's newest cells to do it.  Also fixed while there: the reserve
charged only ONE stream for a per-stream (`--no-kv-unified`) multi-slot draft cache; it now charges
`n_seq_max` streams (35B-A3B `-ncmoe 40 -np 2 -c 8192`, window 1024: 3 072 cells on both arms, 1 536 before on
the per-stream arm — the under-charge direction the reserve header warns about).

### #129 -- `-nkvo` + host experts aborted (block 09) — CLOSED

`-ncmoe <n> -nkvo` aborted during the first graph (`GGML_ASSERT(id >= 0 && id < n_expert)`,
`ggml_backend_sched_copy_input`).  The cause is **not** the expert cache and **not** block 15: this block
prunes a host master's per-op upload using the routing, and reads the ids when the split's inputs are
copied; it searches for **any** `MUL_MAT_ID` consumer of the input inside the split (upstream only considers
the split's first node — that generalisation exists so one merged split hooks the gate, up and down tables),
while the split pass starts a new split for a host weight only once the split already has an input to reuse.
`-nkvo` puts the attention on the host, so the GPU split starts at its output with `n_inputs == 0`, swallows
the router chain and the routed op, and the readback reads the previous split's memory — out of range
aborted, **in range silently selected the wrong experts**.  So this is a **delivery-introduced reachability**
(not an upstream bug: upstream cannot get there, and its whole-table copy is the fallback part A restores).

The fix is two hunks: when the ids root (`view_src` chain of `node->src[2]`) is a node of the split being
copied, the routing-dependent shortcuts stand down (pruned upload, device gather, `moe_cache_update`) and the
general path copies the whole table; and the split pass starts the split AT such a routed op, after the
router chain (`next_moe_layer` keeps the layer's routed ops together), so the pruning and the expert cache
keep working.  **Measured** (1 x R9700, interleaved, `-n 128 -r 2`): Ling-3.0-tiny `-ncmoe 24 -nkvo` — abort
-> **24.6 t/s** (stand-down alone) -> **82.7 t/s** (both) against **176** with the KV on the GPU; the
pre-fill loss on that arm (4480 vs 6600) is the `-nkvo` attention on the CPU, identical with and without the
split boundary.  Cache arm (`MOE_EXPERT_CACHE_MIB=3000`, `-nkvo`): arena 2998.3 MiB, **17547/22584 = 0.777
reach**, so the update hook is fed again (under the stand-down alone it never is).  Graph census
`direct=708 replay=7198 capture=118 properties_changed=96` over 64 decode tokens: the new boundary still
captures and replays.

### #123 -- the attendance pool's mirror grows on demand (block 15)
