## 261107.014 (no release) -- expert-transfer-engine: the prefill gap is not the transport engine, and it is not the VRAM copies either

**No delivery change.**  `patches/`, `release.json` and the fork tree are untouched (r235 is the release).  This
records three measurements and one design direction from `wip/expert-transfer-engine/`, taken on a **PCIe5 x16**
host -- which is itself the first finding, because every transport conclusion in the campaign was derived on an
x8 or x4 link.

**The box differs, so the campaign's crossover does not transfer.**  Endpoint reports 16 lanes @ 32 GT/s; the
delivery's own calibration agrees (`H2D bandwidth calibration: 51.7-52.1 GB/s`, which collapses the staging width
gate to `min_tokens = 64`), and a 333 MiB pinned H2D measures **55.8 GB/s** against the campaign's 14.45 (x4) and
28.6 (gen4 x16) GB/s.  At twice the link, bulk's per-ubatch PCIe cost is half of what §§2-4 assume.

**Copy-engine mechanics** (`h2d-probe.cpp`, bare `hipcc`, no model).  (1) Host allocation kind is irrelevant to an
**async** copy: pinned, registered mmap, write-combined and pageable all measure 55.4-55.8 GB/s.  But a
**synchronous `hipMemcpy` out of `hipHostMalloc` is 27 % slower** (40.7) while sync-from-malloc/registered/WC are
full speed -- and `stage_h2d_gbps()` calibrates the staging gate with a *synchronous* copy (it uses `malloc`, i.e.
the fast path, so the shipped number is honest; point that probe at a pinned buffer and the width gate silently
moves).  (2) Run-coalescing the complement is a free **1.17x** (41.1 -> 48.2 GB/s) because the complement's runs
average **2.3** experts, not the ~1.3 §4 assumed.  (3) A second copy stream takes per-expert fills from 41.1 to
**54.8 GB/s** (+33 %, i.e. single-big-copy speed); four streams add nothing.  (4) A vectorised pull *kernel*
reaches only 50.7 GB/s against the copy engine's 55.8, so the r221 "kernel read beats the DMA" advantage does not
reproduce on a fast link; it showed no interference with a concurrent compute kernel in isolation (+0.3 %).

**The rule, and the number behind it: one stream per consumer chain.**  Eight one-table (343 MiB) copies, identical
bytes every arm: aggregate time is **49.95 / 49.99 / 49.98 ms at 1 / 2 / 4 streams** (link-bound, invariant), but
the **time to the FIRST copy is 6.26 / 10.94 / 10.93 ms**.  Extra streams do not add bandwidth; they delay the copy
the consumer is waiting on by sharing the link with one it does not need yet.  So extra streams pay only for a
**dispatch-bound** fill and cost first-completion latency for a **link-bound** one.

**End-to-end.**  35B-A3B (`-ncmoe 40`, one R9700): pool mirror at 43 % arena with the per-expert copy-engine fill
goes **3551 -> 4702 t/s (+32 %)** at `-ub 8192` and 1647 -> 2060 at `-ub 2048`; the two arms whose fill is one
launch (pinned staging kernel 5090 -> 5096) or one copy (pinned bulk 5219 -> 5238) per table are flat, as is the
shipped pool gather (4931 -> 4957) -- i.e. the gain appears exactly where the op count per table is high.
Flash-Next in the maintainer's `runme` shape (pageable master, bulk, 48.2 % residency) goes the other way:
**1538 -> 1475 (-4.1 %)**, and so does every Flash-Next arm including the one-copy control (-4.0 to -4.7 %), because
its fills are link-bound.  Text is byte-identical in all arms (`262 chars sha=e9db5cb8db0b`) and the staged bytes
are identical (`ok=117; arena=7733.9 MiB host=10430.1 MiB (H2D 57.4 %)`), so the delta is pure transport.
**A global stream knob is therefore not promotable**; the experiment is parked as
`wip/expert-transfer-engine/0002-stage-copy-streams.patch` (never applied to the fork) and only a version scoped to
the many-small-copy fill loop is defensible.  **Also found:** `--load-mode none` silently disables the host-expert
pool (`a pool needs a mapped load`), so a `runme` built on it runs the pageable-bulk path its comments do not
describe.

**The three VRAM copies are three different budget pools, so unifying them does not buy arena.**  Flash-Next at
`-ncmoe 46`, `-c 32768`, 23.69 GiB slab: arena 22.06 GiB (48.2 % residency, sized once from `free - reserve - aux`),
ring sub-region `ring_req` 4-6 GiB, `input_cpy` ~1.0 GiB inside the 1.62 GiB narrow work floor.  Measured with
`GGML_CUDA_SLAB_RING_MIB` 6144 -> 2560: ring 6.00 -> 2.50 GiB, **arena unchanged at 22269.8 MiB**, prefill
**1490 -> 1324 (-11 %)**, decode **48.3 -> 49.6 (+2.7 %)**.  Shrinking the transport footprint *strands* VRAM rather
than converting it into residency (the arena is sized once and `--fit off` never re-derives it), and the ring's
VRAM is buying prefill.  Turning freed VRAM into arena is the §6.1 arena-sizing-policy question, not a merge.

**Design direction recorded, not scheduled** (`TODO` #285 -- **declined at r252**, `WORKLOG.md` 261110.008): representing **all** experts costs ~**1.5 MiB** (70 656
experts x 4 B residency id = 276 KiB; + {VA, host} offsets = 1.08 MiB; the ids remap 276 KiB) -- negligible -- so a
unified store is a VA reservation with VRAM backing for a resident subset (block 15's pattern at expert
granularity).  It would fix `TODO` #271 *structurally* (a stand-down becomes a host-backed page instead of
`slots == 0`, so the table stays addressable) and collapse three allocations and three sizing rules into one; it
does **not** change the bytes, because every prefill ubatch routes essentially the whole table (~15.5 GB of *used*
experts per ubatch) and a host-backed page read in place is 33 GB/s serialised against the copy engine's 55.8
overlapped.  Its baseline to beat is free (r234: 1826 declined vs 1824 staged, +-0.1 %).  **Constraint:** the
store must stay *yieldable* -- a raw `cudaMalloc` outside the slab is the pre-slab crash mode (issue #136).

**Recorded:** `INVARIANTS.md` (stream-per-consumer + first-completion, the sync-copy calibration trap, the three
VRAM pools, the expert-metadata cost), `TODO` #283 (the `GGML_CUDA_GRAPH_OPT` branch streams collide with
`copy_stream()`'s index), #284 (defer the ring's redirect restore to `stage_free_ev` to remove the third copy), #285
(the unified store), and `wip/expert-transfer-engine/README.md` §7 with the full tables.

## 261107.013 (r235) -- PR #283 promoted: the scheduler's async host-input copy stops at the ring's snapshot limit (block 09)

**Delivery change, new release.**  `ggml/src/ggml-backend.cpp` (block 09) + the shared limit in
`ggml-backend-impl.h` + the CUDA ring's definition (block 10, tie only): the `host_src && dev_dst` branch of
`ggml_backend_sched_copy_input` no longer hands a split backend the caller's **live** host pointer for an upload
the backend does not snapshot.  Above `GGML_BACKEND_ASYNC_SNAPSHOT_MAX` (1 MiB) a **non-weight** host split input
takes the existing **synchronous** fallback -- what upstream ggml does for every host input.  ≤1 MiB keeps the r90
ring snapshot; a host **weight** (partial offload, host expert master) keeps the asynchronous copy at any size.
`GGML_SCHED_ASYNC_LARGE_HOST_INPUT=1` restores the old asynchronous copy (A/B and bisection only).  Block count
stays 16; blocks 09-15 were re-cut (commit ids only -- the block bodies are unchanged apart from these hunks).

**Why.**  PR #283 (`overdoingism`, written by Claude) found the leftover instance of the r35/#87 and r90 bug class:
the CUDA backend snapshots a `set_tensor_async` upload through its pinned ring **only up to 1 MiB**, and the
scheduler uses that path for a **CPU split's output** -- the token embeddings when `token_embd` lands in
`CPU_Mapped` (`model.input_embed` / `node_1`, **41,943,040 B** per 2048-token ubatch, 10,485,760 B at `-ub 512`)
-- which the next ubatch's CPU split rewrites **in place**.  Above 1 MiB the copy engine reads the source when the
stream reaches the copy, so a copy still queued behind earlier work reads the next ubatch's bytes or a torn mix:
a prefill corrupted from layer 0 on, in fluent text.  The reporter reproduced it only with 32+ layer-input
exports per ubatch (1.3-2.7 GB of device-to-host readbacks keeping the stream busy) and not under a plain
`llama-server` workload, which matches what this tree does.

**What was verified here (r234 tree, the reporter's config).**  Instrumented the branch on
`Qwen3.8-27B-UD-Q4_K_XL`, `-ngl 99`: `token_embd` in `CPU_Mapped` (682.03 MiB), the CPU split's output in a
`ROCm_Host` compute buffer of **40.96 MiB**, `node_1`/`model.input_embed` uploaded async at exactly
10,485,760 B (`-ub 512`) and 41,943,040 B (`-ub 2048`) per ubatch -- the PR's numbers are right.  **No shipped CLI
config corrupts prefill**: default vs `AMD_SERIALIZE_COPY=2` logits are **byte-identical** (0 differing bytes of
1,013,178,324 at `-ub 512`, 8 chunks; self-A/A also 0), and r234 vs r235 is 0.  So this ships as a **latent**-hole
fix, not a live-defect fix -- the same judgement r35 made for graph-input views.

**Cost (same binary, kill-switch A/B, 27B `pp2048`, `r5`, 4 alternating starts per arm, this box).**  1 GPU
`-ub 2048` **−0.17 %** (1395.2 vs 1397.5 t/s, old arm sd 12.7), 1 GPU `-ub 512` **−0.30 %**, 3 GPU `-sm layer`
`-ub 2048` **+0.08 %** -- inside the arm spread.  The PR's −0.4/−0.7 % (r220 fork, own drift 1.2 %) is compatible
but not reproduced.  Greedy text and prefill logits unchanged.

**Differences from the PR as filed.**  (1) The threshold is **one** `#define`
(`GGML_BACKEND_ASYNC_SNAPSHOT_MAX` in `ggml-backend-impl.h`) that the scheduler uses and the CUDA backend's

## 261107.012 (no release) -- the engine merge was built, measured and withheld: the box's copy-engine "phase" is SDMA dispatch latency

**No delivery change.**  `patches/`, `release.json`, the r234 tag and every gate are untouched; the fork
branch is still `2e31f8819`.  This entry exists because it settles a question three records had left open
("the 8192 stall", "the band", "the cause is not identified") and because it *stops* a change that looked
good on the mean.

**What was tried.**  `TODO` #272's follow-up: make the copy-engine fill the only staged engine for both tiers
(delete `moe_cache_stage_kernel` and the PRS device snapshot, fold the coalesced span read into the surviving
arm, drop `MOE_HOST_POOL_STAGE_BATCH`).  Built, text-byte-identical (`d3d554954cba` 1 GPU / `301b143c1cf5`
2-device tensor), prefill-logit **KLD 0.000000 / 100.000 %** vs `GGML_MOE_CACHE_STAGE=0` on a host-expert
config, `gate-host-pool.sh` **41/41**, the span read preserved *exactly* (59 659 reads, 153 491.3 MiB,
2.57 MiB/read at `-lme 12`, identical to the kernel arm) — and **not shipped**.

**Why not: the engine ranking reverses with a run-to-run phase, and the phase is the DMA op count.**  Pinned
master, `-ub 6144`, 43.4 % residency, arms interleaved so each appears in both phases: low → kernel 1761 vs
copy-engine 1624 (**kernel +8.4 %**); high → kernel 1876 vs copy-engine 2147 (**CE +14.4 %**).  Amplitude by
transport: gather (kernel read) ±0.1 %, one-launch kernel 6.5 %, whole-table bulk upload 17 %, per-expert copy
engine 32 % — i.e. a cost proportional to the number of DMA operations, not to the bytes.  The whole-table
bulk arm (`GGML_MOE_CACHE_STAGE=0`) beat the shipped kernel in **both** phases (+6 % low, +16 % high, 1 GPU /
43 % residency), but loses 1-7 % on a 2-device 99 %-residency shape and sends the arena's bytes over PCIe, so
it is not a default either.

**What the phase is.**  A `rocprofv3` kernel trace of a low vs a high run: identical kernels and identical
21 055 `copyBuffer` dispatches, but the low phase is **67 % GPU-busy against 85 %**, with the copy engine
*less* busy (0.16 s vs 0.36 s) across a longer wall — the copies stall rather than transfer, and the GPU idles
in many < 5 ms gaps.  `HSA_ENABLE_SDMA=0` removes the oscillation entirely (1635/1557/1541/1566 t/s — stable,
at the low level).  So it is ROCm/SDMA dispatch latency, not the fill code.

**Ruled out on the way** (each with its own measurement, because the field report suggested the PLE page
cache): `--lazy-mode auto` / `off` / `mlock` all oscillate with the same ~1.30 ratio (1838/1456/1836/1462 and
1832/1460/1834/1465); on this box `auto` is the *fastest* of the three, because a 47 962.5 MiB host-expert
tier leaves no room for a 26.8 GiB PLE pin (`MemAvailable` 7.7 GiB, the model's non-PLE tensors lose the page
cache) — `mlock`/`off` cost ~15 % here.  Also ruled out: memory pressure, GPU clock, `GGML_SCHED_STAGE_SLOTS`
(8 vs 16: +1 %), the GPU slot (same on gpu0 x8 and gpu2).

**Also re-measured, and the r234 band refuted with the stricter protocol**: pool tier, palindrome order —
gather 1260.6/1261.4, 1322.4/1321.7, 1389.5/1384.2 at `-ub` 4096/4608/5120 against CE 1121.5/1122.9,
1225.1/1216.6, 1331.3/1302.8 → the gather leads by 12.3/8.3/5.3 % (the r234 "+18 % for CE at 5120" does not
reproduce; the CE arm moved ~29 % between sessions, the gather ~11 %).  There is no width threshold to
encode, so the pool tier stays on the gather default and the "width-gated transport rule" idea is dropped.

**What survives as knowledge** (`INVARIANTS.md` r234's second addendum, the campaign record §6c): a transport
A/B on this box needs both phases or a gather control arm; a *default* should prefer the low-DMA-count engine;
and the per-expert copy engine is worth up to +15 % where SDMA is behaving, which is why
`MOE_HOST_POOL_STAGE_BATCH` remains a real (documented) choice rather than dead code.

## 261107.010 (tooling) -- the Lexar's 16 ms idle wake is APST, and the oracle now records the power policy

**No delivery change** (`patches/`, `release.json` and the gates untouched); follow-up to `261107.007`.

**The finding.**  The 16.2 ms "cold read after a pause" that `utilities/storage-oracle` reports on `/llm` is
not the drive's NAND latency and not thermal (Warning/Critical temperature time 0, T1/T2 transitions 0,
41 C composite against an 83 C threshold): it is **APST**, the host-managed autonomous power-state
transition the driver programs as `ITPT 100 ms -> PS3`.  Turning it off takes the same file from
**2 533 us to 88 us** after a 5 ms gap, **4 743 -> 50 us** after 50 ms, and the 250 ms step from
**16 313 -> 4 716 us**, with bulk throughput and every page-cache arm unchanged (`O_DIRECT` 2.46 GB/s both
ways).  A ~5 ms firmware level survives any setting and is reached after roughly a second of idleness,
so the honest summary is "50-90 us in use, ~5 ms cold" rather than "instant".

**Three shortcuts do not work**, each tried: `nvme set-feature -f 0x0c -v 0` returns **EPERM** (the kernel
driver owns the APST feature -- my earlier note that "disabling APST changed nothing" was this: the
command had failed and I read the echo as success); `nvme reset` does not re-read
`nvme_core.default_ps_max_latency_us`; and a user-space admin passthrough of Set Features is refused the
same way.  What works is writing the parameter and **unbind/bind-ing that one PCI function**, because the
parameter is read at controller *creation* -- which also scopes the change to the Lexar (the SN850X keeps
its APST and its 0.6 ms wake).  Executed here with `/llm` unmounted, then remounted on the same
`nvme0n1p1`; the drive reports `APSTE: Disabled` afterwards and `nvme1` still reports `0x00000001`.

**Configured at boot, scoped to one drive.**  `/usr/local/sbin/nvme-apst-off` + a
`Before=local-fs-pre.target` oneshot (`nvme-apst-off-lexar.service`, `WantedBy=sysinit.target`) do it
before `/llm` mounts, when nothing has the device open; the unit refuses to run while `/llm` is mounted
and exits non-zero only if the controller ends up unbound.  Both failure paths were exercised.  These two
files are **host configuration, not repo content** -- `utilities/` is for tools that measure and change
nothing, so the recipe lives in the tool's README instead of shipping a root-level hook.

**The power cost, which is why this is acceptable**: Watts are not readable in band at all (`id-ctrl`'s
`mp` is a per-state ceiling; `IDLP`/`ACTP` are unpopulated on both drives; NVMe SMART has no power field;
the `nvme` hwmon is temperature-only; RAPL is the CPU socket, the drive is on 12 V).  TechPowerUp measured
this model at **1.454 W idle with ASPM disabled** (the configured state here), **7.0 W reading** and
**8.5 W writing** -- against a 10 W descriptor, which is the ceiling-not-measurement argument in one line.
So APST off costs sub-watt-to-~1 W over that figure.

**Re-measured, same file as the example** (Gemma4-E4B Q8_0, one R9700): ladder 88/50/4 716/5 359 us for
5/50/250/1000 ms gaps, `O_DIRECT` 2.46 GB/s, buffered 2.51, `mmap` fault-in 1.23, warm 29.7; recommendation
unchanged at `--load-mode none --lazy-mode mlock` with `pinned 1 table(s), 2856 MiB`, cold 6.88 s reading
7 813 MiB, warm restart **1.29 s reading 0 MiB**.  The `AVOID any on-demand disk tier` entry still fires --
4.7 ms is still 4.7x the 1 ms threshold -- so "never read on demand during decode" survives the change.

**Tool change**: the report now records the policy (`power policy (APST)` in the facts table, read from
`nvme_core.default_ps_max_latency_us` and the controller's own table when root is available) and states it
in the idle-gap caption, because a ladder from a box with APST at its default is not comparable with one

## 261107.007 (tooling) -- `utilities/storage-oracle`: which load mode and residency this model file wants on its device (refs issue #281)

**New: `utilities/` -- a reporter, not the delivery.**  Nothing in `patches/`, `release.json` or the
gates changes.  `utilities/storage-oracle/storage-oracle.sh` takes one model file and measures **that file
on that device**: a band map (an average over the whole file hides the single number that decides the
verdict -- one shard here reads 0.23 GB/s in its first GiB and 12 GB/s from 17 GiB on), cold 4 KiB
latency for `O_DIRECT` / buffered `pread` / `mmap` fault, cold 1 MiB, sequential throughput, the
**idle-gap wake ladder** (no datasheet publishes it; 74 us while busy against **16.2 ms** after a 250 ms
pause on the Lexar, 0.6 ms on the SN850X), cold reads *while the file streams*, page-cache residency, and
the `MemAvailable`/`RLIMIT_MEMLOCK` budget.  The report ranks `--load-mode`/`--lazy-mode` on **two axes --
the first cold load and every restart** -- states the measurement behind every cell, and carries an
explicit avoid list (`AVOID` / `BROKEN` / `INERT` / `UNCONFIRMED` / `UNKNOWN` / `TRADEOFF` / `ADVISORY`).
`--verify` loads the model three times (shipped default cold, the recommendation cold, the recommendation
**warm**) and compares wall clock, **the bytes the block device actually read**, and the restart.  It is
referenced from **issue #281** because the transport trade-off that issue turns on is exactly what these
probes measure: the same file's buffered-pread rate against its `O_DIRECT` rate (3.7 against 6.9 GB/s on
one model here, 3.7 against 3.4 on another -- the ranking is file *and* device specific, which is the
whole reason a tool has to measure it), how many bytes each arm really reads
(`--load-mode dio` reads **15 % more than the file holds** from alignment re-reads: 4 921 vs 4 275 MiB),
and whether an on-demand read during decode is survivable at all.

**Three findings from building it -- the first two are traps in the measurement itself.**

1. **`POSIX_FADV_DONTNEED` cannot drop a 4 KiB page out of a large folio.**  On XFS with large folios a
   page-granular eviction silently does nothing and the "cold" read returns from cache in **0.2 us**; the
   first version of the probe reported exactly that on a file with 39 GiB of hot page cache and believed
   it.  The probe now evicts with folio-aligned windows (2/32/256 MiB), **verifies with `mincore`**, and
   counts and skips samples it cannot make cold (`skipped_warm=`).  Corrected, verified-cold, on the
   Lexar: `O_DIRECT` **74 us**, buffered `pread` **150 us**, `mmap` fault **150 us** at 4 KiB -- the two
   page-cache mechanisms cost ~2x `O_DIRECT` at page granularity, not the parity an unverified probe
   reports.
2. **A failed `llama-cli` arm looks like a spectacularly fast one.**  `--verify` first reported a 0.86 s
   "load" that had read 11 MiB: the arm had OOMed (`-sm layer -ngl 99` put 34.7 GiB on device 0) and the
   tool timed the failure.  An arm now has to exit 0 **and** print a prompt-eval line, or it is `FAILED`
   with its root-cause log line, and the section says the prediction was neither confirmed nor refuted.
3. **`--lazy-mode mlock` is inert on a model with no `TENSOR_READ_LAZY` table.**  Qwen3.5-4B has none:
   `mmap --lazy-mode mlock` 5.17 s against `mmap --lazy-mode off` 5.18 s cold, i.e. the mode did nothing.
   Gemma4-E4B has one (`pinned 1 table(s), 2856 MiB`), and that is the form r230's fastest restart used.
   So the tool reads the loader's `pinned N table(s), X MiB` line out of `--verify`, marks the pinning
   plans `UNCONFIRMED` when the model was never loaded, `INERT` when 0 tables are pinned (and rewrites
   the pin-specific advice, since there is nothing to pin), and prefers the pin on both mapped forms
   (`none`/`mmap`) whenever the working set fits `MemAvailable` and `RLIMIT_MEMLOCK` allows it -- which
   is r230's own conclusion, restated as a measurement: a pin survives the process, a copy does not.

**Measured against the r232 tree** (`8650138aa`, tree `53a43c600`): Gemma4-E4B Q8_0, one R9700,
`/llm` = the Lexar -- cold **7.08 s** reading 7 813 MiB, warm restart **1.30 s reading 0 MiB**, so the
second start is 18 % of the first; on that file `O_DIRECT` reaches 2.97 GB/s, buffered `pread` 2.44 and
the `mmap` fault-in path 1.28, and the idle-gap ladder reads 2.5 / 4.7 / 16.3 / 16.3 ms for 5 / 50 / 250 /
1000 ms -- i.e. the pin/stream question and the "never read on demand" question, both answered from the
same run.  Records:
[`utilities/storage-oracle/README.md`](utilities/storage-oracle/README.md) (thresholds, the why, and the
design rules), [`utilities/storage-oracle/EXAMPLE-REPORT.md`](utilities/storage-oracle/EXAMPLE-REPORT.md)
(a real run, verifying arm by arm).  Not a campaign and not a `wip/` entry: it is a shipped utility, and
it carries no gate of its own.

**1. r122's `off` bought residency with a copy; this buys it with a pin.**  `--lazy-mode off` reads the
whole `TENSOR_READ_LAZY` table into a private host buffer (27 GiB of anonymous memory for the Flash-Next
`per_layer_token_embd`), while `on`/`auto` read the same bytes from the model mapping on demand.  The
copy therefore adds nothing to the *data path* -- both are `host_gather` reads -- it only makes the table
un-evictable.  `mlock` is that same guarantee without the copy: the tensor keeps the lazy mapped buffer
and the loader does one populate + `mlock` of its whole extent at load.  Measured on the 3-GPU server arm:
`VmLck 28125136 kB` (26.82 GiB, i.e. the entire 27,465 MiB table, which is the whole of shard 2 of that
GGUF) with `RssAnon` **1.3 GB**, where the `off` arm's `RssAnon` is 32.2 GB.  `/proc/meminfo`
`Mlocked == Unevictable == ` the same figure.

**2. It is the fastest residency arm on this box, and the state is shared.**  `--load-mode mmap` load:
`mlock` 32.5 s, `off` 25.7 s (a 3.9 GB/s `read_raw` + copy), `auto` 29.1 s (reads nothing).  The 7 s is
the kernel's `__mm_populate` (~4.2 GB/s), not I/O; with the shard already in page cache the pin is a
page-table walk (**0.19 s** for 27 GiB).  That is the number the maintainer's warm restart rides:
`--load-mode none --lazy-mode mlock` is **ready to serve in 8.26 s** on the Flash-Next server (vs 13.6 s
for r122's best cold arm), and the pin releases at exit (`Mlocked`/`Unevictable` -> 0, `Cached` stays), so
the next start re-pins cached pages instead of re-reading 27 GiB.  Maintainer's 70K-token prefill on that
arm: **~4500 t/s at the start and ~3000 t/s at the 70K mark**, both records for the box; generation ~10 %
above the usual figure (not attributable -- MTP/draft variance moves it by itself).

**3. Three traps, all of them real in this tree.**  (a) The range must NOT go into `lazy_read::ranges`:
that set is handed to `llama_mmap`, which applies `POSIX_MADV_RANDOM`, and readahead is exactly what the
one bulk populate needs (r122 measured 0.22 GB/s for that fault-in path).  It goes into a separate `pin`
map instead.  (b) `lazy_read::any()` gates mapping creation on `!ranges.empty()`, so a pin-only mode would
have created no mapping under `--load-mode none`; it now counts the recorded tensors too (verified).  (c)
`llama_mlock::grow_to` is a monotonic prefix lock, so the per-file mlock object must not be reused for a
sparse range -- each pinned table gets its own object.  Also: no 4 GiB threshold (the mode pins the whole
marked set) and a refused `mlock` (`RLIMIT_MEMLOCK`, tested at `ulimit -l 2048`) warns and leaves the table
on the evictable page-cache path, text unchanged -- there is no partial pin.

**4. The pin is per process, deliberately.**  The locks live in the model (`pimpl->mlock_lazy`, declared
after `mappings`), so a model free or a process exit returns every page to ordinary reclaimable page cache;
