## 261125.015 (r365) -- contributor PR #370 promoted into block 16: the server's KV admission (a task that cannot fit beside the running slots is deferred, through the SCHEDULER's oracle)

**The assessment.**  PR #370 (`briansp2020`) reported that with a unified KV cache the server launches every request
that finds a free slot, so two prompts whose sum exceeds the context both prefill until the cache is full and then
**decode** fails: the retry loop can only clear idle slots, so it halves `n_batch` to 1 and answers HTTP 500 "Context
size has been exceeded." (with a speculator, "speculative batch index N is not inside the current sub-batch").  Every
claim checked out on the delivery, at 1/8th scale and with no contributor code: `-c 8192 -np 4 --kv-unified` (the
DEFAULT server shape -- `-np -1` resolves to 4 slots and `kv_unified = true`), two ~4.85k-token prompts, one R9700,
Qwen3.5-4B: both 500 in 0.8 s, versus both 200 and the two texts a lone run gives.  Their numbers, their reserve
arithmetic, their two documented limits and their kill switch were all accurate; the patch applied cleanly to r364.

**What changed in the integration (their one-block veto became the scheduler's decision).**  The submitted patch put
the fit check after `slot_sched.select()`, using the chosen slot only to exclude itself from the sum (a test that can
never fire -- the candidate is always idle), and logged a WARN per deferral.  The maintainer's review took it further
than a hoist: the check has no business in `process_single_task` at all, because the *deferral* already has a home.
`server_slot_sched` now carries an injected **oracle** (`std::function<bool(const server_task &)> admit`) and
`server_slot_plan` a `why` (`none`/`no_slot`/`no_capacity`); `select()` asks it **once, before a candidate is chosen**,
so the predicate stays slot-INDEPENDENT and the scheduler learns nothing about cells or reserves, and a refusal
travels the stock `plan.id_slot == -1 -> defer` path.  One defer site, so `pop_deferred_task()` and `/metrics`'
`n_tasks_deferred` cover it for free and a prompt pinned to an idle `id_slot` is refused by the same path.  The
accounting (`kv_admit_ok`) stays in the context that owns `n_ctx`, and charges each *running* slot
`max(its prompt, its task's tokens)` plus a reply reserve -- **idle** slots are not charged (the launch path parks the
residents and then clears them for want of room) and neither is a realtime slot waiting for audio.

**C (the maintainer's decision): the reserve is `min(n_ctx / n_parallel, n_ctx_slot())` cells**, not their flat 16384
-- the per-sequence share a NON-unified cache would have given each slot, further capped by the request's own
`n_predict`, with `LLAMA_SERVER_KV_ADMIT_RESERVE` as the override.  Measured by the census (the only place the
formula is visible): 2048 at `-c 8192`/4 slots, 4096 at `-c 16384`/4 slots, 256 with the override, and
prompt+`n_predict` when the request caps it.

**Three defects found by stress-testing it, all fixed in the same block (no TODO).**
1. **The idle wake could spin at 100 % CPU.**  `update_slots()`' `all_idle` counts a realtime slot waiting for audio
   as idle, while the admission counted it as running: a re-offered task was refused again, `pop_deferred_task()` kept
   the queue non-empty, and the loop never waited.  The wake now re-offers only when **no** slot is processing --
   which is also the proof it cannot spin, since the popped task is then always admitted (an `audio_wait` slot is not
   `is_processing()`-for-admission either, so the two sides agree).
2. **SIGTERM hung with a deferred queue.**  A task that was never launched is answered by nothing, and
   `server_http_context::join()` waits for its HTTP worker, so the exit died inside HIP's teardown
   (`__hip_module_dtor` -> `amd_comgr_destroy_metadata`, three runs out of three; eu-stack attached).  **PRE-EXISTING**
   -- the stock "no free slot" deferral escaped it only because the release path launches the task and then aborts it
   -- but this feature makes the state ordinary.  `server_context::terminate()` now drains
   `queue_tasks_deferred` (`server_queue::take_deferred_tasks()`, new) and aborts the running slots: exit in 0.1 s.
3. **`LLAMA_SERVER_KV_ADMIT_RESERVE` was documented but never parsed** (my own first cut, caught by the census arm):
   added, and the gate now asserts the override.

## 261125.013 (r364) -- the beta artifact's DELIVERY-level fix folded in (block 14: a row-block D2H is never a 2-D copy -- the abort `TODO` #124 misdiagnosed), and the pair-only piece squashed into the ONE two-arm patch

**The question, and the split.**  `beta/prefill-decode-arms/` carried two delivery-repo fixes it had found while
being developed (`TODO` #376): `state-split-2d-read.patch` (STEP 15) and `two-arm-drop-boundary.patch` (STEP 16).
The maintainer asked whether they are real for the delivery *today* and, if so, to fold them -- with the
two-arm-specific pieces going into the two-arm patch so there is a single beta file to manage.  They are not the
same kind of thing:

* **STEP 15 is a real delivery defect and it was misdiagnosed.**  On ROCm a `hipMemcpy2DAsync` D2H into host memory
  asks for a peer grant of the destination's pinned allocation to the copying device's agent; every buffer of the
  pinned host type (the context's output buffer, its state stage) is allocated by ONE device and read by ALL devices
  of a `-sm tensor` split, so a copy from a non-owning device needs it.  On a box whose slabs leave the driver no
  room the grant is refused (`hsa_amd_agents_allow_access ... err 4096`) and the copy returns `invalid argument` --
  a hard abort.  The delivery issues exactly that copy at three sites (the CUDA buffer's synchronous 2-D read, the
  KV region's row helper, the async 2-D read) and its own record for the abort (`TODO` #124, retired with the
  region-only 1-D routing) blamed the caller's arguments, not the grant: measured on the beta campaign a 5-row
  logits read of a split `result_output` aborted on device 1 while device 0's twin copy of the same bytes
  succeeded.  The async form also issued its copy without selecting its own device (its write twin always did).
* **STEP 16 is pair-only.**  It re-enables the prefill->decode compute-buffer drop inside the pair and fences the
  other arm out with a new `llama_context_set_drop_boundary()` callback; a single-context server installs nothing and
  is unchanged.  Shipping it in `patches/` would add an API nothing in the delivery calls.

**What landed (r364, one re-cut, block 14 amendment).**  `ggml_cuda_rows_to_host()` now serves all three sites:
ONE 1-D copy for a tight block; the device-staged chunked form (2-D device-to-DEVICE gather into the reading
device's own staging buffer, one 1-D D2H per chunk into that device's own pinned chunk, host scatter) when the call
may synchronize and the block is above `ggml_cuda_bounce_min()`; one 1-D copy per row otherwise (the async form,
which must not synchronize, and a block whose row exceeds the 64 MiB staging pair).  **Block 14, not block 09**
(`TODO` #376's guess): the helper needs the region staging primitives block 14 owns (`ggml_cuda_kv_region_dev_stage`,
`ggml_cuda_cpy_2d_rows`), and a later block amending an earlier block's file is the delivery's normal layering (this
same block already amends `ggml-cuda.cu`'s `supports_op`).  The delivery's copy uses `cudaStreamPerThread`; the pair
converts those streams to its per-(thread, device) host stream, which is pair machinery and stays in the artifact.

**Verified.**  Text-neutral everywhere it is reachable: `gate-state-pipe.sh` PASS (batched save+load 1.48x / 1.58x /
1.54x / 1.62x of the synchronous arm against a 3.0x bound), `gate-meta-seg-drain.sh` PASS (the drain fires, 90 per

## 261125.001 (no release; tooling) -- the r358 container images never existed: the worker's stale watcher pinned the RETIRED ROCm 10.1, and a push's exit status was treated as proof of publication (GitHub issue #364)

Reported by **@tazmaniax**: `server-rocm-10.2-v18-919794500-r358` and `server-rocm-7.14.1-v18-919794500-r358` both
answer `manifest unknown`, and the moving `latest` / `server-rocm-7.14.1` tags still report **r353**.  Not "still
pending": **no release from r354 to r358 ever published an image**, and the only trace was the worker's own
`watch.log`.

### 1. The cause: a stale COPY of the watcher pinned a retired ROCm line

The worker (`radiance`) runs `~/bin/rdna-container-watch.sh` — an installed **copy** of
`scripts/container-watch.sh`, last installed 2026-11-06.  That copy defaulted `ROCM_LINES="7.14.1 10.1"` and
always passed it explicitly (`--rocm "$ROCM_LINES"`).  On 2026-11-23 `3785377d` ("drop ROCm 10.1 everywhere")
changed the repo copy to `10.2` **and made `build-containers.sh` refuse a 10.1 request**, so every build after
it died ~4 s in, before touching a single source file:

```
==> release v18-919794500-r358 (fork point 919794500 -> tip dcee0fc34, ... tree 84d50a416...)
==> reusing prepared source at /home/stew675/llama-src (tree 84d50a416...)
ERROR: unsupported ROCm release line: 10.1 (7.2, 7.14.1, 10.2; 10.1 was retired 2026-11-23 ...)
```

The tag being built was correct all along — r358's own `scripts/build-containers.sh` defaults to
`7.14.1 10.2` and the `10.2.0-full` base image pulls on the worker (verified, 23.1 GB).  The stale *wrapper*
shadowed it.  Six such failures were on disk (`failed-*` for r354, r355, r386, r356, r357, r358), `last-built`
was `v17-919794500-r353`, and GHCR's newest version was r353 (2026-11-23T16:58Z) — exactly the reporter's read.

**Why it was invisible for a day.**  `MAX_ATTEMPTS` parks a failing tag after 3 attempts and the park was
logged `ERROR: … has failed 3 times; not retrying` **to `watch.log` only** — which nobody reads — and cron then
repeated that one line every 10 minutes.  A user report was the alarm.  `CONTAINERS.md`'s claim that "the
watcher runs the script as it exists in the TAG it is building" was true of the build script and false of the
wrapper, and nothing detected the drift.

### 2. The fix (three parts, each verified)

1. **The line set is no longer pinned by the watcher** (`scripts/container-watch.sh`): `ROCM_LINES` has no
   default and `--rocm` is passed **only** when the operator sets it, so the ROCm lines always come from the
   tag's `build-containers.sh` — the single source of truth the release already carries.  This kills the class,
   not just the instance.  Tested both arms with a stub build script: unset -> `--push --prune --force` (no
   `--rocm`), set -> `--rocm 7.14.1 10.2` first.
2. **A push's exit status is no longer treated as proof** (`scripts/build-containers.sh`): after the push loop it
   now probes the REGISTRY for **every** tag the release owes (`--push` fails the step if one does not resolve),
   and two new modes are the same code without a build: **`--verify-only`** (present / missing / unverifiable,
   exit 1 unless every tag resolves **and** every MOVING tag — `latest`, `rocm-<line>`, `server-rocm-<line>`,
   `full-`/`light-rocm-<line>` — carries this release's **digest**, not the previous one) and **`--list-tags`**
   (the tag set, so nothing hand-maintains it).  `skopeo inspect` is used when present; otherwise ghcr.io is
   probed over its v2 API with an anonymous pull token (curl + jq).  ABSENT is reported only on a definite
   `manifest unknown`; a timeout/auth failure reads **UNKNOWN** and still fails (a check must not pass on
   ignorance).  Both paths were run against the real registry and agree (`latest` = `sha256:404e02dd9ca0…`);
   `--verify-only` also works on a box with **no** container engine (it is a check, not a build).
3. **A failure is filed, not logged** (`scripts/container-watch.sh`): one GitHub issue per tag, `Release
   container images not published: <tag>`, created on the first failure, commented **only on a state change**
   (attempt N -> N+1, then the park: 4 notifications, then silence — a 10-minute comment storm would be worse
   than the bug), and commented + closed on the next successful build.  The body carries host, attempt, log path
   and the log tail.  `NOTIFY=0` / `NOTIFY_REPO=` are the knobs; a missing `gh` or a failed API call is a
   WARNING, never a build failure.  Unit-tested end to end with a `gh` shim: create -> silent on a repeat ->
   comment per new attempt -> comment on park -> silent -> comment+close on recovery.

### 3. What the check says, today

`--verify-only` reproduces the reporter's report exactly (7.14.1 arm): the four r358 tags `MISSING`, while
`full/light/server/rocm-7.14.1` are `PRESENT` carrying **r353**'s digests — the stale moving tags the report
also named.  The worker is fixed (watcher re-installed from this tree, the six failed markers removed) and the
r358 build is running there.

**No backfill (maintainer's decision):** r358 supersedes r354-r357 and those releases will never carry an
immutable `-<release>` image tag.
